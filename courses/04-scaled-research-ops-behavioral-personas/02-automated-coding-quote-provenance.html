📖 1. Theoretical Grounding & Literature Synthesis

From grounded theory to the affinity wall

Qualitative coding began as a discipline of emergence: Glaser & Strauss's grounded theory demanded that categories arise from the data (open coding) and only then be related to one another (axial coding), with theoretical sampling continuing until saturation. Martin & Hanington (vol. 18, ch. 5, "Representational and Synthesis Methods") translate this into design practice: synthesis methods "translate complex, messy evidence into shared cognitive models" that act as boundary objects (Star & Griesemer) — artifacts engineering, finance, and frontline staff can reason over without sharing the researcher's training.

Three coding idioms matter for this course:

  • Affinity diagramming (the KJ method, Kawakita Jiro) — every discrete observation goes on its own note, preserving the source language; notes are clustered bottom-up by shared underlying need; clusters are named by the need, not the activity. Its failure mode is the "laundry-sort" cluster: groups named after topics ("pricing", "app") that smuggle the org chart into the data.
  • AEIOU coding (Rick Robinson / E-Lab) — a structured taxonomy that codes every field note against Activities, Environments, Interactions, Objects, Users. Its value is discipline: it prevents the coder from collapsing "what people do" into "what we build". Its failure mode is single-source clusters — a category built from one interview is a story, not a pattern.
  • Insight-statement formulation — an insight is observation + tension + implication, not a restated fact. "Users abandon the form" is an observation; "users abandon the form because each broken date promise taught them the channel lies, so the service loses early-warning demand data" is an insight. Stickdorn et al. (vol. 01, ch. 4) and the from-insight-to-implementation literature (vol. 03, ch. 4) both treat the tension as the load-bearing member: remove it and the insight cannot justify a design decision.

Why coding breaks at scale — and what actually fixes it

Manual coding collapses past ~20 interviews for a mechanical reason: the coder's working memory is the index. Cross-referencing quote #341 against cluster #12 requires remembering both. The agentic fix is not a smarter coder; it is a provenance structure that makes citation checkable by a machine:

  • Every cluster/insight node carries evidence: [{evidenceId, quote}] — a SHA-256 reference into the project evidence store plus the verbatim line.
  • The write path resolves every evidenceId against the store and rejects unknown ids (fail-closed).
  • The method contract's acceptance rules (min-nodes, min-evidence-per-node, field-non-empty) execute deterministically at write time, so "a cluster needs two sources" is a gate, not a reviewer preference.

Provenance here means nodes[].evidence[] — not timestamps, not "capturedAt", not chat history. A node is provenance-complete when every claim on it resolves to a content-addressed record whose body is the verbatim source line.

🤖 2. Agentic Topology & Role Contracts

Four registered methods carry this module. All contracts below were retrieved live with asd method-run on 2026-08-22.

Method Phase Owner Output kind Gate condition (critic step, verbatim)
transcript-mining research researcher insight-set "Reject any insight that paraphrases a flagged line without adding a distinct theme."
aeiou-coding synthesis synthesizer affinity-cluster-set "Reject a cluster built from only one source as not yet a pattern."
affinity-diagramming synthesis synthesizer insight-set "Reject any cluster named after an activity rather than a need, or lacking a supporting quote."
insight-statement-formulation synthesis synthesizer insight-set "Reject an insight that only restates what was observed without naming the tension it creates."

Per-role specifics for the shared spine:

  • Researcher (transcript-mining step 1; affinity-diagramming step 1): reads every transcript and flags lines describing a need, frustration, or unmet expectation; writes each discrete observation on its own line preserving the source quote.
  • Synthesizer: merges flagged lines into insights (discarding any insight backed by a single line taken out of context); codes notes against AEIOU; clusters by need; writes insight statements as observation + tension + implication.
  • Critic (reviewGate: "critic" on all four): sits on the write path via sd_review; each method names its rejection condition in the contract itself.
  • Human designer: scope-confirmation before the run and handoff-approval before the artifact moves to the mapper (both declared in humanCheckpoints).

💻 3. Schemas & Verified Execution

The artifact node contract (@asd/core)

// Artifact node — the unit that carries provenance
type ArtifactNode = {
  readonly id: string
  readonly label: string
  readonly evidence: readonly EvidenceRef[]   // { evidenceId: string, quote?: string }
  readonly fields: Record<string, unknown>    // method-specific, closed per kind schema
}

// insight-set node fields (schema-get --kind insight-set):   insight required; theme/confidence/… optional
// affinity-cluster-set node fields:                          cluster required; theme/confidence/… optional
// Both kinds: edges forbidden; references optional with provenance required.

Real response head:

{"accepted": true, "status": "draft",
 "artifact": {"id": "a6472880e8a8410c9d236c12506f4880", "kind": "affinity-cluster-set",
              "methodId": "aeiou-coding", …}}

accepted: true, status: draft is the load-bearing pair: acceptance rules passed at write time, but the artifact stays a draft until the critic gate passes. Provenance and verdict are separate axes.

Two fail-closed behaviors you must be able to reproduce

Dangling citation — rejected at write:

$CLI artifact-write … --nodes '[{"id":"n1","label":"x",
  "evidence":[{"evidenceId":"0000…dead","quote":"fake"}],"fields":{"theme":"t","insight":"i"}}]'
# asd artifact-write: node "n1" cites evidence "00000000…dead" which is not in the project evidence store

Acceptance failure — retained as draft with the failures on the record (a thin persona-set, one evidence ref per node):

{"accepted": false, "status": "draft",
 "artifact": {"id": "35eb069b56b242bb89c641aab96753df",
   "check": {"pass": false, "failures": [
     {"rule": "min-evidence-per-node", "nodeId": "per-thin",
      "message": "node \"per-thin\" cites 1 evidence refs, needs 2"}]}}}

The draft is kept, not discarded — the failure list is reviewable evidence of what the gate caught.

📊 4. Case Study Lens: Lumen EdTech Mental-Model Program (Article 10)

Synthetic illustration — not a production log. Article 10 is a fictional composite; receipt ids above come from the verified live session.

Lumen EdTech (fictional) researched how teachers, parents, and administrators think about grades rather than how the org chart assumed they did. The program's synthesis phase is this module's workflow at program scale: thousands of coded observations clustered into need-named themes, each cluster traceable to specific interviews. Two lessons transfer directly:

  • Name clusters by need, not surface topic. Lumen's value came from clusters like "parents want to intervene before the grade, not after" — a need with a time dimension — not "gradebook features". The affinity-diagramming critic gate encodes exactly this: it rejects clusters named after activities.
  • Single-source clusters are hypotheses. Lumen treated any pattern seen in one school as a follow-up question, not a finding. The aeiou-coding gate ("reject a cluster built from only one source") and the min-evidence-per-node: 2 acceptance rule make that stance executable.

🔬 5. Hands-On Lab

export ASD_WORKSPACE=/tmp/asd-lab-04b
CLI="node suite/packages/runtime/lib/cli.mjs"

$CLI artifact-write --projectId $PID --methodId aeiou-coding \
  --title "Lab AEIOU Clusters" --nodes '<3+ clusters, each citing ≥2 real evidenceIds>'

# Deliberate fail-closed demo: cite an id you never registered
$CLI artifact-write --projectId $PID --methodId aeiou-coding --title "Bad" \
  --nodes '[{"id":"x","label":"x","evidence":[{"evidenceId":"'$(printf '0%.0s' {1..64})'"}],"fields":{"cluster":"A","theme":"t"}}]'
# expect exit 1: "cites evidence … which is not in the project evidence store"

Verification checklist

  • Every node's evidence[].evidenceId exists in evidence/index.json (provenance = node refs, not timestamps).
  • Each cluster cites ≥2 sources; accepted:false drafts retain their check.failures list.
  • Insight statements name a tension (observation + tension + implication), not a restated fact.
  • The critic gate conditions you enforce match the method contract's own steps[].instruction text.

🚀 Key Takeaways

  • ✅ Coding methods are contracts, not vibes: transcript-mining, aeiou-coding, affinity-diagramming, and insight-statement-formulation each declare owner, gate, and acceptance rules that execute at write time.
  • ✅ Provenance lives in nodes[].evidence[]. Timestamps order history; content-addressed refs make claims checkable. Dangling refs are rejected at write, not at review.
  • ✅ Failure is data. Acceptance-unmet writes are retained as drafts carrying their failure list; vetoes persist as review-veto-log artifacts. The gate teaches by refusing.
  • ✅ Clusters are named by need, and insights name their tension — both rules are enforced by the critic step written into the method contract.
