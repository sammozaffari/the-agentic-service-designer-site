1. Theoretical Grounding & Literature Synthesis

Why "machine-checkable" changes the epistemics of a persona

A conventional persona is a claim: a poster asserting that a segment exists. Its quality rests on the maker's reputation and the audience's trust. Stickdorn et al. (vol. 01, ch. 4) warn that research artifacts decay into decoration the moment their link to evidence becomes ceremonial. The correction from the synthesis-methods literature (vol. 18, ch. 5) is procedural — keep the raw material attached — but procedure alone decays under deadline pressure.

The agentic move is to make the contract executable: the persona set is a typed artifact whose claims are checked by a deterministic gate at write time, whose interpretive choices are challenged by an adversarial review gate, and whose final state is reproducible by anyone who re-runs the checks. Trust moves from the maker to the mechanism. Three properties do the work:

  • Referential integrity — every cited evidence id must resolve in the project store at write time. A persona cannot cite a quote that does not exist.
  • Executable acceptance — min-nodes, min-evidence-per-node, field-non-empty, and forbid-field-values run as code, not as reviewer memory.
  • Deterministic rendering — export-artifact compiles the stored artifact to SVG via @asd/render; the picture is a projection of the data, so the picture cannot drift from the evidence.

The spine as a state machine

Every artifact in this toolchain walks the same lifecycle: refused → draft(failing) → draft(accepted) → vetoed(draft) → final → rendered, with the human gate (phase-advance with an approval receipt) beyond it. Knowing the states — and which command moves you between them — is the operational content of this module.

2. Agentic Topology & Role Contracts

Stage Who acts Tool What the gate enforces
Contract load synthesizer sd_method_run Input thresholds fail closed (≥5 evidence, ≥1 insight-set)
Drafting synthesizer sd_artifact_write Schema (closed field policy), referential integrity, acceptance rules
Adversarial review critic sd_review Pass needs ≥1 evidence-cited row, zero defects; veto needs a fix on every defect
Verification any role / CI sd_factcheck Per-artifact integrity + schema + acceptance + review verdict; exit 1 blocks the pipe
Rendering presenter / pipeline sd_export_artifact, sd_export_report Deterministic SVG / HTML dossier from stored state
Authorization human designer sd_phase_advance Fails closed without an approval receipt; drafts block advance

3. Schemas & Verified Execution — the complete live spine

Everything below was executed today against a disposable workspace (ASD_WORKSPACE=/tmp/asd-c04-spine-…). Project: fernwood-repairs-research-ops-b0254f32; 18 evidence records (15 imported CSV quotes, 2 telemetry, 1 document).

Step 1 — load the contract (fails closed without inputs):

$CLI method-run --projectId $PID --methodId behavioural-personas
# {"method":{…"reviewGate":"critic"}, "acceptance":[min-nodes:2, min-evidence-per-node:2,
#  field-non-empty:goal, forbid-field-values:description∉{demographic}],
#  "inputs":[evidence-set≥5, artifact≥1 of kind insight-set], "outputKind":"persona-set", …}

Step 2 — write the draft (three behavioral personas, mixed-kind citations):

$CLI artifact-write --projectId $PID --methodId behavioural-personas \
  --title "Fernwood Behavioural Personas v1" --nodes '<three nodes as in module 04.4>'
# → {"accepted":true,"status":"draft","artifact":{"id":"feca4b7fec5a48e39f9ff9c266e04fac", …}}

Step 3 — critic gate passes with evidence-cited rows:

$CLI review --projectId $PID --artifactId feca4b7fec5a48e39f9ff9c266e04fac --verdict pass --rows '[
 {"rowKind":"proposal","severity":"high","rule":"min-evidence-per-node",
  "message":"per-exhausted-repeater is triangulated: 40-minute verbatim hold matches IVR telemetry mean of 2380s.",
  "evidenceId":"53fccc10d293c1c61cf49d75a8702fddd5f8665f7799754945c84249330472f5"},
 {"rowKind":"proposal","severity":"medium",
  "message":"per-quiet-deserter exit behaviour is corroborated by portal abandon telemetry (0.42 in Q3).",
  "evidenceId":"66bcc28edc7f7171184cdb036d182537033ebdd72c70fe311aa71ccceab606e2"}]'
# → {"status":"final","verdict":"pass", …}

Step 4 — deterministic factcheck (the CI gate). First the honest failure: with a deliberately thin persona-set draft in the project (accepted:false, one evidence ref per node), the gate exits 1:

$CLI factcheck --projectId $PID ; echo $?
# per-artifact report: integrity{dangling[]} + schema + acceptance + review{verdict}
# 35eb069b… → acceptance pass:false ("node \"per-thin\" cites 1 evidence refs, needs 2")
# 1

Remove or remediate the failing draft and the same command exits 0 — verified:

$CLI factcheck --projectId $PID ; echo $?
# 0

Step 5 — render the deliverables:

$CLI export-artifact --projectId $PID --artifactId feca4b7fec5a48e39f9ff9c266e04fac
# → {"path":"…/renders/persona-set.feca4b7f.svg","kind":"persona-set","bytes":4391}

$CLI export-report --projectId $PID --kind artifact-dossier
# → {"path":"…/renders/report.artifact-dossier.html","bytes":24678}

The SVG is compiled from the stored artifact by @asd/render — title, node cards, evidence counts — so what the stakeholder sees is the checked data, not a redrawn approximation.

4. Case Study Lens: Northgate's Register Discipline at Ship Time (Article 02)

Synthetic illustration — not a production log. Receipt ids above come from the verified live session.

Northgate Health's (fictional) telehealth program treated its evidence register as the thing that shipped: journey maps, blueprints, and concept briefs were projections of register-backed artifacts, which is why the 45%→76% completion claim could survive procurement scrutiny. This module's spine is that discipline reduced to five commands. The lesson the case adds is organizational: the human gate is last, not first — sd_phase_advance fails closed without a signed approval receipt and while any design artifact is still a draft, so authorization happens on verified state, not on a slide about state.

5. Hands-On Lab

The lab verifier (courses/labs/lab-04-research-ops-personas/) automates this entire spine against a temp workspace, including the negative case. Run it:

node courses/labs/lab-04-research-ops-personas/verify_lab-04.mjs

It asserts, in order: project creation → CSV import (2+ rows) → insight-set accepted → behavioural-personas contract available → persona-set accepted with mixed-kind citations → dangling-citation write refused (non-zero exit) → review pass → status final → factcheck exit 0 → SVG exported with non-trivial byte size.

Verification checklist

  • You can reproduce all three refusal modes: dangling citation (write exit 1), acceptance failure (accepted:false draft with check.failures), factcheck exit 1 while any artifact fails.
  • The persona set reached final only through a review with ≥1 evidence-cited row and no defects.
  • The exported SVG path and byte size come from the tool's own receipt — never a hand-typed filename.
  • Phase advance is human-authorized: receipt JSON required, drafts block it.

Key Takeaways

  • A machine-checkable persona is a typed artifact under executable contract — schema, integrity, acceptance, review, and render are five separate gates with real exit codes.
  • Failure modes are features: refused writes, retained failing drafts, and factcheck exit 1 are how the toolchain teaches and protects.
  • The render is a projection of checked state — deterministic SVG from @asd/render, so the deliverable cannot drift from the evidence.
  • Humans authorize; machines verify. The phase gate requires an approval receipt precisely because everything before it was mechanical.
