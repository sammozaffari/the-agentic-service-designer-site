Module 08.4: Automated Standards Audit — the Continuous-Audit Loop

Course: Service Quality, Good Services Audits & Continuous Operations · Level: Advanced · Duration: 55 min · Format: Theory, Architecture, Verified CLI & Hands-on Lab

🎯 Learning Objectives

  1. Explain why a service standard is only real if it is measurable, and author standards as a service-standard-set artifact (service-standard-authoring).
  2. Compose the three audit instruments — experience-audit, good-services-audit-15, and the deterministic sd_factcheck — into a continuous-audit loop.
  3. Wire the loop into CI with correct exit-code semantics: factcheck exits 0 only when every artifact passes integrity, schema, acceptance, and review.
  4. State precisely what the review gate permits: pass = evidence-cited rows, no defects; veto = defects each carrying a fix.
  5. Distinguish human judgment (review verdicts) from machine proof (factcheck) and use each where it belongs.

📖 1. Theoretical Grounding

1.1 Standards as measurable contracts

Module 08.1's gap 2 — the standards gap — opens when management perception is translated into specifications that cannot be audited ("respond quickly", "be empathetic"). Grönroos's Moment-of-Truth Quality Mapping (book 19 ch.2) demands the opposite: for each touchpoint, an observable, enforceable behavior or system latency. The UK tradition that produced Downe's principles takes the same position: a standard is a testable promise, not an aspiration.

This is why the ASD service-standard-authoring method (owner orchestrator, gate critic, phase delivery, output kind service-standard-set) instructs the synthesizer to "write a measurable standard for every touchpoint the blueprint marks as customer-facing", and why its acceptance rules are: min-nodes: 4, field-non-empty: measure, and forbid-field-values: measure ∉ {tbd, n/a}. The critic's standing instruction: "Reject any standard whose metric is not measurable, since an unmeasurable standard cannot be audited later." The service-standard-set kind schema closes the loop: measure (string) is required per node.

1.2 From audit event to audit loop

A one-off audit is a photograph; operations is a film. Outside In's governance discipline (book 14 ch.6–7) requires measurement to run continuously — relationship baseline annually, journey instrumentation at milestones, operational telemetry always on — and to be owned. The continuous-audit loop in ASD terms:

  1. Standards (service-standard-set) declare the measurable promise per touchpoint.
  2. Audits (experience-audit for the SERVQUAL gap instrument, good-services-audit-15 → insight-set for the principles scorecard) test reality against the promise, each finding cited to evidence.
  3. Review (sd_review, critic gate) applies human-adversarial judgment: is this finding real, is the evidence sufficient, what must change?
  4. Factcheck (sd_factcheck) re-proves the whole project deterministically — and it is the CI gate.

The loop is continuous because its inputs never stop: every support log batch, complaint export, or telemetry snapshot is new evidence (sd_evidence_import), and new evidence justifies new artifact versions. The audit is never "done"; it is currently passing.

🤖 2. Agentic Topology: Who Judges What

Instrument Role / mechanism Kind of judgment
service-standard-authoring owner orchestrator; synthesizer writes, critic gates Standards authored from blueprint touchpoints; measurability enforced by acceptance + closed schema
experience-audit / service-quality-diagnostic owner measurer; researcher scores, critic gates Evidence-cited gap findings, severity non-empty, ∉ {tbd, n/a}
good-services-audit-15 owner measurer; researcher scores all 15, critic gates Principles scorecard as insight-set, no sampling
sd_review critic role Human-adversarial: verdict on evidence sufficiency; rows are proposal or defect; pass carries no defects, veto requires fix on every defect
sd_factcheck deterministic engine Machine proof: integrity (no dangling evidence ids), closed schema, acceptance rules, review verdict — per artifact, whole project

The separation is the design: the critic can be persuaded; the factcheck cannot. A reviewer might wave through an artifact on a good day — the factcheck re-derives every rule from the store on every run.

💻 3. Verified Execution: Exit Codes as CI Semantics

3.1 What factcheck actually checks

Verified rows from the Kestrel project (asd factcheck --projectId kestrel-quality-ops-1e9bfb41), one per artifact:

{ "artifactId": "ddfee25e…", "kind": "kpi-tree", "status": "final",
  "integrity":  { "pass": true, "dangling": [] },
  "schema":     { "pass": true, "failures": [] },
  "acceptance": { "pass": true },
  "review":     { "pass": true, "verdict": "pass" } }

Four independent checks per artifact: evidence integrity (every cited id resolves in the project store), schema (closed kind fields), acceptance (the method's rules), review (a passing critic verdict). Exit code is 0 only when every row passes.

3.2 The CI gate, verified both ways

# GREEN: all artifacts final and passing
$CLI factcheck --projectId kestrel-quality-ops-1e9bfb41 ; echo $?
# { "pass": true, "rows": [ ... ] }
# 0

# RED: a retained failing draft exists in the project (the 08.3 "FAIL DEMO"
# 3-node audit — retained with accepted:false, failures:[min-nodes])
$CLI factcheck --projectId kestrel-quality-ops-1e9bfb41 ; echo $?
# { "pass": false, "rows": [ ...,
#   { "artifactId": "e8b787a4…", "kind": "insight-set", "status": "draft",
#     "acceptance": { "pass": false, "failures": [ {"rule":"min-nodes"} ] } } ] }
# 1

A retained draft is not invisible bookkeeping — it turns the project red. That is the intended CI semantic: merge nothing while any artifact is unproven.

3.3 Review-gate constraints, verified

# A pass verdict carrying a defect row is rejected outright:
$CLI review --projectId $PID --artifactId a416ee0a… --verdict pass \
  --rows '[{"rowKind":"defect","severity":"high","fix":"…","message":"…","evidenceId":"…"}]'
# asd review: a pass verdict cannot carry defect rows — record them as proposals or veto

# A dangling evidence citation is rejected at write time (before any gate):
$CLI artifact-write … --nodes '[{"id":"x1", …, "evidence":[{"evidenceId":"000…0"}]}]'
# asd artifact-write: node "x1" cites evidence "000…0" which is not in the
# project evidence store

3.4 Minimal CI wiring

# .github/workflows/service-audit.yml (sketch — adapt paths to your repo)
name: continuous-service-audit
on: [push]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - name: Run deterministic service audit
        env:
          ASD_WORKSPACE: ${{ github.workspace }}/.asd-workspace
        run: |
          CLI="node suite/packages/runtime/lib/cli.mjs"
          $CLI factcheck --projectId "$ASD_PROJECT_ID"
          # exit 1 fails the job: some artifact is draft, vetoed,
          # dangling, or acceptance-failing

Evidence refresh belongs upstream of the gate: a scheduled job runs sd_evidence_import (or evidence-add per record) from the support-log export, then the audit methods re-run, then factcheck decides. Human review stays human — CI runs the deterministic half of the loop.

📊 4. Case Study Lens: The Street of Small Business (Article 34)

Synthetic illustration — not a production log. Article 34 (articles/34/README.md, "Banking That Learns the Business") is an illustrative composite.

A small-business bank re-auditing its onboarding and lending journeys each quarter is the continuous-loop archetype: standards (decision turnaround measured in days, document requests counted per application) are re-tested against fresh complaint and telemetry evidence; the audit's job is to detect drift — the service quietly regressing as policy and volume change. The lesson maps directly: standards without a re-audit rhythm decay into gap-2 fiction. The dossier report (sd_export_report --kind artifact-dossier, verified at renders/report.artifact-dossier.html) is the artifact you hand the governance council each cycle.

🔬 5. Hands-On Lab

  1. Author a service-standard-set (≥4 nodes, each with a real measure) from your blueprint. Try "measure":"tbd" on one node — record the forbid-field-values failure.
  2. Run the two audit instruments against the same project and pass them through the critic.
  3. Reproduce both factcheck exit codes (§3.2) by introducing and then fixing a failing draft.
  4. Attempt a pass review carrying a defect row — record the rejection.
  5. Export the dossier and locate each artifact's integrity/acceptance/review rows in the HTML.

Verification checklist

  • Every standard node carries a measurable measure (no tbd/n-a)
  • Both audit artifacts final with evidence-cited review rows
  • Exit 1 observed with a failing draft; exit 0 after remediation
  • CI sketch understood: factcheck is the gate; evidence refresh precedes it

🚀 Key Takeaways

  • A standard you cannot measure is a gap-2 liability; service-standard-set forces measure per node and forbids placeholder values.
  • The continuous-audit loop = standards → evidence-cited audits → critic review → deterministic factcheck → CI exit code; new evidence re-enters the loop forever.
  • Review is human-adversarial judgment; factcheck is machine proof. CI runs the machine half and fails on any retained draft.
  • pass never carries defects; veto always carries fixes; dangling evidence dies at write time.
