Module 08.6: Continuous Service Architecture — Approval Gates, Re-Open Loops, and Living Ownership

Course: Service Quality, Good Services Audits & Continuous Operations · Level: Advanced · Duration: 60 min · Format: Theory, Architecture, Verified CLI & Hands-on Lab

Learning Objectives

  1. Distinguish the project phase enum (discover | define | develop | deliver) from the method phase enum (research | synthesis | ideation | prototyping | delivery | measurement) and explain why the toolchain keeps them separate.
  2. Run and interpret sd_phase_advance, including the approvalReceipt requirement and the preflight conditions it enforces.
  3. Explain the verified idempotency behavior: a rejected phase-gate idempotencyKey replays the recorded rejection; a fresh key re-evaluates preflight after remediation.
  4. Re-open the loop correctly when new evidence arrives: new evidence → new artifact versions → critic gate → factcheck → human gate.
  5. Define ongoing ownership with roadmap and raci-matrix artifacts so the blueprint becomes an operating rhythm rather than a slide.

1. Theoretical Grounding

1.1 A service blueprint is only useful if it stays alive

Service design literature has always wanted more than a workshop artifact. Grönroos wants service quality continuously measured against expectations. Outside In wants journey governance, tied metrics, and industrialized capability. Downe wants a service that keeps responding to change. The only way to satisfy all three is to treat the blueprint, the KPI tree, the audits, the recovery playbook, and the standards set as versioned operational artifacts — always open to new evidence and always passing their gates for now.

In the ASD runtime, "continuous" is not a metaphor. It is a rhythm of typed updates:

  • projects move across project phases: discover → define → develop → deliver
  • methods run within method phases: research | synthesis | ideation | prototyping | delivery | measurement
  • artifacts version whenever evidence changes
  • review verdicts and factcheck rows are recomputed against the current store
  • phase movement requires a human receipt because the machine can prove integrity, not business consent

These two enums are intentionally separate. A project may be in define while you are running a measurement method; a project in deliver may still run research to investigate a new failure mode. Do not conflate them.

1.2 The human gate is the governance seam

sd_phase_advance is the seam between design operations and managerial authority. The runtime refuses to advance without:

  1. a legal next transition (discover → define, never a jump)
  2. an approvalReceipt JSON with receiptId, approvedBy, decision, rationale, approvedAt
  3. all design artifacts final
  4. no vetoed artifacts
  5. a passing factcheck

That is the right split of labor. The machine decides whether the evidence, schemas, acceptance rules, and review states hold together; a human decides whether that evidence is sufficient to spend money, ship, or move the project.

1.3 Re-open loops, do not patch around them

Continuous ops is not a frozen green build. New evidence invalidates old confidence. If the contact centre exports a new complaint cluster tomorrow, the current recovery-playbook is merely the last approved version. The operating rhythm is:

  1. import new evidence
  2. run the relevant method again
  3. write a new artifact version
  4. pass critic review
  5. let factcheck re-evaluate the whole project
  6. if a phase move is needed, submit a new approval receipt

This is why roadmap and ownership artifacts matter: somebody has to own the re-open.

2. Verified Governance Semantics

2.1 sd_phase_advance preflight (source and receipts)

The tool source (suite/packages/engine/src/tools/phase.ts) computes a preflight on every advance attempt:

  • list all artifacts
  • exclude review-veto-log
  • compute finalArtifactIds, draftArtifactIds, vetoArtifactIds
  • run runProjectFactcheck
  • reject if: no design artifacts, any drafts, any vetoes, or factcheck fails

A successful advance stores a phase-gate-decision; a rejection stores a phase-gate-audit entry.

2.3 Rejected key replay, verified on a fresh probe project

This behavior is easy to miss and matters for operators. On a fresh probe project:

# attempt 1: no artifacts yet
$CLI phase-advance --projectId gate-replay-probe-4d155435 --toPhase define \
  --idempotencyKey probe-1 --approvalReceipt '{...}'
# asd phase-advance: phase advance requires at least one design artifact

# after writing + reviewing a final artifact, reusing the REJECTED key
$CLI phase-advance --projectId gate-replay-probe-4d155435 --toPhase define \
  --idempotencyKey probe-1 --approvalReceipt '{...}'
# asd phase-advance: phase advance requires at least one design artifact

# fresh key re-evaluates preflight
$CLI phase-advance --projectId gate-replay-probe-4d155435 --toPhase define \
  --idempotencyKey probe-2 --approvalReceipt '{...}'
# → "outcome": "advanced"

Operational rule: one idempotency key per gate attempt. If the gate was rejected and you subsequently remediated the project, submit a new key so preflight is evaluated again.

3. Roadmap and RACI — ownership of the living system

A living blueprint dies when nobody owns the refresh loop. Two registered delivery methods supply the ownership artifacts:

  • implementation-roadmap / blueprint-to-backlog / wave-gated-rollout → roadmap kind (milestone required in the closed kind schema)
  • raci-definition → raci-matrix kind

Use them together. A minimal operating rhythm for the Kestrel case:

Cadence Artifact refreshed Owner (RACI shorthand) Evidence input
Weekly experience-audit deltas, recovery incidents Service ops lead (R), journey owner (A) complaint logs, telemetry export
Monthly kpi-tree baselines / targets Journey owner (A), analyst (R) KPI warehouse pull
Quarterly 15-principle audit, standards set, phase-gate review CX lead (A), content/ops/compliance (C) support themes, accessibility findings, policy changes

Worked example: six-discipline maturity diagnostic and a 90-day capability backlog

Fixture. A structured self-assessment of Northfield's follow-up service across the six CX operating disciplines, scored on a five-stage maturity scale (1 ad hoc, 2 repeatable, 3 defined, 4 managed, 5 optimizing):

Discipline Score Observable basis
Strategy & mandate 2 follow-up quality named in the annual plan; no accountable owner
Customer understanding 2 interviews exist; the telemetry (5d71a3e8…) is never joined to them
Design & delivery 1 journeys improvised per ward
Measurement 2 62h latency measured; no tiered kpi-tree
Governance & prioritisation 1 no review cadence; fixes compete informally
Culture & capability 2 nurses compensate (~40 min/patient, a64c2f81…) without mandate

Overall stage: 1–2 (ad hoc trending repeatable) — the weakest disciplines cap the whole.

Application. A maturity score matters only as a backlog. Convert the two weakest disciplines into a 90-day plan with named owners, expressed as a roadmap artifact (milestone required by the closed kind schema):

Milestone Discipline raised Owner Day Exit test
Weekly evidence import + experience-audit refresh Governance 1→2 service ops lead (A) 30 factcheck exit 0 on fresh evidence
Tiered kpi-tree published with baselines/targets Measurement 2→3 journey analyst (R), CX lead (A) 60 every KPI cites a data point
First phase-gate review with approvalReceipt Governance 2→3 executive sponsor 90 stored phase-gate-decision

Worked example: an evidence-backed business model canvas with a DFV gate

Fixture. The same provider's proposal to replace the three-portal follow-up with a single coordinated callback service. Nine blocks, every assumption carrying an evidence id:

Block Assumption Evidence
Customer segments day-surgery patients and their GPs 5d71a3e8…
Value proposition results and next steps reach you without you chasing 3f9a1c7e…
Channels outbound call + SMS; portal becomes optional 3f9a1c7e…
Customer relationships named-nurse continuity per episode 3f9a1c7e…
Revenue streams funded from the follow-up cost base, not new spend 5d71a3e8…
Key resources triage-trained nurses, shared scheduling system a64c2f81…
Key activities same-day result dispatch, tracked callbacks 8c2e5f19…
Key partnerships GP practices agree a receipt-confirmation protocol 8c2e5f19…
Cost structure eliminates 40 min/patient of chase work a64c2f81…

As an artifact shape: kind business-model-canvas, one node per block with fields: { assumption, evidenceId, status: evidenced | open }; in the current runtime the DFV decision itself persists as a critic review row on the proposal's governing artifact.

Application — the DFV gate. Desirability: evidenced — patients describe the chasing burden verbatim (3f9a1c7e…). Feasibility: partially evidenced — the receipt-confirmation protocol depends on GP partners and no partner evidence exists yet, so mark Key partnerships open. Viability: plausible but thin — the cost case rests on a single ward's time audit (a64c2f81…), not a system measurement. Gate decision: conditional proceed — a one-ward pilot must convert the two weak cells into evidence before any phase-gate receipt is signed.

Interpretation. The discipline lives in the verdicts, not the blocks: two of nine cells carried the decision, and naming their evidence ids is what made the weakness visible. A canvas without an evidence column is a poster; with one, it is a queue of testable assumptions feeding the pilot plan.

5. Hands-On Lab

  1. Create a fresh project. Attempt phase-advance immediately with a legal receipt JSON — observe requires at least one design artifact.
  2. Add evidence, write and pass-review one design artifact, and re-attempt with the same key; observe the recorded rejection replay.
  3. Re-attempt with a new idempotency key and observe success.
  4. Add a new evidence record that changes the service picture, write a new artifact version, and run factcheck again. Explain why the earlier gate success does not freeze the project forever.
  5. Draft a three-milestone roadmap and a four-role RACI for the next quarter's audit rhythm.

Verification checklist

  • Both enums stated correctly (project vs method phases)
  • Rejected-key replay and fresh-key success observed
  • approvalReceipt fields copied exactly
  • New evidence forces a fresh artifact/versioning cycle, not a patch around the gate
  • Roadmap milestone + accountable owner named for each cadence

Key Takeaways

  • Continuous ops = evidence refresh → method rerun → new artifact version → critic gate → factcheck → human gate; the blueprint stays alive because the loop stays alive.
  • project phases and method phases are different enums; they solve different governance problems.
  • sd_phase_advance proves a strong seam: legal transition, receipt present, all design artifacts final, no vetoes, passing factcheck.
  • A rejected phase-gate idempotency key replays its rejection; remediation requires a fresh key to re-evaluate.
  • Roadmap and RACI artifacts convert the toolkit from an audit stunt into an operating rhythm.
