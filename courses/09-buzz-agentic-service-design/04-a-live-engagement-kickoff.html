Course 09 — BUZZ for Agentic Service Design

A live engagement kickoff: Aster Grove Makerspace

Modules 04 through 07 walk one complete, receipted session end to end: the Aster Grove Makerspace engagement, run live on 2026-08-23. Aster Grove City Libraries is a fictional composite — the librarian, patron, front-desk, and programme quotes are synthetic sentences written for practice — but the BUZZ lane is entirely real: the private channel, the roster, the scoped mentions, six runtime replies under their own identities, the store handoffs, the human gate, and the Canvas round trip all happened and all are receipted. This module covers the setup through the orchestrator's first reply.

Learning Objectives

  • Stand up an isolated engagement: scratch workspace, project, synthetic evidence, channel, roster.
  • Write an owner kickoff that bounds scope, states signals as signals, and names human authority.
  • Dispatch a scoped mention — pubkey + deliverable + evidence boundary + prohibitions + stop condition.
  • Read a runtime-authored reply and know what makes it attributable.

The scenario

Aster Grove City Libraries runs a makerspace: equipment lending (3D printers, laser cutter, VR kits) plus workshop programming across its branches. The presenting tensions, all synthetic: members ask what they can make before they ask what they can borrow; a 45-minute standing induction excludes some members; VR kit booking collides with school hours; and a first 3D print has no starter support. The redesign target is the member journey from first hearing about the makerspace to a first independent making session.

Prerequisites

  1. The persona pack installed and its runtimes materialized (module 03).
  2. The asd CLI (platform/packs/cli/asd) and an isolated workspace: ASD_WORKSPACE pointed at a dedicated directory so the tutorial cannot touch real projects.
  3. The buzz CLI (/Applications/Buzz.app/Contents/MacOS/buzz) with the owner identity supplied through BUZZ_PRIVATE_KEY in the environment. Credentials stay shell-only: never pasted into messages, screenshots, receipts, or commits. The desktop app holds its identity in the macOS keychain; the session loaded that same owner identity into the CLI environment without displaying it.
  4. The Canvas index generator (scripts/buzz-canvas-index.mjs) — used in module 07.
  5. The read-only identity audit before any mention (scripts/buzz-live-identity-audit.mjs, plus buzz channels members and buzz users get --pubkey to join display names to member public keys).

Step 1 — the isolated project

export ASD_WORKSPACE="$PWD/tmp/buzz39/projects"
asd project-create --name "Aster Grove Makerspace" \
  --client "Fictional composite — Aster Grove City Libraries" \
  --sector "public libraries and community making" \
  --service "makerspace equipment lending and workshop programming"

The project id aster-grove-makerspace-6a8498ef becomes the join key for everything that follows: channel messages cite it, the runtimes read it, and the Canvas indexes it. Note the client string says fictional composite in the record itself — the boundary is persisted, not just promised.

Step 2 — register synthetic evidence

Ten records were registered before any agent was mentioned — quotes from a librarian, patrons, front desk, facilities, an accessibility lead and a programme lead; utilization telemetry; two documents:

asd evidence-add --projectId aster-grove-makerspace-6a8498ef \
  --source librarian-01 --kind quote \
  --body "Members ask what they can make before they ask what they can borrow."

Evidence ids are content-addressed sha256 values. Three of the ten, for reference: ce65c266fe6a0b05… (librarian-01), 5589914387f2a33f… (patron-02), ab4e46f7114488672… (teen-patron-03). Keep the id list at hand — it is the mention contract you will hand to the agents. Agents cannot cite what was never captured; everything they may claim lives in those ten hashes.

Step 3 — write artifacts through the review gate

Before opening the channel, the workspace was given real state to coordinate around: the stakeholder map, current journey, KPI tree, and change plan were written with gated writes and promoted by review passes. The service blueprint deliberately exercised the failure path first — a backstage node with an unnamed lane was vetoed and remediated on the same artifact id. Module 06 replays that loop in full; here it matters only as context: the channel was born into a workspace that already had a review history, which is what the critic will verify later.

Step 5 — post the owner kickoff

The kickoff message states four things and mentions no one:

  1. the fictional boundary — what is synthetic and why;
  2. the project id and the workspace state (evidence count, artifact count);
  3. what the channel is for — coordination, not persistence;
  4. where authority lives — the human owner, at every phase gate.

Live capture s02 — the owner kickoff. Read it as a charter in miniature: boundary, join key, state, authority. No agent is mentioned yet — dispatch is a separate, deliberate act.

Why "signals as signals" matters: the kickoff contains figures like the 45-minute induction, but as prose. Module 05 shows both the mapper and (in a second documented run) a researcher refusing to treat prose-in-a-chat as evidence. The kickoff is a charter, not a dataset.

Step 6 — mention the orchestrator by public key

buzz messages send --channel 361023a9-31cb-4b40-845f-19d64f7827ee \
  --mention 1b0d61df9076688c3b84d9c8f5c7fe4b07342f4ca81f0b053c108a11bed63075 \
  --content "@Maya Start Discover coordination … use only these evidence IDs …
  stop for my framing decision before Define."

Two details make this a contract rather than a ping. First, the mention carries the runtime's public key, not its display name — name-only mentions do not notify. Second, the request is scoped: an outcome, an evidence boundary, prohibitions, and a stop condition.

Maya replied (event b47e889a…) with a coordination plan that delegated to Liam and Kai in parallel, kept the evidence boundary, and stopped at the human gate with two open questions for the owner.

Live capture s03 — the orchestrator's runtime-authored reply. It is signed by Maya's key, it delegates in parallel, it restates the evidence boundary, and it ends stopped at the gate with questions — coordination without authority drift.

Step 7 — parallel specialist mentions

The owner then sent Liam (provenance) and Kai (failure demand) their own scoped mentions — each with its own deliverable, its own evidence list, and its own stop condition:

Live capture s04 — two scoped mentions: the researcher asked for a provenance check over the ten evidence ids; the mapper asked for evidence-bounded failure-demand moments. Notice what is not in the asks — no "share your findings" without ids, no open-ended "look into it".

sequenceDiagram
  participant O as Owner
  participant M as Maya orchestrator
  participant L as Liam researcher
  participant K as Kai mapper
  O->>M: scoped Discover coordination
  M->>L: provenance check (10 ids)
  M->>K: failure-demand mapping
  L-->>M: provenance PASS table
  K-->>M: 4 failure-demand moments
  M-->>O: reconciliation gate report

One mention per ask. Each ask names its deliverable ("frame", "provenance check", "failure-demand moments") so replies are auditable against requests. When Maya reconciles both specialists into a gate report addressed to the owner, the structure of the conversation already reads like an engagement, because it is one.

A second documented run: Northfield

The same kickoff discipline was exercised in the course's earlier documented run — sd/northfield-followup-care, a fictional health-system engagement (18% of day-surgery patients missing their first follow-up; 62-hour median wound-check callback latency; three patient portals; forty minutes of nurse time per patient chasing GP confirmation). Same mechanics, different client: private channel, roster by pubkey, kickoff with boundary and authority, then one scoped mention per ask — "frame" (orchestrator), "ground in canon" (librarian), "draft journey skeleton" (mapper), "gate posture" (critic). The framings differ; the contract does not. That is the point of a contract.

Hands-on lab

  1. Create a scratch workspace and a throwaway project with asd project-create; register three evidence records with clearly synthetic bodies.
  2. Create a private channel named for your scratch project and add your audited roster.
  3. Write the kickoff message — boundary, project id, state, authority — and post it without mentioning anyone.
  4. Send one scoped mention to your orchestrator: pubkey, deliverable, evidence ids, prohibition ("do not treat kickoff prose as evidence"), stop condition. Save the returned event ids; module 05 verifies replies against them.

Key Takeaways

  • Isolate first: scratch ASD_WORKSPACE, dedicated project, private channel — the engagement is a sealed room.
  • Evidence before agents: the id list you hand out is the mention contract; nothing outside it may be cited.
  • A kickoff is a charter (boundary, join key, state, authority) — not a dataset.
  • Scoped mentions (key + deliverable + boundary + prohibitions + stop) make replies auditable against requests.
