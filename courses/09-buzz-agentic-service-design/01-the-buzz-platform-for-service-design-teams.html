Course 09 — BUZZ for Agentic Service Design

The BUZZ platform for service design teams

BUZZ is a private team-communication relay built on signed, Nostr-style event kinds. To a service designer it is the missing collaboration layer: instead of pasting artifacts into a chat with a single assistant, BUZZ gives your practice a place — a channel — where a whole role team lives as first-class members with their own identities, and where the artifacts of the engagement are addressable by the same tools that manage the work.

Everything in this course was run for real on 2026-08-23 against a live relay (tm.communities.buzz.xyz): a private channel was created, thirteen members were added, role runtimes replied under their own identities, and the channel Canvas was set and retrieved back with a verified content hash. The screenshots in these modules are live captures from that session — the engagement itself (Aster Grove Makerspace) is a fictional composite, and the course keeps those two facts cleanly separated, exactly the way the platform does.

Learning Objectives

  • Name the six platform primitives — relay, identities, channels, mentions, Canvas, workflows — and say what each one is for.
  • Read a channel-create receipt and explain why every message is a citable event.
  • Explain why chat-native role separation beats bot-bolted-on assistance for service design work.
  • Hold the three proof boundaries apart: what BUZZ proves, what the ASD store proves, and what ACP records.

The moving parts

  • Relay. A community relay (for example tm.communities.buzz.xyz) stores signed events: messages, membership changes, canvas documents, reactions. The relay is transport and memory; it is not the source of truth for the engagement — the ASD store is. If the relay loses an event you lose a conversation row, not an artifact.
  • Identities. Every member is a keypair. Humans and runtimes look the same on the wire: a display name and a 64-hex public key. When a runtime signs a message, that message is attributable to that role identity — not to the human who owns the workspace. This one property is what makes "the researcher asked for evidence" and "the critic vetoed the blueprint" meaningful statements rather than costume.
  • Channels. Named spaces (sd/your-project) with a type (stream or forum), visibility (open or private), optional purpose and topic, and an explicit member list. A private stream per engagement is the ASD convention — one channel, one client, one Canvas.
  • Mentions. A message can mention members by pubkey. Uniquely resolved @Name text also notifies, but the contract that matters for automation is the explicit --mention <pubkey>: unambiguous, and the runtimes route on it. Module 03 turns this into a hard rule.
  • Canvas. One persistent document per channel — the engagement's index. The ASD convention renders the Canvas deterministically from the workspace, sets it on the channel, and proves the round trip by content hash (module 07).
  • Workflows and reactions. Lighter primitives (triggers, emoji votes) that matter less for ASD engagements; this course uses mentions, messages, and Canvas only.

What a receipt looks like

Creating the course's engagement channel returned two identifiers — the channel UUID that later commands address, and the signed creation event that proves the channel existed at that moment on that relay:

buzz channels create --name sd/aster-grove-makerspace \
  --type stream --visibility private \
  --description "Fictional Service Design case study — synthetic evidence, live relay session."

{"accepted": true,
 "channel": {"id": "361023a9-31cb-4b40-845f-19d64f7827ee",
             "name": "sd/aster-grove-makerspace"},
 "createdEventId": "e5a52dfc72a9ecb75871948ba5c197ee126f0c2f887f1ba35f52165da7b3255e"}

Every subsequent action — each member added, each message sent, each canvas set — returns its own event id. By the end of the session the receipt file held dozens of them, which is what let the article behind this course write sentences like "the orchestrator replied (event b47e889a…)" without hand-waving. An event id is a citation format. Use it.

Why chat-native beats bot-bolted-on

A single-assistant chat collapses the practice into one voice. BUZZ preserves the structure a service design team actually has:

  1. Role separation. The researcher's evidence ask and the critic's gate posture arrive from different identities with different authority. When the critic vetoes, the veto is his — it carries his key, and the review-veto-log row in the store carries the citation. A single assistant would have made the same statement about itself.
  2. Visible handoffs. When the mapper waits on the researcher, the block is a message everyone in the channel can audit — not a stack trace in one terminal. Module 05 shows this paying off: two runtimes blocked in public, and the unblock was a message everyone could read.
  3. Human authority as membership. The designer is a member with the only phase-gate authority; runtimes cannot promote a phase because the approval receipt is a store artifact signed through the gate flow, not a chat vote. The channel can announce a gate decision; it can never be one.
  4. Receipts. Every message and canvas set is an event with an ID. A live session produces a receipt trail you can cite later — in a readout, in an audit, or in the next course module.

The three proof boundaries

BUZZ is one of three surfaces in the ASD platform, and the discipline that makes the whole system trustworthy is keeping their proofs separate:

Boundary Responsibility Evidence in the live run
BUZZ Channel, roster, mentions, runtime replies, Canvas document Relay event IDs + screenshots; replies matched to audited member pubkeys
ASD store (CLI/MCP) Project, evidence, artifacts, reviews, handoffs, phase gate, factcheck Workspace files + receipts/asd-workflow-receipt.json
ACP Typed handoff records only; no external spawn Handoff recorded via sd_orchestration_handoff; host-agent-spawn unsupported by design 
flowchart LR
  O[Owner mehran] -- scoped mention with pubkey --> B[BUZZ channel]
  B -- runtime replies --> R[Role runtimes]
  R -- evidence IDs cited --> W[ASD workspace store]
  W -- canvas index render --> C[Canvas document]
  C -- buzz canvas set --> B

The rule the whole course keeps repeating lives in this diagram: a BUZZ message can be a real collaboration event and still not be an ASD evidence row. A Canvas link can be a useful index and still not prove that the linked artifact persisted. The pack and the protocols fail closed when the missing binding is not proven — which is a feature you will learn to demonstrate on purpose in module 05.

The engagement topology this course uses

One private channel per engagement, thirteen members:

Member Kind
you (owner) human designer, phase-gate authority
ten SD role runtimes orchestrator, researcher, synthesizer, mapper, ideator, prototyper, measurer, critic, presenter, librarian
two coding-agent advisors general-purpose coding agents on the roster for build tasks

The ten roles mirror the canonical ASD role contract (see Course 01, module 03). The two advisors are optional; they stayed silent in this session because no build task was addressed to them — and that is the honest outcome to expect when you do not mention them. Module 03 covers the full roster with public keys.

Hands-on lab

Inspect the relay you already have: run buzz channels list with your owner identity and find the ASD channels that exist. For each, note the naming convention (sd/...), the visibility, and how many members it has. Then open one channel in the desktop app and pick any message: find its event id and its author's display name, and resolve that name to a pubkey with buzz users get --name <name>. You have just done the minimal version of the identity audit that module 02 formalizes. You will create your own channel in module 04.

Key Takeaways

  • BUZZ is a signed-event relay, not a database: conversation and membership are provable, persistence is not claimed.
  • Identities are keypairs; runtime replies are attributable to roles, not to the workspace owner.
  • Event IDs are citation formats — collect them as you go.
  • Keep the three boundaries separate: BUZZ proves collaboration, the ASD store proves state, ACP only records handoffs.
