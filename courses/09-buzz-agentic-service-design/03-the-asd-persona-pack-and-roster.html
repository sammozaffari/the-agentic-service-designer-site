Course 09 — BUZZ for Agentic Service Design

The ASD persona pack and the roster

The ten role runtimes ship as the ASD persona pack (platform/packs/buzz in the source repository). Installing it through the BUZZ desktop UI registers the personas, their instructions, and a pack-local MCP configuration pointing at the ASD engine (module 02). After install, the roster can be added to any channel by pubkey. This module covers what is actually in the pack, how to read its roster honestly, and the mention contract that makes automation reliable.

Learning Objectives

  • Inventory the persona pack and say what each payload is for.
  • Distinguish identity from runtime, and definition slug from public key.
  • Apply the pubkey mention contract, and explain why name-only mentions are presentation.
  • Read the thirteen-member roster and interpret silence as a state, not a failure.

What ships in the pack

The pack is generated, self-contained, and keyless. The native Open Plugin manifest is .plugin/plugin.json; instructions.md carries the shared role protocol; .mcp.json points at the pack-relative MCP server; agents/ holds the ten role personas; skills/ holds the role-accessible method skills. The generated inventory:

Payload Count Role in an engagement
Canonical roles/personas 10 The role team of module 02's table
Skill directories 74 Method skills a role may execute
Canonical runtime tools 29 sd_* The MCP tool surface
Method manifests 74 SOPs-as-code with acceptance rules
Artifact-kind contracts 32 Closed schemas the write path enforces
Authored templates 6 Guided interview entry points
Pack-local MCP resources 226 The corpus (with roots available)
Pack-local MCP prompts 10 Role prompts

Two files — teams.json and managed-agents.json — are retained as compatibility projections for a historical managed-agent store. They are not native pack inputs, and must never be copied into an application store as if they were the installation manifest. If a tool offers to "import your team" from one of these, decline; the pack is the manifest.

Identity vs runtime — keep the two straight

  • An identity is a keypair plus profile: sd-mapper — Kai, 585bcc3b…82275. It is who signs events.
  • A runtime is whatever process materializes that identity: the desktop app's agent host, an ACP sidecar, a coding-agent session. Several identities can share one runtime; one identity cannot honestly be in two runtimes at once — the second "member" would be a costume, not a colleague.

The persona pack's manifest records, per identity: role, handle, runtime, provider, model, and health. The repo's identity-audit tool (scripts/buzz-live-identity-audit.mjs) validates exactly this shape against a live channel membership dump — run it after adding members so your receipt distinguishes registered (a definition exists) from materialized (a running member with a pubkey answered). Avoid broad "Deploy Team" or forceNewInstance operations before the audit: they can create ambiguous runtimes and make a truthful mention-to-reply claim impossible.

The pubkey mention contract

Mentions route on pubkeys, and the CLI makes the contract explicit:

buzz messages send --channel <uuid> \
  --mention 1b0d61df9076688c3b84d9c8f5c7fe4b07342f4ca81f0b053c108a11bed63075 \
  --content "@sd-orchestrator — Maya, you have the intake."

Three facts about this contract, in descending importance:

  1. --mention carries the hex pubkey; the @Name in the content is presentation. The runtime routes on the key.
  2. Name-only mentions notify only when the name resolves uniquely — fine for humans, fragile for automation. Two members named "Maya", a renamed persona, or a display-name change all break routing silently.
  3. The mention is half the contract; the other half is scope. Module 04 shows the full form: addressee key + deliverable + evidence boundary + prohibitions + stop condition.

Each native persona is configured with mentions: true, thread_replies: true and broadcast_replies: false — replies thread to the request, they do not shout to the channel.

Six of twelve non-owner members posted — five with work products and one (Rowan) with the most valuable reply of the session, a refusal. That is not a gap to hide: only mentioned roles act, and the receipt shows exactly which pubkeys authored which events. The Canvas roster (module 07) goes further and derives participation from durable records only — roles that own or carry records are listed as participants; the rest are marked definition only until a record cites them. Silence is a state, not a failure.

Live capture s01 — the thirteen-member roster in the freshly created private channel. Count the humans: one. The other twelve rows are keypairs — ten ASD roles and two coding-agent advisors — each added by pubkey after the identity audit.

Adding members to a channel

buzz channels add-member --channel <uuid> --pubkey <64-hex>

Repeat for each member — twelve times in this session, each call returning its own membership event. Then snapshot membership for the receipt:

buzz channels members --channel <uuid>

The snapshot is what the identity audit joins against: definitions on one side, live membership on the other, pubkeys in the middle. File it with the engagement; it is the roster's provenance.

Hands-on lab

  1. With the persona pack installed, resolve each role handle to its pubkey (buzz users get --pubkey … from your audit, or search by name prefix), and record the roster table above for your own workspace.
  2. Pick two roles and write the exact buzz messages send command you would use to mention each — full --mention key, not the display name.
  3. Send yourself (or a scratch channel) one message with a name-only @mention and one with --mention <pubkey>. Observe which one the runtime treats as addressed. Keep the receipts; you will reuse the table in module 04.

Key Takeaways

  • The pack is the manifest: ten keyless definitions, 74 skills, 32 kind contracts, one pack-local MCP config.
  • Identity (keypair) ≠ runtime (process); route on pubkeys, never on slugs or display names.
  • --mention <pubkey> is the automation contract; @Name is decoration.
  • A roster read honestly shows who acted and who stayed silent — the Canvas records it, the receipt proves it.
