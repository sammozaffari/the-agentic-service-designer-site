Course 09 — BUZZ for Agentic Service Design

Agents, MCP, ACP, and the integration landscape

Module 01 placed BUZZ in the picture. This module places everything else: where the ten role agents come from, how they reach the ASD store through MCP, what ACP is allowed to do (and not do), and which hosts the persona pack already integrates with beyond the BUZZ desktop app. By the end you should be able to draw the whole stack on a napkin and defend every arrow on it.

Learning Objectives

  • Describe the ASD platform stack: persona pack → materialized runtimes → pack-local MCP server → ASD workspace store.
  • Say what MCP contributes (29 canonical tools, corpus resources, prompts) and what the ASD_WORKSPACE boundary protects.
  • State the ACP contract precisely: record-only, fail-closed, no external spawn.
  • Map the integration landscape: the six emitted MCP bundles, and where each host's proof stops.

Read it bottom-up for the ownership story: the store owns state; the MCP server is the single governed door to it; runtimes are the only things allowed through that door; hosts are where runtimes live. No arrow lets a chat message write a store record directly, and no arrow lets one host's runtime mutate another host's process space — the two failure modes this architecture exists to prevent.

The ten role agents — and two advisors

The ten canonical roles ship as personas in the ASD persona pack. Every persona receives the same evidence, review, and human-gate contract; what differs is ownership:

Role · handle Primary responsibility Typical outputs or handoff
Orchestrator · sd-orchestrator Plan the engagement, sequence methods, coordinate handoffs, surface phase-gate decisions Orchestration records and human handoffs
Researcher · sd-researcher Gather verbatim evidence, provenance and context Evidence register, research plan, stakeholder/context inputs
Synthesizer · sd-synthesizer Cluster evidence and form insights, personas, first-pass journeys Insight, affinity, persona and synthesis artifacts
Mapper · sd-mapper Build deterministic journey maps, blueprints, mental models, ecosystem maps Evidence-linked map nodes; no hand-authored diagrams
Ideator · sd-ideator Frame HMWs and concepts from the evidence-backed insight set HMW, concept, story and value-proposition artifacts
Prototyper · sd-prototyper Design and test prototypes; separate test evidence from assumptions Prototype/test artifacts and evidence requests
Measurer · sd-measurer Connect service quality, KPIs and outcomes through a causal chain KPI trees, audits, opportunities and roadmaps
Critic · sd-critic Challenge evidence sufficiency; record defect/proposal rows Evidence-cited review-veto-log; a veto keeps the artifact in draft
Presenter · sd-presenter Assemble reports from final artifacts without inventing content Report and export requests
Librarian · sd-librarian Maintain corpus provenance, method/skill drift, template references Knowledge lookups and drift reports

Two coding-agent advisors (claude-code-opus and codex-sol-high in the course's session) round out the roster as general-purpose build agents. They are members like anyone else — mention them with a pubkey and they act; do not, and they stay silent. In the Aster Grove session nobody dispatched a build task, so neither advisor posted, and the honest ledger records exactly that.

MCP: the governed door to the store

The persona pack ships a pack-local MCP configuration — deliberately relative to the installed pack, so every host that loads the pack gets the same server without central configuration:

{
  "mcpServers": {
    "asd": {
      "command": "node",
      "args": ["mcp/bin/server.mjs"]
    }
  }
}

That server exposes the canonical surface of the platform:

MCP surface Count What it gives a runtime
Canonical tools 29 sd_* sd_artifact_write, sd_review, sd_factcheck, phase-advance, orchestration records — the same contract on every host
Resources 226 (with corpus roots) The corpus the model reads: books, articles, templates, methods
Prompts 10 role prompts Role-shaped entry points for each persona

Two properties of this door matter for everything that follows in this course. First, it is the same door everywhere: the runtimes that replied in BUZZ and the standalone CLI all go through one tool contract — which is why an artifact id written by one surface is meaningful to all the others. Second, the server's workspace is bounded by ASD_WORKSPACE, defaulting to ~/.asd/projects: a runtime can only touch the projects its environment points it at. In the Aster Grove session that boundary was load-bearing — it is the reason the ideator in module 05 could not see the workspace and had to refuse rather than fabricate.

Live MCP reads were demonstrated in the session itself: Liam, Marcus, and Nadia all cited exact store ids in their replies (evidence ids, review-log rows, the method registry), which is only possible if their sessions were actually talking to the store through MCP. An agent that guesses ids fails the module 05 verification step; an agent that reads them passes it.

ACP: record-only by design

ACP (Agent Communication Protocol) shows up in the ASD platform as a typed envelope, asd-acp/1, that records a handoff from one role to another. What it does not do is spawn or reach into another host's agents:

  • host-agent-spawn is unsupported for the emitted pack. A request to spawn an agent in another host returns a structured unsupported result — fail-closed, not fake success.
  • The durable artifact of a handoff is a store record made through sd_orchestration_handoff — in the Aster Grove session, the critic → orchestrator handoff after blueprint remediation is exactly such a row.
  • A BUZZ message may announce a handoff; the record id is the handoff. Announcements drift; records don't.

This boundary is easy to present as a limitation. It is better understood as scope control: cross-host process spawning is a security surface with no evidence payoff, so the platform records intent and leaves execution to verified host integrations. When a capability is absent, the honest row in the Canvas stays planned or blocked — never silently upgraded.

The integration landscape

Because the door is MCP-over-stdio, integrating a host means loading the pack and staying out of the way. Six MCP bundles are emitted with fresh disposable stdio evidence — BUZZ, Claude Code, Codex, Kimi, the standalone MCP target, and OpenCode — proving initialize, discovery, and representative ASD tool workflows in isolated environments for each. (Pack-local evidence is candid about its own limits: it does not prove that every host has executed every tool.)

Each host's evidence is its own: a bundle's disposable stdio run proves the pack loads and the tools answer on that host — it does not prove a live engagement ran there. The live-engagement proof in this course is the BUZZ lane itself (modules 04–07): replies matched to member pubkeys, citations resolved against the store, a Canvas round-trip hash. Keep the two proof kinds separate when you report integrations to stakeholders, the same way this course keeps BUZZ, store, and ACP proofs separate. Hosted workbench surfaces beyond the relay — the harness-hosted ASD Studio — are a different course's lane (Course 02), not this one. The architectural point stands either way: hosts come and go, the store and its door stay the same.

Definition identity vs runtime identity

The persona pack is intentionally keyless. A definition has a stable slug, display name, model metadata, and prompt. A running runtime has a separate, identity-backed public key. The safe relationship is a chain, and every link is owner-verified:

Do not use a persona slug as a public key; do not treat a keyless definition and its runtime as duplicates; do not infer from a green persona card that the runtime is reachable in your channel. Before the first mention, run the read-only identity audit:

node scripts/buzz-live-identity-audit.mjs \
  --input ./audit.json \
  --channel-id <channel-uuid> \
  --output ./identity-audit.json

The audit joins definitions, runtimes, public keys, membership, and mention candidates. It never loads credentials and deliberately has no --apply or --confirm mode — an audit that can mutate the thing it audits is not an audit.

Hands-on lab

  1. Install (or locate) the persona pack in your BUZZ desktop app and open its directory: find .plugin/plugin.json, instructions.md, .mcp.json, agents/, and skills/. Count the agent definitions — you should find ten.
  2. Read .mcp.json and confirm the MCP command is pack-relative. Start the server by hand (node mcp/bin/server.mjs) in a terminal and issue an initialize + tools/list request — you should see the canonical sd_* tools.
  3. Set ASD_WORKSPACE to an empty scratch directory before you start the server, then confirm a tools/list + one read tool sees only that workspace. You have just verified the boundary that module 05's refusal depends on.
  4. Run the read-only identity audit against a channel you own and read the join report: definitions → runtimes → pubkeys → membership.

Key Takeaways

  • State lives in the ASD store; MCP is its single governed door (29 tools, corpus resources, prompts) — identical on every host.
  • ASD_WORKSPACE is a security boundary, not a convenience flag; refusals in module 05 are it working.
  • ACP is record-only and fail-closed: handoffs are store rows, announcements are chat messages, and spawning across hosts is unsupported by design.
  • Six MCP bundles all sit on the same contract — hosts change, the door doesn't.
  • Persona definitions are keyless; only owner-verified runtime pubkeys are mention targets.
