Module 07.5: SOPs-as-Code: Versioned Execution Playbooks & Governance

Course: Cross-Channel Orchestration, Prototyping & SOPs-as-Code · Level: Advanced · Duration: 50 min · Format: Theory, Architecture, Code & Hands-on Lab

Learning Objectives

  1. Theoretical Foundations: Why static SOP binders fail under real service change, and why measurable standards plus governed rollout plans are the service-design answer.
  2. Agent Topology & Contracts: service-standard-authoring → service-standard-set, change-pack-authoring → change-plan, implementation-roadmap → roadmap, plus sd_orchestration_plan / sd_orchestration_dispatch for rollout tracking.
  3. Architecture & Schemas: Closed node fields for standards, change plans, and roadmaps; how these typed artifacts replace informal SOP prose.
  4. Case Study Execution: Pilots, Scaling & Organizational Change at Aurelia Insurance (Article 21) through a verified runtime session.
  5. Adversarial Verification: Critic gates on standards and change packs, deterministic factcheck, and human-gated phase advance.
  6. Hands-on Practice: Author a measurable standard, convert it into a change plan, sequence it as a roadmap, then track rollout dispatches.

1. Theoretical Grounding & Literature Synthesis

The binder fails because services change faster than prose

Service Design for Business (Reason, Løvlie, Flu, 2015) makes the core organizational point twice: in Ch. 2 (The Frontline), the authors argue that frontline quality is limited by internal structures — fragmented tools, conflicting incentives, rigid approvals — rather than employee goodwill; in Ch. 6 (Organizational Change), they argue that any serious service redesign is fundamentally an organizational change program. Those two claims explain why the SOP binder fails:

  • It describes the service as if it were stable.
  • It separates the customer-facing standard from the organizational change needed to make the standard true.
  • It is unauditable: nobody can tell which sentence is current, who owns it, what metric proves it, or which rollout wave is blocked.

In service-design terms, a useful SOP has at least four properties the binder almost never has:

  1. Measurability — a standard names a testable measure, not an aspiration.
  2. Ownership — a person or role is accountable for the standard and each rollout action.
  3. Versionability — changes are explicit artifacts with status.
  4. Operational traceability — rollout is observable step by step.

This module treats SOPs as a chain of typed artifacts, not as freeform documentation:

  • service-standard-set — the measurable truth you want the frontline to deliver.
  • change-plan — the operational changes needed to make the standard true.
  • roadmap — the sequence of waves that lands the change.
  • orchestration-plan / dispatch — the record of rollout execution step by step.

There is no separate SOP tool family

This matters because teams often expect a dedicated SOP authoring namespace. The verified runtime surface contains 29 tools, and SOP work is expressed through typed artifacts plus review/governance commands. The project filesystem does contain a sops/ directory, but the runtime uses it as a record surface for orchestration plans (sops/orchestration.json in the verified run), not as a parallel pseudo-tool namespace. In the @asd model, the "SOP" is the typed artifact — a service-standard-set linked to change-plan, roadmap, and rollout dispatch records.

3. Schemas & Verified Execution

TypeScript schema (@asd/core)

// "service-standard-set": measure: string REQUIRED   target: number   owner: string   test: string   status: string
//   relations: derived-from → service-blueprint | journey-map | experience-audit
//              supports     → change-plan | recovery-playbook | kpi-tree
// "change-plan": action: string REQUIRED   owner: string   status: string   priority: string   dependency: string   audience: string
//   relations: derived-from → service-blueprint | roadmap | service-standard-set | stakeholder-map
//              supports     → roadmap | raci-matrix | kpi-tree
// "roadmap": milestone: string REQUIRED   horizon: string   owner: string   dependency: string   status: string   target: number
export interface ServiceStandardNodeFields {
  measure: string               // REQUIRED — measurable, auditable, customer-facing or enabling rule
  target?: number               // quantitative target where appropriate
  owner?: string
  test?: string                 // how the standard is checked in practice
  status?: string
}

4. Case Study Lens: Pilots, Scaling & Organizational Change at Aurelia Insurance (Article 21)

Synthetic illustration — not a production log. Article 21 is an illustrative composite.

Aurelia's composite program did not fail at ideation or prototyping; it failed at the binder stage. Pilot teams had a good idea of the target experience, but one region was operating from an old desk script, another from a local wiki, and a third from a PDF in SharePoint. The move that unlocked scaling was not "write better SOPs" but split the bundle into typed layers: one measurable service-standard-set, one accountable change-plan, one rollout roadmap, and one orchestration record of step execution. In other words, the operational memory moved from prose to artifacts. That is why the runtime's orchestration status matters pedagogically: it is the concrete answer to "how do I know wave 1 actually happened?"

Deliberate fail-closed demos

  1. No pseudo SOP tools: asd sop-author does not exist. The runtime surface is service-standard-authoring, change-pack-authoring, and orchestration tools.
  2. Phase gate without receipt:
asd phase-advance: missing required flag "--approvalReceipt"
  1. Unmeasurable standard: a service-standard-set node with measure: "delight the customer" may pass schema but should be vetoed by the Critic because the contract explicitly rejects standards whose metric is not measurable.

Verification checklist

  • Standard nodes name concrete measures and owners.
  • Change-plan nodes name explicit actions and accountable owners.
  • Roadmap nodes sequence milestones with horizons.
  • orchestration-status shows per-step rollout state, not just a prose note.
  • Phase advancement attempted only with an approval receipt.

Key Takeaways

  • In @asd, an SOP is a typed artifact chain, not a new tool family: service-standard-set → change-plan → roadmap → orchestration-plan.
  • There are no sd_sop_* tools; measurable standards and rollout records are the operational truth.
  • Rollout tracking is first-class: sd_orchestration_plan, dispatch, and status persist step outcomes in sops/orchestration.json.
  • Humans still own authorization. sd_phase_advance refuses to move without an approval receipt.
