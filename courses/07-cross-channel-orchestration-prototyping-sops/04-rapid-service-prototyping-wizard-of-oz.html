📖 1. Theoretical Grounding & Literature Synthesis

Services exist only in performance

Service Design: From Insight to Implementation (Polaine, Løvlie, Reason, 2013), Ch. 6 (Prototyping Services), states the module's premise: a physical product can be prototyped as a static object, but a service exists only in performance, interaction, and temporal sequence. You cannot learn whether a token-based collection feels seamless from a rendering of a kiosk screen; you learn it by staging the moment with real latency, real queues, and a real customer holding a phone. The chapter's practical machinery:

  • Blueprint as rehearsal instrument — the service blueprint is not documentation; it is the script the rehearsal performs.
  • Progressive fidelity — each prototype round answers specific open questions at the minimum fidelity that can answer them, because fidelity is cost and cost is what stops teams from testing.
  • Iterative learning loops — each round ends in a decision: advance, repeat, or kill.

The fidelity ladder and its gates

The ladder, low to high: tabletop/desktop walkthrough (staff rehearse the service with props on a table) → Wizard-of-Oz (the customer experiences apparent automation that a hidden human actually performs) → concierge pilot (a real but manually-delivered service for a few customers) → staffed pilot → operational rollout. The discipline is not the rungs; it is the gates between them. Each gate consumes the prior rung's test evidence and decides: advance a rung, repeat the current rung with changes, or stop. Ungated ladders are how organizations leap from a successful workshop straight to a capital commitment.

Why agentic infrastructure

Wizard-of-Oz testing fails quietly in two ways: the "wizard" behaviors drift between sessions (so results are not comparable), and gate decisions get made in hallways with no record of what evidence justified the leap. The toolchain addresses both: the prototype-plan artifact pins the hypothesis, fidelity, and pass gate before the run (forbid-field-values fidelity rejects placeholder fidelity claims); the test-report demands two evidence records per node (min-evidence-per-node 2) so a single anecdote cannot carry a gate; and prototype-ladder-gating fails closed unless a test-report exists — you structurally cannot advance a rung on vibes.

💻 3. Schemas & Verified Execution

// "prototype-plan":  hypothesis: string REQUIRED   fidelity: string   gate: string   test: string   learning: string   status: string
//   relations: derived-from → concept-set | journey-map | service-blueprint | decision-matrix
//              supports     → test-report | walkthrough-script | roadmap
// "walkthrough-script":  step: string REQUIRED   action: string   role: string   expected: string   result: string
//   relations: derived-from → prototype-plan | journey-map | persona-set
//              supports     → test-report | service-standard-set
// "test-report":  result: string REQUIRED   gate-decision: string   test: string   learning: string   severity: string
//   relations: derived-from → prototype-plan | walkthrough-script | journey-map | service-blueprint
// "decision-matrix":  option: string REQUIRED   recommendation: string   score: number   risk: number   criteria: string
//   relations: derived-from → opportunity-matrix | concept-set | value-proposition-canvas
export interface PrototypePlanNodeFields {
  hypothesis: string            // REQUIRED — the falsifiable claim this rung tests
  fidelity?: string             // acceptance: non-empty, placeholders forbidden
  gate?: string                 // the pass condition, pinned before the run
  test?: string
  learning?: string
  status?: string
}

📊 4. Case Study Lens: Rapid Experiments at Ember Hospitality (Article 17)

Synthetic illustration — not a production log. Article 17 (Prototyping Services: Rapid Experiments at Ember Hospitality) is an illustrative composite.

Ember's composite account runs the full ladder for a lobby-free check-in: a desktop walkthrough exposed that nobody owned the "reservation not found" exception (the rehearsal stalled for six minutes on exactly that beat); a Wizard-of-Oz rung with a staffer behind a fake kiosk validated that guests accepted the token handoff; and the ladder gate repeated the payment-exception rung because only two exceptions had been observed — below the threshold the team had pinned in the prototype-plan's gate field. That repeat decision is the module in miniature: the gate field written before the run is what made "we need more exception data" a mechanical conclusion rather than an argument.

Deliberate fail-closed demo

asd method-run: method "prototype-ladder-gating" requires at least 1 artifact input of
kind test-report; project has 0. Produce the typed input artifact before starting.

A test-report node citing only one evidence record is retained as draft with min-evidence-per-node in check.failures — one anecdote never advances a rung.

Verification checklist

  • prototype-plan pins hypothesis, fidelity, and a numeric gate before any session runs.
  • test-report nodes each cite ≥2 evidence records.
  • The ladder decision-matrix carries an explicit recommendation per open question.
  • Every gate crossed has a critic pass verdict on both the test-report and the decision-matrix.

🚀 Key Takeaways

  • ✅ Services are prototyped in performance: rehearse with walkthroughs, simulate with wizards, deliver manually with concierge pilots.
  • ✅ The ladder's value is its gates — each gate is a Critic review consuming a two-evidence test-report.
  • ✅ Pin the pass condition (gate) before the run; the pre-registered threshold turns "advance?" into arithmetic.
  • ✅ prototype-ladder-gating fails closed without a test-report: no evidence, no rung.
