Course 10 — Installing and operating the platform

Agents, skills, and the /asd command

The plugin carries three component families. Knowing what each one loads — and what it does not do — is the difference between driving the platform and being driven by it.

The ten role agents

Each role is a subagent with its own system prompt derived from the canonical role contract: authority (what it may decide), inputs (which artifacts it reads), outputs (which kinds it authors), handoffs, veto rights, and the human checkpoints it must respect.

Role Reads Authors
orchestrator project, plans orchestration-plan
researcher brief, evidence asks research-plan, discussion-guide, evidence
synthesizer raw evidence insight-set, affinity-cluster-set
mapper insights journey-map, service-blueprint, ecosystem-map
ideator / prototyper insights, HMWs hmw-set, concept-set, prototype-plan, walkthrough-script
measurer baseline + targets kpi-tree, test-report
critic everything review verdicts, review-veto-log
presenter finals executive-report, presentation-deck
librarian corpus canon grounding, provenance checks

In Claude Code you invoke them as subagents (@sd-mapper …) or let /asd route for you.

The {{SKILLS}} method skills

Every method from the corpus ships as a SKILL.md with name + description frontmatter — that frontmatter is what makes them triggerable. Skills encode the same SOPs the engine enforces: which evidence minimums apply, which artifact kind the method produces, which acceptance rules gate finality. Triggering one by name in conversation should end in the same sd_method_run → sd_artifact_write → sd_review sequence as calling the tools by hand; if a session claims an artifact without those calls, nothing was persisted.

What /asd does

The asd command is the orchestrator shortcut: it frames the engagement, routes role work, keeps every write on the tool path, and stops at phase gates. Its own text is generated from the enforcement notes in the emitter — it cannot claim gates that do not exist, because the claim and the code come from one place.

How hosts load all this

  • Claude Code: plugin root components (agents/, skills/, commands/asd.md) plus .mcp.json — verified live: Skills (75), Agents (10), MCP servers (1).
  • Kimi / OpenCode: native agent files + <name>/SKILL.md skill directories + their MCP config formats.
  • Codex: AGENTS.md conventions + .codex/config.toml MCP registration.
  • OMP / Pi: neutral agents/<role>/instructions.md + skills/<skill>/SKILL.md trees to copy into discovery paths.
  • Grok / AGY: prompt adapters only — role posture without runtime tools; pair them with the standalone asd-mcp repo when tools are needed.

Hands-on lab

In your host of choice: trigger three different skills by name and confirm each produced (or requested) real store writes via the tool path. Then ask the critic role to review something that has no producing method and observe the honest refusal — finality requires a gate that exists.
