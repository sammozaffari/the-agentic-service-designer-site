Module 02.2: One Runtime, Two Live Surfaces — CLI and MCP (DSH Studio as a Deferred Integration)

Course: The ASD Platform, Toolchain & DeepSeek Harness (dsh) · Level: Foundation · Duration: 55 min · Format: Theory, Technical Runlog & Hands-on Lab

Learning Objectives

By completing this module, you will be able to:

  1. Explain surface parity: why the asd CLI and the asd-mcp stdio server expose the same 29 tools with the same behavior, and how to verify that claim yourself.
  2. Operate both surfaces over one shared workspace: act via CLI, observe via MCP, and watch the state converge.
  3. Read the DSH Studio integration honestly: what the pack contains (@asd/ui profile, six host slots, loopback RPC boundary), what is verified (pack structure), and what remains deferred (live Studio as a student environment).
  4. Distinguish transport from behavior: transports differ; the registry, schemas, and fail-closed gates do not.
  5. Complete the hands-on lab driving the same project through CLI and MCP in alternation.

1. Foundational Theory & Literature Grounding

Services are delivered through channels; design tools are too

Orchestrating Experiences (Hazard & Resmini, books/08-orchestrating-experiences/01-why-orchestration) argues that a service is never a single touchpoint — it is the coherence across channels that users experience as one service. A council repairs service that is excellent by phone and broken online is, to the resident, a broken service. The same principle applies to the design toolchain itself: if the CLI behaves one way and the MCP server another, the practitioner experiences a broken platform, and — worse — artifacts produced on one surface cannot be trusted on the other.

The User's Journey (Lichaw, books/10-the-users-journey/03-touchpoints-and-channels) gives the design rule: channels may differ in affordance (a terminal streams text; a protocol speaks JSON-RPC) but must converge on state and story. In SDAP terms: transports differ; the registry, the schemas, the evidence store, and the gates are shared.

This module's core claim is therefore architectural, not cosmetic: CLI and MCP are two projections of one @asd/engine registry over one workspace store, and you can prove it by driving both against the same project. The DSH Studio surface, when its live integration lands, will be a third projection of the same registry — which is exactly why it can be deferred without weakening anything you learn here.

Key principles

  • Parity is a test, not a slogan: call sd_factcheck from CLI and from MCP against the same project; the JSON must agree.
  • State lives in the workspace, not the surface: close the CLI, open MCP, the project is exactly where you left it.
  • Deferred means deferred: DSH Studio is taught here as an integration surface with its own acceptance evidence, never as the student environment.

3. Schemas, Tools & Verified Execution

The parity claim, tested live

Same workspace, same project, two surfaces. First the CLI writes; then MCP reads. (Session verified 2026-08-22 against suite/packages/runtime/lib/.)

export ASD_WORKSPACE=/tmp/asd-c02-1787398523
CLI="node suite/packages/runtime/lib/cli.mjs"

# CLI surface: what projects exist?
$CLI project-list
# → lists fernwood-repairs-sprint-6b4b0c26 (phase now "define" after the receipted
#   phase-advance from module 02.1's run) and fail-demo-218ef129

# MCP surface: the same store, over JSON-RPC stdio (newline-delimited; one message per line)
{
  printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"parity-check","version":"1.0.0"}}}'
  printf '%s\n' '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"sd_factcheck","arguments":{"projectId":"fernwood-repairs-sprint-6b4b0c26"}}}'
  sleep 2   # keep stdin open: the server aborts in-flight calls on stdin close
} | node suite/packages/runtime/lib/mcp.mjs
# → id 2 result content: "## Factcheck" + the same JSON the CLI prints:
#   {"pass":true,"rows":[{"artifactId":"5b43c26c...","status":"final",
#    "integrity":{"pass":true},"schema":{"pass":true},"acceptance":{"pass":true},
#    "review":{"pass":true,"gate":"critic","verdict":"pass"}}, ...]}

Same project, same verdicts, same artifact ids. The MCP response embeds the CLI's human-readable rendering (## Factcheck + fenced JSON) inside a JSON-RPC result.content[0].text envelope — transport differs, payload does not.

Operational detail worth memorizing: stdin lifetime

The stdio server processes each line as one JSON-RPC message, and on stdin close it aborts every in-flight tool call (cooperative cancellation — tool bodies run in-process, so this is a polite abort, not a kill). Consequence you will hit in practice: piping a finite batch of requests into mcp.mjs and closing stdin immediately can lose tools/call responses. Long-lived clients (editors, hosts) hold the pipe open by design; shell demos need the sleep 2 idiom above, or a proper client.

Sequence diagram — one project, two surfaces, converging state

The DSH Studio integration surface (deferred — honesty boundary)

What exists and is verified as pack structure (platform/packs/dsh):

  • Capability profile exact-dsh-rc.5, targeting DeepSeek Harness 0.1.0-rc.5 with the @asd/ui 0.5.0 package.
  • Declared execution mode canonical-tool-registry: Studio RPC resolves into the same 29 tool definitions — no forked behavior.
  • Declared boundary behavior: hostAgentSpawn: "bounded-subagent-provider" and unsupportedBehavior: "return-structured-error" — anything Studio cannot honor must fail as a structured error, never as a silent approximation.
  • A capability projection over the shared contract (suite/packages/core/data/capability-contract.json), with support labels (supported / unverified / unsupported) per capability id.

What is not claimed (per the course honesty contract): DSH Studio and BUZZ as live student environments. Host execution across all packs is recorded liveHostExecution: "unverified" unless a host receipt says otherwise. When you read Article 36 (articles/36) below, notice how its §0 splits evidence into two lanes — a current integration receipt for the pack, and bounded prior workflow evidence for the case — instead of blending them. That is the standard this course holds every surface to.

4. Enterprise Case Study Lens

Article 36 — Running a Service Design Engagement Inside the Harness: Wattle Grove Community Care (articles/36)

Synthetic illustration — not a production log. Wattle Grove is a fictional composite; its eight evidence records were authored for the article.

Wattle Grove is the right lens for this module precisely because it is the most careful article in the corpus about surface claims. Its §0 states plainly what this module teaches: the DSH receipt verifies the profile composition (@deepseek-ai/dsh-base + @asd/ui + @deepseek-ai/dsh-web-app, six host slots, official add/update/remove/reinstall lifecycle, clean smoke/accessibility/portability checks) — and the care-scheduling artifacts are bounded prior workflow evidence, not a claim that the current host dispatched providers end to end.

The engagement itself — continuity-of-care scheduling for an aged-care provider — also illustrates why surface parity is an ethical property in high-stakes domains: a care plan drafted on one surface and reviewed on another must be the same object, with the same evidence citations, or families are being quoted different truths. The review-veto-log you saw minted in module 02.1 (09b1dc29d9424fbfab24ab1991422384) is the mechanism: verdicts are artifacts in the shared store, so every surface reads the same gate history.

5. Critic Gate & Review Veto Rules (surface-parity edition)

[!IMPORTANT]

  1. A review verdict recorded via CLI is visible to MCP tools/call sd_review_list identically — the verdict log is workspace state.
  2. A veto on either surface keeps the artifact draft on both surfaces; there is no surface-local override.
  3. sd_factcheck must return the same pass value on both surfaces for the same store state; if it ever disagrees, that is a platform bug, not a surface feature.
  4. Studio RPC, when live, inherits all of the above — its declared canonical-tool-registry execution mode is what makes that a verifiable claim rather than an aspiration.

6. Hands-On Lab Assignment

Objective

Drive one project through both live surfaces and prove state convergence.

Steps

cd ~/Documents/github/agentic-service-designer
export ASD_WORKSPACE=/tmp/asd-lab-02-2
CLI="node suite/packages/runtime/lib/cli.mjs"

# 1. CLI: create + feed
$CLI project-create --name "Lab 02.2 Parity" --client "<client>" --sector government --service "<service>"
$CLI evidence-add --projectId <pid> --source int-01 --kind quote --body "<verbatim 1>"
$CLI evidence-add --projectId <pid> --source int-02 --kind quote --body "<verbatim 2>"
$CLI evidence-add --projectId <pid> --source tel-01 --kind telemetry --body "<metric>"

# 2. MCP: ask for the method contract over stdio (hold stdin open)
{
  printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"lab-02-2","version":"1.0.0"}}}'
  printf '%s\n' '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"sd_method_run","arguments":{"projectId":"<pid>","methodId":"journey-from-transcripts"}}}'
  sleep 2
} | node suite/packages/runtime/lib/mcp.mjs
# expect: "## Method contract" with "availableEvidence": 3

# 3. CLI: write + review; 4. MCP: factcheck — compare with CLI factcheck byte for byte
$CLI artifact-write --projectId <pid> --methodId journey-from-transcripts --title "<title>" --nodes '<json>'
$CLI review --projectId <pid> --artifactId <aid> --verdict pass --rows '<json with one evidence-cited row>'
$CLI factcheck --projectId <pid> > /tmp/cli-factcheck.txt
# repeat factcheck via MCP tools/call; extract result.content[0].text; diff against /tmp/cli-factcheck.txt

Verification checklist

  • MCP sd_method_run reports availableEvidence matching your CLI evidence-add count
  • CLI factcheck text and MCP factcheck text are identical for the same store state
  • Closing stdin without a delay drops an in-flight tools/call (observe it; now you know why)
  • You can state, in one sentence, what the DSH pack verifies and what it does not claim

7. Summary & Reference Anchors

Key takeaways

  • Parity is architecture: one registry, one store, two live transports. You verified convergence with your own diff.
  • Stdio is a session, not a batch: stdin close aborts in-flight calls — hold the pipe open.
  • DSH Studio is a deferred integration surface: pack structure verified, live Studio use not claimed, boundary behavior declared (return-structured-error).
