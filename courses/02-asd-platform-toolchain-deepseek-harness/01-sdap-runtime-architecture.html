Learning Objectives

By completing this module, you will be able to:

  1. Explain the package layering of the @asd monorepo suite — which package owns schemas, which owns tool execution, which owns rendering — and why the layering exists.
  2. Read the capability registry (@asd/core capability contract) and explain the Studio RPC boundary as a projection of one canonical tool registry.
  3. Execute the canonical loop end to end against the real runtime: project → evidence → method contract → artifact draft → critic gate → factcheck.
  4. Predict failure modes: know which errors fail closed (dangling evidence, unmet acceptance, missing approval receipt) and why fail-closed is a design principle, not an inconvenience.
  5. Complete the hands-on lab that reproduces every command in this module on your own machine.

1. Foundational Theory & Literature Grounding

From workshop artifacts to an executable practice

Service design's classical literature is unanimous on one point: the deliverable is not the service. Stickdorn et al. frame service design as an iterative, evidence-based process whose prototypes exist to be tested against reality (This is Service Design Doing, books/01-this-is-service-design-doing/04-research-methods). Polaine, Løvlie and Reason go further in Service Design: From Insight to Implementation (books/03-service-design-from-insight-to-implementation/07-implementation): most service design projects die at the handoff from insight to implementation, because the artifacts — journey maps, blueprints, personas — are static documents that cannot execute anything. They persuade; they do not run.

Lou Downe's Good Services (books/05-good-services/02-the-fifteen-principles) states the operational consequence: a good service is one whose behavior is designed and verifiable, not one whose intentions are documented. Principle-level claims ("the service responds in a timely way") are only meaningful when you can check them against evidence.

This is the theoretical gap the SDAP runtime stack closes. If the workshop artifact is inert, the fix is not a prettier artifact — it is an artifact with a contract: typed schemas, acceptance rules, evidence provenance, and a review gate, all enforced by the same runtime that produced the artifact. The platform treats every design object as data with obligations, not as a drawing.

Why one registry, several surfaces

The second theoretical commitment comes from Service-Dominant Logic (Lusch & Vargo, books/12-service-dominant-logic/03-value-co-creation): value is co-created in use, so the tools of design must remain operable wherever the practitioner actually works — terminal, IDE agent, chat host, or Studio surface. If each surface had its own tool implementation, behavior would drift between surfaces and provenance would fork. SDAP therefore has one executable registry (@asd/engine's 29 sd_* tool definitions) and multiple thin projections of it: the asd CLI, the stdio MCP server, host packs, and the (deferred) DSH Studio RPC. The projections differ in transport and presentation only.

Key principles

  • The registry is the product. Counts are derived from the definitions themselves (deriveRuntimeToolNames in @asd/core), never hand-maintained per surface.
  • Fail closed. Every validation failure is a non-zero exit and a human-readable error. Partial success is not a state the runtime acknowledges.
  • Provenance is structural. Evidence ids are SHA-256 content hashes; artifact nodes cite them; factcheck walks the graph. Drift is mechanically detectable.

The capability registry and the Studio RPC boundary

@asd/core ships a machine-readable capability contract (data/capability-contract.json, consumed via src/capability.ts) with six declared surfaces:

// suite/packages/core/src/capability.ts (verbatim)
export const CAPABILITY_SURFACES = ['runtime-core', 'cli', 'mcp', 'acp', 'host-pack', 'studio-host'] as const
// Support labels are deliberately claims about proof, not implementation modes:
//   'supported' | 'unverified' | 'unsupported'
// Capability ids include: 'runtime-tool', 'tool-execution', 'record-only',
// 'host-agent-spawn', 'phase-gates', 'corpus-resources', 'role-prompts', 'host-execution', ...

Two load-bearing consequences:

  1. Support labels are claims about proof. A capability marked unverified is not "broken"; it is "not yet evidenced." This is why the platform can ship a DSH Studio projection while honestly deferring live-integration claims (Module 02.2 and 02.6).
  2. The Studio RPC boundary is a projection, not a fork. The DSH pack's capability profile declares execution: "canonical-tool-registry" — Studio RPC calls resolve into the same 29 tool definitions the CLI and MCP server expose. The boundary exists so the runtime can return-structured-error for anything the host cannot honor (the pack declares unsupportedBehavior: "return-structured-error"), rather than silently approximating.

Worked example — one sd_project_create call, traced through every layer

Fixture (a real invocation against the built runtime):

export ASD_WORKSPACE=/tmp/asd-w02-verify
node suite/packages/runtime/lib/cli.mjs project-create \
  --name "W02 Verify" --client "Test Client" --sector government --service "permit renewals"

Step-by-step trace (each hop verified against source):

  1. Shell → projection layer. suite/packages/runtime/lib/cli.mjs parses argv generically: --flag value pairs, no per-command code.
  2. Name normalization. project-create maps to the canonical sd_project_create by stripping the sd_ prefix and converting - to _; both spellings hit the same row.
  3. Registry lookup. The name resolves against the one executable registry — @asd/engine's tool definitions (src/tools/project.ts, defineTool({ name: 'sd_project_create', … })).
  4. Contract-layer validation. Flags are checked against the tool's JSON-schema parameters: required stringFields name, client, sector, service; phase constrained to the closed enum discover | define | develop | deliver. Unknown flags die here with unknown flag "--bogus" (known: name, client, sector, service, phase) — before anything touches disk.
  5. Execute. The tool's execute() calls asd.projects.create(...) on the AsdService facade in @asd/core.
  6. Store write. ProjectStore.create (core/src/store/project.ts) mints projectId = slugify(name) + '-' + randomUUID().slice(0, 8), creates the four subdirectories evidence/, artifacts/, renders/, sops/ (each with a .gitkeep), and writes project.json under storeMutex.
  7. Render. The result returns through the tool's output.render (renderJson('Project created')) to stdout; exit 0.

Expected result (from this run — the produced structure, expressed as the project record shape):

{"project":{"projectId":"w02-verify-2f006547","name":"W02 Verify","client":"Test Client",
  "sector":"government","service":"permit renewals","phase":"discover",
  "createdAt":"2026-08-23T00:02:51.923Z","updatedAt":"2026-08-23T00:02:51.923Z"}}

plus on disk: w02-verify-2f006547/{project.json, evidence/, artifacts/, renders/, sops/}.

Interpretation. The trace is the architecture made observable: hops 2–7 are identical whether the call arrives over the CLI or as an MCP tools/call — only hop 1 (framing) differs, which is exactly what "one registry, thin projections" claims. Note also the ordering: validation (hop 4) precedes any write (hop 6), so a rejected call leaves zero partial state behind — fail-closed is a property of the layering, not of individual error messages.

Fail-closed behavior (verified verbatim)

# artifact-write citing evidence that does not exist:

# exit 1 — nothing is written

# method-run without enough inputs (fresh project, 2 evidence records):

# evidence-add with an invalid kind:

4. Enterprise Case Study Lens

Article 02 — From Insight to Implementation: Redesigning Telehealth Onboarding at Northgate Health (articles/02)

Synthetic illustration — not a production log. Northgate Health is a fictional composite; all names, figures, and artifacts are illustrative.

Northgate is the theory of this module wearing a client's clothes. The engagement's central problem — 45% enrollment completion, 23% first-consult no-shows, 26-day median time-to-first-consult — was not a lack of journey maps. It was that previous maps were unverifiable: stakeholders disputed which pain points were real, and nothing could be checked after the workshops ended. The article's agentic intervention maps one-to-one onto the runtime stack you just executed:

"Evidence register" built from 20 stakeholder interviews + 400-member survey sd_evidence_add content-addressed records (quote/telemetry/document)

5. Critic Gate & Review Veto Rules

[!IMPORTANT] Mandatory review criteria for any artifact on this stack:

  1. Evidence citation — structural nodes must cite ids present in the project's evidence store; dangling refs fail at write time.
  2. Acceptance rules — the method contract's acceptance[] (min-nodes, min-evidence-per-node, field-non-empty) is evaluated on write; unmet writes are retained as draft with a failures[] list, never silently passed.
  3. Review gate — pass requires at least one evidence-cited row and zero defect rows; veto requires every defect row to carry a fix, keeps the artifact in draft, and persists a review-veto-log artifact.
  4. Factcheck as CI gate — sd_factcheck exits 0 only when every artifact passes integrity, schema, acceptance, and review checks.
  5. Phase advance is human-gated — sd_phase_advance fails closed without --approvalReceipt and while any design artifact is still a draft.

6. Hands-On Lab Assignment

Objective

Reproduce the verified loop above in a fresh disposable workspace, including one deliberate failure of each fail-closed gate.

Steps

cd ~/Documents/github/agentic-service-designer
export ASD_WORKSPACE=/tmp/asd-lab-02-1
CLI="node suite/packages/runtime/lib/cli.mjs"

# 1. Create a project; record the minted projectId
$CLI project-create --name "Lab 02.1" --client "<client>" --sector government --service "<service>"

# 2. FAIL-CLOSED DEMO A: run a method before feeding it
$CLI method-run --projectId <pid> --methodId journey-from-transcripts
# expect exit 1: "requires at least 3 evidence records; project has 0."

# 3. Add three evidence records (quote, quote, telemetry)
$CLI evidence-add --projectId <pid> --source int-01 --kind quote --body "<verbatim>"
# ... two more; record the minted 64-hex ids

# 4. FAIL-CLOSED DEMO B: cite a fabricated evidence id
$CLI artifact-write --projectId <pid> --methodId journey-from-transcripts --title "x" \
  --nodes '[{"id":"n1","label":"x","evidence":[{"evidenceId":"deadbeef"}],"fields":{"emotion":"anger","touchpoint":"phone"}}]'
# expect exit 1: 'cites evidence "deadbeef" which is not in the project evidence store'

# 5. Write a real draft citing your minted ids, then review it to final
$CLI artifact-write --projectId <pid> --methodId journey-from-transcripts --title "<title>" --nodes '<json>'
$CLI review --projectId <pid> --artifactId <aid> --verdict pass \
  --rows '[{"rowKind":"proposal","severity":"low","message":"...","rule":"evidence-cited","evidenceId":"<eid>"}]'

# 6. Gate the project
$CLI factcheck --projectId <pid>   # expect exit 0, "pass": true

Verification checklist

  • project-create returned a projectId ending in an 8-hex suffix
  • Fail-closed demo A exited 1 with the evidence-minimum error
  • Fail-closed demo B exited 1 with the dangling-evidence error
  • Your draft artifact shows "accepted": true, "status": "draft"
  • After review, "status": "final" and a review-veto-log artifact exists
  • factcheck exits 0

7. Summary & Reference Anchors

Key takeaways

  • SDAP is one executable registry with thin projections: CLI and MCP (today), host packs (vendored server), DSH Studio RPC (deferred). The layering — core contracts → engine tools → runtime transports → render/report compilers — is what makes "same behavior everywhere" a checkable claim instead of marketing.
  • The capability registry encodes proof status, not enthusiasm: supported / unverified / unsupported.
  • The canonical loop is fail-closed at every gate; the errors you saw verbatim are the design.
