Module 02.3: The asd-mcp Server — 29 Tools, 216 Corpus Resources, 10 Role Prompts over stdio

Course: The ASD Platform, Toolchain & DeepSeek Harness (dsh) · Level: Foundation · Duration: 55 min · Format: Theory, Live Protocol Session & Hands-on Lab

Learning Objectives

By completing this module, you will be able to:

  1. Speak the MCP stdio protocol by hand: newline-delimited JSON-RPC 2.0, initialize handshake, notifications/initialized, request/response id matching.
  2. Enumerate the live surface: tools/list (29 tools), prompts/list (10 role prompts), resources/list paginated across three pages to 216 repo-corpus resources.
  3. Retrieve corpus knowledge two ways — resources/read on an asd:// URI and the sd_knowledge tool's resourceQuery/resource arguments — and know when to use which.
  4. Call tools correctly: tools/call argument shapes, error codes (-32602 invalid params, -32002 resource not found), and the stdin-lifetime rule for in-flight calls.
  5. Complete the hands-on lab: a scripted MCP session you run and verify yourself.

1. Foundational Theory & Literature Grounding

A protocol is a service contract for tools

Service-Dominant Logic (Lusch & Vargo, books/12-service-dominant-logic/04-service-ecosystems) describes value creation as governed by institutions — shared rules that let strangers coordinate. MCP plays that role for agent tooling: a host (Claude Code, Codex, any MCP client) and a server (asd-mcp) coordinate without bespoke integration because both honor the same institutional rules: JSON-RPC 2.0 framing, capability negotiation at initialize, and enumerated tools/resources/prompts capability buckets.

Mapping Experiences (Kalbach, books/09-mapping-experiences/02-the-anatomy-of-experience-maps) supplies the second idea: a map (or a corpus) is only useful if its anatomy is legible — you can enumerate its parts and trace any part back to source. The asd-mcp resource surface is exactly that: the repo's Service Design canon (books/ 20 volumes, articles/ 37 case studies) exposed as addressable, paginated asd:// URIs, sorted by URI so successive resources/list calls are stable. The corpus is scanned per request, not at boot (src/corpus.ts), so what the server reports is what is on disk right now.

The verified inventory for this repo's corpus, from the live session below: 29 tools, 216 resources, 10 prompts. Emitted host packs bundle additional pack-local corpus copies, so pack servers report more (the pack README records 225). Teachable rule: 216 from the repo corpus; emitted packs ship more.

2. Agent Topology & Role Contracts

The 10 entries in prompts/list are not generic personas — each is the host-format rendering of a role contract whose canonical source is suite/packages/knowledge/data/practice-contract.json:

Prompt Role's first MCP moves Why
librarian resources/list → resources/read / sd_knowledge Corpus lookup is its whole contract
mapper tools/call sd_method_run → sd_artifact_write Owns journey/blueprint methods
critic tools/call sd_review, sd_factcheck Gatekeeper; verdicts are artifacts

3. The Live Session (verified 2026-08-22)

Everything in this section was executed against suite/packages/runtime/lib/mcp.mjs with ASD_WORKSPACE=/tmp/asd-c02-1787398523. The framing is newline-delimited JSON-RPC: one complete JSON message per line, in each direction.

3.1 Initialize and enumerate

{
  printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"course-02-live","version":"1.0.0"}}}'
  printf '%s\n' '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":3,"method":"prompts/list"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":4,"method":"resources/list"}'
} | node suite/packages/runtime/lib/mcp.mjs

# page 2

#    nextCursor "b2Zmc2V0OjIwMA"  ("offset:200")

#    NO nextCursor — end of corpus. Total: 100 + 100 + 16 = 216.

Cursor rules from the implementation (mcp.mjs): the cursor is an opaque base64url offset:<n> token; an undecodable cursor is rejected with -32602 invalid cursor; omitting params.cursor returns the first page. URIs are sorted, so pagination is stable across calls.

Error behavior, verified: a fabricated URI (asd://books/12-service-dominant-logic/01-introduction, which does not exist) returns {"id":7,"error":{"code":-32002,"message":"resource not found: asd://books/12-service-dominant-logic/01-introduction"}}. Worked example — paginated capture: from page-1 cursor to a lodged evidence record

Fixture. You are building an evidence base and want one chapter of the corpus captured with full provenance. Two protocol calls, then one tool call.

Step 1 — resources/list, first page (no cursor):

// request
{"jsonrpc":"2.0","id":2,"method":"resources/list"}
// response (trimmed, real): 100 descriptors + the cursor for page 2
{"id":2,"result":{"resources":[
    {"uri":"asd://articles/01","name":"article-01","mimeType":"text/markdown",
     "size":52264,"version":"1","provenance":"articles/01/README.md"},
    {"uri":"asd://books/01-this-is-service-design-doing/01-why-service-design",
     "name":"01-why-service-design","title":"Why Service Design?","mimeType":"text/markdown",
     "size":9078,"version":"1","provenance":"books/01-this-is-service-design-doing/01-why-service-design.md"},
    …98 more…],
  "nextCursor":"b2Zmc2V0OjEwMA"}}   // opaque base64url of "offset:100"

Step 2 — resources/read on the chosen chapter URI:

// request
{"jsonrpc":"2.0","id":3,"method":"resources/read",
 "params":{"uri":"asd://books/01-this-is-service-design-doing/01-why-service-design"}}
// response (text elided; envelope fields real)
{"id":3,"result":{"contents":[
  {"uri":"asd://books/01-this-is-service-design-doing/01-why-service-design",
   "mimeType":"text/markdown","size":9078,"version":"1",
   "provenance":"books/01-this-is-service-design-doing/01-why-service-design.md",
   "text":"---\n[frontmatter: corpus provenance fields]\n# Why Service Design?\n…(9040 chars)"}]}}

Step 3 — lodge the capture as project evidence so downstream artifacts can cite it (CLI form shown; the MCP tools/call sd_evidence_add shape is identical):

node suite/packages/runtime/lib/cli.mjs evidence-add --projectId w02-verify-2f006547 \
  --source corpus-capture --kind document \
  --body "asd://books/01-this-is-service-design-doing/01-why-service-design (9078 bytes, provenance books/01-this-is-service-design-doing/01-why-service-design.md) — captured via resources/read after resources/list page 1 cursor b2Zmc2V0OjEwMA."
# → {"evidence":{"id":"60379238d54d33c835273445745e1218a1665c9aa6055c947aafee23129a01ed",
#    "kind":"document","capturedAt":"2026-08-23T00:06:40.816Z", …}}

Interpretation. Notice the division of labor: resources/list gives you descriptors (address, size, provenance) cheaply and stably across pages; resources/read gives you content for exactly one address — paginating to find, then reading precisely what you found. The capture discipline is the point — the evidence record's id is the SHA-256 of its own content, so the lodged record, the asd:// URI, and the repo path in provenance are three pointers to one fact. When a journey-map node later cites 60379238…29a01ed, factcheck can walk that chain mechanically, and nobody has to take the citation on trust.

3.4 Corpus retrieval through the sd_knowledge tool

resources/read is the protocol-native path. The sd_knowledge tool is the role-facing path (the Librarian's lookup): resourceQuery searches corpus URIs/names case-insensitively, and resource fetches an exact URI:

'{"jsonrpc":"2.0","id":8,"method":"tools/call","params":{"name":"sd_knowledge",
  "arguments":{"resource":"asd://books/12-service-dominant-logic/03-value-co-creation"}}}'
# → result JSON with top-level keys {methods, kinds, resource}; resource carries
#   {uri, name, title, mimeType, size, version, provenance, text}
#   provenance: "books/12-service-dominant-logic/03-value-co-creation.md" — the repo path

Rule of thumb: hosts that natively mount resources use resources/list/resources/read; role agents mid-workflow use sd_knowledge so the lookup stays inside the tool contract.

5. Critic Gate & Review Veto Rules (protocol edition)

[!IMPORTANT]

  1. tools/call sd_review with a veto verdict requires every defect row to carry a fix; the artifact stays draft and the veto log persists as a review-veto-log artifact — over MCP exactly as over CLI.
  2. A pass verdict without at least one evidence-cited row is rejected; the gate is not satisfiable by enthusiasm.
  3. Protocol errors fail closed: -32602 for bad params/unknown tool/invalid cursor, -32002 for unknown resource URIs, -32601 for unknown methods.
  4. Tool calls before initialize complete are rejected (-32000 "server not initialized").

# verify counts with jq (or python):
python3 - <<'EOF'
import json
tools=prompts=resources=None
for line in open('/tmp/lab-02-3.jsonl'):
    d=json.loads(line); r=d.get('result',{})
    if d.get('id')==2: tools=len(r['tools'])
    if d.get('id')==3: prompts=[p['name'] for p in r['prompts']]
    if d.get('id')==4: resources=(len(r['resources']), r.get('nextCursor'))
print(tools, len(prompts), resources)
assert tools==29 and len(prompts)==10 and resources==(100,'b2Zmc2V0OjEwMA')
EOF

Verification checklist

  • tools/list count is exactly 29; first tool is sd_project_list
  • prompts/list names the 10 roles in alphabetical order
  • Page 1 is 100 resources with cursor b2Zmc2V0OjEwMA; paginating twice more reaches 216 total with no final cursor
  • sd_method_run over MCP reports your project's availableEvidence
  • A bogus asd:// URI returns error -32002, not a crash

7. Summary & Reference Anchors

Key takeaways

  • The stdio server is a thin, honest projection: newline-delimited JSON-RPC, 29 tools, 216 repo-corpus resources across three stable pages, 10 role prompts. Emitted packs ship more resources (225) from pack-local copies.
  • Cursors are opaque; ids match requests to responses; errors are typed JSON-RPC codes.
  • Corpus retrieval is duplex: protocol-native resources/read, or role-facing sd_knowledge with resourceQuery/resource and repo-path provenance.
