Module 02.6: The Host Matrix, Honestly — Verified Profiles, Unverified Hosts, and the ACP Boundary

Course: The ASD Platform, Toolchain & DeepSeek Harness (dsh) · Level: Foundation · Duration: 45 min · Format: Theory, Pack Audit & Hands-on Lab

Learning Objectives

By completing this module, you will be able to:

  1. Read the host matrix without being misled: which packs vendor the same MCP server, which are prompt/structural projections, and what "verified" does and does not cover.
  2. Classify every distribution target by its capability profile (mcp-host, static, prompt-only, exact-dsh-rc.5) and its liveHostExecution status.
  3. Explain the ACP boundary: asd-acp/1 is record-only and fail-closed — a typed envelope, never a spawn mechanism.
  4. Apply the evidence discipline of the capability contract (supported / unverified / unsupported) to any future host claim you encounter or write.
  5. Complete the hands-on lab: audit the pack manifests yourself and reproduce this module's table.

1. Foundational Theory & Literature Grounding

Distribution is a service-design problem, and honesty is a feature

Service-Dominant Logic (books/12-service-dominant-logic/04-service-ecosystems) frames ecosystems as actors integrating resources through shared institutional arrangements. A toolchain distributed across a dozen agent hosts is exactly such an ecosystem — and its institutional arrangement is the capability contract: a machine-readable statement of what each surface provably does. Without it, every host integration becomes bespoke folklore; with it, "does Codex pack X?" is a lookup, not a rumor.

Good Services (books/05-good-services/04-principles-trust) makes the second point: trust is built by services that "don't make claims they can't back up." Downe's principle is about end-user services, but it is the same muscle a platform needs when describing itself. The ASD host matrix therefore encodes proof status, not aspiration: every pack manifest declares liveHostExecution: "unverified" unless a host receipt exists, and the capability contract's support labels are supported / unverified / unsupported — there is deliberately no "probably works" label.

The theoretical payoff: one registry, honestly labeled projections. Everything you learned in modules 02.1–02.5 travels to every host because the packs vendor or reference the same server and the same contracts — and where a host cannot execute, the matrix says so in the open.

Key principles

  • The vendored server is identical: pack MCP bundles boot with the same 29 tools and 10 prompts; resource counts rise only because packs bundle pack-local corpus copies (225 vs the repo's 216).
  • liveHostExecution: "unverified" is the default truth for every host pack — pack structure is verified, host execution awaits its own receipt.
  • Support labels are claims about proof. A row saying unsupported (e.g. the DSH pack's phase.gate.status row) is the matrix working as designed, not an embarrassment.

The ACP boundary, verbatim

From docs/INTEGRATION.md (the cross-surface integration contract):

asd-acp/1 provides typed record envelopes for identity, capability negotiation, session, handoff and receipt-like events. In the current release it is record-only and fail-closed. A record can say that a host-agent spawn was requested or unsupported; it does not spawn a process or create a relay connection. Host-agent execution requires a host capability and a receipt that proves it.

And from the runtime source (suite/packages/runtime/src/capabilities.ts):

export const ACP_CAPABILITIES = {
  transport: 'record-only',
  liveSpawn: false,
  reason: 'No ACP host transport or process-spawn boundary is implemented.',
} as const

Worked example — the host-matrix decision exercise

Fixture. You are staffing the Northfield Regional Health day-surgery follow-up redesign (18% of patients miss their first follow-up; ward nurses spend ~40 min per patient chasing GP confirmation). Three work lanes need distribution surfaces. Decide each from capability rows, not preference:

  • Lane A — native plugin host. The core design team works in a host with native subagents, slash commands, and skills directories.
  • Lane B — MCP-only host. An analyst's client speaks MCP (one server config slot) but has no plugin/skill format.
  • Lane C — prompt-only review lane. An external red-team reviewer works in a plain chat host with no MCP client at all.

Step-by-step application. Read each candidate's committed capabilities.json and select on decisive rows:

Lane Chosen pack Decisive capability rows Explicit non-claims
A claude-code (mcp-host) tool-execution: supported (pack-local MCP server runs the shared registry); role-prompts: supported; corpus-resources: supported; mcp-self-contained: supported host-execution: unverified; host-agent-spawn: unsupported — the pack never spawns; the host spawns its own subagents; cli-json-coercion: unsupported
B mcp (emitted bundle) mcp-host profile: vendored asd-mcp + asd-mcp.json; disposable-boot verified; same 29 tools / 10 prompts, 225 pack-local corpus resources No host-native UI; anything beyond MCP framing is out of scope
C grok (prompt-only) Every execution row unsupported; role-prompts: unverified; host-execution: unverified This lane can voice the critic role but cannot run sd_review; verdicts it drafts must be re-entered by a human on a real surface — claiming otherwise is a veto-grade defect

Expected artifact. In a live project the decision is recorded, not remembered — as an orchestration plan step whose capability field cites the row it relies on:

{"stepId":"lane-a-mapping","capability":"tool-execution","targetSurface":"claude-code",
 "rationale":"capabilities.json row tool-execution=supported (pack-local MCP server)",
 "nonClaims":["host-execution unverified","host-agent-spawn unsupported"]}

Interpretation. The matrix is a decision procedure: the rows are the evidence, and the labels do the routing — supported selects, unverified cautions, unsupported disqualifies. Two boundaries deserve explicit name-checks because they are the easiest to overstate: buzz is an mcp-host persona pack (10 keyless personas, native pack verified) whose live use is deferred — a persona distribution, not a student runtime; dsh declares execution: canonical-tool-registry with unsupportedBehavior: return-structured-error, but its phase.gate.status row is unsupported and Studio live integration is deferred — never present either one as a verified execution environment.

4. Enterprise Case Study Lens

Article 36 (as honesty benchmark) — Wattle Grove Community Care (articles/36)

Synthetic illustration — not a production log.

Read Article 36's §0 as a style guide for claims: it records the DSH receipt (profile composition, six host slots, official lifecycle commands, smoke/accessibility/portability checks) and then states what the receipt does not show — that the current host chat dispatched providers or completed the case end to end. Its capability projection is equally blunt: 22 rows supported, phase.gate.status unsupported. When you write about any host integration — in a design dossier, a client proposal, or a course answer — this is the register to use: enumerate the evidence, name its class, and let unsupported rows stand in daylight.

5. Critic Gate & Review Veto Rules (claims edition)

[!IMPORTANT]

  1. Any document claiming live host execution without a receipt is a defect (severity: high, rule: "evidence-cited").
  2. Counts must carry provenance: repo-corpus 216 vs pack-corpus 225 is exactly the kind of distinction a veto exists to protect.
  3. ACP records describing a spawn that never happened are record-layer truth only; the claim "the host spawned an agent" requires a host receipt.
  4. DSH/BUZZ statements must use the deferred register: "integration surface with its own acceptance evidence," never "the student environment."

6. Hands-On Lab Assignment

Objective

Reproduce this module's host matrix from the repo, and catch one inflated claim.

Steps

cd ~/Documents/github/agentic-service-designer

# 1. Profiles straight from the packs
for p in claude-code codex kimi opencode agy pi omp grok buzz dsh; do
  jq -c "{pack:\"$p\", profile:.profile, target:.target}" platform/packs/$p/capabilities.json
done

# 2. The honesty field — should print "unverified" for every host pack
jq -r '.liveHostExecution' platform/packs/{claude-code,codex,kimi,opencode,agy,pi,omp,grok,dsh,buzz}/manifest.json | sort | uniq -c

# 3. Counts straight from the manifest
jq -c '.counts' platform/packs/manifest.json

# 4. Prove vendored-server parity yourself: boot one pack's MCP bundle and count tools
{
  printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"lab-02-6","version":"1.0"}}}'
  printf '%s\n' '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  printf '%s\n' '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
  sleep 1
} | node platform/packs/claude-code/mcp/bin/server.mjs | python3 -c \
  "import json,sys; [print('tools:', len(json.loads(l)['result']['tools'])) for l in sys.stdin if '\"id\":2' in l]"

Verification checklist

  • Your table from step 1 matches §3 exactly (mcp-host ×5 packs + mcp/cli, static ×3, prompt-only ×1, exact-dsh-rc.5 ×1)
  • Step 2 shows only unverified (or the new receipt class if one has landed since)
  • Step 4 prints tools: 29
  • You can quote the ACP boundary sentence from docs/INTEGRATION.md without opening this module
