Module 02.4: Terminal Ergonomics — the asd CLI Grammar, Fail-Closed Errors, and the Workspace Layout

Course: The ASD Platform, Toolchain & DeepSeek Harness (dsh) · Level: Foundation · Duration: 45 min · Format: Theory, Verified Command Reference & Hands-on Lab

🎯 Learning Objectives

By completing this module, you will be able to:

  1. Use the real CLI grammar: asd <kebab-short-name> [--flag value] — and recognize the commands that do not exist (init, run, status, agent, render — there are none).
  2. Read errors as documentation: the CLI fails closed with verbatim, actionable error text; this module teaches you to drive your workflow off those messages.
  3. Navigate the workspace layout: <project>/project.json, evidence/index.json, artifacts/, renders/, sops/ — know what lives where and why.
  4. Script headlessly: exit codes are the API (0 = pass, 1 = fail-closed), which is what makes the CLI CI-safe.
  5. Complete the hands-on lab: a scripted sprint driven entirely by exit codes.

📖 1. Foundational Theory & Literature Grounding

Tools should make the right thing easy and the wrong thing loud

The Design of Everyday Things thinking runs through all of Don Norman's influence on service design, but the sharpest operational statement in our canon is Lou Downe's: a good service "is easy to use" and "clearly explains its purpose" (Good Services, books/05-good-services/03-principles-usability). A CLI is a service surface, and the same principles apply. The asd CLI's ergonomics follow three of them directly:

  • Be findable — one grammar, one help text, 29 tools with their flags listed inline. No hidden subcommand trees.
  • Fail usefully — every rejection names the rule, the offending value, and the remedy (Capture evidence with sd_evidence_add first.).
  • Don't pretend — there is no asd init ceremony, no asd status dashboard fiction. State lives in plain JSON you can read.

The deeper principle is from Service Design: From Insight to Implementation (books/03-service-design-from-insight-to-implementation/03-principles-of-service-design): co-created tools must be legible to all parties. A content-addressed JSON store plus a terse kebab-case grammar is legible to the designer, the orchestrator agent, and the CI pipeline alike.

Key principles

  • Kebab short names map 1:1 to sd_* tools: project-create → sd_project_create, export-artifact → sd_export_artifact. Learn one, know the other.
  • Flags are --flag value pairs; values that are JSON payloads (nodes, rows, receipts) are passed as quoted JSON strings.
  • Two different phase enums exist and must not be conflated: method phases (research|synthesis|ideation|prototyping|delivery|measurement, used by method-list --phase) vs project phases (discover|define|develop|deliver, used by phase-advance --toPhase).

3.2 Error-message-driven UX (verbatim, verified today)

Every one of these was produced by a real run. Read them as the user manual:

# 1. Unknown flag — the CLI tells you the known flags for that tool:
asd sd_knowledge: unknown flag "--help" (known: query, phase, source, resourceQuery, resource, type)

# 2. Closed enum violation — evidence kind:
asd evidence-add: invalid arguments: "arguments.kind" must be one of ["quote","telemetry","document"]

# 3. Closed enum violation — knowledge type filter:
asd knowledge: invalid arguments: "arguments.type" must be one of ["methods","kinds"]

# 4. Contract precondition — not enough inputs for the method:
asd method-run: method "journey-from-transcripts" requires at least 3 evidence records; project has 2. Capture evidence with sd_evidence_add first.

# 5. Integrity — dangling evidence citation at write time:
asd artifact-write: node "n1" cites evidence "deadbeef" which is not in the project evidence store

# 6. Human gate — phase advance without a receipt:
asd phase-advance: missing required flag "--approvalReceipt"

# every failure: exit code 1 + "running `asd help` shows usage"

3.3 Workspace layout (real tree from the verified run)

Key ergonomics facts:

  • Storage is per-project JSON under ASD_WORKSPACE (default ~/.asd/projects). No database daemon, no lock files; evidence/index.json is the evidence register.
  • Artifact filenames carry their kind, slug, and short id — journey-map.current-state-repairs-reporting-journey.5b43c26c.json — so a directory listing is already a readable inventory.
  • Export writes into <project>/renders/; nothing is written outside the project tree.

⚖️ 5. Critic Gate & Review Veto Rules (CLI edition)

[!IMPORTANT]

  1. review --verdict pass requires at least one row with evidenceId; a bare "looks good" cannot pass the gate.
  2. review --verdict veto requires at least one defect row, and every defect row must carry fix; the artifact stays draft, and the veto is persisted as a review-veto-log artifact.
  3. factcheck exit 1 means: read the JSON rows — each failing artifact reports integrity/schema/acceptance/review separately, so the error tells you which gate to fix.
  4. phase-advance is the only command that requires a human approvalReceipt JSON (receiptId, approvedBy, decision, rationale, approvedAt) — and it still refuses while drafts exist.

🧪 6. Hands-On Lab Assignment

Objective

Script an entire sprint with shell exit-code checks only — no eyeballing.

Steps

cd ~/Documents/github/agentic-service-designer
export ASD_WORKSPACE=/tmp/asd-lab-02-4
CLI="node suite/packages/runtime/lib/cli.mjs"

$CLI project-create --name "Lab 02.4" --client "<c>" --sector government --service "<s>" || exit 1
PID=<paste the minted id>

# negative asserts — each MUST fail (exit non-zero)
! $CLI method-run --projectId $PID --methodId journey-from-transcripts          || exit 1
! $CLI evidence-add --projectId $PID --source x --kind observation --body "y"   || exit 1
! $CLI phase-advance --projectId $PID --toPhase define --idempotencyKey g1      || exit 1

# positive spine
$CLI evidence-add --projectId $PID --source int-01 --kind quote --body "<v1>"   || exit 1
$CLI evidence-add --projectId $PID --source int-02 --kind quote --body "<v2>"   || exit 1
$CLI evidence-add --projectId $PID --source tel-01 --kind telemetry --body "<m>"|| exit 1
$CLI method-run  --projectId $PID --methodId journey-from-transcripts           || exit 1
$CLI artifact-write --projectId $PID --methodId journey-from-transcripts --title "Lab journey" --nodes '<json citing your evidence ids>' || exit 1
$CLI review --projectId $PID --artifactId <aid> --verdict pass --rows '<one evidence-cited row>' || exit 1
$CLI factcheck --projectId $PID || exit 1
echo "LAB 02.4 PASS"

Verification checklist

  • All three negative asserts exited non-zero with the verbatim errors from §3.2
  • method-list --phase synthesis printed only synthesis-phase methods (never discover)
  • Your artifact file exists at <ws>/<pid>/artifacts/journey-map.<slug>.<shortid>.json
  • factcheck exited 0

📚 7. Summary & Reference Anchors

Key takeaways

  • The CLI grammar is deliberately tiny: asd <kebab-name> --flag value, 29 tools, help is the contract. Anything you remember about init/run/status is from another tool.
  • Errors are the manual: closed enums, contract preconditions, and integrity checks all fail closed with the remedy in the message.
  • The workspace is plain JSON with content-addressed ids; exit codes make the CLI a CI citizen.
