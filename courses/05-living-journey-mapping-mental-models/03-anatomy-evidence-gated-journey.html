Module 05.3: Anatomy of an Evidence-Gated Journey Map Schema

Course: Living Journey Mapping & Mental Model Alignment · Level: Intermediate · Duration: 55 min · Format: Theory, Architecture, Code & Hands-on Lab

🎯 Learning Objectives

By completing this module, you will master:

  1. Theoretical Foundations: Kalbach's five-part anatomy of every alignment diagram — Lens, Context, Journey Spine, Takeaways, Visualization — and why the spine is the only part the toolchain must gate.
  2. Agent Topology & Contracts: The journey-from-transcripts contract — researcher extraction, mapper stage ordering, critic gate — and its four acceptance rules, read from a live method-run.
  3. Architecture & Schemas: The real ArtifactNode schema (id, label, evidence[{evidenceId, quote?}], fields) and the closed journey-map kind schema from asd schema-get.
  4. Case Study Execution: Article 09 — Albatross Airways' disruption-recovery map, the airline's first validated, evidence-per-row journey.
  5. Adversarial Verification: The three ways a journey write can fail — schema rejection, retained failing draft, and dangling-evidence rejection.
  6. Hands-on Practice: Author a journey spine that passes every gate.

📖 1. Theoretical Grounding & Literature Synthesis

The five-part anatomy (Kalbach, ch. 2)

In Mapping Experiences ch. 2, Kalbach deconstructs every alignment diagram — journey map, blueprint, mental model, ecosystem model — into a shared five-part architecture. Mastering it lets you diagnose broken maps and compose hybrids instead of memorizing templates:

  1. The Lens — whose experience, and through what constraints: the persona or archetype the map is filtered through, plus the mapping principles that govern inclusion.
  2. The Context — scope: the beginning and end of the experience, its duration, and the explicit statement of what is out of frame.
  3. The Journey Spine — the chronological or structural backbone: stages, actions, touchpoints, thoughts, and emotional states, each tied to source material.
  4. The Takeaways — the so-what: pain points, opportunities, and recommendations the map exists to surface.
  5. The Visualization — the rendering choices that make the first four legible to a specific audience.

The anatomy explains a recurring pathology: workshop maps invest in #5 (posters, icons, color) while #3 is assembled from stakeholder opinion. The result looks like research and functions like marketing. Kalbach's ch. 2 test for a healthy map is that the spine can be defended row by row against source material — which is precisely the property the ASD schema makes machine-checkable.

🤖 2. Agentic Topology & Contracts

The journey-from-transcripts contract, verbatim from a live asd method-run (2026-08-22, disposable workspace):

{
  "method": {"id": "journey-from-transcripts", "phase": "synthesis",
             "owner": "mapper", "reviewGate": "critic",
             "evidenceRules": {"traceability": "required", "provenance": "required"}},
  "steps": [
    {"role": "researcher", "instruction": "Extract every distinct customer action, channel and breakdown from the transcripts, keeping the verbatim quote for each."},
    {"role": "mapper", "instruction": "Order the actions into stages. Give each stage an emotion drawn from the quotes, never inferred."},
    {"role": "critic", "instruction": "Reject any stage whose emotion or pain point is not supported by a quoted line.", "gate": true}
  ],
  "acceptance": [
    {"rule": "min-nodes", "min": 3},
    {"rule": "min-evidence-per-node", "min": 1},
    {"rule": "field-non-empty", "field": "emotion"},
    {"rule": "field-non-empty", "field": "touchpoint"}
  ],
  "inputs": [{"kind": "evidence-set", "min": 3, "note": "call or interview transcripts"}],
  "handoff": {"to": "ideator", "artifactKind": "journey-map"},
  "outputKind": "journey-map",
  "availableEvidence": 4
}

Read it as a pipeline with per-role duties — no role touches another's tools:

  • researcher owns extraction fidelity: one evidence record per distinct action/channel/breakdown, verbatim preserved. Tools: sd_evidence_add, sd_evidence_query.
  • mapper owns the spine: ordering, stage naming, and the emotion/touchpoint fields. Tools: sd_method_run, sd_artifact_write, sd_schema_get.
  • critic owns falsification: rejects any stage whose emotion or pain lacks a quoted line. Tools: sd_review, sd_review_list.
  • The method fails closed below its input floor: with 2 evidence records it refuses — "requires at least 3 evidence records; project has 2."

💻 3. Schemas & Verified Execution

The real ArtifactNode (@asd/core, suite/packages/core/src/types.ts)

/** A pointer into the project's evidence store, optionally with the quote. */
export type EvidenceRef = {
  readonly evidenceId: string
  readonly quote?: string
}

/**
 * The evidence-bearing unit of an artifact: a journey stage, a blueprint node,
 * an ecosystem actor. `fields` is kind-specific and validated by the kind's
 * registered validator.
 */
export type ArtifactNode = {
  readonly id: string
  readonly label: string
  readonly evidence: readonly EvidenceRef[]
  readonly fields: Readonly<Record<string, unknown>>
  readonly references?: readonly ArtifactReference[]
}

Three properties do the evidentiary work: evidence[] must resolve against the project store at write time (a dangling evidenceId is rejected before anything is persisted), quote? pins the exact words the node claims, and fields is where the kind schema takes over.

The journey-map kind schema (verbatim from asd schema-get --kind journey-map)

{
  "kind": "journey-map",
  "schema": {
    "version": 1,
    "node": {
      "requiredMembers": ["id", "label", "evidence", "fields"],
      "fieldPolicy": "closed",
      "fields": {
        "stage":       {"type": "string",   "required": false},
        "emotion":     {"type": "string",   "required": true},
        "touchpoint":  {"type": "string",   "required": false},
        "actor":       {"type": "string",   "required": false},
        "pain":        {"type": "string",   "required": false},
        "gain":        {"type": "string",   "required": false},
        "opportunity": {"type": "string",   "required": false},
        "description": {"type": "string",   "required": false},
        "notes":       {"type": "string",   "required": false},
        "tags":        {"type": "string[]", "required": false}
      }
    },
    "edge": {"policy": "optional",
             "endpoints": {"from": "node", "to": "node"},
             "fields": {"weight": {"type": "number"}, "label": {"type": "string"}}},
    "references": {"policy": "optional", "provenance": "required", "relations": [
      {"name": "derived-from", "targetKinds": ["persona-set","empathy-map","insight-set","ecosystem-map"]},
      {"name": "supports",     "targetKinds": ["service-blueprint","storyboard","prototype-plan"]}
    ]}
  }
}

Two layers of enforcement coexist, and the difference matters in practice:

  1. Kind schema (hard rejection, exit 1, nothing stored). emotion is required: true at the schema layer. Omit the field entirely and the write fails before the store is touched.
  2. Method acceptance (retained failing draft, exit 0). field-non-empty: emotion and touchpoint are acceptance rules. Write emotion: "" and the artifact persists as a draft with check.failures attached — work-in-progress the team can see and remediate.

📊 4. Case Study Lens: Albatross Airways (Article 09)

Synthetic illustration — not a production log. Albatross Airways is a fictional composite client from articles/09/; figures are illustrative.

Albatross, a fictional EU network carrier (28M passengers/year, 74 routes), knew disruption days were its worst moments but could not say what they felt like. Internal folklore — "passengers want compensation faster" — had survived three improvement programmes and two app redesigns. Over eight weeks, one service designer with an AI agent team built the airline's first validated, evidence-per-row journey map of disruption recovery from 140 interviews, 9,000 disruption tickets, 1.1M app sessions, 45 staff debriefs, and 2,300 social posts.

The anatomy lens shows why the map succeeded where the folklore failed:

  • Lens and Context were fixed before mapping — disruption recovery only, from first alert to rebooked seat; compensation policy explicitly out of frame. That is the scope-confirmation human checkpoint done properly.
  • The spine was evidence-per-row — every stage carried verbatim quotes, which is what made the map falsifiable: the critic could check the claim "passengers were angriest at cancellation" against quoted lines and reject it.
  • The map proved the folklore wrong: sentiment bottomed out not at the cancellation and not at the compensation step, but during the uninformed waiting in between — a finding that only survives because each row's emotion traces to a quote. Module 05.4 takes up that curve.

🔬 5. Hands-On Lab

export ASD_WORKSPACE=/tmp/asd-lab-05-03
CLI="node suite/packages/runtime/lib/cli.mjs"

# 1. Project + 3 transcript-derived evidence records (method fails closed below 3)
$CLI project-create --name "Spine Drill" --client "Meridian Move" --sector transport --service "evening bus"
$CLI evidence-add --projectId <pid> --source int-01 --kind quote --body "<verbatim>"
#   ×3 — capture the SHA-256 ids from the output

# 2. Contract first: note acceptance rules and availableEvidence
$CLI method-run --projectId <pid> --methodId journey-from-transcripts

# 3. Write the spine: ≥3 nodes, edges with relation "next", emotion + touchpoint on every node
$CLI artifact-write --projectId <pid> --methodId journey-from-transcripts \
  --title "Journey v1" --nodes '<json>' --edges '<json>'

# 4. Fail-closed demos (run all three; observe the two exit-1 rejections and one retained draft):
#    a) omit fields.emotion on a node        → exit 1, "…fields.emotion is required"
#    b) set fields.emotion to ""             → accepted:false, failures[rule=field-non-empty]
#    c) cite an invented evidenceId          → exit 1, "…not in the project evidence store"

# 5. Gate + verify
$CLI review --projectId <pid> --artifactId <aid> --verdict pass \
  --rows '[{"rowKind":"proposal","severity":"medium","message":"…","evidenceId":"<eid>"}]'
$CLI factcheck --projectId <pid>
$CLI export-artifact --projectId <pid> --artifactId <aid>   # → renders/journey-map.<id>.svg

Verification checklist

  • method-run with <3 evidence records refused with "requires at least 3 evidence records".
  • The accepted write shows accepted: true, failures: [], and real 64-hex evidence ids.
  • All three failure modes reproduced with the exact behaviors above.
  • export-artifact wrote renders/journey-map.<id>.svg — open it and confirm stages, emotions, and edges match the JSON.

🚀 Key Takeaways

  • ✅ Every alignment diagram is Lens + Context + Spine + Takeaways + Visualization; unhealthy maps over-invest in #5 and under-evidence #3.
  • ✅ The spine is typed JSON: ArtifactNode = id, label, evidence[{evidenceId, quote?}], fields — with the journey-map kind closing the field set.
  • ✅ Two enforcement layers: kind-schema violations are hard rejections (exit 1, nothing stored); acceptance failures are retained failing drafts your team can remediate.
  • ✅ factcheck is a CI gate: exit 0 only when integrity, schema, acceptance, and review all pass for every artifact in the project.
