Learning Objectives

By completing this module, you will master:

  2. Agent Topology & Contracts: The full remediation loop — sd_artifact_write --artifactId in-place update, the verdict-clearing rule, re-review, and deterministic re-export.
  3. Architecture & Schemas: Why a content write clears review (a verdict binds to the content it reviewed) and how experience-mapping widens the same substrate to pre- and post-service life.

  5. Adversarial Verification: A real v1→v2 remediation: new evidence, same artifact id, cleared verdict, fresh pass, new SVG.
  6. Hands-on Practice: Run the complete loop yourself, including the fail-closed gates.

1. Theoretical Grounding & Literature Synthesis

Maps decay; versions don't

Kalbach's facilitation guidance (Mapping Experiences, ch. 7–8) treats a map as a decision instrument with a shelf life: the organization changes, the pilot ships, and yesterday's validated spine becomes today's comforting fiction. The traditional answer is the "living document" — a Mural board someone is supposed to maintain. It fails predictably: edits accumulate without evidence, nobody re-facilitates, and within a quarter the map asserts a world that no longer exists. The map is "living" in the worst sense: it mutates without selection pressure.

The disciplined alternative is versioned remediation: the map changes only when new evidence enters the store, every change passes the same gates that birthed the original, and every version remains inspectable. The map earns the right to change; it never drifts.

The wider frame: experience mapping

Remediation also has a scope dimension. Kalbach's experience-mapping method (ch. 2, ch. 7) lays out the end-to-end experience as phases wider than a single journey — including pre- and post-service life. Its critic instruction is the corrective to transactional myopia: "Reject a phase that only covers the transactional core and skips the surrounding context the evidence describes." Acceptance rises to min-nodes: 4 with field-non-empty: stage. When the Albatross-style pilot changes what happens after the rebooking (does the rider trust the service next month?), the journey map's recovery stage needs the experience map's wider frame — same journey-map kind schema, wider spine, same evidence gates.

Why "living" must mean "versioned artifacts," not a daemon

There is no background process in the ASD runtime that watches the world and re-draws your map. That is a deliberate design stance, and the contract encodes it in three load-bearing facts:

  1. State is files. Every project is per-project JSON under ASD_WORKSPACE. A "live" map would be a file changing beneath reviewers' feet.
  2. Verdicts bind to content. From @asd/core types.ts: "a verdict binds to the content it reviewed, so edited content is unreviewed until re-gated." Any artifact-write against an existing --artifactId replaces content and clears review — the artifact drops back to draft until the critic passes it again. Freshness is enforced, not assumed.
  3. Renders are pure functions. sd_export_artifact compiles the current artifact to a deterministic SVG. The picture is never ahead of or behind the data; it is recomputed.

2. Agentic Topology & Contracts

The remediation loop uses the same journey-from-transcripts contract as 05.3 — the difference is the write mode and who initiates:

Actor Remediation duty Tools
Human designer Decides the map is stale; approves re-scope (scope-confirmation applies again when frame widens) —
researcher Captures post-change evidence: new quotes, new telemetry sd_evidence_add, sd_evidence_query
mapper (owner) Rewrites the spine in place via --artifactId; adds/removes stages; keeps methodId provenance sd_artifact_write --artifactId, sd_artifact_get
critic (gate) Re-gates the new content from zero — the old pass verdict is gone sd_review
measurer Compares derived views across versions (sentiment curve, failure-demand volume) sd_artifact_list, sd_artifact_get
presenter Re-renders for sponsors sd_export_artifact, sd_export_report

Two more contracts frame the loop:

  • experience-mapping (widened spine): owner mapper, gate critic, min-nodes: 4, field-non-empty: stage — use it when remediation evidence spans pre- or post-service life the journey's frame excluded.
  • sd_phase_advance stays human-gated: "phase advance requires all design artifacts to be final; drafts: <id>" — a remediated-but-ungated map blocks the phase gate, which is exactly the leverage that keeps maps honest.

3. Schemas & Verified Execution

The in-place update, from the source

suite/packages/core/src/store/artifact.ts:

/** Supply to update an existing artifact in place. */
readonly artifactId?: string

// `review` is deliberately not carried over: a verdict binds to the
// content it reviewed, and every write replaces the content. Edited
// content is unreviewed until the gate role passes it again.

Same id, same file lineage, createdAt preserved, updatedAt bumped, verdict gone. The CLI exposes it as asd artifact-write --artifactId <existing-id> ….

Verified terminal session — the complete v1→v2 loop (real ids)

export ASD_WORKSPACE=/tmp/asd-c05
CLI="node suite/packages/runtime/lib/cli.mjs"
PID=meridian-night-bus-journey-sprint-d819e68a
AID=4b5752a381c54de4a84ec53869ba53f2   # "Evening Rider Journey v1" — final

# v1 was final with review verdict pass (log a38388f1c3744f6d9452bd9c8a8a8ab0).

# 1. The service changes: post-pilot evidence enters the store
$CLI evidence-add --projectId $PID --source int-04 --kind quote \
  --body "Since they added the rebooking option in the cancellation text, I have not had to call anyone. It just rebooks me."
# → 03d1bc24fca83c00527710461f20376baef85b8f2af9dcc67c290daefd64db11

# 2. Remediate IN PLACE: same artifact id, new stage n4, new edge 'remediates'
$CLI artifact-write --projectId $PID --artifactId $AID \
  --methodId journey-from-transcripts --title "Evening Rider Journey v2 (remediated)" \
  --nodes '[n1, n2, n3 unchanged + {"id":"n4","label":"Auto-rebooked after cancellation SMS",
    "evidence":[{"evidenceId":"03d1bc24…","quote":"It just rebooks me."}],
    "fields":{"stage":"recovery","emotion":"relieved","touchpoint":"SMS rebooking link",
              "gain":"no helpline call needed"}}]' \
  --edges '[e1, e2 "next" + {"id":"e3","from":"n3","to":"n4","relation":"remediates",
    "fields":{"label":"failure-demand fix"}}]'
# → {"accepted":true,"status":"draft","artifact":{"id":"4b5752a3…" — SAME id,
#    "updatedAt":"2026-08-22T11:42:22Z"} …}
#    NOTE: no "review" member in the response — the v1 verdict was cleared by the write.

# 3. Re-gate from zero
$CLI review --projectId $PID --artifactId $AID --verdict pass \
  --rows '[{"rowKind":"proposal","severity":"medium",
    "message":"v2 recovery stage is backed by post-change quote and repeat-call telemetry baseline; remediation claim is evidenced, not asserted.",
    "rule":"evidence-traceability","evidenceId":"03d1bc24…"}]'
# → {"status":"final","verdict":"pass"}

# 4. Re-export: the SVG is a pure function of v2 content
$CLI export-artifact --projectId $PID --artifactId $AID
# → renders/journey-map.4b5752a3.svg  (recompiled; same filename, new geometry)

# 5. CI gate still bites: the deliberately failing draft from 05.3 is retained,
#    so factcheck exits 1 until that draft is remediated — the gate counts EVERY artifact.
$CLI factcheck --projectId $PID   # → EXIT=1, row: f33054a4… acceptance.pass=false

What the loop guarantees

  • No silent staleness: the moment v2 content landed, the artifact was draft again. Nobody could have presented it as validated.
  • No orphan renders: export-artifact recompiles from current content; the SVG cannot drift from the JSON.
  • No forgotten failures: factcheck walks every artifact in the project, so the retained failing draft from an earlier experiment keeps the exit code red until dealt with.

4. Case Study Lens: The Albatross Recovery Pilot (Article 09)

Synthetic illustration — not a production log. Albatross Airways is a fictional composite client from articles/09/; figures are illustrative.

The Albatross engagement did not end at the map. The eight-week mapping programme handed into a twelve-week recovery pilot: instant mobile rebooking notifications shipped against the valley the map had located (uninformed waiting, not the cancellation itself). That pilot is the remediation loop at organizational scale:

  • New evidence was the trigger. Pilot telemetry and post-pilot interviews are exactly the kind of records that enter the evidence store and force a map rewrite — the map's recovery stage asserted "frustrated, repeat calls"; post-pilot evidence asserted something new.
  • The remediation claim needed evidence too. "The fix worked" is itself a journey-map assertion, so it enters the artifact the same way anything else does: a cited quote, a telemetry record, a re-run gate. The v2 rule — evidenced, not asserted — is what separates a living map from a victory lap.
  • The wider frame caught the second-order effects. What changed in passengers' pre-service trust (do they still triple-check the app?) is experience-mapping territory: phases wider than the transactional core, min-nodes: 4, the critic rejecting any phase that skips surrounding context the evidence describes.

The Juniper Retail case (Article 13) runs the same pattern across omnichannel collect-and-return: an 11-week design phase, then a 7-week pilot whose readout re-entered the evidence base. Living maps are pilot-driven everywhere in the corpus — never timer-driven.

5. Hands-On Lab

export ASD_WORKSPACE=/tmp/asd-lab-05-06
CLI="node suite/packages/runtime/lib/cli.mjs"

# 1. Build a final v1 journey (modules 05.3–05.4 spine), critic-passed, exported.
# 2. Add post-change evidence:
$CLI evidence-add --projectId <pid> --source int-04 --kind quote --body "<post-change verbatim>"

# 3. Remediate IN PLACE — same --artifactId, new nodes/edges:
$CLI artifact-write --projectId <pid> --artifactId <aid> --methodId journey-from-transcripts \
  --title "<Journey v2>" --nodes '<json>' --edges '<json>'
#    Observe: status back to draft, review member gone.

# 4. Fail-closed demo: try phase-advance while the remediated map is ungated
$CLI phase-advance --projectId <pid> --toPhase define --idempotencyKey gate-1 \
  --approvalReceipt '{"receiptId":"RCP-1","approvedBy":"<name>","decision":"approve","rationale":"…","approvedAt":"<iso>"}'
# → FAILS CLOSED: "phase advance requires all design artifacts to be final; drafts: <aid>"

# 5. Re-gate and re-render
$CLI review --projectId <pid> --artifactId <aid> --verdict pass --rows '<evidence-cited row>'
$CLI factcheck --projectId <pid>
$CLI export-artifact --projectId <pid> --artifactId <aid>
$CLI export-report --projectId <pid> --kind artifact-dossier

Verification checklist

  • The in-place write kept the artifact id and cleared the review verdict.
  • phase-advance refused while the remediated draft was ungated — with the artifact id in the error.
  • The re-review pass returned status: final against the new content.
  • The re-exported SVG shows the new stage/edge — open it and compare against v1.
  • factcheck exits 0 only once every artifact in the project passes.

Key Takeaways

  • A living map is a versioned artifact lineage, not a daemon: new evidence → in-place rewrite → cleared verdict → re-gate → re-render.
  • Verdicts bind to content: any content write demotes the map to draft until the critic passes the new version — staleness cannot hide behind an old approval.
  • Renders are pure functions of the artifact: the SVG is recomputed, never maintained.
  • Phase gates enforce freshness organizationally: sd_phase_advance fails closed while any design artifact is a draft — humans authorize; agents prepare.
