1. Theoretical Grounding & Literature Synthesis

The diagram that is not chronological

Most journey artifacts are timelines: they answer "what happens, in what order?" Indi Young's mental model diagram answers a different question — "how do people think about this part of their life, independent of our product?" Kalbach places it in the family of alignment diagrams (Mapping Experiences, ch. 6, "Other Alignment Diagrams") and gives it a precise anatomy:

  • Top half — the mental space (demand side). A "city skyline" of user tasks and cognitive intents. Atomic, active-verb task statements ("confirm the bus is actually coming") are stacked vertically into towers; related towers are grouped left-to-right into broader mental spaces (e.g., Anticipate, Verify, Recover). Nothing in the top half mentions your product. It is the user's reasoning, philosophies, and emotional reactions while pursuing a purpose.
  • Bottom half — organizational offerings (supply side). The features, content, and operational capabilities the organization already ships, placed directly beneath the towers they support.
  • The alignment line. The horizontal demarcation between the halves. Alignment is read vertically: a tower with something beneath it is supported; a tower with nothing beneath it is a gap; a feature sitting under no tower is an orphan — operational bloat the user never asked for.

Kalbach's strategic point (ch. 6): towers with no offerings underneath represent unmet market opportunities; features under no user tower represent wasted operational bloat. And mental models are extraordinarily durable — fundamental human purposes change far more slowly than interfaces, so a good mental-model map outlives several redesigns. This durability is exactly why it deserves to be a versioned, evidence-gated artifact rather than a workshop poster.

When the paradigm fails

The mental-model paradigm has known failure modes a designer must respect:

  • Chronology questions get the wrong diagram. Kalbach's ch. 1 decision rule is explicit: match the diagram to the question — chronological maps for time-based experiences, mental models for user purposes, ecosystem maps for networks. Running mental-model research to answer "where in the week does the journey break?" produces a beautiful skyline that cannot sequence anything.
  • Interface contamination. The moment a tower reads "use the filter panel", the diagram has collapsed into a feature inventory. The tower must survive the test: would the user describe their thinking this way if our product did not exist?
  • Task statements without evidence. Affinity-clustering tasks from memory or stakeholder opinion produces a diagram of the organization's mental model of the user — the exact inside-out pathology the method exists to cure.

Why the agentic tooling exists

The failure modes above are all evidence discipline failures, and they are precisely what the ASD toolchain makes structurally impossible: every tower is an ArtifactNode whose evidence[] must resolve to content-addressed records in the project evidence store, whose belief field is required, and whose vocabulary is policed by an acceptance rule that rejects interface words. The critic gate then attempts to falsify each tower against its quote before the map can go final.

2. Agentic Topology & Contracts

The method that operationalizes this paradigm is mental-model-diagramming (synthesis phase), verified live from asd method-run:

Contract member Verified value
outputKind mental-model-map
owner / ownerRole mapper
reviewGate critic
inputs evidence-set, min 3 — "transcripts revealing how users think about the task, independent of the current interface"
sources article 10; book 14-outside-in ch. 4
handoff to ideator, artifact kind mental-model-map, only after the critic passes

Step roles (from the live contract, not invented):

  1. mapper — "Extract each distinct mental step or expectation the user described, grouped into a tower."
  2. critic (gate) — "Reject a tower with no supporting quote, and any tower whose label describes the interface rather than the user's own thinking."

Acceptance rules the write path enforces deterministically:

  • min-nodes: 3 — fewer than three towers is a fragment, not a model.
  • min-evidence-per-node: 1 — every tower carries a resolving evidenceId.
  • field-non-empty: belief — a tower without a stated belief is a label, not a model.
  • forbid-field-values on belief, deny list ["ui", "interface", "screen"] — interface contamination is rejected by the acceptance engine, not by reviewer taste.

Human checkpoints (cannot be delegated): scope-confirmation before the run (authority: human-designer) and handoff-approval before the map moves to the ideator.

3. Schemas & Verified Execution

The ArtifactNode contract (@asd/core suite/packages/core/src/types.ts)

A tower is not a special type. It is the generic evidence-bearing unit with kind-specific fields:

/** A pointer into the project's evidence store, optionally with the quote. */
export type EvidenceRef = {
  readonly evidenceId: string
  readonly quote?: string
}

/**
 * The evidence-bearing unit of an artifact: a journey stage, a blueprint node,
 * an ecosystem actor. `fields` is kind-specific and validated by the kind's
 * registered validator.
 */
export type ArtifactNode = {
  readonly id: string
  readonly label: string
  readonly evidence: readonly EvidenceRef[]
  readonly fields: Readonly<Record<string, unknown>>
  readonly references?: readonly ArtifactReference[]
}

The mental-model-map kind schema (verbatim from asd schema-get --kind mental-model-map)

The kind carries a closed field policy — any field not listed here is rejected at write time:

Field Type Required Role in the tower
belief string yes What the user holds true about the situation (acceptance-gated; interface words denied)
side string no user vs organization — which half of the alignment line the node sits on
goal string no The purpose the tower serves
theme string no The grouping mental space (e.g. anticipate, verify, recover)
context string no Situational qualifier from the transcript
tags string[] no Free classification

Edges are optional (from/to node, weight, label). Cross-artifact references (e.g. derived-from an interview-guide) require provenance.

Worked example: annotating one task tower from a raw interview excerpt

Fixture — raw excerpt (int-04, Meridian rider, evening commute):

"Before I even leave the office I've already opened the app twice. Then at the stop I'm watching the road, not the phone, because the phone has lied to me before. When the bus finally comes I'm half-relieved, half-annoyed. What I never see is anyone on Meridian's side noticing any of this — the driver doesn't know the app said 6 minutes for the last 20."

Step 1 — comb the excerpt into task statements, keeping the user's verbs. Each line yields one atomic, active-verb task; no interface nouns survive the comb:

Excerpt line Temporal position Backstage signal (what the org is doing, invisibly) Task statement
"opened the app twice" before leaving before none — no proactive alert exists reassure myself the bus is coming
"watching the road, not the phone" during prediction feed silently degrades verify the promise with my own eyes
"half-relieved, half-annoyed" after arrival is unlogged; no closure event absorb the mismatch and move on
"the driver doesn't know" cross-cutting prediction never reaches the frontline (belief, not a task — feeds belief)

Step 2 — stack the tasks into one tower. All three tasks serve a single cognitive intent — know whether to trust the prediction — so they form one tower in the verify mental space, not three.

Step 3 — expected artifact: one mental-model-map node. The quote is minted first (sd_evidence_add --source int-04 --kind quote), then the tower:

{"id": "t2", "label": "Tower: Verify the prediction against reality",
 "evidence": [{"evidenceId": "9c1f2b7a4d6e8305f2a94c1be7d035689ab41c2e5f708d3b69a1e4c2075f9d31",
               "quote": "the phone has lied to me before"}],
 "fields": {"side": "user",
            "belief": "the prediction will lie, so only my own eyes count",
            "goal": "trust I can act on the information",
            "theme": "verify",
            "context": "before/during/after: re-checking begins before departure and never resolves"}}

Interpretation. The before/during/after columns keep the comb honest: a task that spans all three positions is a durable concern, which is why it earns a tower rather than a sub-task. The backstage column is the alignment line in embryo — every entry of "none" or "silently degrades" predicts a gap or half-supported tower before a single offering is mapped.

4. Case Study Lens: Lumen EdTech (Article 10)

Synthetic illustration — not a production log. Lumen EdTech is a fictional composite client from articles/10/; figures are illustrative.

Lumen, a B2B school platform serving 240 schools, fielded 12,000 support tickets per quarter — 68% of which were comprehension failures, not defects: parents could not find grades, teachers could not find grading drafts, students missed deadlines buried in a reverse-chronological feed. The platform was engineered around courses and classes; users thought by child, by grading sitting, and by due date.

Read through the mental-model paradigm:

  • The org chart had leaked into the top half of the diagram. Every navigation concept was an organizational offering pretending to be a user tower. The fix was not UI polish but re-derivation of the skyline from interviews — beliefs, questions, and tasks per actor, extracted under a taxonomy that forbids conflating what users think with what users do.
  • Misalignment was made quantitative. Card-sort distance matrices and a gap inventory linked each user-model/system-model divergence to ticket volume — the same vertical read across the alignment line that the skyline diagram encodes visually.
  • The realignment landed as engineering work — a content-model change for a unified Communication Hub. Pilot in 12 schools: support volume −46%, comprehension tickets −69%, parent task success 42%→88%.

This is the pattern the toolchain enforces by default: the forbid-field-values acceptance rule on belief (denying ui, interface, screen) is Lumen's lesson compiled into the write path.

$CLI review --projectId <pid> --artifactId <aid> --verdict pass \

$CLI factcheck --projectId <pid>   # exit 0 only when every artifact passes

Verification checklist

  • method-run returned outputKind: "mental-model-map" and the four acceptance rules above.
  • Artifact write returned accepted: true with real SHA-256 evidence ids.
  • The interface-vocabulary write was rejected with exit 1 (nothing stored).
  • The dangling-evidence write was rejected with exit 1 (nothing stored).
  • review --verdict pass flipped status to final; factcheck exited 0.

Key Takeaways

  • Mental spaces describe purposes, not pages. The skyline's top half must survive the test "would the user say this if our product didn't exist?"
  • Alignment is read vertically across one line: supported towers, gap towers (opportunities), orphan features (bloat).
  • In the toolchain, a tower is an ArtifactNode: belief is required, interface vocabulary is denied by acceptance rule, and every tower resolves to SHA-256 evidence.
  • The critic gate falsifies beliefs against quotes — an overreaching belief earns a veto with a fix, and only a content edit plus a fresh pass can reach final.
