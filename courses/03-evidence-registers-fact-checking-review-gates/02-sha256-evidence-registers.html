By completing this module, you will master:

  2. The Exact Hash Formula: id = sha256(JSON([source, kind, body, origin | null])) — proven live, reproducible on your machine.

  5. Adversarial Verification: Why hashing the body alone would be a traceability bug, not an optimisation.
  6. Hands-on Practice: Prove dedup and avalanche yourself with three paste-able commands.

1. Theoretical Grounding & Literature Synthesis

Content addressing is reliability, formalized

Martin (The Design of Business, ch. 02 "Reliability versus Validity") defines reliability as the orientation that produces "consistent, replicable outcomes across repeated trials. Its core test is: Will different operators following the same process achieve the identical result?" That is precisely the property a service-design evidence base needs and precisely what a mutable store (a wiki page, a quote spreadsheet, a chat log) cannot offer: edit the source and every downstream citation silently changes meaning.

A content-addressed register makes the identifier a pure function of the content:

$$id = \operatorname{SHA\text{-}256}\big(\operatorname{JSON}([source,\ kind,\ body,\ origin \mid null])\big)$$

Two consequences follow mechanically, no policy required:

  • Dedup (idempotent capture). Recording the same quote from the same source twice yields the same id and the register keeps one row. Re-importing a transcript directory after a crash is safe — it converges instead of duplicating.
  • Avalanche (tamper evidence). Change one character of the body and the id changes completely. A downstream artifact that cites the old id now dangles — the edit cannot pass silently.

Kalbach (Mapping Experiences, ch. 03) demands that research-based maps carry "epistemic traceability" — every assertion tagged to its source. Content addressing is what makes that tag unfakeable: the citation does not point at a row somebody could edit; it names the exact bytes of the evidence.

Why source is inside the hash

The runtime's own source comment (suite/packages/core/src/store/evidence.ts) states the design rationale better than any paraphrase:

"Content-addressed over (source, kind, body) — not body alone. Hashing the body only would be a traceability bug, not an optimisation: two participants saying the same sentence in different interviews would collapse into one record keeping whichever source arrived first, and the second interview's provenance would be destroyed with no error."

This is the module's central design lesson: provenance is part of identity. Two interviewees saying "the hold music drives me mad" are two evidence records, not one — because in service research, who said it is evidentiary content, not metadata.

2. Multi-Agent Topology & Role Contracts

Role Responsibility in this module Bound tools
researcher Captures verbatim quotes and field observations as individual records; chooses the source label that will become part of every id. sd_evidence_add, sd_evidence_query
librarian Bulk-imports transcripts, CSV logs and JSON documents; verifies idempotent re-imports converge; curates the register as the project's single source of truth. sd_evidence_import, sd_evidence_query
mapper (and every producing role) Cites evidenceId values in artifact nodes; the runtime rejects any citation the register cannot resolve. sd_artifact_write (integrity-checked)

The register itself is role-neutral infrastructure: every role reads and writes the same <project>/evidence/index.json, and the CLI and MCP server (sd_evidence_* tools) are two surfaces over the identical store.

3. Production Schemas, Code & Verified Execution

The real store types (@asd/core, suite/packages/core/src/store/evidence.ts)

export type EvidenceKind = 'quote' | 'telemetry' | 'document'

export type EvidenceOrigin = {
  readonly source: string
  readonly path: string          // absolute path of the imported file
  readonly relativePath: string
  readonly format: 'transcript' | 'csv' | 'json'
  readonly encoding: 'utf8'
  readonly bytes: number
  readonly record: 'line' | 'row' | 'json-value'
  readonly ordinal: number
}

export type EvidenceRecord = {
  readonly id: string            // sha256, 64 lowercase hex chars
  readonly projectId: string
  readonly source: string
  readonly kind: EvidenceKind
  readonly body: string
  readonly capturedAt: string    // ISO 8601
  readonly origin?: EvidenceOrigin
}

The hashing code, verbatim:

const id = createHash('sha256')
  .update(JSON.stringify([input.source, input.kind, input.body, input.origin ?? null]), 'utf8')
  .digest('hex')

Note what is not in the hash: projectId and capturedAt. A quote's id is reproducible across machines and across time — run the same evidence-add in your own workspace and you will mint the same id shown below. (Imported records are the exception: their origin embeds the absolute file path, so their ids are workspace-specific by design.)

Proof, captured live 2026-08-22 — identical input, identical id

CLI="node suite/packages/runtime/lib/cli.mjs"
PID=meridian-transit-urgent-repair-line-10e68a16

$CLI evidence-add --projectId $PID --source int-01 --kind quote \
  --body "I called the repair line four times before anyone even logged my ticket."
# → "id": "d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4"

# The exact same command a second time:
$CLI evidence-add --projectId $PID --source int-01 --kind quote \
  --body "I called the repair line four times before anyone even logged my ticket."
# → "id": "d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4"   (same record returned)

The register file after both calls contains one row for this quote — dedup is total:

cat $ASD_WORKSPACE/$PID/evidence/index.json

{
  "version": 1,
  "records": [
    { "id": "d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4",
      "source": "int-01", "kind": "quote",

Proof — one word changed, completely different id

$CLI evidence-add --projectId $PID --source int-01 --kind quote \
  --body "I called the repair line five times before anyone even logged my ticket."
# → "id": "1ddec8d7a35fdb1878c4eed18b4069ad4acff661e0cd77ed64e195110e5b9a15"

four → five flips the id from d4ba1329… to 1ddec8d7…. This is the avalanche property doing audit work: had anyone edited the quote after the journey map cited it, every citing node would dangle and sd_factcheck would exit 1 (module 03.5).

Independent recomputation — the formula, no trust required

node -e '
const c = require("crypto");
const id = (s,k,b,o=null) =>
  c.createHash("sha256").update(JSON.stringify([s,k,b,o])).digest("hex");
console.log(id("int-01","quote",
  "I called the repair line four times before anyone even logged my ticket."));
'
# prints: d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4  ← matches the CLI exactly

The same check against an imported record confirms origin participates in the hash: hashing [source, kind, body, origin] for the charter import reproduced dab407b1d6ec0ce2dead9b984cfe430be0e392eb8275b067fa2af1c2867d336a; hashing with null instead produced a different, non-matching id.

Mutation forensics — how an edit becomes visible

Worked example: hashing one record by hand

A workshop capture yields one verbatim line worth keeping. Here is the complete derivation from content to id, with nothing taken on trust.

Fixture — the four hash slots.

Slot Value
source wrk-07 (follow-up workshop, session 7)
kind quote
body The follow-up letter arrived after my appointment did.
origin null (manual capture, no import provenance)

Step 1 — serialize in the fixed order. JSON.stringify over the array [source, kind, body, origin] with compact separators (no spaces; array order is the schema):

["wrk-07","quote","The follow-up letter arrived after my appointment did.",null]

That string is exactly 80 UTF-8 bytes. Byte count matters: the hash commits to these bytes and no others — not to projectId, not to capturedAt, not to whatever tool produced them.

Step 2 — digest. SHA-256 over those bytes, hex-encoded:

sha256(80 bytes above) = 62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644

Step 3 — verify independently. No platform code involved:

node -e 'console.log(require("crypto").createHash("sha256")
  .update(JSON.stringify(["wrk-07","quote",
    "The follow-up letter arrived after my appointment did.",null]),"utf8")
  .digest("hex"))'
# prints: 62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644

Expected artifact. The register row this derivation predicts — an EvidenceRecord with kind: "quote" whose id is the hash:

{ "id": "62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644",
  "source": "wrk-07", "kind": "quote",
  "body": "The follow-up letter arrived after my appointment did." }

Avalanche micro-check. Change one word (after → before) and the id becomes 2adc52e59a54f2ff57c6d36d93d7adcb3d84641f04eaeb25c552eae3ae623fbe — sharing no prefix with the original.

Interpretation. The id is a pure function of content: anyone, on any machine, hashing the same four slots gets 62c845bb…3d8644, so a citation can be checked without asking the register "what did you mean at the time?" And because the body sits inside the hash, the one-word edit cannot be laundered — it mints a new record, leaving every citation of the old id pointing at bytes that either still exist (unchanged, checkable) or dangle loudly. That is what it means for provenance to be unfakeable: the identifier and the content are the same fact.

4. Case Study Lens: Article 34 — The Street of Small Business (Vela Bank)

Synthetic illustration — not a production log. Article 34 is a fictional composite SME-banking engagement; this lens applies the module's mechanics to its narrative.

A bank that "learns the business" accumulates evidence for years: onboarding interviews, cash-flow telemetry, covenant documents. Article 34's banking case is exactly where content addressing stops being hygiene and becomes the product. Re-importing last quarter's transcript bundle must converge (dedup) rather than double-count sentiment; a clause in a credit policy that is silently edited must break the citing artifacts (avalanche) rather than launder the change. The (source, kind, body) identity rule matters doubly in multi-client banking: two café owners saying "the bank never calls back" are two records with two provenances, and collapsing them would destroy the segment analysis the engagement exists to produce.

5. Hands-On Lab Exercise

export ASD_WORKSPACE=/tmp/asd-lab03-$(date +%s)
CLI="node suite/packages/runtime/lib/cli.mjs"
$CLI project-create --name "Lab03 Hashing" --client "Lab" --sector government --service "hash lab"
PID=<your projectId>

# A. Reproduce the lesson's id exactly (same source/kind/body → same sha256)
$CLI evidence-add --projectId $PID --source int-01 --kind quote \
  --body "I called the repair line four times before anyone even logged my ticket."
# expect: d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4

# B. Dedup: run A again. Same id, and index.json still holds one row for it.

# C. Avalanche: change "four" to "five" and mint 1ddec8d7… yourself.

# D. Prove source is part of identity: same body, --source int-99 → a third, different id.

Verification checklist

  • Your step-A id equals the lesson's id character-for-character (reproducibility across machines).
  • evidence/index.json is readable plain JSON with "version": 1 — no SQLite anywhere.
  • Step B did not add a second row.
  • Steps C and D produced two different new ids, demonstrating that both body and source are hashed.

Key Takeaways

  • id = sha256(JSON([source, kind, body, origin | null])) — proven live, recomputed independently, reproducible on your machine.
  • Dedup and avalanche are free consequences of content addressing: re-imports converge; silent edits become dangling citations.
  • Source is identity: hashing the body alone would destroy multi-interview provenance — a traceability bug, not an optimisation.
  • The register is one plain JSON file per project (evidence/index.json); auditable with jq, diffable with git, no database involved.
