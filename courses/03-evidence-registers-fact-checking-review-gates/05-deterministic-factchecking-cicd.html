Learning Objectives

By completing this module, you will master:

  2. The Four Fields: integrity, schema, acceptance, review — what each checks, with the real evaluation code as the spec.
  3. The Exit-Code Contract: asd factcheck --projectId → exit 0 only when every artifact passes; exit 1 otherwise. Run red, then green, live.
  4. CI Integration: A GitHub Actions workflow that gates merges on the factcheck exit code.
  5. Case Study Execution: Article 36 (Running a Service Design Engagement Inside the Harness, Wattle Grove) — evidence receipts as the engagement's spine.
  6. Hands-on Practice: Break a project, watch the red report name the failing field, remediate, go green.

1. Theoretical Grounding & Literature Synthesis

The replay path of rigor

Modules 03.1–03.4 built the authoring side of rigor: artifacts, content-addressed evidence, adversarial review. This module is the replay side: a deterministic verifier that re-derives "is this project sound?" from the files on disk, indifferent to what any agent remembers or claims.

Martin's reliability/validity frame (The Design of Business, ch. 02) tells you both why this exists and where its limits are. Factcheck is a reliability machine: given the same project files, any operator — your laptop, a colleague, a CI runner — gets the identical verdict. That is the property that makes it CI-gateable. But reliability machines cannot adjudicate validity: no exit code can tell you whether the journey map solves the real problem. The honest division of labor, encoded in the platform, is:

  • Machines check: citations resolve, schemas hold, machine-checkable acceptance rules pass, review verdicts are recorded consistently.
  • Humans decide: scope confirmation, handoff approval, phase advance (receipt-gated, course 06), and whether a passing artifact is actually right.

The deep reason determinism matters here is the same one that made content addressing matter in 03.2: a gate that can disagree with itself is not a gate. If factcheck used an LLM judge, two CI runs of the same commit could disagree, and every red build would be negotiable. The verifier is pure — parse files, evaluate rules, emit a report — so red is red.

What "deterministic" buys in practice

  • Diffable failure: the red report names the field, rule, and node — acceptance.failures: ["expected at least 3 nodes, found 1"] — so remediation is mechanical.
  • Non-negotiability in CI: exit codes, not prose. A pipeline cannot be talked out of exit 1.
  • Retained visibility: because acceptance-failing drafts are kept (03.1), a project with unfinished work is red until the work is finished or removed. Factcheck is how the repository refuses to forget.

One precision point from the evaluation code itself (suite/packages/core/src/factcheck.ts): the review field is pass when the artifact is draft, when the method declares no gate, or when the recorded verdict is pass. Drafts are legitimately in the loop; the finality requirement is enforced where it belongs — sd_phase_advance refuses to advance with drafts in play. Factcheck's job is machine-checkable truth, not lifecycle policy.

3. Production Schemas, Code & Verified Execution

The four fields, from the implementation (@asd/core, factcheck.ts)

Field What it re-checks on every run Real failure it catches
integrity Every evidenceId cited by every node resolves in the register; unresolved ids are listed in dangling[] An edited/deleted source quote; an invented hash
schema The artifact kind is registered and its typed schema validates; cross-artifact references resolve with matching kinds and node ids Hand-edited JSON drift; a reference to a renamed node
acceptance The producing method's rules (min-nodes, min-evidence-per-node, field-non-empty, …) are re-evaluated against the current content A draft retained with check.failures (03.1)
review status === 'draft' OR no gate declared OR recorded verdict === 'pass' A final artifact whose gate verdict is missing/veto

methodResolution tells you how the method was found: "recorded" (the artifact's methodId resolves) vs "inferred" (matched by kind — the case for review-veto-log artifacts, which no method produces).

CI gate — GitHub Actions

# .github/workflows/asd-factcheck.yml
name: asd-factcheck
on:
  pull_request:
    paths: ["evidence/**", "projects/**"]   # the versioned store files

jobs:
  factcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "24" }

      # The runtime is built in-repo; cli.mjs is the gate binary.
      - name: Factcheck the engagement (exit-code gate)
        env:
          ASD_WORKSPACE: ${{ github.workspace }}/projects
        run: |
          node suite/packages/runtime/lib/cli.mjs factcheck \
            --projectId meridian-transit-urgent-repair-line-10e68a16
          # exit 0 → step passes; exit 1 → job fails, merge blocked

No JSON parsing in the workflow, no jq gymnastics: the exit code is the contract. If you want the report as a build artifact, append | tee factcheck.json and upload it — the gate decision has already been made by the process status.

Red → green loop as a sequence

Worked example: breaking one citation turns the build red

The red run in §3 was an acceptance failure (a thin draft). This example exercises the other tripwire — integrity — by corrupting exactly one citation.

Fixture. A final, gate-passed journey map whose node n2 cites a live register record:

{ "id": "n2", "label": "caller waits past tolerance",
  "evidence": [ { "evidenceId": "62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644" } ] }

Someone hand-edits the artifact file and changes two hex characters of the id (or deletes the register record — same effect, since the register cannot mutate in place).

Step 1 — run the verifier.

asd factcheck --projectId <pid>

{ "pass": false,
  "rows": [
    { "artifactId": "9f31aa05…", "kind": "journey-map", "status": "final",
      "integrity": { "pass": false,
        "dangling": [ { "node": "n2",
                        "evidenceId": "62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644" } ] },
      "schema": { "pass": true }, "acceptance": { "pass": true },
      "review": { "pass": true, "gate": "critic", "verdict": "pass" } } ] }

exit=1

One edited citation, one red build. Note what the report isolates: schema, acceptance, and review all still pass — the artifact is well-formed, rule-complete, and carries a recorded pass verdict — and the project is still unmergeable, because a citation no longer resolves. The exit code does not negotiate with the other three fields.

Step 2 — repair. Restore the register record (re-run the original evidence-add; content addressing mints the identical id 62c845bb…3d8644) or point n2 at a record that exists. No other file changes.

Step 3 — re-run.

{ "pass": true,
  "rows": [ { "artifactId": "9f31aa05…", "integrity": { "pass": true, "dangling": [] },
              "schema": { "pass": true }, "acceptance": { "pass": true },
              "review": { "pass": true, "verdict": "pass" } } ] }

exit=0

Interpretation. This is the avalanche property from 03.2 doing audit work downstream: a two-character edit did not produce a slightly wrong citation, it produced a dangling one — a fact the verifier can state with certainty because ids are content-derived. It also shows why the repair path is cheap: re-adding the original content reproduces the original id, so the citation heals without touching the artifact. Determinism is what makes both directions mechanical — red names the exact node and id; green is the same command, replayed, on the repaired store.

4. Case Study Lens: Article 36 — Running a Service Design Engagement Inside the Harness (Wattle Grove)

Synthetic illustration — not a production log. Article 36 is a fictional aged-care composite whose distinguishing discipline is separating bounded integration receipts from illustrative narrative — exactly the instinct factcheck mechanizes.

Article 36's care-scheduling case is the CI gate's natural argument. Aged-care scheduling is a domain where a hallucinated constraint ("workers can do 12 visits/day") is a safety issue, not an embarrassment. The article's structure — evidence receipts kept distinct from narrative claims, current host capability stated precisely — is what a red/green verifier enforces by default: you cannot merge the artifact while its citations dangle, whatever the prose around it claims. The lesson generalizes the article's honesty posture into a build rule: the pipeline must be able to say no when the author cannot.

5. Hands-On Lab Exercise

The capstone verifier in courses/labs/lab-03-evidence-gates/ automates exactly this:

node courses/labs/lab-03-evidence-gates/verify_lab-03.mjs

It builds a disposable project, drives the negative path (acceptance-failing draft → factcheck must exit 1) and the positive path (remediate + pass verdict → factcheck must exit 0), asserting both exit codes against the built CLI.

Manually, the loop is:

export ASD_WORKSPACE=/tmp/asd-lab03-$(date +%s)
CLI="node suite/packages/runtime/lib/cli.mjs"
# 1. project + 3 quotes (03.1 lab)
# 2. write a deliberately thin draft: 1 node, empty emotion field
$CLI factcheck --projectId $PID ; echo "exit=$?"   # expect: pass false, exit 1, acceptance.failures named
# 3. remediate in place (--artifactId), review pass, then:
$CLI factcheck --projectId $PID ; echo "exit=$?"   # expect: pass true, exit 0

Verification checklist

  • The red run exited 1 and named acceptance with rule-level messages.
  • Remediation used the same artifactId (in place), not a new artifact.
  • The green run exited 0 with every row's four fields passing.
  • You can explain why an unreviewed draft passes the review field — and which command (not factcheck) enforces finality before phase advance.

Key Takeaways

  • asd factcheck --projectId is the exit-code contract: 0 when every artifact passes all four fields, 1 otherwise — CI-gateable with zero parsing.
  • The four fields divide the truth: integrity (citations resolve), schema (types hold), acceptance (method rules re-evaluated), review (recorded verdict consistent).
  • Retained failing drafts keep the project red by design — the repository refuses to forget unfinished work.
  • Machines check; humans decide: validity, scope, and phase advance stay human-gated (receipt-gated sd_phase_advance), outside the exit code.
