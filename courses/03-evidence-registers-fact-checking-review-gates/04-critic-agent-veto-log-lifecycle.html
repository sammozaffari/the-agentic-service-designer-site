1. Theoretical Grounding & Literature Synthesis

Why the gate must be adversarial

Martin (The Design of Business, ch. 03 "Abduction and Design Thinking") roots design reasoning in Peirce's triad: deduction proves what must be, induction what probably is, and abduction — the leap toward what might be — is the only engine that introduces new ideas. But abduction's gift is its danger: a novel explanatory hypothesis is, by construction, unproven. Martin's design thinker survives by rhythmically orchestrating the three modes: abduct the hypothesis, deduce its necessary consequences, inductively test it against evidence.

The critic agent is that third beat, mechanized. Its mandate is falsification in the Popperian sense: it does not ask "is this artifact good?" but "which specific claims in this artifact fail against the register, the schema, or the acceptance rules — and what exact fix would make them pass?" A review that cannot block is a compliment, not a gate.

This is Service Design Doing (ch. 08) makes the same point organizationally: critique rituals fail when feedback is untraceable opinion. The veto-log design answers that failure mode directly — every objection is a typed row with a severity, an optional rule it violated, a mandatory fix for defects, and an optional evidence citation. Opinion has been made auditable.

Fittingly, the runtime stamps every review-veto-log artifact with source references to exactly this lineage — The Design of Business ch. 03, Design Unbound ch. 04, This is Service Design Doing ch. 08 — which you will see in the live capture below.

2. Multi-Agent Topology & Role Contracts

Role Responsibility in this module Bound tools
critic The method manifest's reviewGate. Reads the draft and the register; writes a verdict whose every defect row names the violated rule and the fix. Cannot edit the artifact — separation of authoring and judging. sd_review, sd_review_list, sd_artifact_get, sd_evidence_query
mapper (authoring role) Receives veto rows as work items; remediates by rewriting the same artifactId, which clears the stale verdict automatically. sd_artifact_write --artifactId
human-designer The veto log is the briefing document for the handoff-approval checkpoint: the human sees what was attacked, what was fixed, and what passed. sd_review_list (the review board)

The row schema and the asymmetric verdict contracts

{ "rowKind": "proposal | defect",
  "severity": "critical | high | medium | low",
  "message": "what is wrong or proposed, specifically",
  "rule": "optional: the machine or method rule implicated",
  "fix": "REQUIRED on every defect row: the remediation that would clear it",
  "evidenceId": "optional: a live register id the row cites" }

The two verdicts have deliberately asymmetric requirements, both enforced before anything is recorded:

  • veto requires ≥1 defect row, and every defect row must carry a fix. A veto without a fix is an unactionable objection — rejected.
  • pass requires ≥1 evidence-cited row. A pass with no citation is an ungrounded compliment — rejected.

3. Production Schemas, Code & Verified Execution

The review surface in types (@asd/core)

export const REVIEW_VERDICTS = ['pass', 'veto'] as const
export type ReviewVerdict = (typeof REVIEW_VERDICTS)[number]

/** The latest review-gate verdict; the rows live in the referenced
 *  review-veto-log artifact. Any content write clears it — a verdict binds to
 *  the content it reviewed, so edited content is unreviewed until re-gated. */
export type ArtifactReview = {
  readonly verdict: ReviewVerdict
  readonly logArtifactId: string
}

Malformed reviews, rejected live (three probes)

# defect without fix
asd review: rows[0]: a defect row requires a "fix"                                    (exit 1)

# pass without an evidence-cited row
asd review: pass verdict requires at least one evidence-cited review row              (exit 1)

# row citing evidence that does not exist
asd review: node "r1" cites evidence "bbbb…bbbb" which is not in the project evidence store   (exit 1)

# and the severity enum is closed
asd review: rows[0]: "severity" must be one of critical, high, medium, low            (exit 1)

Verdict 1 — VETO, run live

$CLI review --projectId $PID --artifactId c0720c4ac9bc4044bf15bdd7ca0f92a9 --verdict veto --rows '[
  {"rowKind":"defect","severity":"critical",
   "message":"Node n3 label says abandons but the cited telemetry does not show per-caller abandonment, only an aggregate rate",
   "rule":"evidence-support",
   "fix":"Split n3 into waits-beyond-tolerance citing the dropped-call quote, and a separate aggregate-demand node citing tele-ivr",
   "evidenceId":"d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4"},
  {"rowKind":"proposal","severity":"low",
   "message":"Add a backstage lane for ticket logging in a later iteration"}]'

{
  "status": "draft",
  "verdict": "veto",
  "logArtifactId": "6d66095b363c42799437696b1830f360",
  "rowsWritten": 2,
  "artifact": { "id": "c0720c4ac9bc4044bf15bdd7ca0f92a9", "status": "draft",
                "review": { "verdict": "veto", "logArtifactId": "6d66095b363c42799437696b1830f360" } }
}

The artifact stays draft; the verdict and its log pointer are stamped on it. The log itself is a first-class artifact — asd artifact-get on 6d66095b363c42799437696b1830f360:

  "artifact": {
    "id": "6d66095b363c42799437696b1830f360",
    "kind": "review-veto-log",
    "title": "Review: Urgent repair caller journey (current state)",
    "status": "final",
    "reviewOf": "c0720c4ac9bc4044bf15bdd7ca0f92a9",
    "sources": [ { "book": "16-the-design-of-business", "chapter": "03" },
                 { "book": "11-design-unbound", "chapter": "04" },
                 { "book": "01-this-is-service-design-doing", "chapter": "08" } ],
    "nodes": [
      { "id": "r1",
        "fields": { "rowKind": "defect", "severity": "critical",
                    "message": "Node n3 label says 'abandons' but the cited telemetry …",
                    "rule": "evidence-support",
                    "fix": "Split n3 into 'waits beyond tolerance' …" },
        "evidence": [ { "evidenceId": "d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4" } ] },
      { "id": "r2",
        "fields": { "rowKind": "proposal", "severity": "low",
                    "message": "Add a backstage lane for ticket logging in a later iteration" },
        "evidence": [] }
    ]
  }
}

Three properties to internalize: the log is final immediately (a verdict is a fact, not a draft); reviewOf points back at the artifact under review; and each row becomes a node whose fields carry the full row schema — so veto rows are themselves integrity-checked (their evidenceId must resolve, as the third probe above proved).

Remediation and Verdict 2 — PASS, run live

The mapper applies the fix by rewriting the same artifact (--artifactId c0720c4a…), splitting n3 exactly as the veto demanded. The content write clears the stale veto. Then:

$CLI review --projectId $PID --artifactId c0720c4ac9bc4044bf15bdd7ca0f92a9 --verdict pass --rows '[
  {"rowKind":"proposal","severity":"low",
   "message":"n3 now correctly scopes the dropped-call quote to waiting behavior; verified against the register body",
   "rule":"evidence-support",
   "evidenceId":"d4ba1329e23a6c4b6833c70aa115b1b5ef78fd7482964ea1270882a4b61baea4"}]'

{ "status": "final", "verdict": "pass",
  "logArtifactId": "6d66095b363c42799437696b1830f360", "rowsWritten": 1,
  "artifact": { "id": "c0720c4ac9bc4044bf15bdd7ca0f92a9", "status": "final",
                "review": { "verdict": "pass", "logArtifactId": "6d66095b363c42799437696b1830f360" } } }

Note the logArtifactId: the pass verdict updated the same review log artifact (its title now reads "…(current state, v2)"). One artifact, one review log, accumulating verdicts — the complete argument is preserved in one place. sd_review_list renders the resulting board: every artifact with its gate, verdict, log pointer, and outstanding failures.

The full lifecycle as a sequence

Worked example: one veto, one remediation, one log

A mapper drafts a callback-journey map (artifactId: 9f31aa05…). The critic reviews it with exactly two rows — one defect with a binding fix, one proposal:

[ { "rowKind": "defect", "severity": "high", "rule": "evidence-support",
    "message": "Node n2 claims callers 'give up on the portal' but cites only a workshop quote; no telemetry supports the magnitude",
    "fix": "Re-scope n2 to the verbatim quote, or add the portal-abandonment telemetry record as a second citation",
    "evidenceId": "62c845bbd3b95533613613b90825bd1af48d901febadb81116df22520a3d8644" },
  { "rowKind": "proposal", "severity": "low",
    "message": "Consider a backstage lane for GP-confirmation chasing in the next iteration" } ]

Step 1 — veto receipt. The call returns "status": "draft", "verdict": "veto", and a logArtifactId (say 4be19c72…). The runtime persists a review-veto-log artifact: status: "final" immediately, reviewOf: "9f31aa05…", and each row as a node whose fields carry the full row schema — the defect's evidenceId is itself integrity-checked against the register.

Step 2 — remediation. The mapper re-scopes n2 and rewrites the same artifactId. The content write clears the recorded verdict: edited content is unreviewed until re-gated.

Step 3 — second pass. The critic re-reviews with one evidence-cited proposal row. Receipt: "status": "final", "verdict": "pass", and the same logArtifactId: "4be19c72…" — the log accumulates both verdicts rather than spawning a second artifact.

Lifecycle states, end to end:

Step Artifact 9f31aa05… review.verdict Log 4be19c72…
draft accepted draft — (none recorded) does not exist
critic veto draft veto → log final, holds defect + proposal rows
content rewrite draft cleared unchanged (history kept)
critic pass final pass → log updated in place; full argument preserved

Interpretation. The table is the module's contracts in miniature. A veto is only representable because every defect carried a fix — the schema made the objection actionable before it was recorded. The pass was only representable because a row cited live evidence — the schema refused an ungrounded compliment. And because the verdict binds to exact content, the remediation write had to clear it: the gate re-asked the question of the new bytes, and the log kept the whole exchange as a final, auditable artifact rather than a chat thread nobody can replay.

4. Case Study Lens: Article 35 — The Butler's Memory (Sable & Slate)

Synthetic illustration — not a production log. Article 35 is a fictional luxury-hospitality composite; this lens applies the veto lifecycle to its narrative.

Article 35 is explicitly about "the ASD Critic on the write path" — a boutique-hotel case where personalization claims ("the butler remembers") are exactly the kind of assertion that sounds wonderful in a workshop and collapses under evidence. Read it alongside the lifecycle you just ran: every "the guest prefers X" in a luxury journey map is an abductive leap that must survive the critic's inductive test — which register record says so? 5. Hands-On Lab Exercise

export ASD_WORKSPACE=/tmp/asd-lab03-$(date +%s)
CLI="node suite/packages/runtime/lib/cli.mjs"
# (reuse the 03.1 lab project, or rebuild: project + 3 quotes + accepted journey-map draft)
PID=<projectId>; AID=<your accepted draft artifactId>; E1=<any real evidence id>

# A. Veto with a fix-bearing defect (then read the log artifact it writes)
$CLI review --projectId $PID --artifactId $AID --verdict veto --rows "[
  {\"rowKind\":\"defect\",\"severity\":\"high\",\"rule\":\"evidence-support\",
   \"message\":\"Node n2's emotion is not traceable to the cited quote\",
   \"fix\":\"Re-derive emotion from the verbatim body or re-cite\",\"evidenceId\":\"$E1\"}]"
$CLI artifact-get --projectId $PID --artifactId <logArtifactId from the output>

# B. Remediate in place, then pass with an evidence-cited row
$CLI artifact-write --projectId $PID --methodId journey-from-transcripts --artifactId $AID --title "… v2" --nodes '<fixed nodes>'
$CLI review --projectId $PID --artifactId $AID --verdict pass --rows "[
  {\"rowKind\":\"proposal\",\"severity\":\"low\",\"message\":\"claims now trace\",\"evidenceId\":\"$E1\"}]"

# C. The review board
$CLI review-list --projectId $PID

Deliberate fail-closed demos (each exits 1): a defect row without fix; a pass without any evidenceId; any row citing an invented hash.

Verification checklist

  • Your veto output shows "status": "draft" and a logArtifactId.
  • The log artifact has kind: "review-veto-log", status: "final", and reviewOf = your artifact.
  • After remediation, the pass output shows "status": "final" and the same log id updated.
  • review-list shows your artifact with verdict: pass and failures: [].

Key Takeaways

  • The critic mechanizes Martin's third beat: abduction proposes, the gate falsifies against the register, induction clears.
  • Veto requires defect + fix; pass requires an evidence citation — asymmetric contracts that make both unactionable objections and ungrounded compliments unrepresentable.
  • The veto log is a final, first-class artifact (review-veto-log, reviewOf pointer, integrity-checked rows) — the argument is preserved, not summarized away.
  • A verdict binds to exact content: any content write clears it, so remediation always re-enters the gate.
