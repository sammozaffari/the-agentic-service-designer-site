Agentic Service Design Fundamentals

Module 01.3: The 10-Role Agent Topology: Role Contracts & Boundaries

Course: Agentic Service Design Fundamentals · Level: Foundation · Duration: 50 min · Format: Theory, Architecture, Verified MCP Run & Hands-on Lab

Learning Objectives

By completing this module, you will be able to:

  1. Explain why one generalist prompt fails on service design work — cognitive postures conflict (empathy vs. skepticism, divergence vs. convergence) and context pollution degrades every role.
  2. Enumerate the 10 roles from the live system — via MCP prompts/list and the owner/steps[].role fields of real method contracts, not from a slide.
  3. Trace a researcher → mapper → critic handoff through typed artifacts, knowing exactly which tool moves which payload at each step.
  4. State the boundary rules: roles never converse; they read and write artifacts. The critic cannot waive acceptance rules; the orchestrator cannot bypass human gates.

Honesty note: there is no asd agent run command and no host-agent spawning in the standalone runtime. Roles exist as (a) MCP prompts that configure a host model's posture, (b) owner/steps[].role fields in method contracts, and (c) responsibility boundaries over the 29 sd_* tools. Host packs (claude-code, codex, kimi, opencode) vendor the same server and add these role prompts in host format — same 29 tools underneath.

1. Theoretical Grounding: Differentiated Cognition as Method

Service design's method canon already separates cognitive postures, long before LLMs. Stickdorn et al. (This is Service Design Doing, books/01-this-is-service-design-doing/03-the-service-design-process.md and Ch. 4) insist research, synthesis, ideation, and prototyping are different activities with different mindsets: research demands empathetic non-judgment ("establish psychological safety… focus on specific past episodes"), while synthesis demands inductive discipline ("data → themes → insights… never forced into predetermined frameworks"). Kumar (101 Design Methods, books/17-101-design-methods/01-innovation-as-a-process.md) places these postures on different quadrants of his 2×2 matrix — Knowing vs. Making, Reality vs. Abstraction — and shows the process fails when a team stays in one quadrant.

A single generalist model asked to "research, synthesize, map, and critique" collapses those quadrants. The critic's posture — assume the claim is false until evidence forces belief — actively contaminates the researcher's posture — suspend judgment and listen. The 10-role topology is the computational form of the canon's separation: each role gets a narrow prompt, a narrow toolset, and artifacts as its only I/O.

2. The Roles as the Runtime Actually Exposes Them

2.1 Verified: the 10 role prompts over MCP

The runtime's MCP server (suite/packages/runtime/lib/mcp.mjs, stdio) exposes roles as prompts. Verified today against the live server: 29 tools, 10 prompts, 216 resources from the repo's books+articles corpus (resources paginate 100 per page; emitted packs that bundle pack-local corpus roots ship more).

// MCP prompts/list (real response, 2026-08-22)
{"prompts":[
  {"name":"critic"}, {"name":"ideator"}, {"name":"librarian"}, {"name":"mapper"},
  {"name":"measurer"}, {"name":"orchestrator"}, {"name":"presenter"},
  {"name":"prototyper"}, {"name":"researcher"}, {"name":"synthesizer"}]}

A host (Claude Code, Codex, Kimi, OpenCode) loads a role prompt to adopt that posture, then uses the same 29 MCP tools every other role uses. The boundary is behavioral and contractual, not a sandbox: what stops the mapper from citing a fabricated quote is not a firewall but the fact that sd_artifact_write rejects any evidenceId not in the store, and the critic's review gate rejects anything the deterministic checks missed.

2.2 Roles as method-contract fields

Roles also appear inside the methods themselves. The journey-from-transcripts contract (captured live in module 01.1) declares:

{"method":{"owner":"mapper","reviewGate":"critic"},
 "steps":[{"role":"researcher", ...}, {"role":"mapper", ...}, {"role":"critic","gate":true, ...}],
 "handoff":{"to":"ideator","artifactKind":"journey-map","condition":"After the critic review passes..."},
 "humanCheckpoints":[{"authority":"human-designer", ...}, ...]}

Read this as a typed org chart: owner is accountable for the artifact; steps[].role says whose posture each instruction needs; reviewGate names the adversary; handoff.to names the next role and the artifact kind it receives; humanCheckpoints name where a person must authorize. Different methods compose different role sequences from the same 10-role pool.

There is deliberately no asd agent run. You interrogate the topology through three honest surfaces:

Worked Example: A Researcher → Mapper Handoff as Typed Payloads

The fixture. The Callorna ws-01 evidence set from module 01.1's worked example — three registered quotes (8b603633…e1a2, bad03326…b579, f70abec0…90ad) and a draft insight-set artifact (6943a57bbf39402ca1f8d3d0c0ff8b2b). The researcher's posture work is done; the mapper needs everything required to draft a journey map without ever asking the researcher a question in chat.

Step 1 — write the handoff payload. Before touching any tool, the researcher composes the handoff as data. Three sections: what exists, what it cites, what is unresolved.

{
  "handoffPayload": {
    "from": "researcher",
    "to": "mapper",
    "artifact": {"kind": "insight-set", "id": "6943a57bbf39402ca1f8d3d0c0ff8b2b", "status": "draft"},
    "evidenceIds": [
      "8b603633b761c25af271d270b1dc4c96e04e9d2d23d5115e24d530ed6d99e1a2",
      "bad03326aca8e84aafed186643bcd6de2ce4c0f189868f47a9daa5e75725b579",
      "f70abec029d50b58237d678e984cb2d0fca51139407f6625bea306125e99d0ad"
    ],
    "openQuestions": [
      "No telemetry yet for portal form-restart rate — i2 confidence is medium; can the mapper stage it as 'suspected' until tel data lands?",
      "P1's 40-minute hold is one data point; phone-queue wait distribution unknown.",
      "Nothing captured about the SMS sender identity — patients may not know messages come from the clinic."
    ],
    "suggestedMethod": "journey-from-transcripts",
    "knownConstraints": ["contract requires min 3 evidence — satisfied", "emotions must come from quoted language"]
  }
}

Step 2 — record the handoff in the runtime. The payload's durable core goes through sd_orchestration_handoff (verified run, 2026-08-23):

{"handoff":{"kind":"orchestration-handoff","id":"4b226fbf1f1446eb9077cd47253e8004",
 "planId":"7b5768a144cc4cf08ca6ad155d878a3c","idempotencyKey":"h1",
 "from":"researcher","to":"mapper",
 "artifactId":"6943a57bbf39402ca1f8d3d0c0ff8b2b","artifactKind":"insight-set",
 "condition":"evidence set complete: 3 ws-01 quotes registered",
 "status":"recorded"}}

Interpretation. Notice the division of labor between the two layers. The runtime record is deliberately thin — who, to whom, which artifact, under what condition — because it is an audit object: immutable, idempotent (h1 replays safely), and resolvable. The thick context (evidence ids, open questions, known constraints) travels as the payload the mapper reads before running sd_method_run. What must never travel is the content of the evidence: the mapper resolves 8b603633… against the store and gets the verbatim quote, not the researcher's memory of it. The open questions are the most valuable section — they tell the mapper which journey stages to hold lightly, converting the researcher's uncertainty into the mapper's staging decisions instead of letting it evaporate at the role boundary.

4. Case Study Lens: Article 06 — "Research Ops at Scale: 200 Interviews, One Agent Team"

Synthetic illustration — not a production log.

Article 06 (articles/06/README.md) is the topology under load: a single engagement ingesting 200 interviews by fanning researcher-posture work across parallel sessions while the critic holds one acceptance bar. The point to extract is not the throughput number — it is that parallelism was safe because roles share no mutable conversational state. Two researcher sessions cannot disagree about what was said, because what was said is a content-addressed record; they can only disagree about synthesis, and that disagreement is the critic's job to adjudicate with veto rows. Contrast with two human analysts sharing a workshop wall, where the disagreement is invisible until the deck is written.

  • You identified owner, reviewGate, handoff.to, and both humanCheckpoints in two different method contracts.

Key Takeaways

  • Ten roles are ten postures, not ten programs. They exist as MCP prompts, method-contract fields, and tool-responsibility boundaries over one shared 29-tool surface.
  • Artifacts are the only channel. Roles never converse; the store is the conversation. That is what makes parallelism and audit safe.
  • The critic is structurally rude. Its gate is part of the write path, and veto defects must carry fixes — skepticism is a role, not a mood.
  • No magic runner. There is no asd agent run; hosts adopt role prompts and call the same tools. Anyone claiming otherwise is selling workshop theater with better graphics.
