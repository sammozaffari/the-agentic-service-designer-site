1. Theoretical Grounding & Literature Synthesis

Why diagnostics must be two systems, not one

Service blueprints fail in two radically different ways:

  1. Structural failure — the artifact is malformed: too few nodes, missing evidence, placeholder lanes, dangling references, malformed edges. These are machine-checkable and should be caught before a human spends judgment on them.
  2. Semantic failure — the artifact is legal JSON but wrong as service design: the fail point is untraceable to a customer symptom, a backstage step is mis-laned as frontstage, a wait mark is asserted with no observational basis. These require an adversary who can say, "this is structurally valid but conceptually false."

The literature anticipated this split long before software: Shostack's blueprinting turned process quality into a question of explicit conformance (cycle times, standardized steps), while Grönroos distinguished technical quality (what was delivered, objectively checkable) from functional quality (how it was delivered, interpretive) (books/19-service-management-and-marketing/07-designing-and-managing-the-service-process.md; books/07-designing-for-service-key-issues/02-service-design-and-management.md). The runtime's design simply operationalizes it:

  • sd_factcheck is the deterministic CI gate.
  • sd_review is the adversarial semantic gate.

Treating either one as sufficient is a category error. Factcheck cannot tell you whether a legal lane assignment is believable; the critic cannot be trusted to remember whether every node has at least one evidence reference. Good diagnostics split the labour.

The four-layer factcheck report

Every artifact row in sd_factcheck reports four layers:

Layer Question answered Example failure
integrity Do all pointers resolve? Dangling evidenceId, nonexistent artifactId in a reference
schema Does the artifact conform to its kind schema? Wrong member shapes, missing required members, malformed edge object
acceptance Does the method contract's rule set pass? min-nodes, min-evidence-per-node, field-non-empty, forbid-field-values
review Has the gate been satisfied? verdict: null on a draft, or veto instead of pass

A design artifact is healthy only when all four are green. The report is not a score; it is a vector of failure classes. That is what makes remediation precise.

Blueprint-specific diagnostics: what factcheck enables

Once the structure is trustworthy, blueprint-specific audits become meaningful:

  • Bottleneck audit — list all nodes marked W and the support-process crossings upstream of them.
  • Fail-point root-cause trace — list all nodes marked F and walk their incoming/outgoing edges across visibility and internal-interaction boundaries.
  • Lane coverage — are any lanes empty? A service-blueprint with no support-processes lane is usually a confession that the team stopped asking how the service actually runs.
  • Reference traceability — can every future-state change point back to the current-state journey stage that motivated it?

Article 11's fail-point register is exactly these diagnostics written out for human discussion. Blueprints-as-code makes them cheap enough to run every time.

3. Verified Execution — The Failure Taxonomy, Live

All receipts below are from the course verification run on 2026-08-22.

1. min-nodes — fewer than 4 blueprint nodes

$CLI artifact-write --projectId fernwood-repairs-blueprint-sprint-7cee33e4 \
  --methodId service-blueprinting --title "NEG min-nodes" --nodes '[m1,m2,m3]'
# → check.failures:
#   {"rule":"min-nodes","message":"expected at least 4 nodes, found 3"}

2. min-evidence-per-node — a node with zero citations

$CLI artifact-write --projectId fernwood-repairs-blueprint-sprint-7cee33e4 \
  --methodId service-blueprinting --title "NEG min-evidence" --nodes '[…, {"id":"v4","label":"unobserved step","evidence":[],"fields":{"lane":"support-processes"}}]'
# → check.failures:
#   {"rule":"min-evidence-per-node","nodeId":"v4",
#    "message":"node \"v4\" cites 0 evidence refs, needs 1"}

3. field-non-empty — lane exists but is empty

$CLI artifact-write --projectId fernwood-repairs-blueprint-sprint-7cee33e4 \
  --methodId service-blueprinting --title "NEG empty-lane" --nodes '[
   {"id":"l1","label":"a","evidence":[{"evidenceId":"1515c366…"}],"fields":{"lane":""}}, …]'
# → check.failures:
#   {"rule":"field-non-empty","nodeId":"l1","message":"node \"l1\" has an empty \"lane\""}

4. forbid-field-values — lane uses a banned placeholder

$CLI artifact-write --projectId fernwood-repairs-blueprint-sprint-7cee33e4 \
  --methodId service-blueprinting --title "NEGATIVE placeholder lane demo" --nodes '[
   {"id":"n2","label":"Placeholder backstage step","evidence":[{"evidenceId":"7079d287…"}],"fields":{"lane":"tbd","stage":"triage"}}, …]'
# → check.failures:
#   {"rule":"forbid-field-values","nodeId":"n2",
#    "message":"node \"n2\" uses a forbidden \"lane\" value"}

5. Integrity failure — dangling evidence reference

$CLI artifact-write --projectId fernwood-repairs-blueprint-sprint-7cee33e4 \
  --methodId service-blueprinting --title "NEG dangling" --nodes '[
   {"id":"d1","label":"a","evidence":[{"evidenceId":"00000000…deadbeef"}],"fields":{"lane":"customer-actions"}}, …]'
# → asd artifact-write: node "d1" cites evidence "00000000…deadbeef" which is not in the project evidence store

6. Review-layer failure — draft without pass verdict blocks the project

When the intentionally broken artifact 6a377957469b429bb80ea6760082aa39 remained in draft, factcheck reported it clearly:

$CLI factcheck --projectId fernwood-repairs-blueprint-sprint-7cee33e4 > /tmp/c06-factcheck.txt 2>&1; echo $?
# → 1

# Relevant row (trimmed):
# {"artifactId":"6a377957469b429bb80ea6760082aa39","kind":"service-blueprint",
#  "status":"draft",
#  "integrity":{"pass":true,"dangling":[]},
#  "schema":{"pass":true,"failures":[]},
#  "acceptance":{"pass":false,"failures":["node \"n2\" uses a forbidden \"lane\" value"]},
#  "review":{"pass":true,"gate":"critic","verdict":null}}

7. Phase-gate failure — humans cannot wave drafts through

$CLI phase-advance --projectId fernwood-repairs-blueprint-sprint-7cee33e4 --toPhase define \
  --idempotencyKey gate-1 --approvalReceipt '{"receiptId":"RCP-2026-001","approvedBy":"Sam Mozaffari","decision":"approve","rationale":"Sprint gate 1 review","approvedAt":"2026-08-22T12:00:00Z"}'
# → asd phase-advance: phase advance requires all design artifacts to be final; drafts: 6a377957469b429bb80ea6760082aa39

That last receipt is the mature-system test: validation is not an advisory linter that management can ignore under deadline pressure. The gate is structural.

4. Case Study Lens: Article 11's Fail-Point Register as Diagnostics

Synthetic illustration — not a production log.

Article 11 ends with a Fail-Point Register — one row per F or W. Read that register as the human-readable surface of the machine-readable diagnostics above:

  • W rows correspond to customer wait nodes with upstream visibility/internal-interaction crossings.
  • F rows correspond to fail-point nodes whose review rows should explain the customer symptom they trace to.
  • A row with no evidence citation would be the human analogue of min-evidence-per-node.
  • A row with no owning lane would be the human analogue of field-non-empty / placeholder-lane failure.

The register matters because it turns the validator's terse output into a remediation backlog. The validator matters because it guarantees the register was not written against a malformed artifact.

5. Hands-On Lab

Use the verifier in courses/labs/lab-06-blueprinting-6lane/verify_lab-06.mjs, then reproduce each failure manually:

# 1. Headless verification (positive spine + negative assertions)
node courses/labs/lab-06-blueprinting-6lane/verify_lab-06.mjs

# 2. Manual failure drills
export ASD_WORKSPACE=/tmp/asd-lab06
CLI="node suite/packages/runtime/lib/cli.mjs"

# a) min-nodes
$CLI artifact-write --projectId <pid> --methodId service-blueprinting --title "too small" --nodes '[<3 valid nodes>]'

# b) min-evidence-per-node
$CLI artifact-write --projectId <pid> --methodId service-blueprinting --title "unobserved" --nodes '[<4 nodes, one with evidence:[]>]'

# c) empty lane
$CLI artifact-write --projectId <pid> --methodId service-blueprinting --title "blank lane" --nodes '[<4 nodes, one with fields.lane:"">]'

# d) dangling evidence
$CLI artifact-write --projectId <pid> --methodId service-blueprinting --title "dangling" --nodes '[<4 nodes, one with evidenceId that does not exist>]'

# e) review gate and project-level factcheck
$CLI review --projectId <pid> --artifactId <aid> --verdict pass --rows '[{"rowKind":"proposal","severity":"low","message":"verified","evidenceId":"<e1>"}]'
$CLI factcheck --projectId <pid>; echo $?

Verification checklist

  • You triggered all four acceptance failures and can name the exact rule each one violated.
  • You observed the difference between a write-time integrity failure (dangling evidence) and a retained draft with acceptance failures.
  • You ran factcheck with both exit 1 (at least one failing artifact) and exit 0 (all artifacts final and passing).
  • You can explain why review.verdict: null is a project-level problem even when integrity, schema, and acceptance all pass.
  • You saw phase-advance fail closed on a remaining draft, even with an approval receipt.

Key Takeaways

  • Diagnostics are layered: integrity, schema, acceptance, review — four different questions, four different remediation paths.
  • sd_factcheck and sd_review are complementary: factcheck catches malformed work; the critic catches misleading work. Neither subsumes the other.
  • Every failure class is teachable because it is explicit: min-nodes, min-evidence-per-node, field-non-empty, forbid-field-values, dangling ids, veto logs, blocked phase gates.
  • A mature service-design toolchain treats validation as architecture, not etiquette: failing artifacts stay auditable, failing projects exit non-zero, and humans cannot approve drafts into the next phase.
