Learning Objectives

By completing this module, you will master:

  2. The Complete Authoring Spine: project → evidence → journey map → five-lane blueprint with references[].provenance → gate → export, executed live.
  3. Cross-Artifact Provenance: the typed derived-from and supports relations that turn isolated deliverables into a traceable system of record.
  4. Schemas & Verified Execution: real payloads, real ids, real exit codes — the entire session is reproduced below.
  5. Case Study Lens: Article 11's artifact portfolio (A1 journey map → A1b blueprint → backlog) as the provenance chain this module builds.
  6. Hands-on Practice: author the full chain yourself in a disposable workspace.

1. Theoretical Grounding & Literature Synthesis

Why "as-code" is a methodological position, not a file format

Service Design: From Insight to Implementation (books/03-service-design-from-insight-to-implementation, ch. 07 — a registered source of the blueprint-to-backlog method) makes the implementation argument: the distance between a design artifact and a delivery backlog is where most service redesigns die. The cause is representational: a workshop poster cannot be diffed against last week's version, cannot be validated in CI, cannot generate its own visualizations, and cannot prove which interview supports which box. Every translation step — poster to slide, slide to ticket, ticket to shipped system — is an opportunity for silent mutation.

Blueprints-as-code removes the translation steps by making the blueprint the single source of truth:

  • Diffable: the blueprint is JSON; a change is a line-level diff a reviewer can actually read.
  • Validatable: acceptance rules (min-nodes, per-node evidence, non-placeholder lanes) run at write time, every time, identically.
  • Traceable: every node cites SHA-256-addressed evidence; every cross-artifact link carries mandatory provenance.
  • Renderable: sd_export_artifact compiles the same JSON to the same SVG deterministically — the picture is a view, never the master.
  • Composable: typed references (derived-from, supports) let artifacts form a graph — journey map → blueprint → roadmap — that diagnostics (module 06.7) can traverse.

This is Shostack's 1984 ambition completed by tooling: the blueprint as an engineering document that operations, finance, and technology can all compute over.

2. Agentic Topology & Role Contracts

The authoring session touches every role this course has introduced, in contract order:

Stage Role Tool calls Contract basis
Evidence intake researcher sd_evidence_add (quote / telemetry / document) inputs: [{kind: evidence-set, min: 4}]
Journey input mapper sd_method_run journey-from-transcripts, sd_artifact_write journey-map = the symptom view the blueprint derives from
Blueprint authoring mapper (owner) sd_method_run service-blueprinting, sd_artifact_write --nodes --edges --references acceptance: min-nodes 4, min-evidence-per-node 1, lane non-empty, no placeholder lanes
Line annotation presenter sd_artifact_write (edge labels, marker) step 2 of the contract
Gate critic sd_review veto/pass reviewGate: "critic", gate: true step
Verification measurer sd_factcheck exit 0 only when every artifact passes
Delivery orchestrator sd_method_run blueprint-to-backlog → roadmap supports reference target; inputs require a validated service-blueprint

3. The Full Verified Session

Every command and id below is from the real disposable-workspace run performed for this course (workspace /tmp/asd-c06-live, 2026-08-22). Reproduce it exactly; only the ids will differ, because evidence ids are content hashes.

Step 1 — project and evidence (with the kind vocabulary failing closed)

export ASD_WORKSPACE=/tmp/asd-lab06
CLI="node suite/packages/runtime/lib/cli.mjs"

$CLI project-create --name "Fernwood Repairs Blueprint Sprint" --client "Fernwood Council" \
  --sector government --service "housing repairs reporting"
# → projectId: fernwood-repairs-blueprint-sprint-7cee33e4

$CLI evidence-add --projectId <pid> --source int-01 --kind quote \
  --body "I reported the leaking tap online and got a text back within an hour with a booking reference."
# → id 1515c366a19faab7…        (also added: int-02, int-03 quotes; obs-04 + doc-05 documents; tel-06 telemetry)

$CLI evidence-add --projectId <pid> --source obs-04 --kind observation --body "…"
# → asd evidence-add: invalid arguments: "arguments.kind" must be one of ["quote","telemetry","document"]
#   (the closed kind vocabulary fails closed — re-add the same body as --kind document)

Step 2 — the journey-map input (the symptom view)

$CLI artifact-write --projectId <pid> --methodId journey-from-transcripts \
  --title "Tenant repairs reporting journey (current)" --nodes '[
   {"id":"j1","label":"Notice leak and report online","evidence":[{"evidenceId":"1515c366…"}],
    "fields":{"stage":"report","touchpoint":"online portal","emotion":"relieved"}},
   {"id":"j2","label":"Wait for triage and booking confirmation","evidence":[{"evidenceId":"b9ed3853…"}],
    "fields":{"stage":"triage","touchpoint":"sms updates","emotion":"anxious"}},
   {"id":"j3","label":"Plumber visit without job context","evidence":[{"evidenceId":"7079d287…"}],
    "fields":{"stage":"visit","touchpoint":"front door","emotion":"frustrated"}},
   {"id":"j4","label":"Reopen ticket after failed fix","evidence":[{"evidenceId":"2bf9ed6f…"}],
    "fields":{"stage":"rework","touchpoint":"contact centre","emotion":"exhausted"}}]' \
  --edges '[{"id":"e-j1-j2","from":"j1","to":"j2","relation":"precedes","fields":{"label":"waits"}}, …]'
# → {"accepted":true,"status":"draft","artifact":{"id":"4c7e9d3c5fea4c67bad20eb16b592398", …}}

Step 3 — the five-lane blueprint with typed provenance (the diagnosis view)

$CLI artifact-write --projectId <pid> --methodId service-blueprinting \
  --title "Fernwood repairs reporting blueprint (current state)" --nodes '[
   {"id":"pe1","label":"Booking reference SMS with job number","evidence":[{"evidenceId":"1515c366…"}],
    "fields":{"lane":"physical-evidence","stage":"report","touchpoint":"sms"}},
   {"id":"ca1","label":"Tenant reports leak via online portal","evidence":[{"evidenceId":"1515c366…"}],
    "fields":{"lane":"customer-actions","stage":"report","emotion":"relieved"}},
   {"id":"ca2","label":"Tenant phones contact centre for status","evidence":[{"evidenceId":"b9ed3853…"}],
    "fields":{"lane":"customer-actions","stage":"wait","emotion":"anxious","marker":"W"}},
   {"id":"fs1","label":"Contact centre agent triages urgency","evidence":[{"evidenceId":"d8ccdeaa…"}],
    "fields":{"lane":"frontstage-actions","stage":"triage","actor":"contact-centre-agent"}},
   {"id":"fs2","label":"Plumber attends without triage context","evidence":[{"evidenceId":"7079d287…"}],
    "fields":{"lane":"frontstage-actions","stage":"visit","actor":"contractor-plumber","marker":"F"}},
   {"id":"bs1","label":"Agent re-keys repair details into scheduler","evidence":[{"evidenceId":"d8ccdeaa…"}],
    "fields":{"lane":"backstage-actions","stage":"triage","actor":"contact-centre-agent"}},
   {"id":"bs2","label":"Depot dispatches job to contractor round","evidence":[{"evidenceId":"7079d287…"}],
    "fields":{"lane":"backstage-actions","stage":"dispatch","actor":"depot-controller"}},
   {"id":"sp1","label":"Policy engine applies 24h/20-day clocks","evidence":[{"evidenceId":"48a61a15…"}],
    "fields":{"lane":"support-processes","stage":"triage"}},
   {"id":"sp2","label":"Ticket system tracks reopen rate","evidence":[{"evidenceId":"2bf9ed6f…"}],
    "fields":{"lane":"support-processes","stage":"rework"}}]' \
  --edges '[
   {"id":"b1","from":"ca1","to":"fs1","relation":"triggers","fields":{"label":"crosses line of interaction"}},
   {"id":"b2","from":"fs1","to":"bs1","relation":"hands-to","fields":{"label":"crosses line of visibility"}},
   {"id":"b3","from":"bs1","to":"sp1","relation":"depends-on","fields":{"label":"crosses line of internal interaction"}},
   {"id":"b4","from":"sp1","to":"bs2","relation":"schedules","fields":{}},
   {"id":"b5","from":"bs2","to":"fs2","relation":"dispatches","fields":{}},
   {"id":"b6","from":"fs2","to":"ca2","relation":"fails","fields":{"label":"fail point F"}},
   {"id":"b7","from":"fs2","to":"fs1","relation":"recovery-loop","fields":{"label":"rework returns to triage"}}]' \
  --references '[
   {"artifactId":"4c7e9d3c5fea4c67bad20eb16b592398","kind":"journey-map","relation":"derived-from",
    "provenance":{"source":"method","methodId":"service-blueprinting",
                  "note":"Current-state journey map mined from tenant transcripts; blueprint lanes operationalise its stages."}}]'
# → {"accepted":true,"status":"draft","artifact":{"id":"4d64fbd3395440efa44c17363e5b8f10", …}}

The references block is the module's heart: relation: "derived-from" points at the journey map, and provenance — {source: "method"|"human"|"import", methodId?, note?} — records why this link is trusted. The schema will not accept the reference without it: a reference never gets provenance invented (@asd/core type doc, verbatim).

Step 4 — gate, verify, export

$CLI review --projectId <pid> --artifactId 4d64fbd3… --verdict pass --rows '[
 {"rowKind":"proposal","severity":"low","message":"Recovery loop explicit; verified against contractor interview.",
  "evidenceId":"7079d287…"}]'
# → {"status":"final","verdict":"pass"}

$CLI factcheck --projectId <pid>; echo $?
# → per-artifact rows {integrity, schema, acceptance, review}; exit 0 only when every artifact passes

$CLI export-artifact --projectId <pid> --artifactId 4d64fbd3…
# → renders/service-blueprint.4d64fbd3.svg  (7,720 bytes, deterministic @asd/render output)

$CLI export-report --projectId <pid> --kind artifact-dossier
# → renders/report.artifact-dossier.html  (25,683 bytes)

$CLI method-run --projectId <pid> --methodId blueprint-to-backlog
# → contract: owner orchestrator, outputKind roadmap, inputs require ≥1 validated service-blueprint,
#   acceptance: min-nodes 3 + field-non-empty horizon + field-non-empty owner
#   (the blueprint becomes a backlog — books/03 ch.07's implementation bridge, executable)

4. Case Study Lens: Article 11's Portfolio as This Provenance Chain

Synthetic illustration — not a production log.

Article 11's artifact portfolio is exactly the chain built in this module: A1 (journey map) → A1b (current-state blueprint, the diagnostic centerpiece) → A1c (fail-point root-cause trace) → A2 (future-state blueprint) → prioritized backlog. The article's Phase 3 prioritization workshop is what blueprint-to-backlog formalizes: every fail point becomes a work item with an owning team, and the critic rejects any item with no wave assignment ("an unsequenced backlog cannot be delivered" — contract, verbatim). Where the article narrates the chain in prose, the toolchain persists it: the derived-from reference and the supports link to the roadmap are queryable data, so six months later a new team member can traverse from any backlog item back to the tenant quote that justifies it.

5. Hands-On Lab

The lab directory's verifier (courses/labs/lab-06-blueprinting-6lane/verify_lab-06.mjs) drives this entire spine headlessly — run it, read it, then reproduce it manually:

# Headless: full spine + negative assertions (empty lane, dangling evidence)
node courses/labs/lab-06-blueprinting-6lane/verify_lab-06.mjs

# Manual: reproduce steps 1–4 above in your own ASD_WORKSPACE, then:
$CLI schema-get --kind service-blueprint        # confirm the reference relations and lane rule
$CLI artifact-get --projectId <pid> --artifactId <bp-id>   # read back your provenance block

Verification checklist

  • Your journey map and blueprint both reached accepted:true, then final after review.
  • The blueprint's references contains derived-from → your journey map with a complete provenance block.
  • factcheck exit code is 0 with all artifacts final, 1 while any draft fails acceptance — you observed both.
  • The exported SVG regenerates byte-identically from unchanged JSON (run export-artifact twice and compare).
  • You can traverse the chain: backlog candidate → blueprint fail point → journey stage → tenant quote, using only ids.

Key Takeaways

  • Blueprints-as-code eliminates translation drift: one typed JSON source of truth, deterministic renders as views, line-level diffs for review.
  • Provenance is mandatory, not decorative: references[].provenance is required by schema, and every node cites content-addressed evidence — the chain from quote to backlog never breaks.
  • The full spine is seven commands: project → evidence → journey map → blueprint → review → factcheck → export, each failing closed on its own class of error.
  • Implementation starts where the blueprint ends: blueprint-to-backlog consumes a validated service-blueprint and emits a sequenced roadmap — the supports reference makes the handoff explicit.
