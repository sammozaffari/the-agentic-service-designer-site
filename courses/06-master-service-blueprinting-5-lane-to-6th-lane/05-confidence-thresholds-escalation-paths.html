  2. The Four Escalation Rungs: deterministic acceptance → adversarial reviewGate → orchestration failure policy (retryable/error/maxRetries) → human checkpoints and signed phase gates.
  3. Agent Topology & Contracts: sd_review verdict semantics — what a pass requires, what a veto requires, and where the veto log lives.

1. Theoretical Grounding & Literature Synthesis

The problem with confidence scores

A tempting design for agentic pipelines is a numeric confidence threshold: if the model's self-reported confidence drops below τ, escalate to a human. It fails in practice for three structural reasons. First, self-reported confidence is uncalibrated — the same model asserts wrong answers and right ones with equal fluency. Second, a single scalar conflates different failure classes — missing evidence, schema violation, and factual dispute need different responses, not different positions on one dial. Third, a threshold is a policy hidden in a constant: nobody can audit why τ was 0.7, and nobody can prove what happened when it tripped.

The service-design literature never trusted self-assessment either. Grönroos's quality model (books/07-designing-for-service-key-issues/02-service-design-and-management.md) separates technical quality (what was delivered — objectively checkable) from functional quality (how it was delivered — judgment-requiring). Shostack's blueprint discipline attached explicit time standards to backstage steps precisely so that conformance could be checked mechanically instead of vibes being asserted (books/02/01). The pattern is always the same: push every check that can be deterministic into a deterministic gate, and route everything irreducibly judgmental to a named adversary or a named human.

The four escalation rungs in the @asd toolchain

There is no sd_confidence_route tool — by design. Escalation is implemented as four independent, auditable rungs, each with its own failure semantics:

Rung Mechanism What it catches Failure semantics
1. Deterministic acceptance Method acceptance[] rules evaluated at sd_artifact_write Structural defects: too few nodes, missing evidence, placeholder lanes accepted:false, retained as draft with check.failures[]
2. Adversarial reviewGate reviewGate: "critic" on every method contract; sd_review Legal-but-wrong content: misassigned lanes, untraceable fail points, weak analysis veto → stays draft; veto rows persist as a review-veto-log artifact
3. Orchestration failure policy sd_orchestration_dispatch with outcome, error, retryable, retryOf; step maxRetries Execution failures: timeouts, host errors, unavailable tools failed + retryable:true → retry chain; exhausted → blocked
4. Human gates Method humanCheckpoints[] (scope-confirmation, handoff-approval); sd_phase_advance with signed approvalReceipt Everything judgmental: scope, ethics, go/no-go, phase transitions Fails closed: no receipt, no advance; drafts block advancement

The rungs are ordered by cost of the check: deterministic rules are free and run on every write; the critic costs a review cycle; a human gate costs a meeting. Escalation means a lower rung declining to decide and handing a well-formed question upward — with the evidence attached.

2. Agentic Topology & Role Contracts

The review contract (sd_review)

Rows are the escalation vocabulary. Each row is:

type ReviewRow = {
  rowKind: 'proposal' | 'defect'          // proposal = suggestion; defect = gate-blocking fault
  severity: 'critical' | 'high' | 'medium' | 'low'
  message: string
  rule?: string                            // the acceptance/house rule the row invokes
  fix?: string                             // MANDATORY on every defect row in a veto
  evidenceId?: string                      // the citation that makes the row checkable
}

Verdict semantics (enforced by the runtime, not by convention):

  • pass requires ≥1 row that cites evidence (evidenceId) and zero defect rows → artifact becomes final.
  • veto requires ≥1 defect row, and every defect row must carry a fix → artifact stays draft; the verdict and its rows persist as a review-veto-log artifact; prior check failures are retained.

The veto-with-mandatory-fix rule is the escalation design's conscience: a critic may not block work with a vague unease. Every escalation downward must carry enough structure for the author to act, and every escalation upward (to humans) arrives as a named defect list, not a feeling.

Failure policy contract (sd_orchestration_dispatch)

From module 06.4: outcome: "failed" + error: "<detail>" + retryable: true|false decides whether the step may be retried; the retry is a new dispatch with retryOf pointing at the failed attempt (attempt counter increments); step-level maxRetries caps the chain. A step whose retries are exhausted — or whose failure was marked non-retryable — goes blocked, which is the machine's way of saying: this is now a human's decision.

3. Verified Execution — A Real Escalation Session

From this course's live run (blueprint 4d64fbd3395440efa44c17363e5b8f10):

CLI="node suite/packages/runtime/lib/cli.mjs"
PID=fernwood-repairs-blueprint-sprint-7cee33e4
BP=4d64fbd3395440efa44c17363e5b8f10

# 1. VETO — every defect row carries rule + fix + evidenceId
$CLI review --projectId $PID --artifactId $BP --verdict veto --rows '[
 {"rowKind":"defect","severity":"high","rule":"fail-point-trace",
  "message":"Node fs2 is marked F but the blueprint does not show a recovery edge back to triage.",
  "fix":"Add an edge from fs2 back to fs1 labelled recovery-loop so the rework path is explicit.",
  "evidenceId":"7079d287e6c6e6b89901f6ebf134fcc8d4d4b760ba9f43d8f050bf974ef8afcc"},
 {"rowKind":"proposal","severity":"medium",
  "message":"Consider marking the 3-week queue wait (ca2) with elapsed-time annotations in a future pass."}]'
# → {"status":"draft","verdict":"veto", …}
#    veto persisted as review-veto-log artifact 11aa2d1962ea44ba92f57b244db85363

# 2. Remediate: rewrite the same artifact with edge b7 (fs2 → fs1, relation recovery-loop)
$CLI artifact-write --projectId $PID --artifactId $BP --methodId service-blueprinting …
# → {"accepted":true,"status":"draft"}

# 3. PASS — evidence-cited row, no defects
$CLI review --projectId $PID --artifactId $BP --verdict pass --rows '[
 {"rowKind":"proposal","severity":"low",
  "message":"Recovery loop from fs2 to fs1 now makes the rework path explicit; verified against contractor interview.",
  "evidenceId":"7079d287e6c6e6b89901f6ebf134fcc8d4d4b760ba9f43d8f050bf974ef8afcc"}]'
# → {"status":"final","verdict":"pass"}

# 4. Orchestration failure policy (from module 06.4's run):
#    d2: outcome=failed, error="presenter host timed out annotating wait points", retryable=true
#    d3: retryOf 02e1e16edae0487bad42e30fbf6137a6 → attempt 2, succeeded

# 5. The ultimate escalation fails closed — phase advance while a draft exists:
$CLI phase-advance --projectId $PID --toPhase define --idempotencyKey gate-1 --approvalReceipt '{"receiptId":"RCP-2026-001", …}'
# → asd phase-advance: phase advance requires all design artifacts to be final; drafts: 6a377957469b429bb80ea6760082aa39

Read the shape of that last error: even with a signed receipt, the human gate refuses while any design artifact is still a draft. Escalation paths terminate at humans, but the humans are protected from rubber-stamping unfinished work — the machine's "no" is structural, not advisory.

4. Case Study Lens: Article 33 — The Critic on Every Gate

Synthetic illustration — not a production log.

Article 33 (The Virtual Ward at Capacity: Scaling Telehealth with the ASD Critic on Every Gate) is the escalation-discipline case study. A telehealth service at capacity cannot afford a single unreviewed clinical-pathway claim reaching production, so the engagement put the critic gate on every artifact — not just headline deliverables. Read through this module: the article's "gates" are rung 2 applied uniformly; its clinical-safety sign-offs are rung 4 human checkpoints with named authorities; and its incident reviews map to rung 3 failure records (error + retryable) rather than post-hoc blame. The transferable lesson: escalation architecture is something you design before the sprint, choosing per artifact which rungs apply — the method contract's reviewGate and humanCheckpoints fields are where those decisions live.

5. Hands-On Lab

export ASD_WORKSPACE=/tmp/asd-lab06
CLI="node suite/packages/runtime/lib/cli.mjs"

# 1. Veto your module-06.2/06.3 blueprint with one well-formed defect
$CLI review --projectId <pid> --artifactId <aid> --verdict veto --rows '[
 {"rowKind":"defect","severity":"high","rule":"lane-correctness",
  "message":"<a specific, evidence-backed fault>",
  "fix":"<what the author must change>","evidenceId":"<e1>"}]'
# EXPECT: status stays draft; a review-veto-log artifact appears in sd_artifact_list --kind review-veto-log

# 2. Try to veto with a defect that has no fix — the runtime refuses malformed escalation
$CLI review --projectId <pid> --artifactId <aid> --verdict veto --rows '[
 {"rowKind":"defect","severity":"low","message":"I just dont like it"}]'
# EXPECT: rejection — every defect row in a veto requires "fix"

# 3. Remediate and pass
$CLI artifact-write --projectId <pid> --artifactId <aid> … (apply the fix)
$CLI review --projectId <pid> --artifactId <aid> --verdict pass --rows '[
 {"rowKind":"proposal","severity":"low","message":"Fix verified against evidence.","evidenceId":"<e1>"}]'

# 4. Drive a step to blocked, then re-plan it as a human decision
$CLI orchestration-dispatch --projectId <pid> --planId <planId> --stepId gate \
  --idempotencyKey b1 --capability record-only --outcome failed --error "critic unavailable" --retryable false
$CLI orchestration-status --projectId <pid> --planId <planId>   # observe the failure ledger

Verification checklist

  • Your veto left the artifact in draft and persisted a review-veto-log.
  • The fix-less defect row was rejected by the runtime.
  • Your pass verdict cited evidence and flipped status to final.
  • A non-retryable failure is visible in orchestration-status as the step's terminal machine state, awaiting human re-planning.
  • phase-advance without all-final artifacts fails closed, naming the offending draft ids.

Key Takeaways

  • There is no confidence-threshold router — deliberately. Calibrated gates beat uncalibrated scalars: deterministic acceptance for structure, an adversarial critic for content, retry policy for execution, humans for judgment.
  • A veto must be actionable: every defect row carries a fix, and the whole row set persists as a review-veto-log. Escalation without structure is just obstruction.
  • Failure policy is data: error, retryable, retryOf, maxRetries turn "something went wrong" into an auditable retry chain with a defined terminal state (blocked → human).
  • Every escalation path terminates at a named human authority — and the human gate fails closed on unfinished work. Agents prepare; humans authorize.
