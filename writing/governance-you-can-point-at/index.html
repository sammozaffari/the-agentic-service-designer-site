Governance you can point at

Responsible AI in a design practice, stated as the guardrails that actually run, with a file behind each one.

September 2026 · The mechanisms below are in repositories I own; the safety research platform was built at KFC South Pacific in 2025, the rest are personal tooling

Job postings for applied-AI roles ask for responsible AI governance, guardrails, tiered autonomy and lifecycle management. Most answers to that are policy documents. This is the other kind of answer: the controls that run in workflows I built, what each one prevents, and where it lives. Every row is a thing a reviewer can open.

The principle underneath

Nothing an AI produces counts until a gate it cannot pass on its own has passed it. The gates are mechanical wherever they can be, human where they must be, and the record of what passed is bound to the thing that passed, so editing after approval sends it back to draft. Autonomy is tiered by consequence: a model may draft freely, may write to a database only through a validator, and may never mark its own work final.

The controls

ControlWhat it preventsWhere it runs
Schema validation before importA model writing a record type, stage or priority that the data model does not allowThe safety research platform: a Python importer validates every extracted JSON record against the SQLite schema before it can land
Checkpoint before every write, rollback by batchAn extraction batch that turns out to be wrong contaminating the record with no way backThe same platform: a git tag before each import and a batch ID on every row, so one batch can be reversed without touching the rest
Mandatory human review of every recordFlattened or overstated extractions being treated as evidenceThe same platform: every extracted insight was read against its transcript passage and placed on the blueprint by a person before it counted
Prompt persisted with its outputA generated recommendation nobody can trace back to what it was askedThe same platform: the recommendation endpoint stores the full prompt alongside each result
One-use token critic gateA drafting agent marking its own work as reviewedMy job-application pipeline: the critic is a separate headless run that alone receives a one-use token; the drafter cannot file a report
Hash-bound approvalEditing a document after it passed review and keeping the passThe same pipeline: a report binds to the artefact's content hash; any edit returns it to draft
Fail-closed queue gateContent reaching a publish queue on a status string the drafter wroteMy content system: a Python gate admits a post only if a critic report file exists and carries a pass verdict; front matter is not accepted as evidence
Evaluation fixturesA critic that has quietly stopped catching the failures it exists forThe same system: three deliberately bad drafts the critic must reject, run as tests
Acceptance rules on the write pathAn artefact with no evidence behind its nodes being marked finalThe Agentic Service Designer runtime: machine-checked rules such as minimum evidence per node and forbidden field values, evaluated when an artefact is written
Fact-check replayA citation to evidence that no longer exists or never didThe same runtime: every evidence reference in every artefact is resolved again before publication, with a per-artefact pass or fail a CI job can stop on
Critic role on the method contractA method declaring itself complete without adversarial reviewThe same runtime: any method that declares a critic gate cannot be final without a critic verdict
Drift check in CICompiled agent packs silently diverging from the canonical sourceThe same runtime: CI recompiles the packs and fails on any diff
CalibrationConfident predictions that are never scoredThe job pipeline: a prediction is frozen when an application is sent and scored against the outcome later
Allow and deny lists on tool useAn autonomous run editing files or running commands outside its laneThe job pipeline: headless runs get an explicit allowed-tools list; file edits, git and destructive shell commands are denied

Tiered autonomy, in practice

Tier one: the model drafts. Transcripts into structured records, opportunity records into mockups, a job description into a cover letter. Nothing here is visible to anyone but me. Tier two: the model writes to a store, but only through a validator, in a batch that can be reversed, with the prompt kept. Tier three: a person decides. Every research record, every published post, every application, every artefact marked final. There is no tier four. Nothing I have built lets a model act on the world without a person having passed it, and the gates above are how that stays true when I am tired or in a hurry.

Lifecycle

Build: the schema and the acceptance rules are written before the first prompt. Test: fixtures that must fail, and a fact-check that replays citations. Deploy: a checkpoint before every write. Monitor: calibration on predictions, and the review rate on extractions, which is the number I most want to publish once it is checked. Retire: batch rollback and the drift check, so removing something is as safe as adding it.

What this does not claim

None of this is a production AI feature serving customers, and none of it is an enterprise governance framework with a risk committee behind it. It is the working governance of one designer's practice, and it is auditable, which is the property I would want first in any larger one.
