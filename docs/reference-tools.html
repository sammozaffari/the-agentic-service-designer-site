Engine tool reference

The engine exposes exactly sixteen tools, named sd_*. One definition set serves every surface: the asd CLI parses its flags from the same JSON schemas, the MCP server advertises the same schemas over tools/list, and the DeepSeek Harness suite registers the same builders. The CLI surface cannot drift from the tool definitions because it is generated from them.

The tools group into eight families: project, evidence, artifact, method, review, export, knowledge, and the fact-check gate. Every JSON excerpt below is real captured output from the CLI, trimmed with […] where nodes or rows repeat.

Conventions

  • Arguments. CLI flags map one-to-one onto tool arguments: --flag value or --flag=value. Array and object arguments take a JSON literal (--nodes '[…]'). Short names work too: asd project-create resolves to sd_project_create by stripping the prefix and normalizing - to _.
  • Required flags. A missing required argument fails before the tool runs: asd sd_project_create: missing required flag "--client", exit 1.
  • Errors. Every failure prints asd <tool>: <message> plus running `asd help` shows usage to stderr and exits 1. Over MCP, the same failure is a tools/call result with isError: true and the same message as text content — not a protocol error.
  • Gate failures. sd_factcheck can complete successfully and still report "pass": false; the CLI exits 1 on that payload too, so CI can gate on it. This is the one case where exit 1 does not mean the tool errored.
  • Workspace. Projects live under $ASD_WORKSPACE when set, else ~/.asd/projects. Files are the record of truth; every tool reads and writes that tree.

Project tools

sd_project_list

Lists every project in the workspace. No arguments. Returns { "projects": [...] } — an empty array on a fresh workspace, exit 0.

sd_project_create

Creates a project directory holding project.json plus evidence/, artifacts/, renders/, and sops/.

ArgumentTypeDescription
namestring, requiredProject name, e.g. "Housing Repairs Redesign"
clientstring, requiredClient or organisation
sectorstring, requiredSector, e.g. government, fintech, healthcare
servicestring, requiredThe service under design
phaseenum, optionalStarting double-diamond phase: discover, define, develop, deliver; defaults to the configured value

Returns { "project": {…} }. The assigned projectId is the slugified name plus an 8-hex-char suffix:

DATA
{
  "project": {
    "projectId": "probe-harbour-f0b87904",
    "name": "probe-harbour",
    "client": "Fictional composite",
    "sector": "local-government",
    "service": "housing repairs reporting",
    "phase": "discover",
    "createdAt": "2026-08-19T03:37:14.784Z",
    "updatedAt": "2026-08-19T03:37:14.784Z"
  }
}

sd_project_open

Opens one project and returns its metadata plus every artifact written so far: { "project": {…}, "artifacts": [...] }.

ArgumentTypeDescription
projectIdstring, requiredProject id, from sd_project_list

Failure mode: an unknown id errors with project not found: <id>, exit 1.

Evidence tools

Evidence is the register every artifact cites. There are exactly three kinds — quote, telemetry, document — and no others; --kind observation is rejected at argument validation:

NOTE
asd sd_evidence_add: invalid arguments: "kind" must be one of ["quote","telemetry","document"]

sd_evidence_add

Adds one piece of evidence to a project.

ArgumentTypeDescription
projectIdstring, requiredProject id
sourcestring, requiredWhere it came from, e.g. "interview-04", "crm-export-2026-08"
kindenum, requiredquote, telemetry, or document
bodystring, requiredThe verbatim quote, figure, or extract

Returns { "evidence": {…} }. The record is content-addressed — the id is the SHA-256 hex digest of source, kind, and body — so adding the same body twice from the same source returns the same record rather than a duplicate:

DATA
{
  "evidence": {
    "id": "c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174",
    "projectId": "capture-meridian-201d0a1d",
    "source": "call-821004",
    "kind": "quote",
    "body": "Told to wait 15 min for next bus; nobody held the tram.",
    "capturedAt": "2026-08-19T00:02:10.443Z"
  }
}

sd_evidence_query

Searches a project's evidence store. Returns { "evidence": [...] }.

ArgumentTypeDescription
projectIdstring, requiredProject id
searchstring, optionalCase-insensitive substring matched against the body
kindenum, optionalRestrict to one of quote, telemetry, document

Artifact tools

Artifacts are typed JSON documents: nodes with evidence references, validated against the producing method's acceptance rules. These two tools read them; writes go through the method family below.

sd_artifact_list

Lists a project's artifacts. Returns { "artifacts": [...] } with each artifact in full — nodes, evidence refs, status, and the attached check report when a write failed acceptance.

ArgumentTypeDescription
projectIdstring, requiredProject id
kindstring, optionalArtifact kind filter, e.g. journey-map, service-blueprint

sd_artifact_get

Fetches one artifact in full: { "artifact": {…} }, including every node and its evidence refs, and the review block once a verdict is recorded.

ArgumentTypeDescription
projectIdstring, requiredProject id
artifactIdstring, requiredArtifact id, from sd_artifact_list

Failure mode: artifact not found: <id>, exit 1.

Method tools

A method is data, not code: a manifest with steps, inputs, acceptance rules, and a review gate. These three tools are the whole model-facing surface for executing one — list what exists, fetch the contract, write the result through a gate that can say no.

sd_method_list

Lists methods from the registry with the book and article sources each derives from. Returns { "methods": [...] } with id, name, phase, produces, and sources per method.

ArgumentTypeDescription
phaseenum, optionalresearch, synthesis, ideation, prototyping, delivery, measurement
producesKindstring, optionalRestrict to methods producing this artifact kind

Failure mode: an out-of-enum phase errors with "<phase>" is not a method phase.

sd_method_run

Fetches the execution contract for a method — it does not "run" work for you; it returns what the work must satisfy. Call it before starting so the acceptance rules and input minimums are known up front.

ArgumentTypeDescription
methodIdstring, requiredMethod id, from sd_method_list
projectIdstring, requiredProject id

Returns the manifest, its steps (each with a role, and gate: true on gate steps), the acceptance rules, the output kind, and how much evidence the project currently holds:

DATA
{
  "method": {
    "id": "good-services-audit",
    "name": "Good Services Audit",
    "phase": "measurement",
    "sources": [ { "article": "27" }, { "book": "01-this-is-service-design-doing", "chapter": "04" } ]
  },
  "steps": [
    { "role": "researcher", "instruction": "Score the live service against each heuristic in the good-services checklist, citing evidence for every score below target." },
    { "role": "critic", "instruction": "Reject any below-target score with no cited evidence.", "gate": true }
  ],
  "acceptance": [
    { "rule": "min-nodes", "min": 3 },
    { "rule": "min-evidence-per-node", "min": 1 },
    { "rule": "field-non-empty", "field": "theme" }
  ],
  "outputKind": "insight-set",
  "availableEvidence": 3
}

Failure modes, each exit 1: unknown method: <id>; project not found: <id>; and an input minimum that is not met — method "journey-from-transcripts" requires at least 3 evidence records; project has 0. Capture evidence with sd_evidence_add first.

sd_artifact_write

Writes the artifact a method produced. This is the gated write path: the candidate is judged against the method's acceptance rules before anything is persisted, and the outcome is always persisted honestly.

ArgumentTypeDescription
projectIdstring, requiredProject id
methodIdstring, requiredThe method that produced this artifact
titlestring, requiredHuman title, e.g. "Disruption Recovery Journey"
nodesarray, requiredEach node needs id, label, evidence: [{ "evidenceId": … }], and a fields object carrying the kind-specific columns
artifactIdstring, optionalSupply to update an existing artifact in place

Returns { "accepted", "status", "artifact", "failures" }. Three outcomes:

  1. Accepted, still draft. All acceptance rules pass, so accepted: true — but every method manifest declares reviewGate: critic, so a fresh write always lands as "status": "draft" until sd_review records a pass. failures is empty.
  2. Failed, persisted as draft. A rule failure persists the artifact as a draft with the check report attached (artifact.check.failures), so it can be repaired and rewritten. The response is accepted: false with the same failures at top level — it is not an error and exits 0:
DATA
{
  "accepted": false,
  "status": "draft",
  "artifact": {
    "id": "dd58b4cf12e0419e9b455c030e448e43",
    "kind": "journey-map",
    "title": "Current-state journey",
    "status": "draft",
    "check": {
      "pass": false,
      "failures": [
        { "rule": "min-nodes", "message": "expected at least 3 nodes, found 1" },
        { "rule": "min-evidence-per-node", "nodeId": "plan", "message": "node \"plan\" cites 0 evidence refs, needs 1" }
      ]
    },
    "[…]": "nodes, sources, methodId, timestamps trimmed"
  },
  "failures": [ "[…]" ]
}
  1. Never persisted. A dangling evidence ref — a node citing an evidenceId that does not exist in the project register — throws from the store and nothing is written. Malformed nodes also throw at the boundary: nodes[0]: "id" must be a non-empty string, nodes[0].evidence[0]: "evidenceId" must be a string, and similar.

Review tools

The review family is the Critic's seat on the write path. Verdicts are themselves artifacts, so the review loop replays from the store like any other work product.

sd_review

Records the review-gate verdict on an artifact.

ArgumentTypeDescription
projectIdstring, requiredProject id
artifactIdstring, requiredArtifact under review, from sd_artifact_list
verdictenum, requiredpass makes the artifact final-eligible; veto demotes it to draft
rowsarray, requiredDefect/proposal rows — see the schema below

Each row is { "rowKind", "severity", "message", "rule"?, "fix"?, "evidenceId"? } where rowKind is defect or proposal and severity is one of critical, high, medium, low. The enforced rules, each an exit-1 error when violated:

  • A defect row requires a non-empty fix — "a veto without a fix suggestion is incomplete".
  • A veto verdict requires at least one defect row: a veto requires at least one defect row — what is wrong, and what fixes it.
  • A pass verdict cannot carry defect rows: record them as proposals or veto.
  • A row citing evidenceId must resolve in the project evidence store.
  • The artifact must record a producing method whose manifest declares a review gate; an ungated method errors with method "<id>" declares no review gate — "<title>" is final-eligible on acceptance alone.

A veto returns "status": "draft" and writes the rows as a review-veto-log artifact linked to its target by reviewOf; a pass returns "status": "final" only when acceptance still passes against the live manifest. Both return { "status", "verdict", "artifact", "logArtifactId", "rowsWritten" }. Row ids (r1, r2, …) continue numbering across verdicts, so the log stays a log:

DATA
{
  "status": "draft",
  "verdict": "veto",
  "artifact": {
    "id": "7f9fefdc44f5469195106e739112f9ae",
    "kind": "journey-map",
    "title": "Drafty journey",
    "status": "draft",
    "review": { "verdict": "veto", "logArtifactId": "25500d7e4a634befb052cfa956bd4f2f" },
    "[…]": "nodes and check report trimmed"
  },
  "logArtifactId": "25500d7e4a634befb052cfa956bd4f2f",
  "rowsWritten": 2
}

sd_review_list

The review board: every artifact's gate state in one call, with acceptance re-run against the live manifest rather than trusted from the write-time check.

ArgumentTypeDescription
projectIdstring, requiredProject id
statusenum, optionaldraft or final

Returns { "artifacts": [...] } where each row carries artifactId, kind, title, status, methodId, reviewGate, verdict, logArtifactId, failures, and reviewOf when the row is a review log:

DATA
{
  "artifacts": [
    {
      "artifactId": "7f9fefdc44f5469195106e739112f9ae",
      "kind": "journey-map",
      "title": "Drafty journey",
      "status": "draft",
      "methodId": "journey-from-transcripts",
      "reviewGate": "critic",
      "verdict": "veto",
      "logArtifactId": "25500d7e4a634befb052cfa956bd4f2f",
      "failures": [ "node \"plan\" cites 0 evidence refs, needs 1", "[…]" ]
    },
    {
      "artifactId": "25500d7e4a634befb052cfa956bd4f2f",
      "kind": "review-veto-log",
      "title": "Review: Drafty journey",
      "status": "final",
      "methodId": null,
      "reviewGate": null,
      "verdict": null,
      "logArtifactId": null,
      "failures": [],
      "reviewOf": "7f9fefdc44f5469195106e739112f9ae"
    }
  ]
}

Failure mode: project not found: <id>.

Export tools

Exports are derived, client-shareable output written to the project's renders/ directory. Both tools are deterministic: the same project state exports the same bytes, because the cover timestamp is caller-supplied or derived from the stored data, never read from the clock.

sd_export_report

Exports a project report as a self-contained HTML document.

ArgumentTypeDescription
projectIdstring, requiredProject id
kindenum, requiredengagement, executive-summary, research-findings, artifact-dossier, traceability-matrix, method-log
generatedAtstring, optionalISO timestamp for the report cover; defaults to the project's latest recorded update

Returns { "path", "kind", "generatedAt", "bytes" }:

DATA
{
  "path": "/var/folders/[…]/ws/capture-meridian-201d0a1d/renders/report.executive-summary.html",
  "kind": "executive-summary",
  "generatedAt": "2026-08-19T00:02:11.208Z",
  "bytes": 2761
}

sd_export_artifact

Renders one artifact to a self-contained SVG diagram. The renderer is deterministic and kind-dispatched; the model never hand-writes diagram markup.

ArgumentTypeDescription
projectIdstring, requiredProject id
artifactIdstring, requiredArtifact id, from sd_artifact_list
widthnumber, optionalDiagram width in pixels; defaults to the renderer's standard width

Returns { "path", "kind", "title", "bytes" } with the file written to renders/<kind>.<id-prefix>.svg. Failure mode: artifact not found: <id>.

Knowledge tool

sd_knowledge

Queries the knowledge base — the method catalogue and the artifact-kind registry — in one call. With no filters it returns the full catalogue.

ArgumentTypeDescription
querystring, optionalCase-insensitive substring matched against ids and names
phaseenum, optionalRestrict methods to one lifecycle phase (artifact kinds are phase-free)
sourcestring, optionalProvenance filter: a book id (09-mapping-experiences), book/chapter (18/05), or article number (11)
typeenum, optionalmethods or kinds; default returns both

Returns { "methods": [...], "kinds": [...] } — methods with id, name, phase, produces, reviewGate, sources; kinds with kind, title, nodeLabel, sources:

DATA
{
  "methods": [
    {
      "id": "blueprint-to-backlog",
      "name": "Blueprint to Backlog",
      "phase": "delivery",
      "produces": "roadmap",
      "reviewGate": "critic",
      "sources": [ { "book": "03-service-design-from-insight-to-implementation", "chapter": "07" }, "[…]" ]
    },
    "[…]"
  ],
  "kinds": [
    {
      "kind": "service-blueprint",
      "title": "Service Blueprint",
      "nodeLabel": "step",
      "sources": [ { "book": "09-mapping-experiences", "chapter": "05" }, "[…]" ]
    }
  ]
}

Fact-check gate

sd_factcheck

Re-runs the deterministic fact-check over every artifact in a project. This is the replay path of the gated write path: nothing here trusts the state recorded at write time.

ArgumentTypeDescription
projectIdstring, requiredProject id

Three checks per artifact:

  1. Integrity — every evidence ref each node cites must resolve in the project register (store-enforced on write, re-asserted here; dangling refs are listed as node -> evidenceId).
  2. Acceptance — the producing method's machine-checkable rules, re-run against the live registry, so a tightened manifest re-gates previously written artifacts.
  3. Review gate — an artifact recorded as final whose method declares a review gate must carry a pass verdict. Drafts always pass this check; a failed final is not a draft.

Returns { "pass", "rows": [...] } with per-artifact integrity, acceptance, review, methodId, and methodResolution (recorded from the artifact's own methodId, inferred as a by-kind fallback for pre-provenance legacy files):

DATA
{
  "pass": false,
  "rows": [
    "[…]",
    {
      "artifactId": "dd58b4cf12e0419e9b455c030e448e43",
      "kind": "journey-map",
      "title": "Current-state journey",
      "status": "draft",
      "integrity": { "pass": true, "dangling": [] },
      "acceptance": {
        "pass": false,
        "failures": [ "expected at least 3 nodes, found 1", "node \"plan\" cites 0 evidence refs, needs 1" ]
      },
      "review": { "pass": true, "gate": "critic", "verdict": null },
      "methodId": "journey-from-transcripts",
      "methodResolution": "recorded"
    }
  ]
}

Exit code is 1 whenever pass is false — a green-looking report with a zero exit code cannot fail a build. On a clean project the same call prints "pass": true and exits 0.

The write path, end to end

The sixteen tools compose into one loop: capture evidence, pull the method contract, write through the acceptance gate, face the review gate, replay the fact-check.

For the transports these tools ride on, see the CLI and MCP server pages; for the artifact kinds they produce, see the artifact kind catalog.
