Engine concepts

Every ASD surface — the CLI, the MCP server, the Claude Code plugin, the harness workbench — is a different door into the same engine. This page is that engine's conceptual model, stated with the engine's own JSON. The contract-shaped examples below are illustrative unless they are explicitly tied to a disposable receipt; host/product workflows are not implied by the examples.

The model in five parts: evidence is captured into a content-addressed register; artifacts are typed JSON documents whose nodes cite that register; every write passes a machine-checked acceptance gate; a human-or-agent Critic verdict moves a gated artifact from draft to final; and a deterministic fact-check replays the whole chain on demand. Method manifests — the 74-entry canon of service design methods — declare which rules and which gate each artifact kind faces.

The evidence register

Evidence is the only thing an artifact is allowed to stand on. A row is captured with a source label, a kind, and a body:

TERMINAL
asd sd_evidence_add --projectId capture-meridian-201d0a1d --source call-821004 \
  --kind quote --body "Told to wait 15 min for next bus; nobody held the tram."
DATA
{
  "evidence": {
    "id": "c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174",
    "projectId": "capture-meridian-201d0a1d",
    "source": "call-821004",
    "kind": "quote",
    "body": "Told to wait 15 min for next bus; nobody held the tram.",
    "capturedAt": "2026-08-19T00:02:10.443Z"
  }
}

The id is the sha-256 content hash of (source, kind, body) — the register is content-addressed. Capture the same quote twice and you get the same id, byte-identically, across workspaces and machines; re-importing a transcript is idempotent by construction. The three kinds are the whole vocabulary:

  • quote — verbatim words from a person, with the source identifying where they were said.
  • telemetry — a measured figure from an instrument or extract (an AVL export, a rota system).
  • document — everything else written down: field notes, rosters, policy, closure notices.

There is no observation kind. Asking for one is a hard error, verbatim from the engine:

NOTE
asd sd_evidence_add: invalid arguments: "kind" must be one of ["quote","telemetry","document"]
running `asd help` shows usage

Exit code 1; nothing is written. Field observations go in as document with the observation in the body — the discipline is that the register stores records of what was seen and said, not interpretations typed as fact.

Artifacts: typed, evidence-cited, string-kinded

An artifact is a typed JSON document: a kind (a string id like journey-map or stakeholder-map, never a number), a title, a schemaVersion, the methodId that produced it, the method's sources (book/article citations), and nodes — each node carrying id, label, fields (kind-specific data like emotion and touchpoint), and evidence, a list of refs into the register:

DATA
{
  "id": "transfer",
  "label": "Missed connection",
  "evidence": [
    { "evidenceId": "c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174" },
    { "evidenceId": "b38cf37fef5b8460e82bad3592964293233aeb627ee291e9f7a64e5007c4c586" }
  ],
  "fields": { "emotion": "1", "touchpoint": "transfer" }
}

A dangling evidence ref — an id not in the register — is a hard error at write time; integrity is structural, not advisory. The runtime currently registers 38 artifact-kind contracts. The practice-facing catalog is a separate 39-row vocabulary: aliases such as insight-register do not create another runtime kind, ten support kinds are registry-only, and eight rows remain pending and non-executable. review-veto-log is the administrative Critic control record. The catalog's per-kind typed runtime schema expansion remains a Phase 2 boundary; see the artifact reference for the exact split and lists.

The acceptance gate and the draft/final lifecycle

Every sd_artifact_write runs the producing method's acceptance rules before the artifact's status is decided. The vocabulary is small and declarative:

  • min-nodes — the artifact must have at least N nodes.
  • min-evidence-per-node — every node must cite at least N register rows.
  • field-non-empty — a named field must be present and not a deny-listed placeholder (unknown, tbd, n/a).

The lifecycle is the part newcomers get wrong, so here it is exactly, with the engine's own output. A write that fails its rules is not refused from the store — it persists as status: draft with the check attached:

DATA
{
  "accepted": false,
  "status": "draft",
  "artifact": {
    "id": "dd58b4cf12e0419e9b455c030e448e43",
    "kind": "journey-map",
    […projectId, title, methodId, sources, nodes, timestamps…]
    "status": "draft",
    "check": {
      "pass": false,
      "failures": [
        { "rule": "min-nodes", "message": "expected at least 3 nodes, found 1" },
        { "rule": "min-evidence-per-node", "nodeId": "plan",
          "message": "node \"plan\" cites 0 evidence refs, needs 1" }
      ]
    }
  },
  "failures": [ […the same list, repeated top-level…] ]
}

The rejection is itself auditable: sd_artifact_list shows the draft with its failures. A failing draft is never final and never exportable; the fix is to rewrite the same artifact in place via --artifactId, at which point an accepting write returns "accepted": true, "status": "draft", "failures": []. Accepted is still draft. The lifecycle in one diagram:

The review verdict is the only path to final, and it exists only when the method manifest declares a reviewGate (the gated methods declare critic). A pass must still carry a valid review-row payload; use an evidence-cited proposal when there is no defect to record. A representative pass response is:

DATA
{ "status": "final", "verdict": "pass",
  "logArtifactId": "6e5b2de08e6b42f1b5ad8c89e39240cd", "rowsWritten": 1,
  "rows": [{ "rowKind": "proposal", "severity": "low",
    "rule": "source-diversity",
    "message": "Keep the roster-constraint source visible in the transfer decision",
    "evidenceId": "ebc691cacc31cf5fb2db2f3c8347e5e085690a0971b0d3ca4d104a6e150fdc6a" }] }

The proposal row is not a defect and therefore does not block promotion, but its evidenceId still resolves to the project register. An empty --rows '[]' pass is invalid.

A veto keeps (or returns) the artifact at draft and writes the verdict as data: a separate review-veto-log artifact, itself status: final, linked to the candidate via reviewOf. A representative veto response:

DATA
{
  "status": "draft",
  "verdict": "veto",
  "artifact": {
    "id": "7f9fefdc44f5469195106e739112f9ae",
    "kind": "journey-map",
    […projectId, title, methodId, sources, nodes, timestamps…]
    "status": "draft",
    "review": { "verdict": "veto", "logArtifactId": "25500d7e4a634befb052cfa956bd4f2f" }
  },
  "logArtifactId": "25500d7e4a634befb052cfa956bd4f2f",
  "rowsWritten": 2
}

Each veto row lands as a node in the log artifact, carrying the full row schema — {rowKind: defect|proposal, severity: critical|high|medium|low, rule, message, fix, evidenceId?} with fix required on defects:

DATA
{
  "id": "r1",
  "fields": {
    "rowKind": "defect",
    "severity": "high",
    "message": "All three nodes cite zero evidence rows; the acceptance gate cannot pass until every node cites the register",
    "rule": "min-evidence-per-node",
    "fix": "Re-derive each node from the register with verbatim quotes attached"
  }
}

(The node's label is the message truncated; its evidence list is empty here.)

The review board — sd_review_list — shows both artifacts side by side: the candidate with verdict: veto and its logArtifactId, and the log with its reviewOf. Remediation is the same loop as before: rewrite by --artifactId, re-review, and a pass reuses the same log artifact so the veto rows remain the record.

The fact-check triad

sd_factcheck is the deterministic replay: no model, no judgment, just the store re-verified. For every artifact in the project it re-runs three checks — integrity (every evidence ref resolves), acceptance (the artifact passes its method's rules as they stand today), and review (a gated artifact that claims finality has the verdict to back it). It reports per-artifact rows and a top-level pass, and its exit code is the contract: 0 when everything holds, 1 on any failure. A representative all-pass row set, after a pass verdict:

DATA
{
  "pass": true,
  "rows": [
    {
      "artifactId": "7bfbea7ad1f34940bd46a6a66c7eaa22",
      "kind": "journey-map",
      "status": "final",
      "integrity": { "pass": true, "dangling": [] },
      "acceptance": { "pass": true },
      "review": { "pass": true, "gate": "critic", "verdict": "pass" },
      "methodId": "journey-from-transcripts",
      "methodResolution": "recorded"
    },
    {
      "artifactId": "6e5b2de08e6b42f1b5ad8c89e39240cd",
      "kind": "review-veto-log",
      "status": "final",
      "integrity": { "pass": true, "dangling": [] },
      "acceptance": { "pass": true },
      "review": { "pass": true, "gate": null, "verdict": null },
      "methodId": null,
      "methodResolution": "inferred"
    }
  ]
}

Exit code 0.

With a failing draft still in the project the same command prints "pass": false with the failing rule named in the row, and exits 1 — which is what makes it CI-usable, as the CI tutorial shows.

Exports and reports

Final artifacts render to files under the project's renders/ directory. sd_export_artifact renders one artifact to SVG, named by kind and id prefix; sd_export_report generates one of six HTML report kinds over the whole project:

DATA
{ "path": "…/capture-meridian-953950ca/renders/journey-map.7bfbea7a.svg",
  "kind": "journey-map", "title": "Current-state", "bytes": 3811 }
DATA
{ "path": "[…]/capture-meridian-201d0a1d/renders/report.executive-summary.html",
  "kind": "executive-summary", "generatedAt": "2026-08-19T00:02:11.208Z", "bytes": 2761 }

The six report kinds are engagement, executive-summary, research-findings, artifact-dossier, traceability-matrix, and method-log. Where the Studio profile is available, its Reports tab offers the same six kinds; this page does not claim a live workbench host run.

Method manifests as data

The knowledge layer is not prose the model improvises from; it is 80 method manifests as JSON, every one executable via sd_method_run, which returns the method's machine contract. A representative contract shape, matching the engine's method manifest:

DATA
{
  "method": {
    "id": "good-services-audit",
    "name": "Good Services Audit",
    "phase": "measurement",
    "sources": [
      { "article": "27" },
      { "book": "01-this-is-service-design-doing", "chapter": "04" }
    ]
  },
  "steps": [
    { "role": "researcher",
      "instruction": "Score the live service against each heuristic in the good-services checklist, citing evidence for every score below target." },
    { "role": "critic",
      "instruction": "Reject any below-target score with no cited evidence.",
      "gate": true }
  ],
  "acceptance": [
    { "rule": "min-nodes", "min": 3 },
    { "rule": "min-evidence-per-node", "min": 1 },
    { "rule": "field-non-empty", "field": "theme" }
  ],
  "outputKind": "insight-set",
  "availableEvidence": 3
}

Read it as the whole platform in one object: role-assigned steps with a gated Critic step, the acceptance rules the write will face, the artifact kind the method produces, and the provenance every method cites (books and articles of the series, resolvable to real chapters). sd_method_list enumerates the manifests by phase or output kind; sd_knowledge searches them by keyword and returns matching methods and kinds together; the skills reference lists the 80 SKILL.md SOPs generated one-per-manifest.

What stays human

The engine enforces evidence, structure, and status. It does not decide. Phase gates are the human designer's call — pass, redirect, or kill — made on the review board with the fact-check as the machine's testimony; there is intentionally no phase-gate-decision artifact to hide that call behind. Which insights survive synthesis, whether a finding is politically feasible, what ships in the report: the platform holds the evidence and the traceability, and the call stays with the designer.
