Host packs and the compiler

Every delivery surface in platform/packs/ is generated. The canonical tree — platform/agents/, platform/skills/, platform/templates/ — is never forked. platform/compiler/emit-packs.mjs copies it into per-host layouts and authors the per-target wrappers (READMEs, config files, prompts) as data inside the emitter, so the whole pack set regenerates deterministically from one source.

The emitter regenerates manifest.json first (so packs never emit from a stale inventory) and refuses to proceed unless it counts exactly ten agents. Then it writes each pack's tree: the shared payloads (role bodies, skill files, vendored server) plus the host-specific wrapper. emit-packs.test.mjs asserts byte-identical regeneration and inventory counts.

The determinism contract

The emitter follows the same rules as the compiler: sorted traversal, no timestamps, no absolute paths, LF endings. The vendored tsdown bundle is byte-identical across runs on the same suite tree. Because the packs are committed artifacts, CI gates drift directly:

TERMINAL
npm run check:packs-drift
# = node platform/compiler/compile.mjs \
# && node platform/compiler/emit-packs.mjs \
# && git diff --exit-code platform/packs

If anyone edits a pack by hand, or changes the canonical tree without re-emitting, the regenerated tree differs and the diff exits non-zero. The fix is always to change the canonical source or the emitter, never the emitted copy.

Why every pack vendors the MCP server

Packs that wire MCP — claude-code, codex, kimi, mcp, opencode — each ship a self-contained copy of the asd-mcp server under mcp/: bin/server.mjs is a tsdown bundle with the entire dependency graph inlined, data/ is the knowledge corpus the server reads relative to its own URL, and a minimal package.json exists only because a bundled dependency resolves its version through createRequire. The emitter self-checks the bundle: any non-node: import fails the emit.

The result is one canonical invocation everywhere, documented per pack:

TERMINAL
node <pack-root>/mcp/bin/server.mjs

How <pack-root> is spelled differs per host — ${CLAUDE_PLUGIN_ROOT} for the Claude Code plugin, project-relative for hosts that start servers from the project root — but the server never needs npm install, a PATH entry, or a sibling suite checkout. Building the bundle requires the suite's own tsdown, so emitting packs requires pnpm --dir suite install first; the emitter fails loud with that instruction when the suite is not installed.

The Claude Code pack has its own page. The rest, with the install snippet each README actually ships:

opencode

TERMINAL
cp -R packs/opencode/agent packs/opencode/mcp /path/to/project/
# merge opencode.json with the project's existing config

Agent files carry YAML frontmatter (name, description) and the full role body. opencode.json starts the server as node mcp/bin/server.mjs relative to the project root; if your OpenCode version resolves it from another working directory, absolutize the path in place.

codex

TERMINAL
cp packs/codex/AGENTS.md /path/to/project/
cp -R packs/codex/mcp /path/to/project/
# merge .codex/config.toml MCP block into the user/global config

The config block the pack ships:

NOTE
# asd-mcp wiring (merge into your Codex config)
[mcp_servers.asd]
command = "node"
args = ["mcp/bin/server.mjs"]
# ASD_WORKSPACE left unset — the server defaults to ~/.asd/projects

AGENTS.md carries the project conventions: quotes are verbatim, dangling evidence refs are hard errors, acceptance rules are machine-checked, no fabricated evidence.

kimi

TERMINAL
cd /path/to/project
mkdir -p .kimi-code
cp -R packs/kimi/agents packs/kimi/skills packs/kimi/mcp packs/kimi/mcp.json .kimi-code/
cat packs/kimi/AGENTS.md >> AGENTS.md   # merge with any existing conventions

The full mirror: ten roles as Kimi custom agents (selectable with kimi --agent <role>), the 74 skills, the vendored server, and the conventions file. Project-level MCP servers require trusting the folder at Kimi's workspace-trust prompt; a user-level install under ~/.kimi-code/ also works, with the server path absolutized.

grok

Grok consumes the platform through the MCP server; the pack ships only the ten role system prompts as shareable text (prompts/<role>.md) for model-only use:

NOTE
1. Place the mcp pack and start the vendored server with the canonical
   invocation `node <mcp-pack>/mcp/bin/server.mjs` (no PATH entry needed).
2. Configure the MCP client with the mcp pack's `asd-mcp.json`.
3. Load the relevant role prompt from `prompts/` for a given phase.

agy

The Critic role as an adversarial review session for AGY. review-session.md is the review contract used by the platform's own milestone gates (herdr-review + AGY, reports in .reviews/):

TERMINAL
agy --file review-session.md   # or herdr-review --tab and feed the contract

pi and omp

The two neutral packs ship the same Eve-style tree — agents/<role>/instructions.md plus skills/<skill>/SKILL.md — emitted through one code path so they can never drift apart. omp's README points the Oh My Pi harness at the pack directory directly. pi's README is deliberately honest:

UNVERIFIED by design: Pi plugin layout is checked at the M4 gate against the then-current Pi docs; nothing here claims a Pi plugin format it does not have.

mcp, cli, dsh

Three special forms. The mcp pack is the standalone server plus its client config and a PATH-optional launcher shim — documented on the MCP page. The cli pack is the asd terminal launcher over the same engine — documented on the CLI page. The dsh pack is a profile pointer: the suite itself (@asd/core, @asd/engine, @asd/knowledge, @asd/agents, @asd/runtime) is the DSH plugin, and the README describes loading it into a DSH profile and wiring each method step's role to the corresponding platform agent. Method steps carry role + gate; @asd/agents validates every manifest against the ten-role registry at apply time.

Format pins are load-bearing

Every pack README records the exact host version or spec revision it was verified against, because upstream layouts change without notice. A pack whose format has not been re-verified says so in its own README — the drift gate keeps the bytes deterministic, and the pins keep the bytes honest.
