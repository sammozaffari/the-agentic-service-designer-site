Skills reference

A skill is the portable, prose form of a method; a method manifest is its machine form. The platform keeps both, generated in one direction only: the manifest is the source of truth, the SKILL.md is its deterministic rendering, and the engine gates artifacts against the manifest — never against the prose.

The pipeline: manifest to SKILL.md

Every method lives as a JSON manifest at suite/packages/knowledge/data/methods/<id>.json: id, name, phase, provenance sources, input minimums, output kind, role-attributed steps, machine-checkable acceptance rules, evidence rules, and the review gate. platform/compiler/generate-skills.mjs renders each manifest into platform/skills/generated/<id>/SKILL.md — deterministically, so the generated tree is never edited by hand; you edit the manifest or the generator.

A generated SKILL.md carries a fixed frontmatter — name, description (when to use), provenance (book/article refs, mandatory), inputs, output, review_gate — then a fixed body: when-to-use, provenance, phase, inputs, output, role-attributed steps with gate flags, acceptance rules, evidence rules, human flags. Real frontmatter from generated/journey-from-transcripts/SKILL.md:

CONFIG
---
name: "journey-from-transcripts"
description: "Journey Mapping from Transcripts turns call or interview transcripts into journey-map output during the synthesis phase; needs Critic sign-off before the artifact is final."
provenance: ["article 09","09-mapping-experiences ch.04"]
inputs: ["evidence-set"]
output: "journey-map"
review_gate: "critic"
---

The authorship rule for every skill, generated or authored: no source, no entry — provenance is mandatory and prose-only acceptance criteria do not exist.

Flagship vs generated

platform/skills/flagship/ holds hand-authored, prose-deep skills for methods that need judgment guidance beyond the manifest — the pattern for future authored skills. The tier currently contains one skill, service-blueprinting, whose description runs to a full when-to-use / when-not-to-use paragraph where the generated twin carries one sentence.

The two tiers coexist by a flagship-wins rule: the compiler walks flagship/ before generated/ and takes first-write-wins per skill id, so a hand-authored flagship replaces its generated twin in every emitted pack. The pack manifest keeps the two counts distinctly named so neither can be misread as the other: skillSources: 81 (every SKILL.md on disk: 80 generated + 1 flagship) against skillsShipped: 80 (what actually lands in a pack after the substitution).

A third source feeds the library over time: SOPs mined from the article corpus (article 29 alone yielded 31 candidates, 26 accepted) become candidate skills that the Librarian files through the registry path.

Every skill is executable

These are not prompt fragments. All 80 manifests are registered in the engine and executable via sd_method_run, which returns the steps, acceptance rules, output kind, and current evidence count; the resulting artifact is written through sd_artifact_write and checked against the manifest's acceptance rules. Verified against the registry: all 80 manifests declare non-empty acceptance rules and reviewGate: "critic" — every artifact any skill produces is draft until the Critic passes it.

How skills collaborate with roles and tools

The manifest's steps are the collaboration contract. Each step names the responsible role, its instruction, and whether it is a gate. A host can ask the role prompt to perform that step, but the runtime remains the authority:

  1. sd_method_run returns the SOP and its role assignments.
  2. The assigned role gathers or queries evidence with the evidence tools.
  3. The role writes the declared output kind through sd_artifact_write.
  4. The Critic role calls sd_review; proposal rows on a pass must cite evidence, while veto defects require a fix.
  5. The Orchestrator records a typed handoff or plan when the next role needs a durable condition; an artifact pointer must resolve in the project.
  6. sd_factcheck replays integrity, acceptance, and review before the human phase gate.

The 29-tool runtime also exposes templates, schemas, canvas links, exports, and phase records. These are shared by the CLI, MCP, and DSH surfaces. ACP is asd-acp/1 record-only/fail-closed; a skill or role prompt never implies that the host spawned another agent. Host packs carry the same 80 skills in native layouts, but host loading is separately evidenced per target.

The twelve-skill canon

The article series exercises a twelve-method canon as its gated spine — the methods whose contracts the engagements pull with sd_method_run and whose acceptance rules the engine re-checks on every write (article 31 §3.3). The engine's registry gates writes for all 80; these twelve are the canon the diary leans on:

contextual-inquiry, stakeholder-mapping, transcript-mining (research); affinity-diagramming, behavioural-personas, journey-from-transcripts, mental-model-alignment, ecosystem-value-mapping, service-blueprinting (synthesis); orchestration-canvas (ideation); evidence-gated-blueprint (delivery); good-services-audit (measurement).

The remaining 68 skills are full SOPs with the same generated shape and the same gates; several appear in the articles' phase logs.
