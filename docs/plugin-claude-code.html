The Claude Code plugin

platform/packs/claude-code is the platform's reference surface: the ten role agents as native Claude Code subagents, the 74 method skills as Claude skills, the /asd orchestrator command, and the engine MCP server vendored inside the pack — installable as a real Claude Code plugin, with nothing on PATH and no sibling checkout required.

Install (plugin)

From the pack README, verbatim:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The marketplace manifest is platform/packs/.claude-plugin/marketplace.json; the plugin manifest is the pack's .claude-plugin/plugin.json:

DATA
{
  "name": "asd",
  "version": "0.1.0",
  "description": "Service Design Agent Platform: 10 role agents, the method-skill library, the /asd orchestrator command, and a self-contained vendored asd-mcp engine server.",
  "author": {
    "name": "Agentic Service Designer"
  }
}

Install (manual copy)

For a project that does not use the plugin mechanism, the README's manual variant drops the same tree into place:

TERMINAL
P=packs/claude-code; T=/path/to/project
mkdir -p "$T/.claude"
cp -R "$P/agents" "$P/skills" "$P/commands" "$T/.claude/"
cp -R "$P/mcp" "$P/.mcp.json" "$T/"
sed -i '' 's|${CLAUDE_PLUGIN_ROOT}|.|' "$T/.mcp.json"

Project-root .mcp.json servers start from the project directory, so . resolves the vendored server copied next to it.

The MCP wiring is the whole point of the vendored server. The plugin-root .mcp.json is loaded automatically for installed plugins:

DATA
{
  "mcpServers": {
    "asd": {
      "command": "node",
      "args": [
        "${CLAUDE_PLUGIN_ROOT}/mcp/bin/server.mjs"
      ]
    }
  }
}

${CLAUDE_PLUGIN_ROOT} resolves inside the installed plugin, so the server needs no PATH entry and no sibling suite checkout — no npm install, no symlink into /usr/local/bin. The bundle inlines its entire dependency graph and reads its knowledge corpus from mcp/data/ relative to its own URL. The MCP page covers the server's tools, resources, and prompts; the host-packs page explains why every pack vendors the same copy.

The /asd session flow

/asd runs an engagement. From commands/asd.md: it plans from the current brief, dispatches the role agents in platform order (research → synthesis → ideation → prototyping → delivery → measurement), grounds every artifact in the project evidence register with machine-checked integrity and acceptance rules, and presents the phase-gate report for the human designer.

In practice the designer drives the loop directly: prompt → agent → skill → tool call → artifact gate → Critic verdict → fact-check. Article 31's public-transport runlog (Riding the Current) executed the full arc on this exact pack, and its invocations are the realistic shape of a session:

NOTE
@researcher run the contextual-inquiry skill for lighthouse-transit: plan
the research (ride-alongs on 14 routes incl. night shift, 32 commuter
interviews, 6 drivers), then add every field note and every verbatim
quote to the project evidence register via sd_evidence_add.
NOTE
@mapper run journey-from-transcripts over the register and write the
current-state journey-map artifact for lighthouse-transit.
@critic review the journey-map before it can go final.
NOTE
@measurer build the kpi-tree from the four success criteria with
kpi-tree-design: each row names its driver, experience link, business
link, baseline, and source.
@presenter assemble the executive report from final artifacts only.
@librarian produce the handover pack with full provenance.

Each @role dispatch lands on one of the ten subagent files in agents/. The roles in platform order:

RoleDispatchOwns
Orchestrator@orchestratorPlans the engagement, dispatches roles, advances phase gates, owns human handoffs
Researcher@researcherGathers evidence into the project register; verbatim quotes; provenance on every row
Synthesizer@synthesizerPattern-finds across evidence; insight sets and themes; divergence/convergence
Mapper@mapperMapping methods: journey, blueprint, ecosystem, stakeholder, mental model. Nodes cite evidence; never hand-draws Mermaid
Ideator@ideatorGenerates options against the insight set; never resolves framing alone
Prototyper@prototyperBuilds and tests prototypes; evidence comes from test runs, not assumptions
Measurer@measurerKPI chains, audits, maturity, evaluation; numbers trace to evidence
Critic@criticReviews artifacts with evidence-cited defect/proposal rows; verdicts are artifacts
Presenter@presenterExecutive report and deck assembly from final artifacts; adds no new evidence
Librarian@librarianCorpus to manifest/skill drift; provenance; knowledge sync; case-study citations

Behind every dispatch the agents call the same sixteen sd_* engine tools over the vendored MCP server — the identical surface the CLI exposes in a terminal. Skills are the SOP layer in between: 74 readable SKILL.md files, one per method manifest, and every manifest is executable via sd_method_run, which returns the method's steps, role assignments, acceptance rules, and output kind.

Skills and the method canon

Each skill is a plain-text SOP: who does what, in what order, with which evidence discipline, and the acceptance gate the artifact write will face. Twelve of the 74 carry the article series' engagement spine — affinity-diagramming, behavioural-personas, contextual-inquiry, ecosystem-value-mapping, evidence-gated-blueprint, good-services-audit, journey-from-transcripts, mental-model-alignment, orchestration-canvas, service-blueprinting, stakeholder-mapping, transcript-mining — but every one of the 74 is a real method manifest with the same machine-checked contract, and sd_method_list enumerates them by phase or by the artifact kind they produce. One skill is hand-authored: the flagship service-blueprinting, which replaces its generated twin in the pack. sd_knowledge --query blueprint is the discovery path when you know the artifact you want but not the method — it answers with the methods that produce it and the provenance (books, chapters, articles) each method cites.

The enforcement boundary

The pack's contract splits machine-forced guarantees from human judgment, and the split is worth stating exactly.

Machine-forced, on every run:

  • Evidence resolution. Every artifact node cites evidence ids from the project register; a dangling ref is a hard error. Evidence rows are content-addressed — the id is the sha-256 of source kind body, so the same quote added twice returns the same id.
  • Acceptance rules. Each method manifest declares machine-checkable rules (minimum nodes, minimum evidence refs per node, non-empty fields with deny-listed values like unknown/tbd/n/a). A failing sd_artifact_write is not refused — it persists the artifact as status: draft with check.failures attached, so the rejection itself is auditable on disk.
  • Draft/final status. Artifacts are born draft. Only a Critic verdict moves a gated artifact to final.
  • The review gate. A method manifest declaring reviewGate: critic makes the artifact final-eligible only after a Critic verdict. sd_review --verdict pass flips status to final; --verdict veto keeps the artifact draft and writes a separate, final review-veto-log artifact linked to the candidate via reviewOf, one node per row: {rowKind: defect|proposal, severity: critical|high|medium|low, rule, message, fix, evidenceId?}, with fix required on defects.
  • The fact-check. sd_factcheck replays integrity, acceptance, and review state across every artifact in the project, reports a top-level pass, and exits 1 on any failure — a green-looking report with a zero exit code cannot fail a build, so the gate inverts exactly that case.

Human judgment, always:

  • Phase gates. The Orchestrator presents the phase-gate report; the human designer passes, redirects, or kills. No automated veto runs on the write path — the gate is a decision, not a script.
  • Pricing, scope, and editorial calls. Which personas survive clustering, fare capping versus flat fare, whether a finding is politically feasible — the platform holds the evidence and the traceability; the call stays the designer's.

The failure modes are deliberately loud. A rejected write, a vetoed review, and a failing fact-check all leave typed artifacts on disk with the failure rows attached — the platform's answer to "trust me" is "audit the files."
