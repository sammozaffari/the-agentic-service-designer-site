The CLI

asd is the same engine the MCP server exposes, in a terminal. One command per engine tool, parsed generically from each tool's JSON-schema parameters — the CLI surface cannot drift from the suite's tool definitions, because it is generated from the same builders, names, descriptions, and validation.

Install and the shim

The pack at platform/packs/cli ships one file, the asd launcher. It prefers a standalone @asd/runtime bin when one is installed and otherwise resolves the built suite relative to the pack — the whole shim, verbatim:

TERMINAL
#!/usr/bin/env bash
# asd launcher (pack convenience). Prefers the standalone @asd/runtime bin
# when installed; otherwise resolves the suite checkout relative to this pack.
if command -v asd >/dev/null 2>&1 && [ "$(command -v asd)" != "$0" ]; then exec asd "$@"; fi
ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
CLI="$ROOT/../../suite/packages/runtime/lib/cli.mjs"
if [ ! -f "$CLI" ]; then
  echo "asd: runtime not found — run \`cd suite && pnpm install && pnpm --filter @asd/runtime build\` in the repo, or \`npm i -g @asd/runtime\` for a standalone install" >&2
  exit 1
fi
exec node "$CLI" "$@"

From a repo checkout, build the runtime and go:

TERMINAL
cd suite && pnpm install && pnpm --filter @asd/runtime build

Usage

NOTE
asd <tool-name> [--flag value] [--flag=value] [--json '{"...": ...}']
asd help

The sixteen tools are exactly the MCP server's: sd_project_list, sd_project_create, sd_project_open, sd_evidence_add, sd_evidence_query, sd_artifact_list, sd_artifact_get, sd_method_list, sd_method_run, sd_artifact_write, sd_review, sd_review_list, sd_export_report, sd_export_artifact, sd_knowledge, sd_factcheck. asd help lists each with its parameter names, straight from the schemas (trimmed):

NOTE
usage: asd <tool> [--flag value ...]

tools:
  sd_project_list
  sd_project_create      name, client, sector, service, phase
  sd_project_open        projectId
  sd_evidence_add        projectId, source, kind, body
  […]
  sd_review              projectId, artifactId, verdict, rows
  sd_review_list         projectId, status
  […]
  sd_factcheck           projectId

Dashed aliases are equivalent to the sd_* names — strip the prefix, normalize - to _: asd project-create is asd sd_project_create, asd evidence-add is asd sd_evidence_add, and so on. Both spellings appear throughout the platform's own runlogs.

Flags follow three forms: --flag value, --flag=value, and bare booleans — a flag whose schema type is boolean passed with no value means true and never consumes the next token. Parameters whose schema type is object or array are JSON-typed: pass them inline and the CLI parses them as JSON, failing loudly on invalid input:

TERMINAL
asd artifact-write --projectId <id> --methodId journey-from-transcripts \
  --title "Current-state journey" \
  --nodes '[{"id":"plan","label":"Plan","kind":"step","fields":{"emotion":"3","touchpoint":"website"},"evidence":[]}]'

Unknown flags, missing required flags, and positional arguments are usage errors — the message names what went wrong and points at asd help:

NOTE
asd sd_evidence_add: invalid arguments: "kind" must be one of ["quote","telemetry","document"]
running `asd help` shows usage

The workspace

Every project lives on disk under the workspace root. ASD_WORKSPACE overrides it; the default, resolved in suite/packages/runtime/src/config.ts, is ~/.asd/projects:

TERMINAL
export ASD_WORKSPACE=/tmp/asd-ws   # default: ~/.asd/projects

Older pack text named ~/sd-projects as the default. That is stale — the engine resolves ~/.asd/projects. Check config.ts, not memory.

A project directory after a real session (evidence added, one artifact written and reviewed to final, one SVG exported):

NOTE
~/.asd/projects/capture-meridian-953950ca/artifacts/journey-map.current-state.7bfbea7a.json
~/.asd/projects/capture-meridian-953950ca/artifacts/review-veto-log.review-current-state.6e5b2de0.json
~/.asd/projects/capture-meridian-953950ca/renders/journey-map.7bfbea7a.svg
~/.asd/projects/capture-meridian-953950ca/evidence/index.json
~/.asd/projects/capture-meridian-953950ca/project.json
~/.asd/projects/capture-meridian-953950ca/sops/

The layout is flat and auditable: project.json is the project record; evidence/index.json is the whole register; artifacts are one JSON file each, named <kind>.<title-slug>.<id-prefix>.json; renders/ holds exported reports and SVGs; sops/ is scaffolded empty (only a .gitkeep in the captured tree). Nothing is hidden in a database — the create tool's own description says it plainly: "a directory holding project.json plus evidence/, artifacts/, renders/ and sops/. Files are the record of truth."

Scripting patterns

The output is Markdown with a JSON fence, so scripts parse the fence, not the prose.

Capturing ids. Evidence ids are content-addressed — the sha-256 of source kind body — so an id is stable across projects and re-adding the same row returns the same id. Capture them as you add rows:

TERMINAL
EVID=$(asd evidence-add --projectId "$PID" --source call-821004 --kind quote \
  --body "Told to wait 15 min for next bus; nobody held the tram." \
  | sed -n '/```json/,/```/p' | sed '1d;$d' | jq -r '.evidence.id')

In-place rewrites. A write that fails acceptance persists as a draft with check.failures; pass the same id back with --artifactId to remediate that draft instead of creating a sibling:

TERMINAL
ART=$(asd artifact-write --projectId "$PID" --methodId journey-from-transcripts \
  --title "Current-state" --nodes "$NODES" \
  | sed -n '/```json/,/```/p' | sed '1d;$d' | jq -r '.artifact.id')
# fix the nodes, cite the missing evidence, then:
asd artifact-write --projectId "$PID" --methodId journey-from-transcripts \
  --title "Current-state" --nodes "$NODES_FIXED" --artifactId "$ART"

The review loop. sd_review --verdict pass flips a gated artifact to final; --verdict veto keeps it draft and writes a final review-veto-log artifact (rows: rowKind defect/proposal, severity critical/high/medium/low, rule, message, fix required on defects, optional evidenceId). sd_review_list is the board you poll to see what is still gated:

TERMINAL
asd review --projectId "$PID" --artifactId "$ART" --verdict veto \
  --rows '[{"rowKind":"defect","severity":"high","rule":"min-evidence-per-node","message":"node cites 0 evidence refs","fix":"Re-derive the node from the register with verbatim quotes attached"}]'

Exit codes, built for CI

The contract from src/cli.ts: exit code is 1 when the tool errors — and also when a gate tool completes with a failing verdict. sd_factcheck reporting "pass": false exits 1 even though the call succeeded, because a green-looking report with a zero exit code cannot fail a build. That makes the fact-check a one-line CI gate:

TERMINAL
#!/usr/bin/env bash
set -euo pipefail
export ASD_WORKSPACE="$CI_WORKSPACE"
asd factcheck --projectId "$PID"   # exit 1 if any artifact fails integrity, acceptance, or review

A failing run prints the per-artifact rows and exits 1:

DATA
{
  "pass": false,
  "rows": [
    […one passing draft row…]
    {
      "artifactId": "dd58b4cf12e0419e9b455c030e448e43",
      "kind": "journey-map",
      "title": "Current-state journey",
      "status": "draft",
      "integrity": { "pass": true, "dangling": [] },
      "acceptance": {
        "pass": false,
        "failures": [
          "expected at least 3 nodes, found 1",
          "node \"plan\" cites 0 evidence refs, needs 1"
        ]
      },
      "review": { "pass": true, "gate": "critic", "verdict": null },
      "methodId": "journey-from-transcripts",
      "methodResolution": "recorded"
    }
  ]
}
NOTE
factcheck exit code: 1

Each row replays three independent checks — referential integrity (no dangling evidence refs), the method's acceptance rules, and the review gate — so a pipeline can fail on exactly the layer that broke.

Format pin

Node ≥ 20; lib/ emitted by tsdown 0.22; package 0.1.0. The same sixteen tools over stdio instead of a terminal: the MCP server. The same engine behind role agents and skills: the Claude Code plugin and the other host packs.
