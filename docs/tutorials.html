Tutorials

Three tutorials, three surfaces, one engine. The CLI lifecycle is a disposable, pack-local workflow; the Claude Code section is an illustrative prompt flow; and the CI section describes the deterministic gate. Outputs are representative contract-shaped examples unless a disposable receipt is named. These tutorials do not prove a native host installation, BUZZ/DSH live workflow, or ACP spawn. Host execution is unverified in this documentation release. The concepts are in Engine concepts; this page is the doing.

Your first gated artifact in ten minutes (CLI)

The whole lifecycle in a shell: project → evidence (including a deliberate kind rejection) → a failing write that persists as a draft → in-place remediation → a Critic veto → remediation → a pass → the deterministic fact-check → renders. You need the suite built and the asd shim from platform/packs/cli — see the CLI page. Work in a scratch workspace so nothing touches real projects:

TERMINAL
export ASD_WORKSPACE=/tmp/asd-docs-w3-t1
ASD=platform/packs/cli/asd    # from the repo root

Create the engagement:

TERMINAL
$ASD sd_project_create --name docs-w3-demo --client "Fictional composite" \
  --sector public-transport --service "commuter journeys" --phase discover
DATA
{
  "project": {
    "projectId": "docs-w3-demo-01f2de9f",
    "name": "docs-w3-demo",
    "client": "Fictional composite",
    "sector": "public-transport",
    "service": "commuter journeys",
    "phase": "discover",
    […createdAt / updatedAt timestamps…]
  }
}

Capture four evidence rows — two quotes, a document, a telemetry figure:

TERMINAL
ID=docs-w3-demo-01f2de9f
$ASD sd_evidence_add --projectId $ID --source call-821004 --kind quote \
  --body "Told to wait 15 min for next bus; nobody held the tram."
$ASD sd_evidence_add --projectId $ID --source call-821020 --kind quote \
  --body "Road closed since 6am; no sign, no message."
$ASD sd_evidence_add --projectId $ID --source rosters-07 --kind document \
  --body "Eleven routes cannot hold a 3-minute connection under current roster rules."
$ASD sd_evidence_add --projectId $ID --source avl-extract-2025-11 --kind telemetry \
  --body "Route 41 weekday OTP 71 percent; peak-shoulder misses cluster 16:00-19:00."
DATA
{ "evidence": { "id": "c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174",
  "projectId": "docs-w3-demo-01f2de9f", "source": "call-821004", "kind": "quote",
  "body": "Told to wait 15 min for next bus; nobody held the tram.",
  "capturedAt": "2026-08-19T04:09:39.430Z" } }

The ids are sha-256 content hashes of (source, kind, body) — run this tutorial twice and the ids reproduce byte-identically. Now the deliberate mistake, because it teaches the register's vocabulary better than any paragraph:

TERMINAL
$ASD sd_evidence_add --projectId $ID --source int-07 --kind observation --body "…"
NOTE
asd sd_evidence_add: invalid arguments: "kind" must be one of ["quote","telemetry","document"]
running `asd help` shows usage

Exit code 1; nothing was written. Field notes go in as document with the observation in the body. Put the four ids in shell variables and write the journey map — first with the transfer node citing zero evidence, to watch the gate work:

TERMINAL
E1=c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174   # call-821004 quote
E2=b38cf37fef5b8460e82bad3592964293233aeb627ee291e9f7a64e5007c4c586   # call-821020 quote
E3=ebc691cacc31cf5fb2db2f3c8347e5e085690a0971b0d3ca4d104a6e150fdc6a   # rosters-07 document
E4=553d5015b4910740c2c2bfafc5aa4681b33997a2db3949d7c9004d72951809b2   # avl telemetry
NODES_BAD='[{"id":"plan","label":"Plan journey","kind":"step","fields":{"emotion":"3","touchpoint":"website"},"evidence":[{"evidenceId":"'$E3'"}]},{"id":"wait","label":"Wait at stop","kind":"step","fields":{"emotion":"2","touchpoint":"stop"},"evidence":[{"evidenceId":"'$E1'"},{"evidenceId":"'$E4'"}]},{"id":"transfer","label":"Missed connection","kind":"pain","fields":{"emotion":"1","touchpoint":"transfer"},"evidence":[]}]'
$ASD sd_artifact_write --projectId $ID --methodId journey-from-transcripts \
  --title "Current-state journey" --nodes "$NODES_BAD"
DATA
{ "accepted": false, "status": "draft",
  "artifact": { "id": "1a6ee17b92624f76aea97c407140a635", "kind": "journey-map",
    "methodId": "journey-from-transcripts", "status": "draft",
    "check": { "pass": false, "failures": [
      { "rule": "min-evidence-per-node", "nodeId": "transfer",
        "message": "node \"transfer\" cites 0 evidence refs, needs 1" } ] } },
  "failures": [ […the same list, repeated top-level…] ] }

Note what did not happen: the write was not rejected from the store. The artifact exists, as a draft, with its failures attached — sd_artifact_list shows it — and it can never go final or export in this state. Remediate the same artifact by id, the transfer node now citing the two rider quotes:

TERMINAL
ART=1a6ee17b92624f76aea97c407140a635
$ASD sd_artifact_write --projectId $ID --methodId journey-from-transcripts \
  --title "Current-state journey" --artifactId $ART --nodes "$NODES_FIXED"
# → { "accepted": true, "status": "draft", "failures": [] }  (same artifact id)

Accepted drafts under a critic gate are still drafts. Now the Critic reviews — here with a representative veto: one defect (severity high, fix required, evidence-cited) and one proposal:

TERMINAL
ROWS='[{"rowKind":"defect","severity":"high","rule":"evidence-sufficiency","message":"The missed-connection node needs the roster-constraint document cited alongside the rider quotes; without it the 3-minute connection fix looks feasible and is not","fix":"Cite rosters-07 on the transfer node","evidenceId":"'$E3'"},{"rowKind":"proposal","severity":"medium","rule":"source-diversity","message":"Quote the closure notice verbatim on the transfer node so the emotion score stays evidence-coded"}]'
$ASD sd_review --projectId $ID --artifactId $ART --verdict veto --rows "$ROWS"
DATA
{ "status": "draft", "verdict": "veto",
  "logArtifactId": "b7b97bdfd65f46d7bd96ecbe025255db", "rowsWritten": 2 }

The artifact is demoted to draft; the rows live in a new review-veto-log artifact (status final, reviewOf the journey map — sd_review_list shows both). Apply the fix — cite E3 on the transfer node — rewrite by id, and re-review:

TERMINAL
$ASD sd_artifact_write --projectId $ID --methodId journey-from-transcripts \
  --title "Current-state journey" --artifactId $ART --nodes "$NODES_FINAL"
PASS_ROWS='[{"rowKind":"proposal","severity":"low","rule":"source-diversity","message":"Keep the closure notice visible in the transfer decision","evidenceId":"'$E2'"}]'
$ASD sd_review --projectId $ID --artifactId $ART --verdict pass --rows "$PASS_ROWS"
DATA
{ "status": "final", "verdict": "pass",
  "logArtifactId": "b7b97bdfd65f46d7bd96ecbe025255db", "rowsWritten": 1 }

The pass carries an evidence-cited proposal row; an empty --rows '[]' pass is invalid. It reuses the same log artifact as the veto, so the rows remain as the record. Run the fact-check and render the deliverables:

TERMINAL
$ASD sd_factcheck --projectId $ID
DATA
{ "pass": true, "rows": [
  { "artifactId": "1a6ee17b92624f76aea97c407140a635", "kind": "journey-map",
    "status": "final", "integrity": { "pass": true, "dangling": [] },
    "acceptance": { "pass": true },
    "review": { "pass": true, "gate": "critic", "verdict": "pass" },
    "methodId": "journey-from-transcripts", "methodResolution": "recorded" },
  { "artifactId": "b7b97bdfd65f46d7bd96ecbe025255db", "kind": "review-veto-log",
    "status": "final", "integrity": { "pass": true, "dangling": [] },
    "acceptance": { "pass": true },
    "review": { "pass": true, "gate": null, "verdict": null },
    "methodId": null, "methodResolution": "inferred" } ] }

Exit code 0. Render the artifact and a report, then look at what landed on disk:

TERMINAL
$ASD sd_export_artifact --projectId $ID --artifactId $ART
# → { "path": "…/renders/journey-map.1a6ee17b.svg", "kind": "journey-map", "bytes": 3819 }
$ASD sd_export_report --projectId $ID --kind executive-summary
# → { "path": "…/renders/report.executive-summary.html", "kind": "executive-summary", "bytes": 2765 }
NOTE
docs-w3-demo-01f2de9f/artifacts/journey-map.current-state-journey.1a6ee17b.json
docs-w3-demo-01f2de9f/artifacts/review-veto-log.review-current-state-journey.b7b97bdf.json
docs-w3-demo-01f2de9f/evidence/index.json
docs-w3-demo-01f2de9f/project.json
docs-w3-demo-01f2de9f/renders/journey-map.1a6ee17b.svg
docs-w3-demo-01f2de9f/renders/report.executive-summary.html

Everything is plain files you can audit — the platform's answer to "trust me" is "open the directory."

An engagement in Claude Code

The same loop, driven conversationally. The following is an illustrative prompt and installation recipe, not a host acceptance receipt; host execution is unverified in this release. Install the plugin from the pack README, verbatim:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The plugin-root .mcp.json wires the vendored asd-mcp server automatically — nothing on PATH, no sibling checkout, no npm install. (A manual-copy variant for projects that do not use the plugin mechanism is on the plugin page.)

Open a project and run /asd. The orchestrator command plans from your brief and dispatches role agents in platform order; in practice you also drive the roles directly. The mapping from conversation to engine is one-to-one — every dispatch lands on a subagent that calls the same sd_* tools you typed in the first tutorial, now over MCP:

NOTE
@researcher run the contextual-inquiry skill for lighthouse-transit: plan
the research (ride-alongs on 14 routes incl. night shift, 32 commuter
interviews, 6 drivers), then add every field note and every verbatim
quote to the project evidence register via sd_evidence_add.

The Researcher captures rows into the register — the same content-addressed ids, the same three-kind vocabulary, the same refusal if a model improvises a fourth kind.

NOTE
@mapper run journey-from-transcripts over the register and write the
current-state journey-map artifact for lighthouse-transit.
@critic review the journey-map before it can go final.

The Mapper's sd_artifact_write faces the identical acceptance gate — a zero-evidence node comes back as a persisted draft with failures, exactly as in the CLI. The Critic's sd_review writes the same evidence-cited defect/proposal rows (severity, fix on defects) and the same veto-log artifact. And at the phase gate you run the same sd_factcheck — from the CLI shim or any MCP client — before the human decision.

Later roles close the engagement the same way:

NOTE
@measurer build the kpi-tree from the four success criteria with
kpi-tree-design: each row names its driver, experience link, business
link, baseline, and source.
@presenter assemble the executive report from final artifacts only.
@librarian produce the handover pack with full provenance.

The skills the roles name — contextual-inquiry, journey-from-transcripts, kpi-tree-design — are the SOP layer in between: 80 readable SKILL.md files, one per method manifest, each spelling out who does what, in what order, with which evidence discipline, and which acceptance gate the write will face. The agent reads the skill, the skill names the tools, and the engine enforces the rest. Nothing in the conversational surface bypasses the machine checks you saw in the terminal — the plugin is a different driver for the same gates, not a way around them.

Article 31, Riding the Current, is an illustrative fictional engagement that demonstrates the conversational flow at scale. Its technical boundary is the current disposable CLI/MCP receipt; Claude Code, OpenCode, Codex, Kimi, BUZZ, DSH, and ACP live execution are not implied by the article or this tutorial.

The gate in CI

The fact-check's exit code is the integration point: 0 when every artifact in the project passes integrity, acceptance, and review; 1 on any failure. A minimal pipeline step — run it from a checkout with the suite built, against the workspace your pipeline materialized:

TERMINAL
#!/usr/bin/env bash
set -euo pipefail
export ASD_WORKSPACE="$CI_WORKSPACE"        # where the project's files live
platform/packs/cli/asd sd_factcheck --projectId "$ASD_PROJECT_ID"
# non-zero exit fails the step; the JSON above the exit code names every failing row

Both outcomes are representative contract-shaped outputs. With a failing draft still in the project — the zero-evidence transfer node from the first tutorial, before remediation:

DATA
{ "pass": false, "rows": [
  { "artifactId": "1a6ee17b92624f76aea97c407140a635", "kind": "journey-map",
    "status": "draft", "integrity": { "pass": true, "dangling": [] },
    "acceptance": { "pass": false,
      "failures": [ "node \"transfer\" cites 0 evidence refs, needs 1" ] },
    "review": { "pass": true, "gate": "critic", "verdict": null },
    "methodId": "journey-from-transcripts", "methodResolution": "recorded" } ] }
NOTE
factcheck exit code: 1

After remediation and the pass verdict, the same command prints the all-pass rows from the first tutorial and exits 0. Two properties make this trustworthy as a gate. The replay is deterministic — no model in the loop, so a green run cannot be talked into existence. And the exit code inverts the dangerous case: a report that looks green but exits 1 cannot pass a build, because CI reads the code, not the JSON. Note what the gate checks and what it does not: it proves every artifact is evidence-backed, rule-passing, and properly reviewed as of right now; whether the project should ship is still the human phase-gate decision the concepts page describes.

Two practical notes for wiring it up. The gate is per-project, so a monorepo of engagements loops over project ids — or over the directories in the workspace, since each project is a self-contained directory of plain files and the workspace itself is the only state the check needs; archive it as a build artifact and the failing run is auditable offline, row by row. And because the workspace is files, the check runs anywhere the suite builds — no service to deploy, no database to migrate, no credentials to scope.
