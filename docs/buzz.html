BUZZ integration

BUZZ is the collaboration surface for the Agentic Service Designer team: a private channel where a human designer can coordinate role personas, inspect handoffs and keep a visible project index in Canvas. The ASD pack does not turn BUZZ into a second project database. The ASD workspace, evidence register, artifact store, review log and fact-check remain owned by the shared runtime and are accessed through the CLI, MCP or a host that has actually integrated those tools.

This distinction matters. A BUZZ message can be a real collaboration event and still not be an ASD evidence row. A Canvas link can be a useful index and still not prove that the linked artifact persisted in the ASD store. The pack and the protocols fail closed when the missing binding is not proven.

What ships in the Persona Pack

platform/packs/buzz/ is a generated, self-contained, keyless Persona Pack. The native Open Plugin manifest is .plugin/plugin.json; instructions.md contains the shared role protocol; .mcp.json points to the pack-relative MCP server; agents/ contains the ten role personas; and skills/ contains the 74 generated role-accessible method skills. teams.json and managed-agents.json are retained as compatibility projections for the historical managed-agent store. They are not native Persona Pack inputs and must not be copied into an application store as if they were the installation manifest.

The generated inventory is:

Payload Current value
Canonical roles/personas 10
Skill directories 74 (75 sources, including the authored flagship source)
Canonical runtime tools 29 sd_* tools
Method manifests 74
Registered artifact-kind contracts 32
Vocabulary/catalog rows 38
Authored templates 7
Pack-local MCP resources 226 when the corpus roots are available
Pack-local MCP prompts 10 role prompts

The six emitted MCP bundles with fresh disposable stdio evidence are BUZZ, Claude Code, Codex, Kimi, the standalone MCP target and OpenCode. This is pack-local evidence: it proves initialize, discovery and representative ASD tool workflows in isolated environments. It does not prove that BUZZ's native host has executed every tool or role.

The ten roles and their handoff responsibilities

Every persona receives the same evidence, review and human-gate contract. The role-specific ownership is:

Role / BUZZ handle Primary responsibility Typical outputs or handoff
Orchestrator · sd-orchestrator Plan the engagement, sequence methods, coordinate handoffs and surface phase-gate decisions. Orchestration records and human handoffs.
Researcher · sd-researcher Gather verbatim evidence, provenance and context from interviews, observations and documents. Evidence register, research plan, stakeholder/context inputs.
Synthesizer · sd-synthesizer Cluster evidence and form insights, personas, empathy maps and first-pass journeys. Insight, affinity, persona and synthesis artifacts.
Mapper · sd-mapper Build deterministic journey maps, service blueprints, mental models and ecosystem maps. Evidence-linked map/blueprint nodes; no hand-authored Mermaid.
Ideator · sd-ideator Frame HMWs and concepts from the evidence-backed insight set. HMW, concept, story and value-proposition artifacts.
Prototyper · sd-prototyper Design and test prototypes; separate test evidence from assumptions. Prototype/test artifacts and evidence requests.
Measurer · sd-measurer Connect service quality, KPI and outcomes through a causal measurement chain. KPI trees, audits, opportunities and roadmaps.
Critic · sd-critic Challenge evidence sufficiency and record defect/proposal rows. Evidence-cited review-veto-log; veto keeps a candidate in draft.
Presenter · sd-presenter Assemble reports and presentation narratives from final artifacts without inventing content. Report/export requests; decks remain a planned vocabulary item unless a renderer produces one.
Librarian · sd-librarian Maintain corpus provenance, method/skill drift and template/catalog references. Knowledge lookups and drift reports.

The handles above are Persona Pack definitions. They are not runtime public keys. Mention routing must use the identity-backed runtime chosen after the owner has materialized and verified each persona.

Definition identity versus runtime identity

The Persona Pack is intentionally keyless. A definition has a stable canonical slug/persona ID, display name, model/runtime metadata and prompt. A running BUZZ runtime has a separate identity-backed public key. The safe relationship is:

Do not use a persona slug as a public key, do not treat a keyless definition and its runtime as duplicates, and do not infer that a green persona card means the runtime is reachable in the chosen channel. Identity creation, provider health and channel membership require owner-authorized BUZZ UI/CLI operations outside the generated pack.

Safe install and audit sequence

The compiler emits files; it does not create identities, write BUZZ application storage, contact a relay or bind a channel. Use BUZZ's native Persona Pack installation UI for the pack directory and retain the emitted digest. The repository's installer helper is an atomic, keyless file-copy/validation library used by the disposable acceptance runner; it is not a credential or identity provisioner.

After an owner has materialized runtimes and selected a channel, run the read-only audit from an isolated environment:

TERMINAL
node scripts/buzz-live-identity-audit.mjs \
  --input ./audit.json \
  --channel-id <channel-uuid> \
  --output ./identity-audit.json

The audit joins definitions, runtimes, public keys, optional membership and mention candidates. It never loads credentials and has no --apply or --confirm mode. When membership is supplied, its only emitted BUZZ CLI inspection is:

TERMINAL
buzz channels members --channel <channel-uuid>

Review the exact runtime public key and membership before sending a mention. Avoid broad “Deploy Team” or forceNewInstance operations: they can create ambiguous runtimes and make a truthful mention-to-reply claim impossible.

Mention routing and collaboration

Each native persona is configured with mentions: true, thread_replies: true and broadcast_replies: false. The safe routing sequence is:

  1. Confirm the keyless definition slug maps to exactly one active runtime.
  2. Confirm that runtime's public key is a member of the designated channel.
  3. Address the message to that exact runtime in BUZZ and retain the visible sent state, recipient attribution, response and handoff.
  4. Match the reply to the audited runtime public key, not only to a display name or persona card.
  5. If the workflow writes ASD records through MCP/CLI, record the resulting project/evidence/artifact/review IDs separately and index them from Canvas with the generator below.
  6. Stop at the human phase gate; the human designer authorizes progression.

An unaddressed message, a working indicator, a seeded transcript or a reply from an ambiguous runtime is not an end-to-end acceptance result.

Build the channel Canvas index

The channel Canvas is the visible project index for an engagement: one page that navigates every service-design artifact the team has persisted for that channel. scripts/buzz-canvas-index.mjs renders it deterministically from persisted ASD records — it never invents a row and never contacts a relay.

The generated document carries the twelve sections of the Canvas contract (charter and data boundary, phase and human-gate state, participant roster, evidence register, artifact register with kind/ID/status/owner/evidence coverage, critic findings and remediation, typed handoff queue, decisions/ assumptions/risks, prototypes and tests, KPI ownership, final report and recovery playbook, and index integrity with a round-trip content hash).

Render it from a live ASD workspace project directory:

TERMINAL
node scripts/buzz-canvas-index.mjs render \
  --project-dir ~/.asd/projects/<project-id> \
  --channel sd/<engagement> --fictional \
  --planned research-plan --planned prototype-plan \
  --out ./canvas

or from a checked-in artifact portfolio plus its verified run receipt, the mode used for the Article 37 Metrovale canvas:

TERMINAL
node scripts/buzz-canvas-index.mjs render \
  --portfolio articles/37/artifacts \
  --receipt docs/reports/buzz-case-study-disposable-receipt.json \
  --channel sd/metrovale-one-recovery --fictional \
  --out articles/37/canvas

The generator is fail-closed: every evidence, artifact, review-log and handoff ID that would appear in the document must resolve in the source records, planned rows must name registered artifact kinds that do not yet exist, and any dangling reference aborts the render with a problem report instead of writing a stale link. Statuses are the ASD gate substrate's own (final/draft), never aspirational.

Setting the Canvas on a channel stays an owner-driven live action. The manifest records the exact commands; run them only against an authorized channel with credentials kept shell-only:

TERMINAL
node scripts/buzz-canvas-index.mjs verify --canvas-dir ./canvas \
  --portfolio articles/37/artifacts \
  --receipt docs/reports/buzz-case-study-disposable-receipt.json

verify recomputes the content hash, checks all twelve sections, resolves every ID token in the document against the manifest inventory (the offline stale-link check), and — when the source is supplied — proves the committed document still matches a fresh render. After the owner runs buzz canvas set --channel <uuid> --content - with the document on stdin, a retrieved copy from buzz canvas get --channel <uuid> can be checked with --retrieved <file> to prove the round trip survived the relay.

The pack-local MCP boundary

.mcp.json is deliberately relative to the installed pack:

DATA
{
  "mcpServers": {
    "asd": {
      "command": "node",
      "args": ["mcp/bin/server.mjs"]
    }
  }
}

The server exposes the canonical 29 tools and, when its corpus is available, 226 resources and 10 prompts. Its workspace is controlled by the same ASD_WORKSPACE boundary as the other runtime surfaces and defaults to ~/.asd/projects. Keep a BUZZ channel's messages and Canvas separate from this workspace unless an explicitly verified host integration writes and reads the same project IDs.

The pack supports tool execution, metadata/schema/template lookup, evidence import, orchestration recording and phase-advance requests through MCP. ACP is not bundled as a transport: asd-acp/1 is a record-only, fail-closed envelope. host-agent-spawn is unsupported for the emitted BUZZ pack and host execution is unverified unless a later BUZZ receipt proves it.

The observed Article 37 slice

Article 37 is the authoritative live-UI evidence for the current BUZZ boundary. In the captured private channel sd/metrovale-one-recovery, the owner first observed the ten ASD personas and then added general Claude and Codex advisory identities, producing a visible 13-member roster. The slice includes a genuine orchestrator reply, relay-confirmed orchestrator → researcher/mapper handoffs, synthetic researcher/mapper content, a Canvas artifact index and advisory Claude/Codex storyboard responses. The human Discover gate remained blocked.

The capture does not prove MCP project/artifact IDs, durable persistence, visible Critic verdict, ACP spawn/transport, host execution, reload/recovery/ cleanup, phase completion, a Talia reply or a rendered deck file. The Canvas is an observed collaboration index with observed/draft/planned statuses and persona ownership; it is not the ASD store. Read the full Article 37 case study for screenshots and the evidence ledger.

Recommended project operating model

For a real engagement, keep the systems legible:

Concern System of record BUZZ role
Team discussion and human decisions BUZZ private channel Conversation, mention, visible gate discussion
Research/evidence/artifacts/reviews ASD workspace via CLI/MCP/verified host Link IDs and summaries; do not duplicate records in prose
Role SOPs and provenance Canonical knowledge/skills + Persona Pack prompts Ask the relevant persona to apply the method, then cite the produced record
Phase authorization Human designer and ASD phase gate Canvas checklist may index the decision; it does not authorize it
Cross-tool handoff Typed ASD/ACP record when supported Message may announce it; record ID is the durable handoff

This model supports collaboration without turning a chat transcript into unverifiable evidence. When a capability is absent, keep the Canvas row planned or blocked and record the exact acceptance evidence still required.

Evidence and troubleshooting

Symptom Safe interpretation Next check
Persona appears in the pack but cannot be mentioned Definition exists; runtime or membership is not proven. Run the read-only identity audit and verify the exact channel member public key.
BUZZ reply appears but no ASD ID exists Collaboration occurred; ASD persistence is unproven. Execute the shared MCP/CLI workflow with an isolated ASD_WORKSPACE.
MCP discovery is empty Corpus roots may be unavailable outside the source checkout. Verify the pack-local corpus and receipt; tools can still be independently tested.
host-agent-spawn or ACP transport is requested Capability is outside this pack's verified boundary. Record a structured unsupported result and stop; do not substitute a fake spawn.
Canvas link points to a planned artifact Index is honest; artifact is not complete. Keep the human gate blocked until the ASD artifact and review receipt exist; regenerate with buzz-canvas-index.mjs render once records persist.
Committed canvas disagrees with current records The document drifted from its source. buzz-canvas-index.mjs verify with --project-dir or --portfolio re-renders and fails the drift check until regenerated.
Retrieved canvas differs after buzz canvas set Round trip may have normalized content. Run verify --retrieved <file>; treat anything other than a hash or trailing-whitespace match as a failed round trip.
