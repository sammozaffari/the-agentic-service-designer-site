The MCP server

asd-mcp is the Service Design Agent Platform engine as an MCP stdio server — protocol revision 2025-06-18, newline-delimited JSON-RPC 2.0, zero npm dependencies beyond the engine. Any agentic tool that can spawn a stdio MCP server gets the full platform: the sixteen sd_* tools, the knowledge corpus as resources, and the ten role contracts as prompts. The Claude Code plugin is one consumer; this page is about the server itself, for everyone else.

Invocation

Every pack that wires MCP ships the server vendored under mcp/ — a tsdown bundle with the entire dependency graph inlined, plus the knowledge corpus as data. One canonical invocation, no npm install, no PATH entry, no suite checkout:

TERMINAL
node <pack-root>/mcp/bin/server.mjs

The standalone platform/packs/mcp pack adds a launcher shim (asd-mcp) that resolves the vendored server relative to itself, and a client config template, asd-mcp.json:

DATA
{
  "mcpServers": {
    "asd": {
      "command": "node",
      "args": [
        "mcp/bin/server.mjs"
      ]
    }
  }
}

Clients spawn servers from arbitrary working directories, so absolutize the path after placing the pack:

TERMINAL
sed -i.bak "s|mcp/bin/server.mjs|$PWD/mcp/bin/server.mjs|" asd-mcp.json

Tools

Sixteen tools, one per engine capability. tools/list returns every sd_* tool with its JSON schema as inputSchema; tools/call validates name and arguments, executes, and renders content blocks — tool failures return isError: true, not a protocol error.

ToolContract
sd_project_listList the projects in the workspace.
sd_project_createCreate a project (name, client, sector, service, phase); returns the generated projectId.
sd_project_openThe project record plus its artifacts — the state snapshot.
sd_evidence_addAppend a {source, kind, body} row to the evidence register; kind is exactly quote, telemetry, or document. The id is content-addressed (sha-256 of the row), so re-adding the same row returns the same id.
sd_evidence_queryQuery the register by kind and/or search.
sd_artifact_listList a project's artifacts, optionally by kind.
sd_artifact_getOne artifact by id, including status and any check.failures.
sd_method_listThe method manifests, filterable by phase and producesKind.
sd_method_runA method's executable contract: steps with role assignments and gates, acceptance rules, output kind, available evidence count.
sd_artifact_writeWrite nodes through structural-integrity and acceptance checks. A failing write still persists — as status: draft with check.failures; passing artifactId rewrites that draft in place.
sd_reviewThe Critic's verdict. pass flips the artifact to final; veto keeps it draft and writes a final review-veto-log artifact linked via reviewOf, one node per row (rowKind: defect|proposal, severity, rule, message, fix required on defects, optional evidenceId).
sd_review_listThe review board: per artifact, its status, review gate, verdict, log artifact, and outstanding failures.
sd_export_reportRender a report (e.g. executive-summary) into the project's renders/.
sd_export_artifactRender one artifact (e.g. SVG) into renders/.
sd_knowledgeSearch the method and artifact-kind catalog by query, phase, source, or type.
sd_factcheckReplay integrity, acceptance, and review state across the project; reports pass: false on any failure.

Resources

The knowledge canon is readable as MCP resources. The URI grammar:

  • asd://books/<book> — book overview + chapter index
  • asd://books/<book>/<chapter> — one chapter
  • asd://articles/<NN> — one case study

215 resources in total: 20 books, 159 chapters, 36 articles. All are text/markdown; URI segments come straight from directory and file names, so the book segment is the same provenance slug the corpus uses everywhere (e.g. 09-mapping-experiences) and the chapter segment is the chapter file stem (e.g. 04-customer-journey-maps).

resources/list is cursor-paginated, 100 per page, with an opaque nextCursor. The real page-1 response from a live server (trimmed; full frame is a single line):

DATA
{"jsonrpc":"2.0","id":2,"result":{"resources":[
  {"uri":"asd://articles/01","name":"article-01","title":"The AI-First Service Design Operating System","description":"Case study — Foundations & Process","mimeType":"text/markdown"},
  {"uri":"asd://articles/02","name":"article-02","title":"From Insight to Implementation: Redesigning Telehealth Onboarding at Northgate Health","description":"Case study — Foundations & Process","mimeType":"text/markdown"},
  {"uri":"asd://articles/03","name":"article-03","title":"Service Design for Business: Turning Claims into an Experience at Aurelia Insurance","description":"Case study — Foundations & Process","mimeType":"text/markdown"},
  […97 more resources…]
],"nextCursor":"b2Zmc2V0OjEwMA"}}

resources/read returns one resource's Markdown by URI, or -32002 when the URI is not in the listing.

Prompts

prompts/list exposes the ten agent roles (orchestrator, researcher, synthesizer, mapper, ideator, prototyper, measurer, critic, presenter, librarian); prompts/get returns one role as a single user message — the shared role contract plus the role's own instructions. The critic, live:

DATA
{"jsonrpc":"2.0","id":3,"result":{
  "description":"The adversarial conscience of the engagement. Sits on the write path, not after it: any artifact whose method manifest declares `reviewGate: critic` is final-eligible only after a Critic verdict. The Critic's job is to make every claim earn its place — evidence-cited, machine-checked first, judgment second. The Critic does not design; it defends the truth of the work.",
  "messages":[{"role":"user","content":{"type":"text","text":"# SDAP Role Contract — the collaboration protocol\n\n> Canonical source: `docs/plans/2026-08-17-service-design-agent-platform.md` (§3.2, §3.5).\n> Every role agent […]"}}]
}}

Loading a role prompt is how a generic host gets the platform's collaboration protocol without a native subagent mechanism — the grok pack ships exactly this as text files.

Errors and lifecycle

initialize advertises tools, resources, and prompts (no subscribe/listChanged); the server answers with serverInfo {name: "asd-mcp", version: "0.1.0"}:

DATA
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{},"resources":{},"prompts":{}},"serverInfo":{"name":"asd-mcp","version":"0.1.0"}}}

Every method except initialize/ping requires initialization first. Notifications (no id) are never answered.

CodeMeaning
-32700Parse error
-32601Unknown method
-32602Invalid params — bad cursor, missing name/uri, unknown tool or prompt, non-object arguments
-32000Not initialized
-32002Resource not found
-32603Internal error

Corpus roots and empty-corpus behavior

Resources and prompts are discovered from the filesystem at request time. Three env vars override the roots individually:

ASD_BOOKS_ROOToverrides books/
ASD_ARTICLES_ROOToverrides articles/
ASD_AGENTS_ROOToverrides platform/agents/
fallbackthe nearest ancestor of the installed module carrying the repo layout (books/README.md, articles/README.md, platform/agents/)
ASD_WORKSPACEthe engine tools' project-workspace override (default ~/.asd/projects) — unrelated to the corpus roots

The npm tarball does not ship the corpus. Installed outside the repo with no env vars set, resources/list and prompts/list return empty arrays and reads answer -32002 — tools are unaffected. This is deliberate, not a broken install.

Do not confuse two corpora. The vendored mcp/data/ tree inside each pack is the method and artifact-kind catalog — runtime data the server reads relative to its own URL, and the reason sd_knowledge and sd_method_list work anywhere. The asd:// books/chapters/articles resources and the role prompts are the repo's Service Design canon, discovered per the table above: a pack copied out of the repo keeps its tools and its method catalog, and serves empty resource/prompt lists until the env vars point at a corpus.

Format pin

MCP spec revision 2025-06-18; JSON-RPC 2.0; node ≥ 20; bundle emitted by tsdown 0.22 from suite @asd/runtime. Verified end-to-end (initialize → tools/list → tools/call → error) against the vendored bundle from a scratch directory, 2026-08-18. For the same engine in a terminal instead of a client, see the CLI page.
