Every surface runs the same engine and the same core loop: capture evidence → gated artifact write → critic review → final → factcheck. This page gets you to your first gated artifact on whichever surface you already work in, quoting real captured runs — so when the outputs below match what you see, the loop has already worked once for you.

Claude Code plugin

The reference distribution. Ten role agents as native subagents, the 74 method skills, the /asd orchestrator command, and the engine vendored into the pack as an MCP server — no npm install, nothing on PATH. Verbatim from platform/packs/claude-code/README.md:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The plugin manifest is the pack's .claude-plugin/plugin.json; MCP wiring is the plugin-root .mcp.json, which Claude Code loads automatically for installed plugins — ${CLAUDE_PLUGIN_ROOT} resolves inside the installed plugin, so the vendored server needs no PATH entry and no sibling checkout. Once installed, /asd dispatches the orchestrator; the role agents and skills run the loop for you, and the engine tools enforce the gates underneath.

CLI

The same engine as a standalone asd binary — the surface used for every capture in these docs. The launcher ships at platform/packs/cli/asd (or build the suite and link suite/packages/runtime/lib/cli.mjs). Projects live in ~/.asd/projects by default; point ASD_WORKSPACE elsewhere for scratch work:

TERMINAL
export ASD_WORKSPACE=/tmp/asd-ws   # default: ~/.asd/projects

TERMINAL
$ asd sd_project_create --name capture-meridian --client "Fictional composite" --sector public-transport --service "commuter journeys" --phase discover

Capture evidence. Three rows went in during the captured session — two rider quotes and one roster document:

TERMINAL
$ asd sd_evidence_add --projectId capture-meridian-201d0a1d --source call-821004 --kind quote --body Told to wait 15 min for next bus; nobody held the tram.
## Evidence captured
DATA
{ "evidence": { "id": "c0f1736916289286b470528c08711c2b39ec7a7e3e853b00a162590b1197a174", "kind": "quote", […] } }

The evidence vocabulary is closed on purpose: quote, telemetry, document. Anything else is a hard failure at the argument parser — the capture shows --kind observation rejected with "kind" must be one of ["quote","telemetry","document"]. Field notes land as quote or document; sensor and counter data lands as telemetry.

Write the first artifact against a method — here journey-from-transcripts. The captured session tried a one-node journey with zero evidence first:

TERMINAL
$ asd sd_artifact_write --projectId capture-meridian-201d0a1d --methodId journey-from-transcripts --title Current-state journey --nodes […]
## Artifact write
DATA
{
  "accepted": false,
  "status": "draft",
  "artifact": {
    "id": "dd58b4cf12e0419e9b455c030e448e43",
    "kind": "journey-map",
    "status": "draft",
    "check": {
      "pass": false,
      "failures": [
        { "rule": "min-nodes", "message": "expected at least 3 nodes, found 1" },
        { "rule": "min-evidence-per-node", "nodeId": "plan", "message": "node \"plan\" cites 0 evidence refs, needs 1" }
      ]
    },
    […]
  }
}

A rejected write is not lost work: the draft persists with its check report attached, so you fix the nodes and write again — the store never silently drops an artifact.

The retry — three nodes, four evidence refs — came back accepted: true (still draft; acceptance is necessary, not sufficient). Then the critic gate, from a second captured session of the same loop:

TERMINAL
$ asd sd_review --projectId capture-meridian-953950ca --artifactId 7bfbea7ad1f34940bd46a6a66c7eaa22 --verdict pass --rows []
## Review verdict
DATA
{ "status": "final", "verdict": "pass", "logArtifactId": "6e5b2de08e6b42f1b5ad8c89e39240cd", "rowsWritten": 0, "artifact": { […] } }

A veto verdict instead puts the artifact back to draft and writes a review-veto-log artifact holding the critic's defect and proposal rows — the veto capture shows "rowsWritten": 2 and the log appearing on the review board beside the artifact it reviews. Either way the verdict is an artifact, not a chat message.

Finally, prove the whole project:

TERMINAL
$ asd sd_factcheck --projectId capture-meridian-953950ca
## Factcheck
DATA
{ "pass": true, "rows": [ { "artifactId": "7bfbea7ad1f34940bd46a6a66c7eaa22", "status": "final", "integrity": { "pass": true }, "acceptance": { "pass": true }, "review": { "pass": true, "gate": "critic", "verdict": "pass" }, […] } ] }

sd_factcheck replays referential integrity, acceptance rules and review verdicts for every artifact and exits 1 on any failure — the earlier capture, with a broken draft still in the store, exited 1. That is the loop: evidence in, gated write, critic verdict, final, verifiable.

MCP server

The same 16 tools plus the knowledge corpus, exposed to any MCP client as a self-contained stdio server vendored at platform/packs/mcp/mcp/bin/server.mjs. Client config (from the pack's asd-mcp.json; absolutize the path after placing the pack, since clients spawn servers from arbitrary working directories):

  "mcpServers": {

DSH workbench

The suite is the DeepSeek Harness plugin — suite/ (@asd/core, @asd/engine, @asd/knowledge, @asd/agents, @asd/runtime) packages the engine, tools, artifact renderers and role validation as the asd bundle. From platform/packs/dsh/README.md:

TERMINAL
cd suite && pnpm install && pnpm -r --filter '@asd/*' test
# then load the plugins in a dsh profile and wire each method step's role to
# the corresponding platform agent (agents/<role>/instructions.md)

Method steps carry role + gate, and @asd/agents validates every manifest against the 10-role registry at apply time. The harness page has the workbench context; the loop underneath is the one you just ran.

The loop, once

Writes are gatedA failing sd_artifact_write persists as status: draft with check.failures — never as final.
Review is a state changesd_review pass flips the artifact to final; veto keeps it draft and writes a review-veto-log artifact.
Factcheck is replaysd_factcheck re-runs integrity, acceptance and review for every artifact and exits 1 on any failure.
Kind ids are stringsjourney-map, service-blueprint — not numbers. phase-gate-decision and orchestration-plan are not implemented.
Methods are executableAll 74 skills' method manifests run via sd_method_run — the SOP is the contract.
