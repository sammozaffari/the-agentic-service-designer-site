The DeepSeek Harness workbench

DeepSeek Harness (DSH) is a plugin-based agent host. Agentic Service Designer (ASD) integrates with it as a profile-composed plugin surface rather than as a fork of the Harness application. The shipped DSH pointer is platform/packs/dsh/; the UI implementation is @asd/ui and the shared runtime remains in the ASD suite.

This page deliberately separates three kinds of evidence:

Evidence class What it means here
Source/manifest The committed package, compatibility and capability contract.
Disposable verification A clean profile or bundle test with isolated files and no ambient host state.
Pinned DSH receipt (historical run record) The pinned docs/reports/dsh-live-integration.receipt.json, which records the rc.5 profile lifecycle, bundle safety, UI smoke and accessibility checks for that run.

This historical receipt proves the Studio plugin lifecycle and a live UI smoke. It does not constitute a blanket claim that every model provider, chat trajectory, external MCP client or host-specific agent dispatch path is live-proven.

The profile lifecycle was exercised through the host's official add/update/remove and reinstall path. The result is a portable, deterministic @asd/ui bundle: 502 entries, no absolute source paths, no source-tree imports, no symlinks, and a stable SHA-256 recorded in the receipt. The platform/packs/dsh/manifest.json file is a compatibility pointer and inventory; it is not a replacement for the official DSH profile installer.

Package composition

The DSH surface is assembled from the shared suite packages. Their boundaries are intentionally explicit:

Package Responsibility in DSH
@asd/core Workspace-backed projects, evidence, artifacts, canvases, acceptance, review, fact-check, phase gates, ACP envelopes and capability contracts.
@asd/engine The canonical 30 sd_* tool definitions and execution handlers.
@asd/knowledge 80 method manifests, 38 registered artifact-kind contracts, seven authored templates and provenance data. Per-kind runtime typed JSON schemas remain a Phase 2 boundary.
@asd/agents The ten role registry and bounded role-dispatch instructions used by the host.
@asd/runtime Shared runtime used by the CLI and MCP bundles; it is not a second DSH UI.
@asd/ui The DSH host adapter, loopback RPC, Studio browser, skill registration, role prompt registration, settings item and conversation/side-panel slots.

The current canonical inventory is 30 tools, 80 methods, 38 registered kinds, 39 catalog rows, seven authored templates, 10 roles, 80 shipped skills from 81 sources, 228 corpus resources and 10 role prompts. These numbers describe the shared ASD payload; they do not mean that every DSH UI route is a separate tool.

How the DSH integration works

At host startup, @asd/ui validates the rc.5 compatibility seam, registers the canonical tools and skills, adds the shared role contract to the system prompt, registers the ASD settings namespace, and exposes the Studio assets and RPC on loopback. The browser client contributes the Studio view and the sidebar activity. The UI calls the canonical tool runtime; it does not maintain a second project database.

The resulting topology is:

Browser surfaces

The current UI has three supported entry points:

  1. Service Design activity in the sidebar, which opens the Studio panel.
  2. Studio conversation view, registered through conversation.view and available beside the host's conversation surfaces.
  3. Settings → Plugins, where the ASD settings item is registered through settings.plugin.item and reads/writes the ASD workspace/default-phase configuration through the host settings seam.

The host routes are deliberately loopback-only. /asd/app serves the static Studio assets and /asd/rpc exposes a closed JSON-RPC allowlist. The adapter refuses to register these routes when the server host is not 127.0.0.1. RPC requests are size-capped, validate their own parameters and return a structured unsupported-capability error instead of silently executing a different operation.

The Studio browser reads the same project store as the canonical tools. It can show projects, artifacts, evidence, methods, artifact kinds, review rows and reports. The browser is an inspection and coordination surface; acceptance, review and phase-gate decisions remain engine operations and human decisions.

Direct Studio capability projection

The DSH-specific projection contains 24 rows: 23 supported and one explicit unsupported row. It is not a claim that the UI owns all 30 tools as bespoke buttons. Supported rows execute through the canonical tool runtime and include project, evidence, artifact, canvas, method, template, schema, review, fact-check, orchestration and phase-advance operations.

The explicit unsupported row is:

Capability Status Reason
phase.gate.status unsupported The canonical engine exposes phase-gate advance, not an independent read-only status operation.

method.run and evidence.query are canonical tool concepts, but they are not separate direct Studio capability-projection rows. A client must use the canonical tool path or the supported Studio query surface; it must not invent a new direct RPC method. Unsupported or unknown capability IDs fail closed with CAPABILITY_UNSUPPORTED.

The host advertises a bounded subagent provider for the role registry. This is a host capability boundary, not proof that every model/provider combination can dispatch every role in every session. The receipt's live evidence is the installed profile, UI smoke, workspace isolation and accessibility result.

Install and verify a profile

Use the official DSH CLI for the installed rc.5 checkout. The exact package or local bundle path is deployment-specific; keep it outside the project workspace and do not edit the Harness source tree. The profile lifecycle shape is:

TERMINAL
# Run from the DeepSeek Harness checkout.
dsh plugin --profile <profile> add <asd-ui-package-or-bundle>
dsh plugin --profile <profile> update <asd-ui-package-or-bundle>
dsh plugin --profile <profile> remove <asd-ui-package-or-bundle>

# Start the host with the same profile after installation.
dsh web --profile <profile> --port <loopback-port>

The placeholders are intentional: this repository does not publish a universal registry URL or a credential-bearing profile. Verify the resolved package and compatibility revision in the profile before opening the UI. The authoritative release check must include:

  • official add/update/remove/reinstall succeeds;
  • @asd/ui version and six required slots match the manifest;
  • the bundle has no source-tree imports, absolute paths or symlinks;
  • Studio loads from the loopback URL;
  • the project count and workspace root are the expected disposable values;
  • the ASD-owned accessibility scan has no serious/critical findings; and
  • stopping the server removes only the disposable workspace.

The pinned receipt reports these checks as pass for asd-live-review2. A local profile with another Harness revision is not covered by that receipt until the compatibility and lifecycle checks are rerun.

A verified Studio workflow shape

The shared engine's governed workflow remains:

  1. Create/open a project.
  2. Add or import evidence with one of the three accepted kinds: quote, telemetry, or document.
  3. Run a method and write an artifact whose nodes resolve to evidence rows.
  4. Let the acceptance engine retain an invalid candidate as a draft with failures rather than silently treating it as final.
  5. Run the Critic review. A veto keeps the target in draft and records a linked review-veto-log; a pass requires evidence-cited review rows and can promote the artifact to final.
  6. Run fact-check/export from a surface that exposes those operations.
  7. Stop at the human phase gate. The engine records the decision; it does not authorize a phase advance on behalf of the designer.

The DSH receipt links a prior evidence → artifact → review/veto → remediation → evidence-cited pass → human-gate → report workflow and records reload/session isolation plus fail-closed capability-adapter behavior. The receipt is the source of truth for that claim; a screenshot or a prose transcript alone is not.

Current boundaries

Do not infer these capabilities from the presence of the pack:

  • DSH installation into one profile does not prove installation into every DSH profile or every future rc version.
  • A Studio card is not proof of a model-produced chat turn, provider health or external MCP-client interoperability.
  • A registered role is not proof of live role execution unless the host receipt records the dispatch and resulting output.
  • The DSH pack does not make ACP a transport. asd-acp/1 is record-only and fail-closed; live spawn/transport needs a host capability and a receipt.
  • BUZZ is a separate collaboration surface. Its Canvas and messages are not automatically the ASD project/evidence/artifact store.

For the BUZZ boundary and the observed Metrovale channel slice, read BUZZ integration and the Article 37 case study. For command-line and stdio MCP workflows, use Getting started, CLI and MCP.
