Artifact kind reference

An artifact is the platform's unit of work: a typed JSON document in the project's artifacts/ directory. Every artifact carries id, kind, projectId, title, schemaVersion, sources (book/article provenance), nodes, timestamps, and status (draft or final); artifacts written through a method also record methodId, and gate outcomes attach as check (acceptance failures) and review (the verdict and its log). Each node is { id, label, evidence: [{ evidenceId, quote? }], fields } — the fields object holds the kind-specific columns (a journey map's emotion and touchpoint, a KPI tree's baselines), while evidence links the node to the project register.

Kind ids are strings (journey-map, insight-set, review-veto-log), never numbers; the catalog numbers below are a human index, not part of the id.

Two catalogs, stated plainly

There are two related layers and they are not interchangeable:

  • The practice vocabulary — platform/templates/catalog.md contains a 39-row practice vocabulary: 18 canonical labels, 13 aliases, and 8 pending concepts. A row is a practice-facing name and design intent; it is not proof of a live runtime kind, authored template, renderer, skill, or per-kind typed schema.
  • The runtime registry — suite/packages/knowledge/data/artifact-kinds/*.json contains 38 registered artifact-kind contracts. This is the runtime set used by artifact persistence, export, and metadata lookup. Registry presence must not be inflated to 39 by counting aliases or pending vocabulary rows.

The seven authored fillable templates are separately declared in suite/packages/knowledge/data/templates/*.json and point to the Markdown sources under platform/templates/. The catalog's per-kind typed runtime schema expansion is a Phase 2 boundary; the current documentation must not describe the 39-row vocabulary as 39 live typed schemas/templates.

There are ten registry-only kinds, deliberately outside the 39-row catalog promise: actor-network-map, change-plan, day-in-the-life, expectation-map, raci-matrix, roadmap, service-profit-chain, service-scenario, touchpoint-inventory, and walkthrough-script. They have runtime registry metadata and producing support, but no authored template claim.

review-veto-log is a separate administrative control record produced by sd_review, not a user-facing authored template or method output. It records Critic verdict rows and remains part of the 38-kind runtime registry.

The eight pending, non-executable vocabulary rows are design-brief, reframe-register, co-design-plan, evaluation-framework, executive-report, presentation-deck, orchestration-plan, and phase-gate-decision. They are practice concepts only until their future registry/template/renderer/skill gates are met.

Aliases preserve useful practice language without creating extra runtime kinds: for example, insight-register maps to insight-set, standards-audit maps to service-standard-set, and storyboard-walkthrough maps to the shipped storyboard view.

Renderers

The 38 registered kinds have deterministic renderer coverage in suite/packages/render/src/, dispatched on artifact.kind; an unregistered kind falls back to a legible node listing rather than throwing. The model writes contract-shaped JSON and the renderers produce all diagram markup — hand-written diagram syntax by a model is a rejected pattern. Renders land in the project's renders/ directory: derived data, rebuildable from the store at any time via sd_export_artifact (SVG) or folded into the HTML reports from sd_export_report. This renderer coverage does not turn pending catalog rows into executable kinds.

Fillable templates

Seven kinds have authored, human-fillable templates — the flagship set named in the catalog. Download the Markdown form, fill it by hand or with a team, and use the runtime contract/acceptance rules to turn the result into an evidence-cited artifact; a template is not a promise that every catalog row has its own typed runtime schema:

  • Stakeholder map
  • Ecosystem map
  • Insight register
  • Persona set
  • Journey map
  • Service blueprint
  • Jobs-to-be-done map

The full catalog with per-kind fields and references is on the templates page.

Anatomy of a review-veto-log

The administrative control record every gated engagement can accumulate is the review log. A Critic verdict — pass or veto — persists as a review-veto-log artifact whose nodes are the review rows (rowKind, severity, message, rule, fix in fields), linked to its target by reviewOf, and always status: final from birth. The following is an illustrative veto-log shape; IDs and prose are examples, not a live engagement receipt:

DATA
{
  "id": "25500d7e4a634befb052cfa956bd4f2f",
  "kind": "review-veto-log",
  "projectId": "veto-demo-50d92ebc",
  "title": "Review: Drafty journey",
  "schemaVersion": 1,
  "sources": [
    { "book": "16-the-design-of-business", "chapter": "03" },
    { "book": "11-design-unbound", "chapter": "04" },
    { "book": "01-this-is-service-design-doing", "chapter": "08" }
  ],
  "nodes": [
    {
      "id": "r1",
      "label": "All three nodes cite zero evidence rows; the acceptance gate cannot pass unti…",
      "evidence": [],
      "fields": {
        "rowKind": "defect",
        "severity": "high",
        "message": "All three nodes cite zero evidence rows; the acceptance gate cannot pass until every node cites the register",
        "rule": "min-evidence-per-node",
        "fix": "Re-derive each node from the register with verbatim quotes attached"
      }
    },
    {
      "id": "r2",
      "label": "Add the roster-constraint document row to the transfer node alongside the rid…",
      "evidence": [],
      "fields": {
        "rowKind": "proposal",
        "severity": "medium",
        "message": "Add the roster-constraint document row to the transfer node alongside the rider quotes",
        "rule": "evidence-sufficiency"
      }
    }
  ],
  "createdAt": "2026-08-19T00:05:12.374Z",
  "updatedAt": "2026-08-19T00:05:12.374Z",
  "status": "final",
  "reviewOf": "7f9fefdc44f5469195106e739112f9ae"
}

Note the shape choices: row labels are the message, cut to 77 characters plus an ellipsis once it passes 80; row ids (r1, r2) keep numbering across successive verdicts on the same artifact, so the log stays a log; a defect carries a mandatory fix while a proposal does not; and reviewOf is the only link — the reviewed artifact points back through its own review.logArtifactId.
