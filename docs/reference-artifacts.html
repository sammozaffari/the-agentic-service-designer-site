Artifact kind reference

An artifact is the platform's unit of work: a typed JSON document in the project's artifacts/ directory. Every artifact carries id, kind, projectId, title, schemaVersion, sources (book/article provenance), nodes, timestamps, and status (draft or final); artifacts written through a method also record methodId, and gate outcomes attach as check (acceptance failures) and review (the verdict and its log). Each node is { id, label, evidence: [{ evidenceId, quote? }], fields } — the fields object holds the kind-specific columns (a journey map's emotion and touchpoint, a KPI tree's baselines), while evidence links the node to the project register.

Kind ids are strings (journey-map, insight-set, review-veto-log), never numbers; the catalog numbers below are a human index, not part of the id.

Two catalogs, stated plainly

There are two kind catalogs and they are not the same size:

  • The design contract — platform/templates/catalog.md specifies 38 kinds, each with a fillable template file, a typed JSON schema, a deterministic renderer spec, and a producing skill. It is the load-bearing requirement that every template in the practice is designed and shipped, and it numbers the kinds 01–38. Six entries carry authored fillable templates today (below); the rest are [draft] catalog entries — fields and references designed, template file pending.
  • The machine registry — suite/packages/knowledge/data/artifact-kinds/*.json holds the 32 kinds the engine checks today, each a JSON schema record (kind, title, nodeLabel, sources). This is the set sd_artifact_write can persist and sd_export_artifact can render.

The relationship: the engine implements 32 of the 38 cataloged kinds. Two catalog entries are designed but deliberately not implemented as machine kinds: orchestration-plan (36) and phase-gate-decision (37) — the Orchestrator's dispatch log and the human's gate record live in the engagement process, not in the typed registry. The remaining gap is naming and granularity drift between the design index and the registry: kinds the catalog spells one way, the registry spells another (insight-register vs insight-set, standards-audit vs service-standard-set), or splits (storyboard-walkthrough ships as two kinds, storyboard and walkthrough-script).

Of the 32 machine kinds, 31 are produced by at least one of the 74 method manifests. The exception is review-veto-log: it is written only by sd_review, never by a method — nothing gates the gate record.

Renderers

Every one of the 32 kinds has a dedicated deterministic renderer in suite/packages/render/src/, dispatched on artifact.kind; an unregistered kind falls back to a legible node listing rather than throwing. The model writes typed JSON and the renderers produce all diagram markup — hand-written diagram syntax by a model is a rejected pattern. Renders land in the project's renders/ directory: derived data, rebuildable from the store at any time via sd_export_artifact (SVG) or folded into the HTML reports from sd_export_report.

Fillable templates

Six kinds have designed, human-fillable templates — the flagship set named in the catalog. Download the markdown form, fill it by hand or with a team, and the same fields are what the engine validates when the artifact is written as JSON:

  • Stakeholder map
  • Ecosystem map
  • Insight register
  • Persona set
  • Journey map
  • Service blueprint

The full catalog with per-kind fields and references is on the templates page.

Anatomy of a review-veto-log

The one kind every engagement accumulates is the review log. A Critic verdict — pass or veto — persists as a review-veto-log artifact whose nodes are the review rows (rowKind, severity, message, rule, fix in fields), linked to its target by reviewOf, and always status: final from birth. Real artifact, from a vetoed journey map:

DATA
{
  "id": "25500d7e4a634befb052cfa956bd4f2f",
  "kind": "review-veto-log",
  "projectId": "veto-demo-50d92ebc",
  "title": "Review: Drafty journey",
  "schemaVersion": 1,
  "sources": [
    { "book": "16-the-design-of-business", "chapter": "03" },
    { "book": "11-design-unbound", "chapter": "04" },
    { "book": "01-this-is-service-design-doing", "chapter": "08" }
  ],
  "nodes": [
    {
      "id": "r1",
      "label": "All three nodes cite zero evidence rows; the acceptance gate cannot pass unti…",
      "evidence": [],
      "fields": {
        "rowKind": "defect",
        "severity": "high",
        "message": "All three nodes cite zero evidence rows; the acceptance gate cannot pass until every node cites the register",
        "rule": "min-evidence-per-node",
        "fix": "Re-derive each node from the register with verbatim quotes attached"
      }
    },
    {
      "id": "r2",
      "label": "Add the roster-constraint document row to the transfer node alongside the rid…",
      "evidence": [],
      "fields": {
        "rowKind": "proposal",
        "severity": "medium",
        "message": "Add the roster-constraint document row to the transfer node alongside the rider quotes",
        "rule": "evidence-sufficiency"
      }
    }
  ],
  "createdAt": "2026-08-19T00:05:12.374Z",
  "updatedAt": "2026-08-19T00:05:12.374Z",
  "status": "final",
  "reviewOf": "7f9fefdc44f5469195106e739112f9ae"
}

Note the shape choices: row labels are the message, cut to 77 characters plus an ellipsis once it passes 80; row ids (r1, r2) keep numbering across successive verdicts on the same artifact, so the log stays a log; a defect carries a mandatory fix while a proposal does not; and reviewOf is the only link — the reviewed artifact points back through its own review.logArtifactId.
