ACP and collaboration records

ASD's Agent Collaboration Protocol (ACP) is a typed JSON event envelope for recording collaboration across humans, roles, services, and host adapters. It gives an engagement a replayable history without pretending that every host can spawn or transport an agent. The current protocol identifier is asd-acp/1.

What the protocol records

An ACP event contains version, protocolVersion, eventId, monotonically increasing sequence, type, actorId, and a JSON-only payload. Event types include:

Type Use
identity identify a human, agent, or service and its host
capability-negotiation record provided/required capabilities and missing capabilities
message record a JSON-safe message between identities
handoff record a role-to-role condition and optional artifact pointer
orchestration record a plan step state
dispatch record a dispatch attempt and capability outcome
retry link a retry to its previous attempt
critic-veto record the artifact review log and reason
human-gate record who approved or rejected a phase transition
error record a structured, retryable or terminal failure

Tool-call records use the same JSON-only boundary and can name the ASD tool, arguments, result, status, and error. Non-JSON values are rejected before an event is recorded.

The current capability contract

The generic CLI/MCP adapter supports exactly:

DATA
{"protocolVersion":"asd-acp/1","capabilities":["record-only"]}

record-only means the adapter can validate and persist a collaboration record. It can represent a queued or unsupported dispatch, an evidence-cited handoff, or a human gate. It cannot make a host process appear, invent a reply, or claim that an external relay delivered a message.

host-agent-spawn is intentionally unsupported on the generic surface. A request that requires it fails closed with a structured unsupported-capability error. A host may provide a real dispatch function, but that must be supplied by the host adapter and proved by a separate live acceptance test. The presence of sd_orchestration_dispatch, a role prompt, or an ACP row is not proof of spawn or transport.

Typed handoffs

When a handoff carries an artifact pointer, the pointer is resolvable in the same project and its optional artifactKind must match the stored artifact. Supplying an artifactKind without an artifactId, or pointing at a missing or mismatched artifact, fails before the handoff is recorded. A handoff without a pointer is still a record of a condition, not evidence that an artifact exists.

DATA
{
  "projectId": "metrovale-access-…",
  "planId": "plan-…",
  "from": "researcher",
  "to": "synthesizer",
  "condition": "Evidence register has been reviewed",
  "artifactId": "artifact-…",
  "artifactKind": "insight-set"
}

The runtime's orchestration tools make this same check for CLI, MCP, and DSH tool calls. The human designer still owns phase decisions.

Host integration pattern

An integration should follow this order:

  1. Exchange identities and capabilities.
  2. Reject missing capabilities before promising a workflow.
  3. Persist an explicit orchestration plan with role and method steps.
  4. Dispatch only with a host capability that is actually present; otherwise record unsupported and stop the branch.
  5. Attach artifact IDs to handoffs once the artifacts resolve.
  6. Record Critic veto/pass and the human phase-gate decision.
  7. Reopen the project and replay the record after reload.

This allows BUZZ to show a visible channel collaboration and DSH to project capabilities into a Studio canvas while preserving the common record contract. It does not make a generic coding-agent client a BUZZ relay or a DSH host.

Validation and examples

The protocol implementation and tests live in suite/packages/core/src/acp.ts and the core/runtime test suites. The generated pack capability manifests and release receipts are the evidence boundary. When documenting an ACP workflow, label each row as recorded, executed, unsupported, or observed-live. Never write a fabricated agent reply into a transcript to make a record look complete.

What ACP does not provide

  • It is not a replacement for MCP JSON-RPC transport.
  • It does not authenticate a user, relay credentials, or discover a BUZZ channel.
  • It does not spawn Claude Code, OpenCode, Codex, Kimi, or another host.
  • It does not turn a role prompt into a durable project artifact.
  • It does not bypass Critic review or the human phase gate.

For actual tool execution use the MCP server or CLI. For the role content carried into a host, see roles and skills. For BUZZ and DSH evidence boundaries, follow their dedicated case-study and workbench receipts.
