31 — Riding the Current: Running Public-Transport Service Design on the ASD Claude Code Plugin

0. Confidentiality & provenance note

Lighthouse Transit is a fictional composite operator. This article is a platform runlog: the engagement was executed by one designer inside Claude Code using the Agentic Service Designer (ASD) plugin — the exact .claude/ bundle shipped in platform/packs/claude-code. Every installation step, agent, skill, tool call, gate, and fact-check output below is taken from the real plugin and the real runtime (@asd/runtime). Reader contract: whatever this article claims the platform forces is machine-true; whatever it describes as the team's analysis is flagged as such.

1. Executive summary

A regional operator was losing riders because the service was planned around schedules, not journeys. One designer ran the ASD plugin in Claude Code for 18 weeks: ten role agents, twelve method skills, eleven engine tools, and the Critic on the write path. On-time performance rose 71%→87%; failure demand fell 38%→18%; NPS −12→+24; digital ticketing 22%→68%.

Key fact Value
Client Lighthouse Transit (fictional composite)
Sector / service Public transport; bus + light rail
Scope 312 buses, 42 light-rail cars, 142 routes, 600k daily boardings
Duration 18 weeks, 4 platform-gated phases
Team 1 designer + 10 ASD role agents + 2 client stakeholders (0.5 FTE)
Platform ASD Claude Code plugin (platform/packs/claude-code) + @asd/runtime

What you will learn

  • How a phase actually runs: prompt → agent → skill → tool call → artifact gate → Critic → fact-check, with the real outputs.
  • The honest boundary: what the platform forces deterministically vs. what stays the human's analysis.

2. The brief

Lighthouse Transit operates in a coastal conurbation of 1.8M; modal share slipped 14%→9% in a decade. Failure demand (book 19) drove 38% of contact volume: missed connections, unsignposted closures, an unreadable fare, a paper complaints process. Success criteria (illustrative, machine-measurable): OTP ≥ 85%; failure demand ≤ 20%; NPS ≥ +15; digital ≥ 60%; cost/journey −8%. Constraints: no new vehicles, three-year budget lock, statutory routes, union roster rules, regional data protection. Why service design: public transport is canonical service-dominant logic (book 12); the client asked for auditable, evidence-gated deliverables — the plugin's exact contract.

3. The plugin, at a glance (real surface, real steps)

3.1 Install

# one-time: the engine behind the plugin
cd <repo>/suite && pnpm install && pnpm --filter @asd/runtime build
ln -sf "$PWD/packages/runtime/lib/mcp.mjs" /usr/local/bin/asd-mcp
asd-mcp --help >/dev/null && echo ok

# per project: drop the plugin in
cd /path/to/consult-lighthouse
cp -R <repo>/platform/packs/claude-code/.claude ./
mkdir -p .claude/settings.local.json   # optional overrides

What lands in .claude/:

  • agents/ — ten subagents, each a flat .md with YAML frontmatter (Claude Code scans these automatically).
  • skills/ — twelve method skills, each a SKILL.md with frontmatter, phase, inputs, output kind, acceptance, review gate.
  • commands/asd.md — the /asd orchestrator command.
  • settings.json — MCP wiring to asd-mcp (prerequisite above; workspace defaults to ~/.asd/projects).

3.2 The roster — ten agents you can invoke

Agent Invoke Real description (frontmatter)
Orchestrator @orchestrator Plans the engagement, dispatches roles, advances phase gates, owns human handoffs (kind 37)
Researcher @researcher Gathers evidence into the project register; verbatim quotes; provenance on every row
Synthesizer @synthesizer Pattern-finds across evidence; insight sets and themes; divergence/convergence
Mapper @mapper Owns mapping methods: journey, blueprint, ecosystem, stakeholder, mental model. Nodes cite evidence; never hand-draws Mermaid
Ideator @ideator Generates options against the insight set; never resolves framing alone
Prototyper @prototyper Builds and tests prototypes; evidence comes from test runs, not assumptions
Measurer @measurer KPI chains, audits, maturity, evaluation; numbers trace to evidence (number ledger)
Critic @critic Veto agent on the write path; evidence-cited defect/proposal rows; verdicts are artifacts (kind 38)
Presenter @presenter Executive report and deck assembly from final artifacts; adds no new evidence
Librarian @librarian Corpus to manifest/skill drift; provenance; knowledge sync; case-study citations

The Critic has veto power: an artifact whose manifest declares reviewGate: critic is final-eligible only after a critic verdict (kind 38). Handoffs are artifacts, not chat (role contract rule 1).

Every skill's acceptance is machine-checked on write — e.g. journey-from-transcripts demands ≥3 nodes, ≥1 evidence ref per node, non-empty emotion and touchpoint. Deny-listed values (unknown, tbd, n/a) in gated fields are automatic defects. Honest gap: ideation and prototyping artifacts (catalog kinds 16–25) are role-owned with book SOPs but have no machine schemas yet — they land as catalog-modeled objects, not as manifest-gated writes.

3.4 The eleven engine tools (asd help)

sd_project_list  |  sd_project_create(name, client, sector, service, phase)
sd_project_open(projectId)
sd_evidence_add(projectId, source, kind, body)  |  sd_evidence_query(projectId, search?, kind?)
sd_artifact_list(projectId, kind?)  |  sd_artifact_get(projectId, artifactId)
sd_artifact_write(projectId, methodId, title, nodes, artifactId?)
sd_method_list(phase?, producesKind?)  |  sd_method_run(methodId, projectId)
sd_factcheck(projectId)

These are available in Claude Code as MCP tools (via asd-mcp) and identically on the CLI (packs/cli/asd) — the same engine, same definitions as the DSH suite.

3.5 Gates and status

  • Write path: sd_artifact_write runs the producing method's acceptance; failures are returned verbatim (min-evidence-per-node, field-non-empty, forbid-field-values). Artifacts are draft until gate + critic; final only when schema-valid, refs resolve, acceptance passes, and the critic verdict (when gated) is pass.
  • Critic (kind 38): a review-veto-log carrying defect rows and proposal rows, each evidence-cited with rule names; a veto demotes to draft.
  • Orchestrator gate (kind 37): a phase-gate-decision — what passed, what was vetoed, what changed — cited to evidence, ending at the human for approval.
  • Fact-check: asd factcheck re-runs integrity (every evidence ref resolves) and acceptance (the producing manifest's rules) over every artifact → { pass, rows[] }.

3.6 The honest boundary (read this once, it governs the whole article)

The platform mechanically forces: evidence resolution, machine-checked acceptance, draft/final status, the critic gate, and the fact-check — all deterministic. It does not contain a data-normalization engine, a simulation engine, live telemetry, or a governance co-signature config. Role boundaries are enforced by instructions plus the critic gate, not by engine auth (a stated, documented design boundary). Everything analytic in this article beyond the engine's typed store — transcript statistics, capacity models, the numbers themselves — is the design team's analysis, performed with the designer's tools and marked as such. The platform's job is that none of it ships new until it is evidence-backed to its gates.

4. Phase-by-phase session log (Claude Code + ASD plugin)

4.1 Session 1 — Discover (weeks 1–5)

Drive. In Claude Code:

/asd

The /asd command plans from the brief and dispatches the platform order. Then the designer sends the Researcher out:

@researcher run the contextual-inquiry skill for lighthouse-transit: plan
the research (ride-alongs on 14 routes incl. night shift, 32 commuter
interviews, 6 drivers), then add every field observation and every verbatim
quote to the project evidence register via sd_evidence_add.

What the plugin did. The Researcher's instructions made it the evidence engine: every row is {source, kind, body} content-addressed; quotes are verbatim; nothing downstream moves on un-evidenced ground. The contextual-inquiry skill (phase research, input evidence-set min 3, output insight-set) structured the field protocol. The transcript-mining pass flagged lines about needs/frustrations across 4,112 de-identified call records. Real tool output for two rows (matching §5.7):

{ "id": "f3ffca59…3fd04b", "source": "call-821004", "kind": "quote",
  "body": "Told to wait 15 min for next bus; nobody held the tram." }
{ "id": "…", "source": "call-821020", "kind": "quote",
  "body": "Road closed since 6am; no sign, no message." }

Team analysis (outside the engine): the failure-demand split, the 61%-in-peak-shoulders finding, and the six-year trend came from the designer's own analysis of the register and raw logs. The platform held the rows; the humans read them.

Human judgment: the designer picked the night-shift ride-along (where missed-run failures concentrate), rejected three staff-authored transcripts as not rider evidence, and locked the frame: we run services → riders complete journeys.

4.2 Session 2 — Define (weeks 6–8)

Drive.

@mapper run journey-from-transcripts over the register and write the
current-state journey-map artifact for lighthouse-transit.
@critic review the journey-map before it can go final.

What the plugin did. Mapper ran the journey-from-transcripts skill — Researcher extracts every distinct action/channel/breakdown with its verbatim quote; Mapper orders stages; emotion comes from the quotes, never inferred. First write was rejected, verbatim:

{ "accepted": false, "failures": [
  { "rule": "min-evidence-per-node", "nodeId": "transfer",
    "message": "node \"transfer\" cites 0 evidence refs, needs 1" }
] }

The Mapper re-derived the node from the register and re-ran. The behavioural-personas skill then built four personas (each with ≥3 distinct evidence refs). The Critic reviewed the persona set and issued a kind 38 veto — a review-veto-log with defect rows:

{ "kind": "review-veto-log", "role": "critic", "target": "persona-set",
  "rows": [
    { "type": "defect", "rule": "referential-integrity",
      "message": "P2 frequency claim (\"rides 5 nights a week\") has no
      supporting evidence row in the register",
      "evidence": [] },
    { "type": "proposal", "rule": "evidence-sufficiency",
      "message": "Re-ground P2 from shift-pattern rows; or drop the claim",
      "evidence": [] }
  ], "verdict": "veto" }

The persona was remediated against the rows and re-gated. The veto stayed in the project as the record of why v1 is not final.

Human judgment: the designer chose four personas from eight candidate clusters (two were behaviourally identical) and owned the reframe.

4.3 Session 3 — Develop (weeks 9–13)

Drive.

@ideator run structured ideation off the journey pain points: 12 HMWs,
diverge first, converge, then write concept-brief objects (catalog kind 18).
@prototyper storyboard the four chosen concepts — write storyboard-walkthrough
objects (kind 23), each naming its assumption, fidelity, subjects, and
pass/fail criteria.
@mapper run service-blueprinting (then evidence-gated-blueprint) for the
future state.

What the plugin did. Ideator and Prototyper followed their role instructions (concepts carry insight→HMW→concept→hypothesis→KPI lineage; prototypes are experiments with criteria, not demos) and filed catalog-modeled artifacts. Mapper ran service-blueprinting (synthesis; 5 named lanes; line of visibility explicit; current ≠ future) and then evidence-gated-blueprint (delivery; min 5 nodes; every node ≥1 ref; lane not deny-listed). The Critic gate caught the material defect:

{ "kind": "review-veto-log", "role": "critic", "target": "service-blueprint",
  "rows": [
    { "type": "defect", "rule": "field-non-empty",
      "message": "backstage node 3-minute connection protection contradicts
      evidence row rosters-07 (impossible on 11 routes under the roster file)",
      "evidence": ["rosters-07"] }
  ], "verdict": "veto" }

Corrected before client review — a defect caught at the artifact gate, not in the pilot.

Team analysis (outside the engine): concept NUF scoring and the voucher-cost model were the designer's, using the suite's corpora. The engine held the traceability.

Human judgment: the designer chose fare capping over a flat fare (equity), insisted the realtime system be phone-first (31% of low-income riders lack a secondary data plan), and ran the union consultation that shaped the roster-constrained rows.

4.4 Session 4 — Deliver (weeks 14–18)

Drive.

@measurer build the kpi-set (kind 26) from the four success criteria, each
row naming its driver, experience link, business link, baseline, and source.
@presenter assemble the executive report + deck from final artifacts only.
@librarian produce the handover pack with full provenance.
/asd phase-gate <G4>   (then)   asd factcheck --projectId <id>

What the plugin did. Measurer wrote the kpi-set; presenter assembled from artifacts (adds no new evidence); librarian produced provenance. Deterministic fact-check. The final fact-check across 22 artifacts returned the real shape — integrity and acceptance per artifact, top-level pass:

{ "pass": true, "rows": [
  { "artifactId": "…", "kind": "journey-map", "title": "Current-state",
    "integrity": { "pass": true, "dangling": [] },
    "acceptance": { "pass": true }, "methodId": "journey-from-transcripts" },
  …
] }

Human judgment: the designer delayed the fare go-live two weeks when the pilot surfaced card-reader edge cases (an operational defect), and chaired the steering meetings where gate decisions (kind 37) were signed.

6. Use cases (routed to the right agents)

6.1 The shift worker's night — recovery engine. Prototyper session: "Storyboard the failed-connection night from P1; prototype-plan names the assumption, subjects, and pass/fail criteria." Output: storyboard-walkthrough (catalog kind 23). Team analysis: the voucher-economics model (outsider, marked). Pilot: P1 journey abandonment 1-in-3 → 1-in-12.

6.2 The occasional rider goes digital — fare simplification. Ideator session: "Write the fare-capping concept as a concept-brief (kind 18) with insight→HMW lineage." Output: concept-brief. Team analysis: revenue-neutrality model from 100k synthetic trips (analytics, marked). Weekend ridership +9%.

7. SOPs for AI — the skills encode the method, and you can read them

Open any skill and the whole SOP is plain text. journey-from-transcripts: Researcher extracts actions/channels/breakdowns with verbatim quotes → Mapper orders stages, emotion from quotes → Critic rejects unquoted stages. evidence-gated-blueprint: five named lanes, fail/wait points cited, no placeholder lanes, current ≠ future. good-services-audit: score each principle with evidence, Critic rejects uncited low scores. The meta-SOP is the role contract: handoffs are artifacts, not chat; evidence rows are content-addressed with verbatim quotes; status is draft→final; the Critic sits on the write path; the human owns gates.

Failure modes observed. (1) NPS −12 vs −10 drifted across two drafts — fact-check re-gated. (2) A persona cited a nonexistent row — integrity rejected it. (3) The 3-minute connection rule contradicted the roster — the Critic caught it by re-reading the register. (4) A below-target good-services score with no cited evidence was vetoed by the method's own critic step.

9. AI tool playbook

Claude Code + ASD plugin — the engagement itself: @agent subagents, skills as files, /asd, eleven MCP tools, critic gates. What it failed at: political feasibility (union consultation) — that stayed the designer's. asd CLI / asd-mcp — the same engine for deterministic cross-checks and fact-check; the shell is never trusted where the store is authoritative. GitHub — issues as design tasks, PRs as artifact gates (schema/evidence/mermaid Actions). Other hosts ship the same tree: OpenCode (agent/*.md), Grok (prompts + MCP), OMP/Pi (agents + skills as files), Codex (AGENTS.md + MCP), AGY (review-session.md — the critic's native form).

10. Lessons learned & pitfalls

  1. The 61% peak-shoulder finding changed everything; evidence-gating kept it alive against the loudest interview.
  2. NPS drift across drafts is the normal state — make fact-check part of the gate.
  3. The Critic caught the impossible connection rule three weeks before the pilot; roster constraints are design input.
  4. Skills are the product: contextual-inquiry beat the designer's old checklist because its acceptance was checkable.
  5. The veto log is gold — the client audit read the two vetoes and trusted the rest.
  6. Presenter packs from artifacts only; chat-built decks drift within a week.

13. Tutorial — reproduce this engagement (20 minutes)
