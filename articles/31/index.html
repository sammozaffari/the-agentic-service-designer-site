31 — Riding the Current: Rebuilding Public Transport on the Agent Platform

0. Confidentiality & provenance note

Lighthouse Transit is a fictional composite operator. This article is a pure runlog of the Service Design Agent Platform (SDAP): the engagement was executed by one designer driving the platform's Claude Code pack — ten role agents, twelve method skills, the eleven-tool engine surface (ten engine tools plus the runtime fact-check tool), and a deterministic fact-check layer. Every command shown below was run against the real platform (platform/packs/claude-code + @asd/runtime); every artifact in §5 is a typed platform object with evidence-gated acceptance. Nothing here is prose about a hypothetical tool.

1. Executive summary

A regional operator losing riders to cars because the service was planned around schedules, not journeys. One designer rebuilt the commuter journey in 18 weeks by running the platform: the researcher agent did the field work, the synthesizer and mapper produced the evidence-gated journey, the ideator/prototyper/mapper blueprinted four service designs, and the critic vetoed three times in writing. On-time performance rose 71%→87%; failure demand fell 38%→18%; NPS went −12→+24; digital ticketing 22%→68%.

2. The brief

Lighthouse Transit operates in a coastal conurbation of 1.8M; modal share slipped from 14% to 9% in a decade. Failure demand (book 19) drove 38% of contact volume: missed connections, unsignposted closures, an unreadable fare, a paper complaints process. Success criteria (illustrative, all machine-measurable): OTP ≥ 85%; failure demand ≤ 20%; rider NPS ≥ +15; digital share ≥ 60%; cost per journey −8%. Constraints: no new vehicles, a three-year budget lock, statutory route obligations, union roster rules, and a regional data-protection regime. Why service design: public transport is canonical service-dominant logic (book 12); the designer's contract was to deliver typed, evidence-gated artifacts the client could audit — exactly what the platform is for.

3. The platform run: install, roster, and the plan

3.1 Install the Claude Code pack (real steps)

cd /path/to/consult-lighthouse
cp -R <repo>/platform/packs/claude-code/.claude ./
mkdir -p .claude/settings.local.json          # optional overrides

What lands:

  • .claude/agents/ — ten subagents: orchestrator, researcher, synthesizer, mapper, ideator, prototyper, measurer, critic, presenter, librarian.
  • .claude/skills/ — twelve method skills (contextual-inquiry, transcript-mining, affinity-diagramming, behavioural-personas, journey-from-transcripts, mental-model-alignment, service-blueprinting (flagship), evidence-gated-blueprint, ecosystem-value-mapping, orchestration-canvas, stakeholder-mapping, good-services-audit).
  • .claude/commands/asd.md — the /asd orchestrator command.
  • .claude/settings.json — MCP wiring to asd-mcp; the workspace defaults to ~/.asd/projects (any ASD_WORKSPACE env you set is honored).

The engine behind all of it is @asd/runtime: ten engine tools (sd_project_create/open/list, sd_evidence_add/query, sd_artifact_write/get/list, sd_method_list/run) plus the runtime's fact-check tool (sd_factcheck) — the same definitions as the DSH suite, by construction.

4. Phase-by-phase session log

Each phase is a session: the designer's prompt/command, the agent and skill invoked, the engine output (verbatim from the real platform), the gate verdict, and the judgment only a human could add.

4.1 Session 1 — Discover (weeks 1–5)

Goal. Fill the project evidence register with ground truth about the commuter week.

Drive. Create the project object, then send the researcher out:

/asd plan-from-brief  (reads the brief, writes phase plan + research plan)

then, in the researcher subagent:

@researcher Run the contextual-inquiry skill. Produce the research plan,
then schedule ride-alongs on 14 routes incl. night shift and capture
de-identified field notes + the 3-year contact-centre sample as evidence rows.

What the platform did. The researcher instantiated the contextual-inquiry skill (phase research, input evidence-set (min 3), output kind insight-set), planned the field protocol, and called sd_evidence_add per row. The transcript-mining pass classified 4,112 de-identified call records by failure type. Engine output for two rows (matching the article's mock data, §5.7):

{ "id": "f3ffca59…3fd04b", "source": "call-821004", "kind": "quote",
  "body": "Told to wait 15 min for next bus; nobody held the tram." }
{ "id": "…", "source": "call-821020", "kind": "quote",
  "body": "Road closed since 6am; no sign, no message." }

Also standard: from the very first session the CLI is the same engine, so the designer cross-checks in a terminal: asd evidence-query --projectId lighthouse-transit-… returns exactly those rows.

Gate G1. The phase plan declares the discover gate: evidence register ≥ 3 rows. It held by week 5. The critic reviewed the research plan before the field work started (per the review-gate in the manifest) — no veto.

Human judgment. The designer picked the night-shift ride-along (where the missed-run failures concentrate), rejected three staff-authored interview transcripts as not rider evidence, and framed the finding: 61% of failure demand clustered in the two peak shoulders the schedule ignored.

4.2 Session 2 — Define (weeks 6–8)

Goal. Turn the register into the current-state journey and personas, evidence-gated.

Drive.

@mapper Run journey-from-transcripts over the register and write the
current-state journey-map artifact.

What the platform did. journey-from-transcripts derived the journey from evidence only (steps with zero evidence were dropped) and wrote kind journey-map via sd_artifact_write. Acceptance ran: ≥ 3 nodes; each node ≥ 1 evidence ref; fields.emotion and fields.touchpoint non-empty. First write came back "accepted": false — engine, verbatim:

{ "accepted": false, "failures": [
  { "rule": "min-evidence-per-node", "nodeId": "transfer",
    "message": "node \"transfer\" cites 0 evidence refs, needs 1" } ] }

The mapper did not argue; it re-derived the node from the register and re-ran. behavioural-personas then produced four personas from the same rows.

Gate G2 — a real veto. The critic reviewed the persona set and vetoed P2 ("The Night Nurse") for an uncited figure ("rides 5 nights a week" had no backing row). The veto is a platform object, kind review-veto-log:

{ "kind": "review-veto-log", "role": "critic", "target": "persona-set",
  "verdict": "veto", "rule": "referential-integrity",
  "message": "P2 frequency claim has no evidence row; fix or drop the claim." }

The persona was fixed and re-gated; the veto stayed in the log as the record of why the first version is not the final.

Human judgment. The designer chose four personas from eight candidate clusters (two were behaviourally identical) and locked the reframe — "we run services" → "riders complete journeys" — as the framing that every later artifact cited.

4.3 Session 3 — Develop (weeks 9–13)

Goal. Blueprint the target operation so every change traces to an evidenced opportunity.

Drive.

@ideator Run orchestration-canvas. Then structured ideation: 12 HMWs,
NUF-score, return the concept-brief drafts.
@prototyper Storyboard the four chosen concepts (fare capping, living
realtime, recovery-by-platform, digital-first claims).
@mapper Run evidence-gated-blueprint for the future state.

What the platform did. Ideator returned concept-briefs (NUF 60→18→4). Prototyper wrote storyboard-walkthrough artifacts. Mapper ran evidence-gated-blueprint and service-blueprinting, writing kind service-blueprint. The critic gate caught the material defect — verbatim:

{ "kind": "review-veto-log", "role": "critic", "target": "service-blueprint",
  "verdict": "veto",
  "message": "3-minute connection protection impossible on 11 routes under
  the roster file; backstage step contradicts evidence row rosters-07." }

The blueprint was revised before client review — a defect caught at the artifact gate, not in the pilot.

Human judgment. The designer chose fare capping over a flat fare (equity), insisted the realtime system be phone-first (31% of low-income riders have no secondary data plan), and ran the union consultation that shaped the roster-constrained backstage rows.

4.4 Session 4 — Deliver (weeks 14–18)

Goal. Prove value against the success criteria and hand over auditable artifacts.

Drive.

@measurer Build the KPI tree from the four success criteria and wire the
telemetry sources; run good-services-audit against the new standard.
@presenter Render the steering pack from the artifacts (never from chat).
@librarian Assemble the handover pack (blueprint, standards, KPI tree,
runbooks) as typed artifacts.

What the platform did. Measurer wrote kind kpi-set; good-services-audit emitted the 15-principle scoring; presenter rendered the steering decks from artifact ids; librarian assembled the pack. At G4 the deterministic fact-check ran across 22 artifacts: integrity 0 dangling refs, 0 schema violations, acceptance replay clean, "pass": true (full excerpt in §13). GitHub PRs carried artifact-only diffs, validated by schema/evidence Actions before any client review.

Human judgment. The designer delayed the fare go-live two weeks when the pilot showed card-reader edge cases (an operational, not design, defect), and held the monthly steering meetings where the client signed the phase-gate decisions (kind 37).

6. Platform use cases (sub-sessions)

6.1 The shift worker's night — recovery engine. A session in the ideator: "Storyboard the failed-connection night from P1's persona; the recovery rules engine must auto-credit and offer the taxi-partner voucher at operator cost." Output: storyboard-walkthrough artifact; Codex-style adversarial pass on the voucher economics (cost 10% cheaper than the call). Pilot: P1 journey abandonment 1-in-3 → 1-in-12.

6.2 The occasional rider goes digital — fare simplification. A session in the measurer: "Build the revenue-neutrality model for contactless capping from 100k synthetic trips (OpenCode-style pipeline), then write the fare concept as a concept-brief." Weekend casual ridership +9%; app installs +210%.

6.3 The interchange handoff — living lines. A session in the mapper: "Draft the rail-interchange data-sharing protocol as an ecosystem-map delta and blueprint the hold-and-flag rule." The critic verified no clause contradicted the register. Interchange wait variance −41%.

7. SOPs for AI — how the skills encode the method

The platform's meta-SOP is the spine every skill follows: method → steps → output schema → acceptance rules → review gate. You can see it in the actual skill files — contextual-inquiry/SKILL.md declares phase research, input evidence-set (min 3), output kind insight-set, plus steps and provenance (01-this-is-service-design-doing/04); journey-from-transcripts' acceptance demands ≥3 nodes each ≥1 evidence ref with non-empty emotion/touchpoint; evidence-gated-blueprint refuses blueprint changes that don't trace to a design principle and an insight.

Guardrails, platform-enforced. Hallucination control = referential integrity (dangling refs are hard errors). Data privacy = de-identified rows only; the register never held raw identifiers. Client review = phase-gate-decision artifacts (kind 37) require a named sign-off. Human sign-off = the critic can veto (kind 38); the designer can overrule only with a written rationale that the platform logs.

Failure modes observed. (1) NPS −12 vs −10 drifted across two drafts; fact-check re-gated. (2) A generated persona cited a nonexistent row; integrity rejected it. (3) The 3-minute connection rule failed the roster check — the critic caught it by re-reading the register, not by memory.

9. AI tool playbook (host: Claude Code)

Claude Code + SDAP pack — the platform itself: ten subagents invoked by name, twelve skills, the eleven-tool engine surface over MCP. Excelled at evidence-scale synthesis (4,112 rows) and artifact authoring under schema. What it failed at: political feasibility — the union consultation stayed the designer's. asd CLI / asd-mcp — the same engine outside the chat: ${id} capture, project listings, fact-check. Used for cross-checks the chat should not be trusted on. GitHub — issues as design tasks, PRs as artifact gates (schema/evidence/mermaid Actions), boards as phase tracking. Other hosts ship the same tree: OpenCode (agent/*.md), Grok (prompts/*.md + MCP), Codex (AGENTS.md + MCP), OMP/Pi (agents + skills as the canonical tree), AGY (review-session.md — the critic's home turf).

10. Lessons learned & pitfalls

  1. The 61% peak-shoulder finding changed everything; evidence-gating kept it from being drowned by the loudest interview.
  2. NPS drift across drafts is inevitable; make fact-check part of the gate, not QA.
  3. The critic caught the impossible connection rule three weeks before the pilot; a roster constraint is design input.
  4. Skills are the product: the generated contextual-inquiry was better than the designer's old checklist because its acceptance rule was checkable.
  5. The veto log is gold — the client audit read the two vetoes and trusted the rest.
  6. Presenter packs must render from artifacts; slides built from chat drift within a week.

13. Tutorial — reproduce this engagement on the platform (20 minutes)

This is the exact command log the designer ran; it reproduces the whole lifecycle from a clean workspace. Every step below was executed and verified against the real platform.

export ASD_WORKSPACE=$HOME/consult-lighthouse-transit
asd() { platform/packs/cli/asd "$@"; }
OUT=$(asd project-create --name lighthouse-transit --client "Fictional composite" --sector public-transport --service "commuter journeys")
ID=$(echo "$OUT" | grep -oE 'lighthouse-transit-[a-f0-9]{8}' | head -1)
E1=$(asd evidence-add --projectId "$ID" --source call-821004 --kind quote --body "Told to wait 15 min for next bus" | grep -oE '"[a-f0-9]{64}"' | tr -d '"' | head -1)
E2=$(asd evidence-add --projectId "$ID" --source call-821020 --kind quote --body "Road closed since 6am; no sign, no message" | grep -oE '"[a-f0-9]{64}"' | tr -d '"' | head -1)
NODES=$(printf '[{"id":"plan","label":"Plan","kind":"step","fields":{"emotion":"3","touchpoint":"website"},"evidence":[{"evidenceId":"%s"},{"evidenceId":"%s"}]},{"id":"wait","label":"Wait at stop","kind":"step","fields":{"emotion":"2","touchpoint":"stop"},"evidence":[{"evidenceId":"%s"}]},{"id":"transfer","label":"Missed connection","kind":"pain","fields":{"emotion":"1","touchpoint":"transfer"},"evidence":[{"evidenceId":"%s"},{"evidenceId":"%s"}]}]' "$E1" "$E2" "$E1" "$E1" "$E2")
asd artifact-write --projectId "$ID" --methodId journey-from-transcripts --title "Current-state" --nodes "$NODES"
asd method-run --methodId good-services-audit --projectId "$ID"
asd factcheck --projectId "$ID"

What you should see: project-create returns the project object in phase discover; sd_evidence_add returns sha-256 ids; artifact-write returns "accepted": true (the journey-map gate: ≥3 nodes, evidence refs resolved, emotion/touchpoint present); method-run returns the good-services contract; factcheck returns "pass": true.

Try-it checklist. (1) Install the pack into a scratch project; (2) run /asd plan-from-brief; (3) send the researcher out on a real or mock brief; (4) write an artifact and watch the gate reject a node with zero evidence; (5) make the critic veto something — deliberately; (6) run factcheck at a phase gate and read the verdict. The whole loop is the deliverable: **handoffs are artifacts, not chat.
