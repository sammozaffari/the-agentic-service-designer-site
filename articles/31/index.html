01 · Executive summary

Executive summary

A regional operator was losing riders because the service was planned around schedules, not journeys. In this illustrative scenario, one designer uses the ASD operating model for 18 weeks: ten role agents, a 74-skill library whose twelve machine-gated method skills carry the engagement spine, 29 engine tools, and the Critic's evidence-cited verdicts on every gated artifact. The outcome figures remain illustrative: on-time performance 71%→87%; failure demand 38%→18%; NPS −12→+24; digital ticketing 22%→68%.

Key fact Value
Client Lighthouse Transit (fictional composite)
Sector / service Public transport; bus + light rail
Scope 312 buses, 42 light-rail cars, 142 routes, 600k daily boardings
Duration 18 weeks, 4 human-gated phases
Team 1 designer + 10 ASD role agents + 2 client stakeholders (0.5 FTE)
Platform ASD Claude Code plugin (platform/packs/claude-code) + vendored asd MCP server + CLI shim

  • How an illustrative phase runs: prompt → agent → skill → tool call → artifact gate → Critic verdict → fact-check, with synthetic outputs, including the failures.

02 · The brief

The brief

Lighthouse Transit operates in a coastal conurbation of 1.8M; modal share slipped 14%→9% in a decade. Failure demand (book 19) drove 38% of contact volume: missed connections, unsignposted closures, an unreadable fare, a paper complaints process. Success criteria (illustrative, machine-measurable): OTP ≥ 85%; failure demand ≤ 20%; NPS ≥ +15; digital ≥ 60%; cost/journey −8%. Constraints: no new vehicles, three-year budget lock, statutory routes, union roster rules, regional data protection. Why service design: public transport is canonical service-dominant logic (book 12); the client asked for auditable, evidence-gated deliverables — the plugin's exact contract.

03 · Approach

The plugin, at a glance (source-verified surface, illustrative steps)

3.1 Install

From the pack README (platform/packs/claude-code/README.md), verbatim:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The marketplace manifest is platform/packs/.claude-plugin/marketplace.json; the plugin manifest is the pack's .claude-plugin/plugin.json. MCP wiring is the plugin-root .mcp.json, which Claude Code loads for installed plugins automatically; ${CLAUDE_PLUGIN_ROOT} resolves inside the installed plugin, so the vendored server under mcp/ needs no PATH entry and no sibling checkout. The README also documents a manual-copy install (drop agents, skills, commands into a project's .claude/, copy mcp/ and .mcp.json to the project root, and rewrite ${CLAUDE_PLUGIN_ROOT} to .). There is no symlink-into-/usr/local/bin step; that path is obsolete.

What lands with the plugin:

  • agents/ — the ten role agents as native Claude Code subagents, each a flat .md with YAML frontmatter.
  • skills/ — 74 skill directories, one SKILL.md each, generated from the suite's method manifests (with the hand-authored flagship service-blueprinting replacing its generated twin).
  • commands/asd.md — the /asd orchestrator command.
  • mcp/ + .mcp.json — the vendored asd-mcp server: self-contained bundle plus knowledge corpus. No npm install, nothing on PATH.

The CLI shim platform/packs/cli/asd is the pack-local executable outside a host. The current article evidence verifies a copied pack in an isolated disposable environment; the command transcript below is illustrative and does not claim a host install or a live project run.

Presenter @presenter Executive report and deck assembly from final artifacts; adds no new evidence
Librarian @librarian Corpus to manifest/skill drift; provenance; knowledge sync; case-study citations

The Critic is the veto role: any artifact whose method manifest declares reviewGate: critic is final-eligible only after a Critic verdict. Every verdict lands as a review-veto-log artifact — evidence-cited defect and proposal rows — and a veto demotes the target back to draft. Handoffs are artifacts, not chat (role contract rule 1). Phase gates themselves are human decisions: the engine has no phase-gate artifact kind, and none is claimed anywhere in this article.

3.5 Gates and status — the lifecycle the engine actually enforces

  • Write path. sd_artifact_write runs structural integrity (a dangling evidence ref is a hard error) plus the producing method's acceptance rules. Crucially: a failing write is still persisted — the artifact lands as status: draft with check: { pass: false, failures: [...] } and the same list repeated top-level. You remediate by writing again with --artifactId, updating the same draft in place.
  • Review. sd_review --verdict pass flips a clean draft to final and stamps review: { verdict, logArtifactId }. A pass cannot carry defect rows and requires at least one review row with a project-resolving evidenceId. --verdict veto demotes the artifact to draft. Either way the engine writes a review-veto-log artifact (status final, linked to its target via reviewOf) whose nodes carry the rows: { rowKind: "defect" | "proposal", severity: "critical" | "high" | "medium" | "low", rule, message, fix, evidenceId? } — fix is required on defect rows.
  • Fact-check. sd_factcheck re-runs, over every artifact: (1) integrity — every cited evidence ref resolves; (2) acceptance — the producing manifest's rules, re-asserted against the live registry; (3) the review-gate assertion — a final artifact under a critic gate must carry a pass verdict. Output is { pass, rows[] }; the CLI exits 1 when any row fails.
  • Phase gates. Human. The designer reads the review board (sd_review_list) and the fact-check, then decides. The engine records no gate artifact.

3.6 The honest boundary (read this once, it governs the whole article)

The platform mechanically forces: evidence resolution, machine-checked acceptance, draft/final status, evidence-cited review verdicts, and the fact-check — all deterministic. It does not contain a data-normalization engine, a simulation engine, live telemetry, or a governance co-signature config. Role boundaries are enforced by instructions plus the review path, not by engine auth (a stated, documented design boundary). Everything analytic in this article beyond the engine's structured store — transcript statistics, capacity models, the numbers themselves — is the design team's illustrative analysis, performed with the designer's tools and marked as such. The platform's job is that none of it ships new until it is evidence-backed to its gates.

04 · The work, phase by phase

Phase-by-phase session log (Claude Code + ASD plugin)

The engagement arc is the UK Design Council Double Diamond — Discover, Define, Develop, Deliver — which maps onto the platform's phase tags (research, synthesis, ideation/prototyping, delivery/measurement); the TISDD loop (book 01) runs inside it as research → ideation → prototyping → implementation.

06 · Use cases

Use cases (routed to the right agents)

6.1 The shift worker's night — recovery engine. Prototyper session: "Storyboard the failed-connection night from P1 with storyboard-authoring; the storyboard names the assumption, subjects, and pass/fail criteria." Output: a storyboard artifact plus a concierge-pilot plan (concierge-pilot skill). Team analysis: the voucher-economics model (outside the engine, marked). Pilot: P1 journey abandonment 1-in-3 → 1-in-12.

6.2 The occasional rider goes digital — fare simplification. Ideator session: "Author the fare-capping concept with concept-brief-authoring, insight→HMW lineage intact." Output: a concept-set artifact. Team analysis: revenue-neutrality model from 100k synthetic trips (analytics, marked). Weekend ridership +9%.

6.3 The interchange handoff — living lines. Mapper session: "Re-run ecosystem-value-mapping on the interchange partners, then draft the delta into the evidence-gated blueprint variant." The Critic's verdict on the variant cited the register; no clause contradicted it. Interchange wait variance −41%.

07 · SOPs for AI

SOPs for AI — the skills encode the method, and you can read them

Open any skill and the whole SOP is plain text. journey-from-transcripts: Researcher extracts actions/channels/breakdowns with verbatim quotes → Mapper orders stages, emotion from quotes → Critic rejects unquoted stages (gate). evidence-gated-blueprint: five named lanes, fail/wait points cited, deny-listed lane names rejected, current ≠ future. good-services-audit: score each principle with evidence; the Critic step rejects uncited low scores. The meta-SOP is the role contract: handoffs are artifacts, not chat; evidence rows are content-addressed with verbatim quotes; status is draft→final through sd_review; the Critic's rows are required schema, not vibes; the human owns gates.

Failure modes observed. (1) NPS −12 vs −10 drifted across two drafts — fact-check re-gated. (2) A persona cited a nonexistent row — integrity made the write a hard error. (3) The 3-minute connection rule contradicted the roster — the Critic caught it by re-reading the register (the veto log of §4.2). (4) A field note went in as kind observation and the tool refused it — evidence kinds are quote, telemetry, document, full stop. (5) A rejected write still lands as a draft with its failures attached — remediate the same id with --artifactId; do not leave failing drafts lying around, because sd_factcheck will (correctly) report pass: false and exit 1 over them.

10 · Lessons learned

Lessons learned & pitfalls

  1. The 61% peak-shoulder finding changed everything; evidence-gating kept it alive against the loudest interview.
  2. NPS drift across drafts is the normal state — make fact-check part of the gate.
  3. The Critic caught the impossible connection rule three weeks before the pilot; roster constraints are design input.
  4. Skills are the product: contextual-inquiry beat the designer's old checklist because its acceptance was checkable.
  5. The veto log is gold — the client audit read the review-veto-log artifact, traced reviewOf to the journey map, and trusted the rest.
  6. Presenter packs from artifacts only; chat-built decks drift within a week.
  7. A failing write is a persisted draft, not a refusal — treat check.failures as a work queue and remediate by id.
