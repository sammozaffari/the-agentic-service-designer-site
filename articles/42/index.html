00 · Provenance note

Provenance note

Copperline Chicken — 2,000 charcoal-grill stores, 41,300 crew, a support centre in Port Meridian — is a fictional composite. Every person, quote, figure, and outcome in this article and the linked artifacts is synthetic. No real company, store, or person is described.

The lane needs its own boundary note. Article 41's channel was a simulated-but-faithful rendering of channel coordination; the terminal transcripts here are simulated run logs following each CLI's real conventions — codex exec, kimi chat, agy run, zai exec — with our OMP plugins and ASD MCP bundles mounted as we actually mount them. 01 · Executive summary

Executive summary

One engagement, three lanes. Lane 1 (Article 41) ran Copperline 2000 through a BUZZ channel with role runtimes replying under their own identities. Lane 2 — this article — runs it with no channel at all: five terminal sessions, four coding-agent CLIs, six plugins from OMP (our open plugin library), and the six ASD MCP bundles exposing 29 tools, 225 resources, and 10 prompts. Lane 3 (Article 43) will hand the same canon to DSH plugin agents.

The point of a second lane is not preference, it is proof: the practice does not live in the collaboration surface. The canon is the contract, the note-ID band map is the interface between agents, the artifacts are the deliverables. Change every tool and the deliverable set should not move — and it did not: same 14 artifacts, same 560 notes, same canon numbers, from a shell prompt instead of a channel.

02 · Motivation

Why a terminal lane

A channel UI optimizes for visibility: stakeholders watch work happen. A terminal optimizes for scriptability, reproducibility, and headless runs — the three properties that made this lane worth running:

  1. Everything is a command, so everything is replayable. Session 4's analysis→proposals→deck chain is a YAML file; re-run it against a revised canon and you get a revised portfolio with the same note bands — the basis of proposal 10, Blueprint-as-Living-Document.
  2. No UI means CI means. The fact-check loop (session 5) ran as a plain exit-code gate: 560 note IDs, 560 unique, 0 collisions, or the run fails. Nothing that needs a person clicking a channel can hang off a nightly job.
  3. Per-CLI strengths are real and worth routing around. In this engagement's pattern — and this is our observed pattern, not a benchmark — Codex held long structured generation best (the 180.9 KB blueprint in one coherent pass), Kimi's long context synthesized the whole 88.3 KB interview corpus in a single pass with no chunk seams, AGY earned its keep as pipeline glue, and ZAI's critique caught contract defects the generators are blind to.

That routing is a judgment call, framed here as this engagement's pattern: canon §5 seated Codex CLI and Kimi CLI as the coding-agent advisors observing the lane-1 channel; in this lane they do the work, joined by AGY and ZAI, which never appear in the channel.

03 · Setup

The working setup

One directory, one source of truth. Everything the CLIs needed lived in engagement/copperline-2000/, and every session began by reading canon.md — the same 8.1 KB file lane 1 treated as authoritative:

TREE
engagement/copperline-2000/
├── canon.md                  ← single source of truth (8.1 KB, 10 sections)
├── .mcp.json                 ← six ASD bundles mounted as asd:// resources
├── pipelines/
│   └── copperline-report.yaml← AGY chain: analysis → proposals → deck
├── research/raw/             ← corpus: 88.3 KB interviews · 35.0 KB surveys · 33.7 KB channels
└── artifacts/                ← the shared 14-artifact set (linked as ../41/artifacts/…)

The MCP config is deliberately boring — six bundles, mounted read-only, shared by all four CLIs so they cite the same catalog and book chapters:

Across the six bundles: 29 tools, 225 resources, 10 prompts — the same sd_* tool surface Article 39 documented on the channel host, consumed here from the shell. OMP plugins loaded per invocation, so each session's transcript records exactly which contracts were in force. This engagement's library:

  • omp/asd-roles — the ten ASD role prompts (researcher, mapper, critic, …) as CLI-invocable personas
  • omp/evidence-ledger — deterministic claim and note-ID verification
  • omp/html-render — self-contained artifact rendering with the house color code (canon §6.3)
  • omp/note-id — allocation and enforcement of the continuous N001–N560 band map
  • omp/canon-guard — injects the canon and fails runs that contradict it
  • omp/pipeline — AGY-compatible step chaining with artifact-to-artifact dependencies
04 · The work, session by session

Session-by-session walkthrough

Five sessions, one per phase. Each block is the simulated run log of the session's headline invocation; sibling invocations (different kind mount, different band) produced the remaining artifacts and are elided. Session boundaries were the human gates — the owner read the output and typed the next command.

Session 1 — Brief (Codex)

The brief locks scope before anything else exists. Codex planned four steps, read the canon, and rendered the kind-01 design brief with its own closing note band:

TERMINAL — session 1/5 · brief
[sd@meridian copperline-2000] $ codex exec --plan \
    "compose design-brief per canon §5 structure and §8 proposal inventory;
     kind 01 design-brief; cite 01/02 and 01/07; embed house color code §6.3;
     allocate notes N501–N540" \
    --mount asd://catalog/kinds/01-design-brief \
    --mount asd://books/01-this-is-service-design-doing/07 \
    --plugin omp/asd-roles:presenter --plugin omp/html-render \
    --plugin omp/note-id --plugin omp/canon-guard --from canon.md \
    > artifacts/brief.html

Session 3 — Blueprint (Codex + ZAI critique)

The blueprint is the engagement's center of gravity: kind 12, full operation, six lanes, note-range contract N001–N220. 05 · Tooling

The OMP plugin library

OMP is our open plugin library: small, named, versioned contracts that any of these CLIs can load per invocation. Six plugins carried this engagement:

Plugin What it contributed here Why not ad-hoc prompting
omp/asd-roles The ten ASD role prompts as CLI personas — presenter wrote the brief, researcher ran the corpus pass, critic ran both ZAI checks A role typed into a prompt drifts per session; a plugin pins the persona, its prohibitions, and its stop conditions
omp/note-id Allocated the N001–N560 band map and rejected any artifact that renumbered or collided Numbering discipline is exactly what free-form generation breaks first
omp/evidence-ledger Row import in session 2; the fail-closed whole-set verification in session 5 Turns "please cite your sources" into an exit code
omp/html-render Self-contained artifacts with the canon §6.3 hexes, sticky legends, print-friendly layout Visual contract compliance is mechanical — generators left alone will re-pick colors
omp/canon-guard Injected canon.md into every Codex run and failed outputs contradicting canon numbers The canon wins (canon preamble) — this makes "wins" enforceable rather than aspirational
omp/pipeline The AGY-compatible step chain with band-level input contracts Chains declared as data re-run on a revised canon; chat-orchestrated chains exist only in their own transcript

The pattern across all six: plugins beat ad-hoc prompting wherever the requirement is repeatability. A prompt is a suggestion; a plugin is a versioned contract with a failure mode. When lane 3 re-runs this engagement with different agents, five of the six load unchanged.

06 · Integration

MCP in the terminal lane

All four CLIs mounted the same six ASD bundles — 29 tools, 225 resources, 10 prompts — so "which catalog did you cite?" has one answer. Resources did the heavy lifting in this lane:

  • Book chapters. asd://books/01-this-is-service-design-doing/07 rode the brief session; asd://books/09-mapping-experiences/05-service-blueprints rode the blueprint session. Artifacts cite chapters as NN/CH per canon §6.2, and those citations resolve to mounted resources, not memory.
  • Template kinds. Every artifact's kind mount — 01 design-brief, 05 stakeholder-map, 06 ecosystem-map, 07 insight-register, 09 persona-set, 11 journey-map, 12 service-blueprint, 28+32 analysis, 31 opportunity-matrix, 33 presentation-deck — came from asd://catalog/kinds/….
  • Prior article patterns. asd://patterns/articles/39-terminal-blocks supplied the terminal-panel conventions this article follows; the lane-1 transcript pattern informed the session-log format.

Tools (sd_*) mattered less here than on the channel host — the terminal lane writes files, not store records — but the evidence bundle's read tools backed the ledger verification, and the 10 prompts (one per ASD role) duplicate as omp/asd-roles sources of truth. One contract, two consumption styles — that is the point.

07 · Comparison

Comparison with the BUZZ lane

Same canon, same artifacts, different lane. The honest deltas, lane 1 (Article 41, channel) versus lane 2 (this article, terminal):

Dimension BUZZ lane (41) Terminal lane (42)
Coordination overhead Mention scoping, thread discipline, orchestrator reconciliation posts Session sequencing by the owner; plugin contracts instead of mention contracts
Auditability Relay event IDs, channel receipts, Canvas index Run logs, git diff on artifacts, exit codes, sealed ledger hash
Parallelism Orchestrator fans out scoped mentions to idle runtimes AGY steps run concurrent where bands allow; otherwise strictly sequential
Human gates In-channel decision posts backed by store receipts Manual — the owner reads output and types the next command; no receipt unless you script one
Stakeholder visibility High — work is watchable as it happens None — stakeholders see artifacts, not process
Reproducibility Re-run means re-staging a channel Re-run means agy run on a revised canon
Pick when The engagement needs shared visibility and multi-party gating The engagement is yours to run, batch-shaped, or destined for CI

The gate row is the one that stings: lane 1's gates left receipts, lane 2's left shell history. For an engagement like Copperline 2000 — a sponsor (Priya Nair) and four functional heads who want to see the thinking — we would run lane 1, and use this lane's pipeline for the quarterly re-baseline, where nobody needs to watch and everybody needs it identical.

10 · Lessons learned

Lessons and pitfalls

  • Budget the window before the artifact. The 180.9 KB blueprint is roughly 45k tokens of HTML — pasting it whole into a critique pass wastes the window on markup. ZAI's checks took the canon, the kind contract, and band slices (N001–N020, the drive-thru band), never the full file.
  • The note-ID contract is the lane's load-bearing wall. Four CLIs that cannot message each other composed one artifact set because the band map (N001–N560) was the interface. Enforce it mechanically (omp/note-id), or the first renumbering silently corrupts every downstream citation.
  • Long context pays off exactly where chunking hurts. Kimi's single pass over the 88.3 KB interview corpus surfaced the swap-waterfall agreement between Grace Mwangi and Bo Chen — adjacent-in-meaning, distant-in-corpus quotes that a chunked summarizer averages away.
  • Generation and acceptance must be different agents. Codex drew the Route56 handoff solid and would have shipped it; ZAI's critic pass exists to be pedantic about exactly that. Both defects were visual-contract failures, not factual ones — the kind generators don't notice about their own output.
  • Pipelines as files beat pipelines as conversation. Session 4 exists as copperline-report.yaml, re-runnable against whatever revised canon a quarterly re-baseline produces. No transcript to reverse-engineer.
  • Manual gates are the lane's honest weakness. The owner's session-boundary decisions live only in shell history. If you need gated governance, take the channel lane or script the receipts — do not let a convenient prompt substitute for an audit trail.
  • Elided ≠ invented. This article shows five headline invocations, not every command. The artifact table's "built in" column is the complete attribution; anything not in it was not claimed.
