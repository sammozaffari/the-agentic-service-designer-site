01 · Executive summary

Executive summary

A digital SME bank with 120,000 customers was winning on price and losing on friction: 9-day onboarding with 62% abandonment, 11-day loan decisions with 27% applications erroring before underwriting, "relationship" promised but absent for 91% of customers. One designer rebuilt the SME lifecycle in 19 weeks on the ASD plugin. Onboarding 9→2.1 days, abandonment 62%→31%, loan decisions 11→4.5 days, NPS 12→44, monthly churn 4.8%→2.1%.

02 · The brief

The brief

Vela is a digital-native SME bank with a strong price story and a weak service story. Onboarding: 14 fields, 3 document uploads, 5-day verification queue. Lending: 13 documents for a £15k loan, 11-day decisions. Support: 4.1 contacts/customer/year, 38% progress-chasing. Strategic shift: from "cheap banking" to "the bank that knows my business," with compliance as the non-negotiable spine.

Success criteria (illustrative): onboarding ≤ 3d, abandonment ≤ 35%; loan decision ≤ 5d, error ≤ 12%; NPS ≥ +40; churn ≤ 2.5%/mo; cash-flow-foresight adoption ≥ 50%. Constraints: no change to regulatory obligations; read-only legacy core; risk-committee lending appetite; fair-lending rules the design must not route around; data-protection limits on transaction-derived products. Why service design: SME banking is high-context, high-consequence service (books 03, 19); economics run through retention and deepening (book 20); the staged experience is the differentiation (book 13).

03 · Approach

The plugin, at a glance

For this banking walkthrough, the relevant source surface is the emitted Claude Code pack. The following install commands are quoted from platform/packs/claude-code/README.md; their presence documents the pack, not a completed installation:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The marketplace manifest is platform/packs/.claude-plugin/marketplace.json; the plugin manifest is the pack's .claude-plugin/plugin.json. MCP wiring is the plugin-root .mcp.json, which Claude Code loads for installed plugins automatically — the vendored server (mcp/bin/server.mjs) needs no PATH entry and no sibling checkout. A manual-copy install (cp -R of agents, skills, commands, mcp, .mcp.json into the target project) is documented in the same README for hosts without the plugin flow.

What ships in platform/packs/claude-code: 10 role agents in agents/, 74 SKILL.md files in skills/, the /asd orchestrator command in commands/asd.md, and the vendored MCP server under mcp/. Three surfaces, one engine:

  1. Claude Code plugin — /asd plans the engagement from the brief and dispatches the role agents in platform order; each role is a native subagent (@researcher, @mapper, @critic, …); each method skill loads as a Claude skill when its role runs it.
  2. MCP server (asd-mcp) — 29 tools, 225 cursor-paginated asd:// resources, and the 10 role-contract prompts in the current shared-pack release. The historical modernization probe recorded 224 resources; host use is unverified.
  3. CLI shim — platform/packs/cli/asd; usage asd <tool> [--flag value]. Dashed aliases (asd project-create) and full tool names (asd sd_project_create) both work; the pack README describes it as the same engine as a standalone fallback.

This article's 12-method canon is drawn from the 74 executable skills whose acceptance rules run on sd_artifact_write: affinity-diagramming, behavioural-personas, contextual-inquiry, ecosystem-value-mapping, evidence-gated-blueprint, good-services-audit, journey-from-transcripts, mental-model-alignment, orchestration-canvas, service-blueprinting, stakeholder-mapping, transcript-mining.

The write path, as executed for this article (§13 has the full run):

  • Evidence rows are content-addressed (sha256 ids) and typed quote, telemetry, or document — observation is rejected at argument validation, exit 1.
  • sd_artifact_write runs structural integrity plus the method's acceptance rules. A failing write still persists the artifact as status: draft, with the failure list attached under check.failures — drafts are inspectable, not refused.
  • sd_review records the critic verdict. pass promotes the artifact to status: final; veto keeps it at draft and writes a final review-veto-log artifact linked to its subject by reviewOf.
  • sd_factcheck replays integrity, acceptance, and review over every artifact in the project and exits 1 on any failure — the deterministic gate before any steering pack.

The compliance twist: this engagement's gate convention adds "a lending-change artifact does not reach status: final without a critic pass whose rows name the regulatory obligation and the fair-lending evidence, and without the risk-committee minute registered as a document evidence row." A human-and-artifact rule the platform carries mechanically — the committee keeps the judgment. There is no engine kind that "decides" compliance; gates are conventions the humans sign.

07 · SOPs for AI

SOPs for AI — skills as the encoded method

Identical discipline to article 31 §7. Each method is a manifest — steps with role assignments, acceptance rules, output kind — that sd_method_run prints as a contract and sd_artifact_write enforces mechanically. For financial services the load-bearing rules: referential integrity is absolute (a lending claim must cite a sha256 register row; dangling refs are hard errors); every KPI names its baseline and source; the critic's sd_review rows carry rowKind/severity/rule/message — with a fix required on every defect row — and persist as a review-veto-log artifact; and the compliance gate is a human decision carried as a critic verdict plus a document-kind minute, not an engine feature. Failure modes observed: (1) the decision-time model was optimistic for mixed-income businesses — analyst-corrected before launch; (2) a persona lacked variance evidence — acceptance re-gated the write; (3) product pressure for auto-approval — held by the fair-lending veto; the rows are in the log.

10 · Lessons learned

Lessons learned & pitfalls

  1. Onboarding ends at first transaction, not account open — the scope doubled because someone read the register.
  2. Compliance staffed as design partners produced the fast path; as reviewers it would have reverted to the 13-document form.
  3. Fair-lending evidence is a design constraint; the explainability layer shipped because of it.
  4. Assisted chat is a cast, not a fallback (book 13); understaffing it produced the only pilot scare.
  5. Quantitative checks beat optimism; the mixed-income correction is the artifact of record.
  6. Present the risk committee the evidence model, not the mock — the review-veto-log travels with the artifact it cleared.
