35 — The Butler's Memory: Staging Luxury with the ASD Critic on the Write Path

00 · Provenance note

Confidentiality & provenance note

Sable & Slate is a fictional composite of luxury boutique hotel groups; no real property, guest, or financial data appears. This article is a runlog of the Agentic Service Designer (ASD) in Claude Code, and the plugin's Critic role is the star: its verdicts are recorded with sd_review as review-veto-log artifacts, and every method manifest in the engine declares the critic review gate, so no artifact reaches final without passing it. The heaviest gates also ran the same adversarial posture as an external AGY review session (platform/packs/agy/review-session.md). Consent is a designer-and-privacy-officer convention carried inside the platform as review rows that cite a consent-spec evidence row — plain and auditable, no special machinery.

01 · Executive summary

Executive summary

A nine-property luxury group with €680 ADR digitized its way to impersonality: the app could do everything, so nobody did anything, and reviews said "the technology remembers nothing about me, the staff remember everything busy." One designer rebuilt the stay around a guest-context memory that serves the cast, not the screen, in 17 weeks on the ASD plugin. Check-in 14→4 min, first-touch resolution 61%, turnover 34%→21%, repeat 38%→52%, NPS 41→68, pilot RevPAR +7%.

02 · The brief

The brief

Sable & Slate: nine boutique properties, €680 ADR, "we remember you." A three-year digital program removed human touchpoints — and with them the memory. Guests re-told preferences at every property; staff had no continuity between shifts or visits; turnover at 34% drained the expertise luxury sells.

Success criteria (illustrative): check-in ≤ 5 min; first-touch resolution ≥ 60%; repeat ≥ 50%; turnover ≤ 20%; NPS ≥ +60; pilot RevPAR +5%. Constraints: no renovation; a unionized nights/concierge workforce to design with; GDPR-grade consent; the brand's non-negotiables (no visible tracking, no "algorithmic" service language, human final authority). Why service design: the canonical experience-economy case (book 13) — the offering is the staged event, the cast is the product (book 20, literal).

03 · Approach

The plugin, at a glance

Same surface as article 31 §3, re-grounded on what actually ships. The platform is one engine behind three delivery surfaces: the Claude Code plugin, the MCP server vendored inside it, and the asd CLI pack. Install is the Claude Code plugin marketplace flow, quoted verbatim from platform/packs/claude-code/README.md:

TERMINAL
claude plugin marketplace add <repo>/platform/packs
claude plugin install asd@asd-platform

The marketplace manifest is platform/packs/.claude-plugin/marketplace.json; MCP wiring is the plugin-root .mcp.json, which Claude Code loads for installed plugins automatically — ${CLAUDE_PLUGIN_ROOT} resolves inside the installed plugin, so the vendored server needs no PATH entry and no sibling checkout. (A manual-copy install for a project-local .claude/ is documented in the same README.) What ships in the pack: .claude-plugin/plugin.json, .mcp.json pointing at mcp/bin/server.mjs, the self-contained vendored asd-mcp server under mcp/ (no npm install, nothing on PATH), the ten role agents under agents/, the method-skill library under skills/, and commands/asd.md providing the /asd orchestrator command.

The skills library is 74 skills, not twelve. Twelve of them are the machine-gated method skills this series runs end-to-end through the engine's write→check→review loop: affinity-diagramming, behavioural-personas, contextual-inquiry, ecosystem-value-mapping, evidence-gated-blueprint, good-services-audit, journey-from-transcripts, mental-model-alignment, orchestration-canvas, service-blueprinting, stakeholder-mapping, transcript-mining. The rest of the 74 run through the same manifests and the same gates.

The engine exposes sixteen tools — in Claude Code over MCP, or on the CLI as asd <tool> with dashed aliases (asd project-create maps to sd_project_create): sd_project_list/create/open, sd_evidence_add/query, sd_artifact_list/get, sd_artifact_write, sd_method_list/run, sd_review, sd_review_list, sd_export_report, sd_export_artifact, sd_knowledge, sd_factcheck. Over MCP the same server also publishes resources — 215 asd:// URIs (20 books, 159 chapters, 36 articles), cursor-paginated at 100 per page — and the ten role contracts as prompts. The handshake, as captured from the vendored server:

NOTE
initialize → {"protocolVersion":"2025-06-18","capabilities":{"tools":{},"resources":{},"prompts":{}},"serverInfo":{"name":"asd-mcp","version":"0.1.0"}}
prompts/get critic → description="The adversarial conscience of the engagement. Sits on the write path, not after it: any artifact whose method manifest declares `reviewGate: critic` is final-eligible only after a Critic verdict. …"

The write path, mechanically. sd_artifact_write judges the candidate against the producing method's acceptance rules and always persists the result: a passing write on a review-gated method lands as draft (a fresh write carries no verdict), a failing write lands as draft with the check report attached, and only a dangling evidence reference is refused outright — a hard error, nothing written. sd_review then records the Critic's verdict: pass promotes to final (re-checking acceptance against the live manifest), veto demotes to draft. Every one of the 74 method manifests declares reviewGate: critic, so the Critic is not a phase — it is structurally on the write path. Review rows are {rowKind: defect|proposal, severity: critical|high|medium|low, rule?, message, fix?, evidenceId?}; a veto needs at least one defect row, every defect needs a fix, and a pass may not carry defects. The verdict persists as a review-veto-log artifact (status: final, linked to its target by reviewOf), and rows append across verdicts so the log stays a log. sd_factcheck replays integrity, acceptance, and review state over every artifact in the project and exits non-zero on any failure.

What the platform does not do. There is no phase-gate or orchestration-plan artifact kind implemented in the engine: phase gates remain the human designer's decision, presented by the orchestrator and recorded in the engagement report and the review rows. The engine checks structure, acceptance, and evidence — never staging taste, consent ethics, or brand judgment; those enter as review rows written by a role and signed off by a human. And the Critic never designs: rows name the defect and the fix, the owning role reworks.

04 · The work, phase by phase

Phase-by-phase session log (Claude Code + ASD, Critic-led)

4.1 Session 1 — Discover (weeks 1–5)

Drive.

NOTE
/asd
@researcher run contextual-inquiry for sable-slate: 28 guest interviews, 5
shadow days across desk/concierge/housekeeping/lobby, a 32-person staff
diary, and 24 months of review text mined with the transcript-mining skill.

What the plugin did. The register reached 1,847 content-addressed rows — each evidence id is the sha256 of its (source, kind, body), so two identical quotes from two interviews are two rows and the same row captured twice resolves to the same id. One discipline cost us an evening and bought the whole register's credibility: evidence kinds are exactly quote, telemetry, document. My night-audit field note went in as an observation and came straight back:

NOTE
$ asd evidence-add --projectId sable-slate-0cca4c00 --source shadow-night-03 --kind observation --body "Night audit at 3am runs on one associate and a paper handover."
asd evidence-add: invalid arguments: "kind" must be one of ["quote","telemetry","document"]

It re-entered as a verbatim quote from the night auditor's diary. Transcript-mining then classified needs and frustrations across 18,000 review phrases; the method's contract (fetched with sd_method_run) requires the evidence set to exist before it will hand over its steps and acceptance rules — the engine's real behavior, nothing more.

Team analysis (outside the engine, marked). The critical correction — the "impersonal" reviews were about the loss of a human reference point (staff who no longer knew the guest), not about the app per se — came from the designer's analysis of the classified phrases. It changed the brief from "undo automation" to "re-point automation."

Gate G1. Register in place; sd_review_list (the review board) empty of artifacts and the research plan reviewed by the Critic in session: one HIGH finding (the attribution error) — adopted before design locked. Gate decisions stay human; the platform's part is that nothing downstream could cite evidence that was not in the register.

Human judgment. The designer ran shadow days across all shifts (incl. the 3am night audit), chose staff diaries over a survey, and framed privacy as a brand asset in front of leadership first.

The defect row cites evidenceId — the brand book's non-negotiables, captured as a document row in Discover, so the veto's authority is itself evidence in the register. And the verdict is an artifact, not chat: review-veto-log.review-context-memory-concept.0d98b38e.json sits in the project store with status: final, reviewOf pointing at the concept, rows r1–r2 carrying rowKind, severity, rule, message, and the fix. The concept was reworked — facts, requests, boundaries, no trait inferences — re-written in place, and passed on the next sd_review. The consent spec was drafted the same week and added to the register as a document row; the privacy officer's signature is the human half of the convention, the rows citing it are the machine half.

Human judgment. The designer named the design object from book 13 — the butler's memory: staff-facing, guest-invisible, read in 30 seconds — and locked the consent default (opt-in, granular, revocable in-app and in-person) with the privacy officer at this phase.

Drive.

NOTE

What the plugin did. The blueprint's five lanes and per-node evidence rule held staging honest: a backstage node whose wait time silently reverted to the old 5-day request queue contradicted the roster evidence it cited, and the Critic's number-ledger defect row forced the correction before the artifact could pass review. Prototype discipline made every storyboard falsifiable — assumption, subjects, pass/fail, evidence from the test run.

Team analysis (outside the engine, marked). The shift-handoff timing check — the "60-second brief" that degrades to 3 minutes under short staffing, fixed as a two-tier brief (minimum/complete) — was the designer's operational analysis with the front-desk cast. The platform did not simulate.

Human judgment. The designer set the staging rule (book 13): the system cues, the staff perform; no script substitutes for judgment. The front-desk co-design veto on "we will make it right" boilerplate became verbatim in the final script.

A second veto — the brand call. An old analytics roadmap item — a guest "emotion score" — re-appeared in a concept review. The Critic vetoed it under the same no-trait-inference rule it had enforced in Define; the item was dropped and the boundary persists in the project's veto logs. The platform's own gate, not the designer, killed a feature that would have broken the brand.

07 · SOPs for AI

SOPs for AI — the adversarial write path

Same role contract and skills as article 31 §7. The Critic is the headline mechanic here, and its plugin manifest names the run order: schema → referential integrity → acceptance rules → then judgment — never skip the machine checks to "save time" — then falsification (absence of contrary evidence is not confirmation), the placeholder hunt (deny-listed values like "unknown"/"tbd"/"n/a" are automatic defects), and the number ledger (a figure that disagrees with the register is a defect, not a coincidence). Its quality bar is written down: a veto without a fix suggestion is incomplete; a pass without at least one proposal is complacency — and the engine enforces the first half (a defect row without a fix is rejected at the boundary; a veto with no defect row is rejected outright).

The encoding pattern, end to end: method manifest (steps per role, acceptance rules, output kind, reviewGate: critic) → sd_method_run fetches the contract and refuses if the register holds fewer evidence rows than the method declares → the role executes → sd_artifact_write machine-checks and persists a draft → sd_review records the verdict → sd_factcheck replays the whole store at the gate. Consent rides this as a convention: the consent spec is a document evidence row, and every personalization artifact's review rows cite it by id — the privacy officer signs, the rows make the signature auditable.

Failure modes observed: (1) the attribution error (app vs lost human reference) — analyst-corrected before design locked; (2) a persona draft citing an evidence id that did not exist — the write was refused outright (node "p5" cites evidence "aaaa…" which is not in the project evidence store), nothing persisted, the fabricated detail never entered the store; (3) the emotion-score roadmap item — the Critic killed it by applying its own Define-era rule; the veto log records the boundary holding.

10 · Lessons learned

Lessons learned & pitfalls

  1. The "impersonal" signal misattributed to the app was really the lost human reference; attribution checks change briefs.
  2. Privacy is a brand asset in luxury; the consent-spec convention bought more trust than any marketing line — and because it rides ordinary evidence and review rows, it survives replay.
  3. Stage the system to cue, staff to perform (book 13); every script needs a human-judgment escape.
  4. Two-tier briefs survive short-staffing; single-tier promises fail at 3am.
  5. Staff co-design is not consultation; the front-desk veto measurably improved the recovery script.
  6. Opt-out is a design success, not a leak; handling it well turned one complaint into praise.
