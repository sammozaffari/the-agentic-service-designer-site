Provenance note

01 · Executive summary

Executive summary

Lane 3 reruns the Copperline 2000 engagement — a six-week, full-operation service blueprint and field study for a 2,000-store fictional chicken chain — inside DeepSeek Harness. Same brief, same 214-ID evidence ledger, same 560 numbered notes, same 14 artifacts, same three human gates. What changed is the substrate: in the BUZZ lane (article 41) the roles, evidence rules and gates were conventions held by disciplined agents in a channel; in the CLI lane (article 42) they were scripts wrapped around a store; here they are plugins — TypeScript modules loaded into the harness itself. The role roster is a plugin. The evidence ledger with its note-ID contract is a plugin. The artifact renderer is a plugin. The phase gates are enforced by a plugin that refuses to advance a phase without the owner's receipt.

That is the whole finding: when the workflow becomes code in the harness, discipline stops depending on every agent remembering the convention. The blueprint's note-range contract (N001–N220) was not a prompt instruction — it was a write-gate that rejected out-of-range citations. And the critic's two blueprint defects from lane 1 reappeared here verbatim, caught by the same rules — exactly what a rerun should show: variance between lanes belongs in the substrate, not in the findings.

02 · The brief

Why a harness lane

DSH's architectural bet is stated in its README: everything is a plugin. The core stays small; capabilities — tools, agents, UI panels, permissions — are registered by Cordis plugins that load and unload cleanly. A plugin is a TypeScript module exporting an apply(ctx) function; bundles ship patches that insert plugin rows; profiles compose bundles into a runnable setup booted with dsh --profile <name>. That composition model is what made this lane worth running.

In a service design engagement, four things want to be enforced rather than remembered: who may speak as which role, which evidence a claim may cite, what an artifact must look like to be reviewable, and who may advance a phase. Compare the three substrates on those four:

Discipline BUZZ channel (41) CLI wrappers (42) DSH plugins (43)
Roles Persona-pack runtimes as channel members; identity audit before mentions Role scripts invoked per phase; identity is the invoking shell asd-roles registers 8 role agents the harness routes to directly
Evidence rules Convention: replies must cite ledger IDs; owner verifies Check scripts run after each write evidence-ledger plugin rejects non-resolving writes at write time
Rendering Artifacts rendered offline; channel links to files Same, plus CLI smoke-checks html-render plugin previews artifacts inside the web UI with the canon color code
Gates Receipts posted in-channel; convention says runtimes may not advance phases Gate script refuses without a receipt file gatekeeper plugin holds the phase lock; no agent path can advance it

When does the harness lane win? When you will run the same shaped engagement more than once, with more than two people watching, and you want the workflow itself — roles, contracts, gates — versioned next to the code. When does it lose? When setup cost dominates: a one-off study is faster in a channel (article 41), and a deterministic pipeline you already trust is faster from the CLI (article 42). DSH is also a developer preview with announced compatibility-breaking changes, so a plugin suite is a maintenance commitment, not a one-time install.

03 · Approach

Setup: harness, profile, engagement

Setup follows the published path. Node.js installed, then the harness boots its web UI from npm — the README's one-liner is the front door:

Three DSH behaviors mattered. First, the harness uses its invoking directory as the default filesystem location, but the web UI has no selected workspace until you add one — binding the engagement directory is an explicit act, and the evidence-ledger plugin refuses writes from any session whose workspace is not the bound one. Second, the model route is configured in Settings → Models and becomes usable without a restart, so keys could rotate mid-engagement without disturbing sessions. Third, the web UI asks before operations that need approval under the active permission policy — tightened here so phase advance and evidence-ledger mutation were owner-only from the start.

On composition: our bundles are ordinary npm packages whose package.json declares a dsh.bundle pointing at a Cordis patch file; the copperline-asd profile lists the six bundles in order, and dsh --profile copperline-asd boots the composition. During development we loaded individual plugins through a cordis.yml overlay with --patch; anything registered through the Cordis context cleans up on unload, so toggling a plugin off is safe mid-profile.

04 · The work, phase by phase

The ASD plugin suite

Six plugins, one per responsibility. Each registers only what it needs through the Cordis context — asd-mcp injects the tool registry; gatekeeper injects the permission surface; none of them touches another plugin's state.

Plugin Responsibility Artifacts it touched
asd-roles Registers the 8 ASD role agents (orchestrator, researcher, synthesizer, mapper, ideator, measurer, presenter, critic) with scoped-mention contracts; routes @role dispatch inside sessions All 14 — every artifact has an owning role
asd-mcp Bridges the six ASD MCP bundles into the harness as one surface: 29 sd_* tools, 225 asd:// resources, 10 prompts All 14 — the read/write path behind every artifact
evidence-ledger Holds the 214-ID evidence ledger and the note-ID contract (N001–N560); rejects writes whose citations do not resolve or whose note IDs drift out of the artifact's assigned range Blueprint (N001–N220 contract), research packs, analysis, proposals, deck
html-render Renders self-contained artifact HTML inside the web UI preview pane with the canon color code and sticky legend Blueprint, journeys, stakeholder/ecosystem maps, deck
gatekeeper Phase receipts and the phase lock: no session, role or tool call may advance scaffold→research→synthesis→delivery without the owner's receipt Gates 1–3 across the set; delivery package authorization
asd-packager Assembles the final delivery package: index of all 14 artifacts by template-catalog kind, close-out receipt, completeness check Package index + buzz-transcript-equivalent session log

Weeks 2–3 — research dispatch

The researcher agent ran the flagship interview set (all 8 participants across Harbourgate Flagship #14 and Northline Flagship #3) and the measurer agent ingested the survey and channel packs. Every write went through asd-mcp tools into the store; the evidence-ledger plugin assigned the research note bands as they landed — interviews N221–N270, surveys N271–N300, channels N301–N320 — and rejected one early draft that tried to cite an interview verbatim before its evidence ID was registered. In lane 1 the same slip would have been caught by the owner reading the channel; here it never persisted at all. Gates 1 and 2 were approved by mehran on 2026-07-17 and 2026-07-31, receipts recorded by gatekeeper.

Weeks 4–5 — blueprint build and the critic cycle

The mapper agent built the full-operation blueprint under the note-range contract: 220 annotations, N001–N220, nothing else. The contract was enforced, not requested — the evidence-ledger plugin compares every write against the artifact's assigned band, and when an early draft renumbered two adjacent annotations, the drift was flagged before the critic ever saw the artifact. 06 · Use cases

The MCP bridge

The harness did not need a new ASD API — it needed the existing one composed in. The asd-mcp plugin bridges the six ASD MCP bundles into DSH as a single surface: 29 tools, 225 resources, 10 prompts. The tools are the same sd_* contract every lane uses — sd_evidence_add, sd_artifact_write, sd_review, sd_factcheck, sd_orchestration_handoff — so an agent that learned the contract in the BUZZ lane already knows it here. The resources expose the readable corpus under asd:// URIs:

NOTE
asd://book/01-this-is-service-design-doing/ch07     # This Is Service Design Doing, ch.7
asd://book/09-mapping-experiences/ch05             # blueprint method refs
asd://templates/12-service-blueprint               # kind 12 acceptance rules
asd://templates/31-opportunity-matrix              # proposals scaffold
asd://projects/copperline-2000/evidence            # 214 IDs, read-only
asd://projects/copperline-2000/notes?range=N001-N220
asd://projects/copperline-2000/canvas              # navigation index, regenerated

The 10 prompts are the role-canonical instruction templates — orchestrator dispatch, critic review policy, measurer baseline frame — which the asd-roles agents load instead of carrying prompt text in their definitions. The practical effect: agents browsed before they mutated. The critic read the acceptance rules from asd://templates/12-service-blueprint before reviewing the blueprint, and its two defect rows cite those rules by name — the same rules the BUZZ-lane critic had to be trusted to remember. The bridge is read-mostly by design: the store stays the single system of record and the harness stays a composition layer, never a second database.

07 · SOPs for AI

Three-lane comparison

Same engagement, three substrates. Honest scoring, including where this lane lost:

Dimension BUZZ channel (41) CLI wrappers (42) DSH plugins (43)
Coordination Excellent — threaded, multi-agent, visible to everyone on the relay Adequate — pipelines are sequential; parallel dispatch is shell work Good — sessions route to role agents; cross-session visibility needs the sessions list
Auditability Strong — every reply is a signed channel event; verification is manual Strong — receipts are files; readable by anything Strongest — writes are gated in-code; ledger, reviews and receipts are enforceable records
Gates Convention + receipts; runtimes trusted not to advance phases Gate scripts refuse without receipts Phase lock in gatekeeper; no agent path to advance
Plugin/tool reuse Reuse is the persona pack; workflow rules live in prose Reuse is scripts in a repo; discipline depends on invoking them Reuse is the unit of shipment — bundles compose into any future profile
Learning curve Low if you already use the relay; mention contracts take practice Moderate — comfort with CLIs and exit codes required Highest — Cordis composition, bundles vs profiles, permission policies, preview-mode churn
Stakeholder viewing Read-only channel access Shared artifact files Live web-UI preview of artifacts inside the session (this lane's quiet win)

10 · Lessons learned

Lessons and pitfalls

  • Plugin contracts caught what conventions missed. The note-ID drift incident — two adjacent blueprint annotations swapped in a draft — would have surfaced (if at all) at critic review; the evidence-ledger write-gate rejected it at write time. Enforcement moved left by a full phase.
  • The same defects in every lane is a feature. The critic found the same two blueprint defects here as in lane 1. When findings replicate across substrates, the substrate is not steering the work — that is the control this three-lane design gives you.
  • The web UI was the quiet win for stakeholders. Priya's ops council (people who would never join a relay or read a CLI log) could watch the blueprint render live in the preview pane during the gate-3 week. Lane 1 gave them a channel; this lane, a window.
  • Developer preview is a maintenance commitment. DSH iterates rapidly with announced compatibility-breaking changes; two plugin updates mid-lane changed registry APIs. Pin bundle versions per profile and re-run the smoke suite on every harness bump.
  • Permission prompts interrupt long dispatches. A research session that touches hundreds of evidence writes generates approval fatigue; we ended up pre-authorizing read-only tool classes and keeping writes scoped per role.
  • What to improve in the suite: asd-roles has no per-role memory between sessions, so the critic re-reads its policy resources each time; html-render re-renders full artifacts on every annotation write (a diff-render is on the list); asd-packager should emit a Canvas-compatible index so lane 1's channel and lane 3's harness share one index format.
  • Keep the store as the only system of record. The bridge is read-mostly on purpose; the moment a harness-local cache becomes writable, you have two databases and one truth problem.
